# rewind-task

작업 도중 자동으로 쌓인 **wip 커밋**(auto-wip-commit 훅이 매 턴 박아두는 임시 저장 커밋) 하나를 골라 그 시점으로 되돌아가는 스킬. **후보 목록 제시 → 방법 선택 → 백업 태그 → 실행** 한 흐름.

이 프로젝트 흐름은 `new-task`(브랜치 생성) → 작업(매 턴 wip 커밋 자동 누적) → `done-task`(PR·squash 머지) 순환이라, main에는 PR당 커밋 1개만 남는다. 그래서 **턴 단위로 돌아가는 길**이 따로 필요하다 — 이 스킬이 그 길이다. 이게 없어서 main을 즉흥적으로 되감으면, 머지된 PR이 main 로그에서 통째로 사라지는 사고로 이어질 수 있다.

이 스킬은 `context: fork`로 git-flow 서브에이전트(sonnet)에서 격리 실행된다 — 메인 세션 토큰 절약 목적. 실행 중 사용자 질문이 불가능하므로 결정 지점은 [결정 필요] 반환 → 메인이 사용자에게 확인 → **사용자가 직접** 결정을 args에 담아 슬래시 명령으로 재호출하는 프로토콜을 쓴다. (`disable-model-invocation: true`라 AI는 이 스킬을 재호출할 수 없다 — 재호출 입력은 반드시 사용자 몫.)

## 호출 인자

이번 호출의 인자: **$ARGUMENTS**

위가 비어 있으면 인자 없이 호출된 것. 인자에는 되돌리고 싶은 지점 힌트(PR 번호·커밋 번호·시각)와 [결정 필요]에 대한 결정 지시가 자연어로 담긴다 — 해석은 §호출 패턴. (fork 실행 시 호출 인자는 위 자리표시자를 치환해 전달된다 — 이 섹션이 이 스킬의 인자 수신 지점이므로 삭제 금지.)

## 진입 전 가정

- 프로젝트 루트가 git repo
- 되돌아갈 wip이 다음 둘 중 하나에 있음:
  - **아직 작업 중인 feature 브랜치** — wip이 `git log`에 그대로 보임
  - **이미 ship한 PR** — 브랜치는 지워졌지만 GitHub의 PR 보관 기록(`refs/pull/<번호>/head`)에 wip이 통째로 살아 있음
- PR을 한 번도 안 거친 브랜치를 `git branch -D`로 지웠다면 **이 스킬로 못 살린다** (§엣지 케이스)
- 이 스킬은 워크트리(worktree — 같은 저장소를 작업 폴더 여러 개로 펼치는 git 기능) 안에서도 그대로 작동한다 — 되돌리기는 현재 폴더의 브랜치에만 영향을 주고, 다른 워크트리는 건드리지 않는다.

## 실행 흐름

### 1. 안전 검사 (실패 시 사용자 안내 후 중단)

```bash
# 1-a. 현재 브랜치 확인
git rev-parse --abbrev-ref HEAD
```

- **브랜치에 안 묶인 상태 (detached HEAD)** — 어느 브랜치에도 속하지 않고 과거 커밋만 보고 있는 상태 → 중단. "지금 어느 브랜치에도 위치하지 않고 과거 커밋한 파일들을 보고 있어. 이 스킬은 브랜치 위에서 wip을 되돌리는 도구라, 어느 브랜치에서 시작할지 알려줘 (`git switch <브랜치>`)."

```bash
# 1-b. working tree 깨끗한가
git status --porcelain
```

- 비어있지 않으면 args에 결정 지시(예: "변경은 커밋하고 진행")가 있으면 그대로 적용하고 계속. 없으면 **[결정 필요] 반환**:
  ```
  [결정 필요] 커밋되지 않은 변경(수정·추가·삭제된 파일)이 남아 있어.
  이 스킬은 과거 시점으로 되돌리는 도구라, 이 변경이 덮어써져 사라질 수 있어. 먼저 정리해야 해.

  선택지:
  (a) 지금 변경을 커밋하고 진행
  (b) 임시 보관소에 넣어두고 진행 (`git stash` — 나중에 다시 꺼낼 수 있어)
  (c) 중단 — 직접 정리할게

  재호출 예시: `/rewind-task <되돌릴 지점> — 변경은 커밋하고 진행` / `/rewind-task <되돌릴 지점> — stash하고 진행`
  ```

#### 1-c. 현재 브랜치가 main인 경우

main에는 wip이 없다 (auto-wip-commit 훅이 main에서는 안 돈다). 그래서 갈래가 둘이다.

- args에 PR 번호나 "지난 PR" 류 지시가 있으면 → ⓐ로 보고 **§2-b로 계속 진행**.
- args에 "main 커밋을 되돌린다" 류 지시가 있으면 → ⓑ. 아래 안내하고 **중단**:
  ```
  main에 이미 합쳐진 커밋 자체를 되돌리려는 거면 이 스킬 범위 밖이야.
  이 스킬은 작업 중 쌓인 임시 저장(wip)으로 돌아가는 도구고, main에는 wip이 없어.

  main 커밋을 무르려면 `git revert <커밋번호>` 를 써 — 되돌리는 내용을 *새 커밋으로 얹는* 방식이라
  기록이 사라지지 않고 안전해. (`git reset --hard` + 강제 밀어넣기(force push)는 쓰지 마 —
  다른 사람 기록까지 날아가고, 머지된 PR이 통째로 main 로그에서 사라지는 사고로 이어질 수 있어.)
  ```
- args에 아무 지시도 없으면 **[결정 필요] 반환**:
  ```
  [결정 필요] 지금 main 브랜치 위에 있어. main에는 wip 커밋이 없어서(훅이 main에선 안 돎)
  뭘 되돌리려는 건지에 따라 길이 갈려.

  선택지:
  ⓐ 지난 PR 작업 중간의 wip으로 돌아가고 싶다 → GitHub에 남은 PR 기록에서 꺼내올게
  ⓑ main에 합쳐진 커밋 자체를 무르고 싶다 → 이 스킬 범위 밖. `git revert`가 맞아

  재호출 예시: `/rewind-task 지난 PR #12 작업 중간으로` / `/rewind-task 지난 PR의 wip 꺼내줘`
  ```

### 2. 후보 wip 목록 수집

origin/main 원격 추적 참조를 최신으로 갱신한다 (로컬 main 브랜치나 현재 작업 트리는 건드리지 않음):

```bash
git fetch origin main
```

fetch가 실패하면(네트워크 등) 경고를 띄우고 로컬 main 기준으로 진행한다. 목록이 부정확할 수 있으니 사용자에게 알린다.

#### 2-a. 현재 feature 브랜치에 wip이 있는 경우

```bash
git log origin/main..HEAD --oneline | wc -l
```

비어있지 않으면 이 경로. 아래로 목록을 뽑는다:

```bash
git log origin/main..HEAD --format='%h|%ar|%s' | head -20
```

출력은 `번호|상대시각|커밋제목` 형태다. 커밋 제목이 `wip: ` 로 시작하면 훅이 만든 것이고 형식이 이렇다:

```
wip: <사용자 프롬프트 힌트> — <파일1>, <파일2> 외 N개 (X files changed, Y insertions(+), Z deletions(-))
```

이걸 `wip: ` 뒤 ` — ` 앞 = **힌트**, ` — ` 뒤 = **바뀐 파일·증감**으로 잘라 아래 표로 제시한다 (1이 가장 최근):

| # | 커밋번호 | 언제      | 무슨 얘기 하다가 (힌트) | 바뀐 파일 · 증감                                |
| - | -------- | --------- | ----------------------- | ----------------------------------------------- |
| 1 | `ed3523a` | 3시간 전  | ㅇㅇ                    | components.md, App.jsx 외 1개 (+55 −9) |
| 2 | `3797c4d` | 4시간 전  | 색깔 이거 말고 다른거… | components.md, HomeScreen.jsx (+37 −12)          |

**힌트만 보여주지 마라.** 힌트는 사용자의 마지막 말을 60글자로 자른 것이라 `ㅇㅇ`, `ㄱㄱ` 같은 짧은 승인일 때가 많다. (구버전 훅이 만든 옛 커밋에는 한글이 중간에서 잘려 깨진 힌트도 남아 있을 수 있다.) **시각·파일 목록·증감 숫자를 같이 보여줘야** 사용자가 어느 시점인지 알아본다. 이게 이 스킬의 핵심이다.

`wip: `로 시작하지 않는 커밋(사용자가 직접 만든 `fix:`·`refactor:` 등)은 제목을 그대로 쓰고, 파일·증감은 아래로 따로 채운다:

```bash
git show --stat --format='' <커밋번호> | tail -1
```

목록이 20개를 넘으면 최근 20개만 보여주고 **"그 앞은 N개 더 있어 — 더 필요하면 알려줘"** 라고 **자른 사실을 반드시 밝힌다.**

#### 2-b. 브랜치가 없거나 args에 PR 번호가 있는 경우

이미 ship한 작업의 wip은 GitHub이 PR별로 영구 보관한다. 브랜치를 지워도 `refs/pull/<번호>/head`에 그대로 남는다 — 브랜치를 지운 뒤에도 남아 있는 것을 실제 저장소에서 확인된 동작이다.

**① PR 번호 정하기**

- args에 번호(`#12`, `12` 등)가 있으면 그걸 쓴다.
- 없으면 후보를 뽑아 물어본다. **두 곳을 다 본다** — main 로그에는 안 보이는데 실제로는 머지된 PR이 있을 수 있다:

```bash
git log main --format='%h|%ar|%s' -10          # main의 squash 커밋. 제목 끝 (#N)이 PR 번호
gh pr list --state merged --limit 20 --json number,title,mergedAt
```

  뽑은 목록으로 **[결정 필요] 반환**:
  ```
  [결정 필요] 어느 PR 작업 중간으로 돌아갈지 골라야 해. 최근 머지된 PR이야:

  | PR   | 제목                                          | 머지    |
  | ---- | --------------------------------------------- | ------- |
  | #14  | 홈 화면 필터·빈 상태 정리                     | 2일 전  |
  | #12  | 인라인 스타일을 화면 전용 클래스로 이관       | 3일 전  |

  재호출 예시: `/rewind-task #12`
  ```

**② PR 기록 되살리기**

```bash
git fetch origin pull/<N>/head:recover-<N>
```

같은 이름 브랜치가 이미 있으면 뒤에 숫자를 붙여 재시도한다 (`recover-12-2`). 사용자에게 그 사실을 알린다.

**③ 그 PR의 wip 목록 뽑기**

```bash
git log origin/main..recover-<N> --format='%h|%ar|%s'
```

`origin/main..` 은 "origin/main에 없는 커밋만"이라는 뜻이다. origin/main의 squash 커밋은 wip들의 조상이 아니라서 이 계산에 끼어들지 않는다 — **실측으로 확인함**: `origin/main..` 결과와 갈라진 지점 기준(`git merge-base origin/main recover-<N>` 이후) 결과가 여러 PR에서 똑같았다.

숫자가 이상해 보이면(예: 0개, 또는 origin/main 커밋이 섞여 나옴) 갈라진 지점을 직접 계산해 교차 확인한다:

```bash
git log $(git merge-base origin/main recover-<N>)..recover-<N> --format='%h|%ar|%s'
```

목록은 2-a와 **같은 표**로 제시한다.

### 3. [결정 필요] — 어느 wip, 어떤 방법

표와 함께 되돌리는 방법 3가지를 제시하고 각각 재호출 예시를 단다.

```
[결정 필요] 후보 wip이야. 어느 시점으로, 어떤 방법으로 돌아갈지 골라줘.

<§2에서 만든 표>

되돌리는 방법 세 가지:

(A) 파일 하나만 되살리기 — 나머지 작업은 그대로 두고 그 파일만 그때 내용으로 바꾼다.
    `git checkout <커밋번호> -- <파일경로>`
    → 가장 안전. 실수해도 나머지가 안 다친다.

(B) 새 가지로 살리기 — 그 시점을 시작점으로 삼는 브랜치를 새로 만들어 거기서 이어 작업한다.
    `git switch -c <새이름> <커밋번호>`
    → 지금 브랜치는 손대지 않는다. 두 갈래를 비교하고 싶을 때.
    → 워크트리 안에서 실행하면 폴더는 그대로고, 그 워크트리의 브랜치만 <새이름>으로 바뀐다.

(C) 통째로 되감기 — 지금 브랜치를 그 시점으로 되돌리고, 그 뒤 작업은 다 버린다.
    `git reset --hard <커밋번호>`
    → 가장 확실하지만 되돌린 뒤 작업이 사라진다. 아직 GitHub에 밀어넣지(push) 않은 브랜치에서만 안전.

재호출 예시:
  `/rewind-task 3번으로 src/screens/HomeScreen.jsx 만 되살려줘`
  `/rewind-task 3번을 새 브랜치 fix/home-retry 로 살려줘`
  `/rewind-task 3번으로 통째로 되감아줘`
```

각 방법의 결과는 위처럼 **쉬운 한 줄**로 설명한다. 커밋번호(commit hash) 같은 용어를 처음 쓸 때는 풀어 준다.

### 4. 실행

#### 4-a. 백업 태그 먼저 (건너뛰기 금지)

되돌리기 명령을 실행하기 **직전에** 지금 위치에 이름표를 박는다. 이게 이 스킬의 안전장치다.

```bash
git tag "rewind-backup/$(git rev-parse --abbrev-ref HEAD)-$(date +%Y%m%d-%H%M%S)"
```

- 태그 이름에 `/`가 들어가도 정상 동작한다 (실측 확인).
- **로컬에만 만든다.** 원격 push는 하지 않는다 (사용자 승인 없는 원격 변경 금지). 완료 보고에 "원격에도 남기려면 `git push origin <태그이름>`" 이라고 안내한다.
- 만든 태그 이름은 완료 보고에 반드시 적는다.

#### 4-b. 방법별 실행

**(A) 파일 하나만**

```bash
git checkout <커밋번호> -- <파일경로>
```

- 되살린 파일은 **커밋 대기 상태(staged)로 남는다.** 자동 커밋하지 마라 — 사용자가 내용을 보고 결정할 몫이다.
- 이 상태에서는 auto-wip-commit 훅이 "이미 대기 중인 파일이 있으면 건드리지 않는다"는 규칙 때문에 **다음 턴 자동 저장이 멈춘다.** 완료 보고에 이 점을 꼭 알린다.

**(B) 새 가지로 살리기**

```bash
git switch -c <새이름> <커밋번호>
```

- 이름 충돌 시 뒤에 숫자를 붙여 재시도하고 알린다.

**(C) 통째로 되감기**

실행 전에 이 브랜치가 이미 GitHub에 올라가 있는지 먼저 본다. 로컬에 캐시된 원격 추적 정보(`origin/<브랜치>`)는 다른 컴퓨터에서 올린 push를 못 볼 수 있으니, GitHub에 직접 물어본다:

```bash
git ls-remote --exit-code --heads origin "$(git rev-parse --abbrev-ref HEAD)"
```

- 원격에 있으면 exit code 0 + 참조가 출력된다. 없으면 exit code 2다.
- **명령이 실패하거나(네트워크 등) exit code가 0·2가 아니면 "없다"고 단정하지 말고 있다고 가정한다** — 확인이 안 될 땐 파괴적 작업을 하지 않는 쪽이 안전하다.
- **결과가 나오면(원격에 있음, exit 0)** → 실행하지 말고 **[결정 필요] 반환**:
  ```
  [결정 필요] 이 브랜치는 이미 GitHub에 올라가 있어. 통째로 되감으면 GitHub 쪽과 어긋나서
  강제로 밀어넣어야(force push) 하는데, 이 워크플로는 강제 밀어넣기를 금지해 —
  다른 기록까지 날아갈 수 있어서야.

  선택지:
  ⓐ (B) 새 가지로 살리기로 바꾸기 — 지금 브랜치는 그대로 두고 그 시점에서 새로 시작
  ⓑ (A) 파일 하나만 되살리기로 바꾸기
  ⓒ 중단 — 직접 처리할게

  재호출 예시: `/rewind-task <커밋번호>를 새 브랜치 <이름>으로 살려줘`
  ```
- **결과가 안 나오면(원격에 없음, exit 2)** → 안전. 실행:
  ```bash
  git reset --hard <커밋번호>
  ```

### 5. 완료 보고

```
✓ 되돌린 시점: <커밋번호> "<힌트 또는 커밋 제목>" (<상대시각>)
✓ 방법: <A 파일 하나만 / B 새 가지 / C 통째로 되감기> — <실제 실행한 명령>
✓ 백업 태그: rewind-backup/<브랜치>-<날짜시각>
  잘못됐으면 `git switch -c <아무이름> rewind-backup/<...>` 로 되돌리기 전 상태로 다시 갈 수 있어.
  원격에도 남기려면 `git push origin rewind-backup/<...>`
✓ 되살린 PR 기록: recover-<N> 브랜치로 가져옴 (PR #N) — 2-b 경로였을 때만

다음에 할 일:
- (A였으면) 되살린 파일이 커밋 대기 상태야. 내용 확인하고 커밋해줘 —
  대기 상태로 두면 다음 턴 자동 임시 저장(wip 커밋)이 건너뛰어져.
- (B였으면) 지금 <새이름> 브랜치 위야. 이어서 작업하면 돼.
- (C였으면) 브랜치가 그 시점으로 돌아갔어. 이어서 작업하면 자동 임시 저장이 다시 쌓여.
- recover-<N> 브랜치는 다 쓰면 `git branch -D recover-<N>` 로 지워도 돼 (GitHub 원본은 안 지워짐).
```

## 사용자 응대 톤

톤은 CLAUDE.md의 응답·문서 작성 원칙을 따름(친근한 반말, 조어 금지, 전문용어는 `번역(외국어 표기)`로 풀어 쓰기). 이 스킬 고유:

- 결정이 필요하면 진행을 멈추고 [결정 필요] 보고로 반환한다 (fork 실행이라 실행 중 질문 불가).
- **커밋 목록은 무조건 표로.** 줄글로 나열하면 사용자가 못 고른다.
- **강제 밀어넣기(force push)를 절대 권하지 않는다.** force push는 실제 사고로 이어지기 쉬운 명령이다.
- 되돌리기는 무서운 작업이다. 뭐가 사라지고 뭐가 남는지 매번 한 줄로 명시한다.

| 후보가 20개 넘음                                    | 최근 20개만 + "그 앞은 N개 더 있어" 명시                                                    |

## 호출 패턴

- `/rewind-task` — args 없음. 현재 브랜치 wip 목록을 표로 뽑아 §3 [결정 필요] 반환
- `/rewind-task #12` — 그 PR 기록을 되살려 wip 목록 제시
- `/rewind-task 3번으로 <파일경로> 만 되살려줘` — 방법 (A) 실행
- `/rewind-task 3번을 새 브랜치 <이름>으로 살려줘` — 방법 (B) 실행
- `/rewind-task 3번으로 통째로 되감아줘` — 방법 (C) 실행 (원격 확인 후)
- `/rewind-task <지점> — 변경은 커밋하고 진행` / `— stash하고 진행` — §1-b [결정 필요]에 대한 결정
- `/rewind-task 아침에 지도 만지기 전으로` — 자연어 지점 힌트. 시각·파일로 후보를 좁혀 표로 제시

번호는 §2에서 제시한 표의 `#` 열을 가리킨다. 커밋번호(`ed3523a`)를 직접 줘도 된다.

## 안 하는 것 (의도적)

- ❌ 강제 밀어넣기(force push) — 어떤 경우에도 안 함. 필요해지는 상황이면 멈추고 다른 방법을 권한다
- ❌ main 되감기·main 직접 push — main 커밋을 무르는 건 `git revert` 안내만 하고 중단
- ❌ 자동 커밋 — (A) 방법으로 되살린 파일은 대기 상태로 남긴다. 커밋은 사용자 몫
- ❌ 백업 태그 원격 push — 로컬 태그만. 원격은 사용자가 직접
- ❌ 기존 태그·브랜치 삭제 — `recover-<N>` 정리도 안내만 하고 사용자가 직접
- ❌ 되살린 내용 자동 판단 — 어느 wip이 "맞는" 시점인지 AI가 고르지 않는다. 표로 보여주고 사용자가 고른다
- ❌ Claude 자동 invoke — `disable-model-invocation: true`
- ❌ 브랜치 생성·PR·머지 — 그건 `new-task`·`done-task` 스킬
