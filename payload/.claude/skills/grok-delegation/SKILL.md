# 그록 위임

그록(Grok)은 xAI가 만든 다른 회사 AI다. 터미널에서 부르는 도구라 클로드의 서브 에이전트와는 부르는 법이 다르다.

**시작 전 브랜치 확인** — 파일을 바꾸기 전에 지금 어느 브랜치인지 먼저 본다.

```bash
git rev-parse --abbrev-ref HEAD
```

**main이면 `/new-task`를 직접 호출해 작업 브랜치를 연 뒤 진행한다.** main에서 파일을 바꾸면 `auto-wip-commit` 훅이 안 돌아 자동 저장이 안 되고(되돌릴 지점이 안 남는다), 나중에 `no-main-push` 훅에 막혀 올리지도 못한다.

## 언제 위임하나

- **사용자가 그록을 콕 집어 시켰을 때만 이 스킬을 쓴다** — 판단 기준은 CLAUDE.md 위임 절이 본진이다. 사용자가 도구를 안 골랐으면 이 스킬로 오지 말고 서브 에이전트로 간다.
- **한두 줄 고치는 정도면 위임하지 말고 클로드가 직접 한다** — 브리지를 띄우는 값이 일보다 비싸다.
- **자잘한 일이 여럿이면 묶어서 한 번에 위임한다** — 건별로 띄우지 않는다.
- **큰 일은 두 번 나눠 맡긴다** — 먼저 「검토 (코드 고치지 말고 설계 문서만)」로 읽기 모드에서 돌리고, 메인이 검수해 사람이 정할 것을 물은 뒤, 확정안으로 「구현」을 쓰기 모드에서 돌린다.

## 어떻게 부르나

- grok-build 브리지(bridge — 클로드와 그록을 이어주는 다리 역할 프로그램)로 위임한다. `Bash`로 이렇게 부른다:

  ```
  node ~/.claude/plugins/cache/xai-grok-build/grok-build/<버전>/scripts/grok-bridge.mjs run --cwd <프로젝트> --prompt-file <지시서 경로>
  ```

- **지시를 셸이 건드리지 못하게 넣는다** — 파일(`--prompt-file <경로>`)이나 따옴표 씌운 heredoc(`<<'GROKEOF'`) 둘 중 하나. **명령줄 인자로는 절대 넣지 않는다** — 셸이 역따옴표를 명령으로 실행해 그 부분이 통째로 사라지고 `$HOME` 같은 것도 엉뚱한 값으로 바뀐다. 조용히 깨져서 결과가 왜 틀렸는지 알 수 없다. 길이 문제가 아니라 셸이 내용을 바꾸는 게 문제다 (실측은 references/reference.md). 짧고 한 번만 돌릴 것은 heredoc이 도구 호출 한 번 싸고, 큰 구현 지시서는 파일로 남겨야 재시도·`--resume`가 공짜이고 백그라운드로 돌 때 `ps`로 살아있는지 확인된다.
- 오래 걸리거나 여러 개를 같이 돌리는 작업은 `Bash(run_in_background)`로 뒤에서 돌리고 출력은 파일로 받는다. 짧고 분명한 작업은 그냥 앞에서 기다린다.
- **뒤에서 돌릴 땐 반드시 상한을 건다** — 상한이 없으면 그록이 매달렸을 때 종료 알림이 영영 안 와서, '진행 중'과 '매달림'을 구분할 길이 없어진다. macOS엔 `timeout` 명령이 없을 수 있으니(이 머신에서 실측 확인) 어디서나 되는 perl로 건다: `perl -e 'alarm shift; exec @ARGV' 2400 node <브리지 경로> run …`. 기본 2400초(40분) — 실측 소요(§검증 참조)보다 넉넉하게, 큰 구현이면 더 늘린다.
- `grok-build:grok-delegate` 에이전트는 쓰지 않는다 — 600초에 잘려서 결과를 못 받아온다.
- **표식 처방 — 모든 위임 공통**: 지시서 완료 기준에 "최종 보고서 맨 첫 줄에 정확히 `=====REPORT=====` 한 줄"을 항상 요구한다. 진행 메시지와 보고서를 기계로 가르는 표식이다 — 읽는 법은 §검증.
- **병렬 서브 에이전트는 조건부 허용** — 전제 둘: grok CLI **1.0.5 이상** + 표식 처방. 1.0.4 이하는 최종 보고까지 글자 단위로 뒤섞여 못 쓴다(실측 — references/reference.md 연대기). 전제가 갖춰지면 조사·구현 모두 병렬이 되지만, **여러 에이전트가 같은 파일을 고치게 나누지는 마라** — 파일 단위로 갈라 맡긴다(공유 파일 동시 갱신은 실측 1회 통과뿐이라 확률 위험이 남는다). 진행 스트림은 여전히 섞일 수 있으나 어차피 버리는 부분이다. 전제를 못 갖췄으면 지시서에 "서브 에이전트를 병렬로 띄우지 마라"라고 적는다 — 안 적으면 출력을 읽을 수 없게 된다.

## 읽기 모드 vs 쓰기 모드

- **코드를 고치게 하려면 `--write`를 붙인다** — 안 붙이면 브리지가 그록을 읽기 전용 샌드박스로 띄운다 (근거는 references/reference.md). 작은 작업은 `Operation not permitted`로 그냥 실패하지만, **큰 작업은 그록이 서브 에이전트 워크트리에 써버려서 보고는 「구현 끝」인데 메인 폴더는 그대로**가 된다. 이게 제일 위험하다 — 거짓 보고가 아니라 엉뚱한 곳에 진짜로 고친 것이라 보고만 읽으면 알 수 없다. 그래서 `git diff`를 직접 봐야 한다.
- 조사·진단만 시킬 땐 일부러 빼는 게 안전하다.

## 토큰 절약 3원칙

- **잔일은 묶어서 한 번에** (기준은 §언제 위임하나)
- **후속 작업은 `--resume`으로 이어붙여 본다 — 다만 자주 실패한다** — 같은 영역의 후속 작업이면 새로 띄우지 않는 게 싸다(새로 띄울 때마다 그록이 저장소를 처음부터 다시 훑는 비용이 반복된다). 실패가 잦고 실패해도 종료 코드가 0일 수 있다 — 끝나면 `## 검증`의 `git status` 확인을 반드시 거친다. 안 바뀌었으면 `--resume` 없이 새로 띄우되, **읽어야 할 파일 목록을 지시서 맨 앞에 적어라** — 새 세션은 앞 대화를 모르니 "네가 방금 만든 것" 같은 말이 안 통한다.
- **지시서를 구체적으로 쓴다** — 대상 파일 경로·요구사항·완료 기준을 다 적는다. 그록이 뭘 고칠지 몰라 파일을 뒤지며 헤매는 구간이 토큰을 제일 많이 먹는다. 하네스 규칙(`AGENTS.md`·`CLAUDE.md`·`.claude/rules`)은 그록이 알아서 읽으니 지시서에 복사하지 말고, 쓸 스킬은 이름을 콕 집어 적는다 — 스킬은 이름·설명만 자동으로 들어가고 본문은 안 들어간다.

## 검증

결과 확인은 **두 갈래**다 — 종료 알림이 와서 깨워졌으면 갈래 1, 상한이 지나도록 무소식이면 갈래 2. 어느 쪽이든 이 절차를 건너뛰고 "됐겠지"로 넘어가지 않는다.

**갈래 1 — 깨워졌을 때: 검증 후 보고**

- **끝나면 `git status`부터 본다** — 종료 코드와 알림을 믿지 마라. `--resume`이 죽었을 때도 **종료 코드가 0(성공)으로 나올 수 있어서**, 알림은 「완료」인데 파일은 하나도 안 바뀐 상태가 된다. `--resume`을 붙였든 아니든 **파일이 진짜 바뀌었는지 먼저 확인한다.** 안 바뀌었으면 실패한 것이다 — `--resume` 없이 다시 띄우되 읽어야 할 파일 목록을 지시서 맨 앞에 적는다.
- **보고서 말고 `git diff`를 읽는다** — `git diff`는 코드가 실제로 어떻게 바뀌었는지 보여주는 명령이다. 보고서는 "했다고 주장하는 것"이고 diff가 "실제로 바뀐 것"이다. 끝나면 diff를 직접 읽고 빌드·린트·타입 검사를 돌려 판정한다. 결론을 떠받치는 숫자·사실도 메인이 한 번 다시 재본다 — 낡은 정보가 섞여 온다.
- **보고서는 문자열 `=====REPORT=====`를 찾아 그 뒤만 읽는다** — 표식 앞은 진행 찌꺼기다(섞여 있을 수 있고 버려도 된다 — 출력 파일에 남으니 부검이 필요한 날만 연다). 표식이 줄 머리가 아니라 앞 문장 꽁무니에 붙어 올 수 있으니 **줄이 아니라 문자열로** 찾는다(실측).
- 보고서 전문은 조사·진단처럼 **diff가 안 남는 작업**일 때만 읽는다.

**갈래 2 — 상한이 지나도록 무소식일 때: 생존 확인부터**

- **매달렸다고 단정하지 말고 `ps`로 프로세스가 살아 있는지부터 본다.** 살아 있으면 진행 중인 것이다 — 그대로 더 기다린다.
- **진행 상황을 CPU·파일 조용함으로 판단하지 마라** — 모델이 답을 만드는 동안은 로컬 CPU를 안 쓴다. 그래서 "23분 동안 CPU 6초", "세션 파일이 5분째 조용"은 멈춤의 증거가 아니라 **정상 동작**이다. 도구 기록에 뜬 MCP 서버 이름도 붙잡힌 표시가 아니다. 믿을 만한 신호는 **프로세스가 살아 있는지** 하나뿐이고, 나머지는 기다리는 수밖에 없다. 실측 소요 시간은 **검토 12~18분, 구현은 25분을 넘기도 한다.** 사용자에게 알릴 때도 "멈춘 것 같다"고 단정하지 말고 경과 시간과 프로세스 생존만 말해라 — 성급한 판정이 멀쩡한 작업을 죽인다.
- **죽어 있는데 알림을 못 받았으면**(앱 재시작 등으로 깨움이 유실된 경우) 출력 파일을 직접 열고 갈래 1을 그대로 적용한다.
- 상한(§어떻게 부르나)을 걸어뒀으면 무소식은 길어야 상한까지다 — 상한에서 강제 종료되며 알림이 반드시 온다. 그래서 상한 없이 뒤에서 돌리는 것 자체가 규칙 위반이다.

## 주의

- gitignore로 제외한 파일은 그록이 못 읽는다 (`CLAUDE.local.md` 등).
- 프로젝트에서 처음 한 번은 터미널에서 `grok`을 대화형으로 열어 이 프로젝트를 믿어도 되는지 확인(프로젝트 신뢰)해 둔다. `grok inspect`로 어떤 지시 파일·스킬이 불려 오는지 볼 수 있다.

## 경계

이 스킬은 **위임 실행만** 한다. 그록 CLI·플러그인 설치, 인증, 연동 방식 조사, 이 스킬 자체의 갱신은 `delegation-integrator` 에이전트가 맡는다. 플래그가 안 먹거나 새 옵션을 확인해야 하면 여기서 고치지 말고 그 에이전트를 부른다. 플래그별 검증 상태는 `references/reference.md`, 설치·인증·테스트 현황은 `references/status.md`에 있다.
