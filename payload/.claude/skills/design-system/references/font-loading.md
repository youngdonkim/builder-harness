# 한글 웹폰트 로딩

한글 폰트를 웹에서 빠르고 안전하게 띄우는 방법. damangochi 프로젝트에서 실제로 겪고 검증한 내용이다.

**어디까지 프레임워크와 무관한가**: §1 원리, §2 개념 구분, §3 토큰 계층에서의 자리는
어떤 프레임워크를 쓰든 그대로 통한다. §4 로딩 방법부터 §6 산출물 경로까지는 **Next.js 기준**이다.
다른 프레임워크라면 **"조각화된 폰트를 자체 호스팅(self-hosting) — 내 서버에서 직접 내려주는 것 — 한다"**
는 원칙만 가져가고, 도구별 방법은 그 프레임워크 문서에서 찾으면 된다.

## 1. 원리 — 한글 폰트는 조각 배달이 전부다

한글은 글자가 1만 자가 넘는다. 그래서 폰트 파일 하나에 전부 담으면 MB 단위가 되고, 그걸 통째로
받게 하면 첫 화면이 그만큼 늦어진다.

해법은 폰트를 90개 남짓한 조각으로 잘라 두는 것이다. 이걸 **조각화(subsetting) — 폰트를 글자 범위별로
잘라 두는 것** 이라고 한다. 조각마다 "나는 이 글자들을 담당한다"는 표시를 CSS 표준인
`unicode-range`로 적어 두면, 브라우저가 화면에 실제로 나온 글자를 보고 필요한 조각만 알아서 받아 간다.

유저가 어떤 글자를 입력할지 몰라도 안전하다. 서버에는 전 글자가 다 있고, 배달만 필요할 때 하는 구조라서
희귀한 글자가 나와도 그 글자가 든 조각(보통 몇 KB)만 새로 받아서 그린다.

## 2. 깜빡임과 자리 흔들림은 다른 문제다

둘을 섞어 이해하면 "이렇게 하면 깜빡임이 사라진다"는 잘못된 결론에 이른다.

| 현상 | 뜻 | 무엇이 줄여주나 |
|---|---|---|
| 깜빡임(FOUT, Flash of Unstyled Text) | 웹폰트가 도착하기 전 대체 글꼴로 보이다가 웹폰트로 바뀌는 것 | 자체 호스팅 + 조각화. 폰트가 빨리 도착하니 바뀌는 순간이 수십 ms로 짧아진다 |
| 자리 흔들림(CLS, Cumulative Layout Shift) | 글꼴이 바뀌는 순간 글자 자리가 튀는 것 | `next/font`의 자리 보정(대체 글꼴의 크기를 웹폰트에 맞춰 미리 맞춰 둠) |

`display: swap`을 쓰면 캐시가 없는 첫 방문에서는 글꼴이 바뀌는 순간 자체는 생길 수 있다.
`next/font`가 없애 주는 건 그 순간에 **글자 자리가 튀는 것**이지, 바뀌는 것 자체가 아니다.
**"FOUT 완전 제거"라고 문서나 커밋 메시지에 쓰면 과장이다** — 짧아진다고 써라.

## 3. 토큰 계층에서의 자리

- 폰트 패밀리(글꼴 이름)는 **foundation(1층) 원료**다. 색 팔레트 램프와 같은 자리다.
- 제품 코드는 semantic 별칭(`--font-family-base` 등)만 참조한다. 그래서 폰트를 통째로 갈아끼워도
  foundation만 바뀌고 화면 코드는 한 줄도 안 바뀐다.
- **로딩 방식은 토큰이 아니다.** 어떤 파일을 어떻게 받아올지는 빌드 인프라의 일이라 3층 밖에 있다.
  토큰 파일에 로딩 설정을 섞지 마라.

토큰 이름 문법은 [naming-taxonomy.md](naming-taxonomy.md) §2 `typography/family` 행 참조.

## 4. 로딩 방식 결정표 (Next.js)

| 폰트가 어디 있나 | 방법 | 핵심 설정 |
|---|---|---|
| 구글 폰트 | `next/font/google` | 조각화·자체 호스팅·자리 보정을 전부 알아서 해준다. 한국어 폰트는 `subsets: ["latin"]` + `preload: false` — 라틴 조각을 미리 받아 봐야 한글 화면에서는 안 쓰이고 자리만 차지한다 |
| npm 패키지 (Pretendard 등) | 패키지에 같이 들어 있는 dynamic-subset(조각화된) CSS를 `globals.css` **맨 위**에서 `@import` | 번들러가 조각 woff2를 산출물로 복사해 주니 자체 호스팅이 된다. **`next/font/local`은 쓰지 마라** — `unicode-range`를 지원하지 않아서 MB급 통짜 파일이 모든 화면에 미리 받기(preload)로 걸린다. 실제로 밟은 함정이다 |
| CDN `<link>` | 쓰지 않는다 | 외부 서버까지 왕복이 한 번 더 생기고, 캐시 상태에 따라 깜빡임이 가장 심해지는 방식이다 |

## 5. 마무리 체크 3가지

1. **폰트 스택 정리** — CDN 시절에 쓰던 이름 폴백은 지운다. 다만 OS 기본 글꼴 폴백
   (`-apple-system`, `"Apple SD Gothic Neo"` 등)은 남긴다. 웹폰트가 도착하기 전 그 짧은 순간에
   실제로 쓰이는 글꼴이다.
2. **폰트 정의는 한 파일에 모은다** — 흩어져 있으면 나중에 갈아끼울 때 빠뜨린다. 다만 로딩 방법이
   섞이면(예: 구글 폰트는 `fonts.ts`, npm 패키지는 `globals.css` 맨 위 `@import`) 한 곳으로 못 합칠
   수 있다. 이렇게 어쩔 수 없이 갈라질 때는 **왜 갈라졌는지 주석으로 남겨라.**
3. **검증은 브라우저가 아니라 산출물로** — 아래 §6 관문을 통과해야 끝이다.

## 6. 필수 관문 — 산출물로 검증한다

**폰트를 새로 넣거나 바꾸는 작업은 아래 세 가지를 전부 통과해야 끝난 것이다.** 하나라도 안 보면
"잘 되는 것처럼 보이는데 통짜 파일을 매번 받고 있는" 상태가 그대로 배포된다.

**이건 화면을 눈으로 보는 검증이 아니라 빌드 결과 파일을 확인하는 검증이다.
그러니 에이전트가 직접 끝까지 확인해라. 사람한테 "확인해주세요"로 넘기지 마라.**
(하네스에 "화면 검증은 사람 몫"이라는 원칙이 따로 있는데, 이 관문은 화면이 아니라 파일을 보는 일이라
그 원칙의 예외다.)

먼저 프로덕션 빌드를 한 번 돌린 뒤 확인한다.

**(1) 조각 woff2가 수십 개 있는가**

```bash
ls .next/static/media/*.woff2 | wc -l
```

수십 개(보통 90개 안팎)면 정상. 1~2개뿐이라면 조각화가 안 된 것이다. 파일 크기도 같이 본다 —
조각 하나는 보통 수~수십 KB다.

```bash
ls -lhS .next/static/media/*.woff2 | head -5
```

여기서 MB급 파일이 보이면 통짜 폰트가 그대로 들어간 것이다.

**(2) 불필요한 미리 받기(preload)가 없는가**

```bash
grep -o '"[^"]*\.woff2"' .next/server/next-font-manifest.json | sort -u
```

여기 나오는 파일이 브라우저가 무조건 미리 받는 대상이다. 없거나 아주 적어야 정상이고,
조각 수십 개가 줄줄이 나오면 `preload: false`가 안 걸린 것이다.

**(3) 빌드된 CSS의 `url()`이 해시 경로로 바뀌었는가**

```bash
grep -ho 'url([^)]*)' .next/static/css/*.css | sort -u | head -20
```

`/_next/static/media/…woff2` 같은 내부 해시 경로만 나와야 자체 호스팅에 성공한 것이다.
외부 주소가 남아 있으면 실패다.

```bash
grep -rl 'fonts.gstatic.com\|fonts.googleapis.com\|cdn.jsdelivr.net' .next/static/css/
```

이 명령이 파일 이름을 하나라도 뱉으면 아직 외부에서 폰트를 받아오고 있다는 뜻이다.
아무것도 안 나와야 통과.
