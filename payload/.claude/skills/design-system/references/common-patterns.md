## 1. 홈 첫 화면 — 최상단에 무엇을 두나

[실측] 2026-09, 한국·일본·영미권 서비스 **37곳**(커머스 19 · 게시판 커뮤니티 18)을 직접 열어 스크롤 전 첫 화면을 기록했고, 2026-09-29에 **51곳**(SaaS 17 · 커뮤니티·SNS 16 · 커머스 5 · 콘텐츠·미디어 6 · 마켓플레이스·O2O 7)을 더 봤습니다. 모두 **37곳 + 51곳**입니다.

한계가 셋 있습니다.

- **모바일 폭은 못 봤습니다** — 추가 51곳은 전부 데스크톱(1440×900)으로만 봤습니다. 모바일에서 히어로·배너·검색 줄이 어떻게 줄어드는지는 이 자료로 말할 수 없습니다.
- **로그인 후 화면이 거의 없습니다** — 커뮤니티·SNS, 커머스, O2O는 로그인 후 화면을 한 곳도 못 봤습니다. 로그인 후를 본 곳은 SaaS 1곳(Vercel)·콘텐츠 1곳(YouTube)과 표본 밖 참고 1곳(GitHub)뿐입니다.
- **같은 서비스의 로그인 전과 후를 둘 다 본 곳은 0곳입니다** — 아래의 로그인 전후 차이는 서로 다른 서비스를 견준 것입니다.

원자료(서비스별 관찰 표)는 하네스 원본 저장소(builder-harness)의 `docs/research/home-first-screen-survey-2026-09.md`에 있습니다.

**아래 유형별 차례와 규칙은 관례에서 나온 기본값이지, 꼭 따라야 하는 법이 아닙니다.** 같은 유형이라도 프로젝트마다 다른 요구가 있을 수 있습니다. 사용자가 관례와 다르게 원하면 **그 결정이 관례보다 우선합니다** — AI는 「관례는 이렇습니다」를 한 번 알려 주고 사용자가 정한 대로 갑니다. 관례를 근거로 사용자 결정을 되돌리거나 설득하지 않습니다. 대신 관례와 다르게 정한 것은 **이유와 함께 적어 둡니다** — 화면 인벤토리(`mvp/information-architecture.md`)의 홈 항목(「목적」 칸이나 비고)과 `mvp/design-brief.md`의 「첫 화면 결정」 절에. 적어 두지 않으면 뒤 단계(목업·프론트엔드 빌드)가 관례로 되돌려 버리니, 이 기록만은 빠뜨리면 안 됩니다. 그래서 뒤 단계는 「관례와 맞나」가 아니라 **「적어 둔 결정과 맞나」**를 봅니다. 단 [표준] 표시가 붙은 규칙(접근성 등)은 이 예외 없이 지킵니다.

### 1.1 유형부터 정한다

| 유형 | 홈이 답하는 질문 | 최상단부터의 차례 | 근거 |
|---|---|---|---|
| SaaS | 이게 뭐 하는 서비스지? | 히어로 → (고객사 로고 띠) → 기능 → 고객 사례 → 최종 행동 유도 → 푸터 | 16곳 관찰 (로그인 전) |
| 커머스 | 살 만한 게 있나? | 검색 → 카테고리 → 기획전 배너 → 목록 일부 | 19곳 + 5곳 관찰 |
| 마켓플레이스·O2O | 내 조건에 맞는 게 있나? | 위치·날짜 조건 입력 줄이 맨 위. 제목 한 줄과 조건 입력 줄을 사진 위에 얹는 구성이 흔함 | 7곳 관찰 |
| 커뮤니티·SNS | 오늘 무슨 얘기 있나? | **로그인 전** — 한국: 검색·게시판 메뉴 → (광고) → 글 목록 (콘텐츠 먼저) / 해외: 가입 화면이나 가입 랜딩 (가입 먼저). **로그인 후** — 검색·탭 → 피드 | 로그인 전 18곳 + 16곳 관찰. 로그인 후는 SNS 피드 3곳(표본 적음), 추가 조사에선 0곳 |

「홈이 답하는 질문」 칸은 구조를 설명하려고 붙인 해석이지 측정한 값이 아닙니다. 유형을 고를 때 참고만 하고, 근거로 쓰지 않습니다.

- **커머스와 O2O의 경계** — 자유 검색어로 찾으면 커머스, 위치·날짜 조건으로 찾으면 O2O입니다. O2O 7곳 중 2곳(직방·당근)은 조건 입력 줄 대신 카테고리·검색이 맨 위였습니다.
- **SaaS 차례의 로고 띠에 괄호를 친 이유** — 첫 화면 안에 고객사 로고 띠·숫자를 둔 곳이 16곳 중 6곳이라 관례라 부를 만큼 모이지 않았습니다.
- **콘텐츠·미디어는 보류입니다** — 뉴스·글은 커뮤니티 편집형을, 영상 스트리밍은 한국 커머스형을 참조합니다. 6곳으로는 한 유형으로 묶이지 않았습니다.

### 1.2 관찰에서 나온 규칙

- [ ] 최상단 1·2번은 **탐색 진입점**(검색바·카테고리 줄)입니다. 37곳 중 **추천 슬라이드가 최상단인 곳은 0곳**이었습니다. 큰 배너는 그 아래로 갑니다. 추가 조사의 커머스도 5곳 중 5곳이 검색·카테고리가 맨 위였고, 히어로 문장은 0곳이었습니다. [실측] **예외 둘** — SaaS는 히어로(16곳 중 16곳), O2O는 조건 입력 줄(7곳 중 5곳)이 맨 위입니다. 해외형 커뮤니티의 로그인 전 화면은 아래 커뮤니티 규칙을 따릅니다. [실측]
- [ ] **SaaS의 로그인 전 홈은 히어로로 시작합니다.** 16곳 중 16곳이었고, 제목(16/16)·부제(15/16)·행동 단추(14/16)를 갖췄습니다. [실측]
- [ ] **SaaS 히어로는 넘기지 않습니다.** 여러 장을 넘기는 히어로는 16곳 중 0곳이었습니다. 움직임이 필요하면 제품 영상(16곳 중 6곳)으로 줍니다. [실측]
- [ ] **SaaS 히어로의 시각물은 제품 화면이 기본값입니다.** 16곳 중 10곳이 실제 제품 화면(이미지·영상)이었습니다. [실측]
- [ ] **SaaS 히어로 단추는 주 1개 + 보조 1개가 흔합니다.** 16곳 중 10곳. 주 단추는 「무료로 시작」 계열(10곳), 보조는 「데모·도입 문의」 계열이 많았습니다. [실측]
- [ ] **SaaS 홈에 가격표·FAQ 섹션을 넣지 않아도 됩니다.** 16곳 중 0곳이었고, 가격은 상단 바 링크로 따로 뺐습니다(15곳). [실측]
- [ ] **SaaS 홈은 최종 행동 유도 섹션으로 끝냅니다.** 푸터 바로 앞에 한 번 더 단추를 둔 곳이 16곳 중 14곳이었습니다. [실측]
- [ ] (후보 — 표본 적음, 3곳) **로그인한 사람에게는 히어로를 보여주지 않습니다.** 로그인 후 본 곳 모두(Vercel·YouTube + 참고 GitHub) 히어로 대신 작업 화면(대시보드·개인화 목록)이 떴습니다. 같은 서비스의 전후를 비교한 곳은 없습니다. [실측]
- [ ] **커뮤니티에는 자동으로 도는 배너를 두지 않습니다.** 18곳 중 0곳, 추가 조사의 커뮤니티·SNS 16곳 중에도 0곳이었어요. 큰 시각 요소가 있으면 대부분 외부 광고였고 그것도 돌지 않았습니다. [실측]
- [ ] **커머스의 도는 배너는 관례입니다.** 한국 7곳 중 6곳, 일본 6곳 중 4곳이 실제로 돌았고, 추가 조사에서도 한국 3곳 중 3곳이 돌았습니다. 커뮤니티 규칙을 커머스에 그대로 옮기지 않습니다. [실측] 간격은 두 조사가 다릅니다 — 기존 한국 7~9초(일본 2~4초), 추가 조사 한국 약 2~4초. 표본과 재는 방법이 달라 어느 쪽이 대표값인지 모릅니다. **재측정 필요.** 해외 2곳(Amazon·Etsy)은 돌지 않았지만 2곳뿐이라 일반화하지 않습니다.
- [ ] **O2O는 맨 위에 조건 입력 줄을 둡니다.** 위치·날짜 입력이 맨 위인 곳이 7곳 중 5곳 — 자유 검색창 하나만 두는 커머스(0곳)와 다릅니다. [실측]
- [ ] **O2O 첫 화면은 제목 한 줄 + 조건 입력 줄을 사진 위에 얹는 구성이 흔합니다.** 제목 문장 7곳 중 5곳, 사진 배경 4곳. 큰 배너는 돌리지 않았습니다(0곳). [실측]
- [ ] **커뮤니티 홈은 두 갈래 중 하나를 고릅니다** — 글 제목이 바로 깔리는 **글 피드형**, 게시판 이름만 보이는 **게시판 허브형**. 어느 쪽인지 화면 인벤토리에 적습니다. [실측] 18곳이 12 대 6으로 갈렸습니다. 추가 조사의 한국 7곳은 편집형(여러 게시판 글을 묶은 섹션이 여럿) 5 · 목록형 1 · 허브형 1이었습니다.
- [ ] **커뮤니티의 로그인 전 화면은 지역에 따라 갈립니다** — 한국은 콘텐츠부터(8곳 중 7곳, 예외는 가입 랜딩인 밴드), 해외는 가입부터(8곳 중 7곳 — 가입 화면 3·가입 랜딩 3·콘텐츠 옆 가입 패널 1, 예외는 Stack Overflow). 우리 서비스가 어느 쪽인지 화면 인벤토리에 적습니다. [실측]
- [ ] **훑는 화면은 밀도를 올리고 읽는 화면은 여백을 올립니다.** 피드형은 첫 화면에 글이 10~18건 들어갔어요. 여백을 키워 5건만 담으면 훑을 수가 없습니다. [실측]
- [ ] **게시판 커뮤니티는 로그인하지 않은 사람에게도 목록을 보여줍니다.** 19곳 중 막은 곳은 1곳뿐이었습니다. [실측] 해외 SNS·커뮤니티는 가입부터 받는 곳이 많으니(위 지역 규칙) 어느 쪽으로 갈지는 §1.3에서 정합니다.

### 1.3 프로젝트가 정할 것

- 큰 배너를 둘지, 둔다면 돌릴지 (커머스면 돌리는 쪽이 관례, 커뮤니티면 두지 않는 쪽. SaaS 16곳·O2O 7곳도 도는 큰 배너는 0곳)
- 커뮤니티라면 글 피드형인지 게시판 허브형인지
- 첫 화면에 글쓰기 진입점을 둘지 — 한국 커뮤니티 6곳은 **전부 없었고**, 일본·영미권은 섞였습니다. 없으면 게시판에 들어가야 글을 씁니다. [실측]
- 로그인 전후 홈을 다른 화면으로 둘지 — 유형별 기본값은 **SaaS·해외형 커뮤니티는 둘로**(로그인 전 랜딩·가입 화면 / 로그인 후 작업 화면·피드), **한국형 커뮤니티·커머스·O2O는 하나로**입니다. 뒤쪽 셋은 로그인 후 화면을 한 곳도 못 봐서, 로그인 전 화면에 이미 콘텐츠·탐색이 있다는 데서 나온 기본값입니다.
- 커뮤니티라면 로그인 전에 콘텐츠를 먼저 보여줄지, 가입부터 받을지 (한국은 콘텐츠 먼저 8곳 중 7곳, 해외는 가입 먼저 8곳 중 7곳)
- SaaS라면 히어로 주 단추가 무료 시작인지 도입 문의인지 (주 단추가 「무료로 시작·가입·체험」 계열 16곳 중 10곳, 「도입 문의·데모」 계열 3곳. 한국과 해외의 차이는 판정하지 못했습니다)
- 위 기본값과 다르게 정한 것은 **이유와 함께** 화면 인벤토리의 홈 항목과 `mvp/design-brief.md` 「첫 화면 결정」에 적습니다.

## 2. 반드시 통과할 것 — 접근성 표준

만들고 나서 이 아홉 개를 훑습니다.

- [ ] 모든 입력 칸과 아이콘 단추에 접근 이름이 있다. 안내 문구(placeholder)를 이름 대신 쓰지 않습니다 — 글을 치면 사라지니까요. 자리가 없으면 `aria-label`. [표준] WCAG 3.3.2·4.1.2
- [ ] 글 칸 글자가 16px 이상이고 화면 확대를 막지 않는다. 16px 아래면 모바일 사파리가 저 혼자 화면을 키웁니다. 그걸 `user-scalable=no`로 막는 것은 위반이에요. [표준] WCAG 1.4.4
- [ ] 끌어다 놓기 말고 단추로도 첨부가 된다. [표준] WCAG 2.5.7
- [ ] 글 칸에서 탭 키가 밖으로 나갈 수 있다. 탭을 들여쓰기로 가로챈다면 빠져나갈 다른 길을 만들고 화면에 알립니다. [표준] WCAG 2.1.2
- [ ] 올라간 결과를 소리로도 알린다. 새 글이 붙은 사실이 눈으로만 보이면 안 됩니다(`role="status"` 같은 자리). [표준] WCAG 4.1.3
- [ ] 오류는 그 칸 옆에, 고치는 법까지 적는다. 「제목을 써 주세요」가 아니라 「제목은 60자 이하로」. 칸이 여럿이면 맨 위 요약도 함께 두고 각 줄이 그 칸으로 건너뛰게 합니다. [표준] WCAG 3.3.1·3.3.3, GOV.UK
- [ ] 넣은 사진에 설명을 적을 자리가 있다. 안 썼다고 막지는 않습니다 — 막으면 아무 글자나 넣어 더 나빠져요. [표준] WCAG 1.1.1
- [ ] 되돌리기 어려운 선택에는 확인할 기회가 있다(공개 범위 등). 되돌리기·검사·확인 중 하나. [표준] WCAG 3.3.4
- [ ] 도구 단추 줄은 탭 한 번으로 들어가고 안에서는 화살표로 옮긴다(`role="toolbar"`, 줄에도 이름). 단추가 열 개면 탭을 열 번 눌러야 본문에 닿습니다. [표준] ARIA 작성 지침

## 3. 한국어라서 챙길 것

- [ ] 엔터로 확정하는 칸마다 조합 가드를 단다. 한글은 글자를 만드는 중에도 엔터가 와서, 안 막으면 마지막 글자가 한 번 더 들어갑니다. 댓글창만이 아니라 태그·검색·주소 칸 전부예요.

  ```ts
  if (event.key !== "Enter" || event.nativeEvent.isComposing) return;
  ```

- [ ] 제목 칸의 엔터가 발행이 되지 않게 막는다. HTML은 원래 그렇게 동작해서, 본문이 빈 글이 그대로 올라갑니다. 한글을 확정하려 누른 엔터가 그대로 발행이 돼요. [표준] HTML 암묵적 제출

## 4. 실제 서비스가 자주 빼먹는 것 — 그래서 더 봐야 하는 것

표준인데 현실에서 잘 안 지켜지는 자리예요. 「다들 안 하니까 괜찮다」가 아니라 「여기가 빠지기 쉽다」로 읽습니다.

- 결과를 소리로 알리기 — 인스타그램·페이스북 댓글창에는 알림 자리가 아예 없었고 유튜브만 있었습니다. 단추 이름은 다들 꼼꼼히 달면서 이것만 빠져요. [실측]
- 모바일 확대 막기 — 조사한 국내외 서비스 거의 전부가 모바일에서만 확대를 막습니다. 같은 주소를 데스크톱으로 열면 허용해요. 원인은 하나같이 글자를 16px 아래로 둔 것입니다. 화면이 작아 확대가 가장 필요한 쪽에서만 막는 셈이라 따라 할 일이 아닙니다. [실측]
- 에디터가 댓글창보다 접근성이 나쁘다 — 같은 회사 안에서도 댓글창에는 이름을 제대로 달고 게시물 작성창에는 안 답니다. 칸과 단추가 늘수록 빠지는 자리가 늘어요. 에디터를 만들었으면 §2를 한 번 더 훑습니다. [실측]

## 5. 컴포저 — 댓글·답글·채팅

```
[아바타] ┌─────────────────────────┐
        │ 글 칸 (자동 높이)         │
        │ [도구]        [보내기]   │
        └─────────────────────────┘
```

- [ ] 테두리와 포커스 표시는 바깥 상자 하나만 갖는다(`:focus-within`). 안쪽 글 칸이 따로 가지면 눌렀을 때 이중으로 보입니다.
- [ ] 글 칸이 쓰는 만큼 늘어나되 최대 높이에서 멈추고 안쪽만 스크롤한다. 한 줄 입력(`<input>`)을 쓰지 않습니다. 한계가 없으면 긴 댓글이 화면을 덮어요. [실측] 인스타그램이 이 방식입니다.
- [ ] 도구 아이콘은 글 칸 아래 줄에. 오른쪽에 붙이면 도구가 늘 때마다 글 칸이 좁아집니다.
- [ ] 보내기는 아이콘이든 글자든 좋고, 비었을 때 꺼 둔다. 실제 서비스는 글자 단추가 다수예요(「게시」·「댓글」). 아이콘만 쓸 거면 이름을 반드시 답니다.
- [ ] 엔터는 기기마다 다르게. 데스크톱은 엔터로 보내고 시프트+엔터로 줄바꿈, 모바일은 엔터가 줄바꿈이고 보내기는 단추로만 받습니다(모바일 키보드엔 시프트+엔터가 없어요). `enterkeyhint`로 키보드 엔터 키에 적힌 말을 실제 동작과 맞춥니다.
- [ ] 모바일 키보드가 올라와도 글 칸과 보내기가 가려지지 않는다. 모바일은 화면이 두 겹이고 키보드는 보이는 겹만 줄여서, `100vh`나 화면에 붙인 것은 키보드 뒤로 숨습니다. 뷰포트에 `interactive-widget=resizes-content`를 더하고 안 되는 브라우저는 `visualViewport`로 받칩니다. 데스크톱에서는 끝까지 안 드러나는 함정이에요. [표준] 웹 표준
- [ ] 보내고 나면 칸을 비우고 높이를 되돌리고 포커스를 그 칸에 둔다. 연달아 쓰는 일이 많고, 포커스가 날아가면 모바일에서 키보드가 오르내립니다.
- [ ] 로그인이 필요하면 쓰던 글이 살아남는다. 로그인 창을 열기 전에 적어 두고, 로그인을 마치면 그 화면으로 돌아와 그대로 올린 뒤 그 자리로 옮겨갑니다. 로그아웃할 때는 지웁니다. 적어 둔 것을 꺼내는 순간 지워지므로, 꺼낸 뒤 올리기가 취소될 수 있는 자리에서 꺼내지 않습니다.

## 6. 에디터 — 게시글·포스트

- [ ] 쓴 것과 올라가는 것이 같다. 저장 형식을 만들려고 사용자가 쓴 글을 변환하지 않습니다. 미리보기가 필요하다고 느껴지면 변환이 과하다는 신호예요(마크다운처럼 결과가 원래 다른 방식을 일부러 고른 경우는 예외).
- [ ] 넣는 즉시 실제 모습으로 보인다. 자리표시 글자를 본문에 박지 않습니다. 편집 화면에서만 블록으로 다루고 저장 형식은 그대로 두되, 풀었다 되감았을 때 값이 같은지 검사를 둡니다.
- [ ] 제목은 따로 받는다. 본문 첫 문단을 잘라 쓰면 제목을 고를 수 없고 본문을 고칠 때마다 따라 바뀝니다.
- [ ] 자동으로 임시 저장하고 저장됐다는 것을 알린다. 에디터에서는 사실상 예외가 없어요(댓글창과 가장 크게 갈리는 점). 저장 자리를 미리 비워 둔 채 화면에 두고 실제로 저장된 시점에만 갱신합니다 — 글자마다 갱신하면 화면 읽어주는 프로그램 쓰는 사람은 자기 글이 안 들려요. 「임시 저장됨」과 「올렸어요」는 다른 말로 씁니다.
- [ ] 되살릴 초안은 언제 것인지 보여 주고 사용자가 고르게 한다. 묻지 않고 덮어쓰지 않습니다. 초안 열쇠에 「누가」와 「어느 글」을 담아 서로 덮어쓰지 않게 합니다.
- [ ] 글을 잃어버리는 길을 전부 막는다. 나가기 확인 창은 브라우저를 떠날 때만 뜹니다 — 앱 안에서 링크를 눌러 이동하거나 뒤로 갈 때는 안 떠요. 앱 안 이동에도 따로 걸고, 화면이 가려지는 순간에 임시 저장합니다. 로그인이 끊겨도 쓰던 글이 남아야 합니다.
- [ ] 고치기는 왕복이 맞는다. 열면 쓴 그대로 돌아오고 다시 올리면 같은 값이 저장됩니다. 푸는 함수와 되돌리는 함수를 한 자리에 짝으로 두고 기존 글 전량으로 검사합니다.
- [ ] 한 화면에 다 둔다. 제목·본문·딸린 값을 나누지 않습니다. 꼭 나눠야 하면 「2/3」 같은 단순한 표시만.
- [ ] 필수 칸에 별표 대신, 선택 칸에 「(선택)」을 적는다. [표준] GOV.UK

한국 게시판을 쓰던 사람이 기대하는 것 — 도구 줄이 두 겹입니다. 위는 넣기(사진·동영상·링크), 아래는 서식(크기·굵게·색·목록·정렬·되돌리기). 되돌리기는 화면에 단추로 두는 쪽이 관례예요(단축키만 두면 모바일에서 되돌릴 길이 없습니다). 모바일에서도 넣기 도구를 줄이지 않습니다. [실측] 서식을 지원할지는 프로젝트가 정하되, 없으면 허전하게 느껴진다는 것을 알고 정합니다.

## 7. 프로젝트가 정할 것

구조와 동작만 여기서 정합니다. 아래는 프로젝트 몫이에요.

- 도구 줄에 무엇을 둘지, 본문에 서식을 지원할지
- 안내 문구, 글자 수 제한값, 첨부 개수·하루 상한
- 임시 저장 주기와 저장 위치
- 글 칸을 `<textarea>`로 할지 `contenteditable`로 할지 — 실제 서비스도 갈립니다(같은 회사 안에서도 다름). 서식이 필요 없으면 `<textarea>`가 다루기 쉽고, 쓰기로 했다면 `role="textbox"`·`aria-multiline`·접근 이름을 손으로 달아야 합니다.
- 색·간격·모서리 값(전부 semantic 토큰으로)
