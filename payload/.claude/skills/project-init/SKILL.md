# project-init — 프로젝트에 하네스 적용·동기화

하네스는 **파일 복사로 배포**한다. builder-harness 저장소가 원본(SoT, Source of Truth — 정답이 되는 하나뿐인 출처)이고, 그 저장소의 `payload/`가 **프로젝트 루트의 미러(mirror — 거울처럼 같은 모양)**다. 적용은 이 미러를 프로젝트 루트에 그대로 복사하는 일이다. 복사된 파일은 프로젝트 저장소에 커밋되므로, 팀원은 프로젝트를 clone(내려받기)만 하면 하네스가 이미 들어 있다 — 하네스 저장소를 따로 받을 필요가 없다.

이미 하네스가 적용된 프로젝트에서 재실행하면, 신규 복사 대신 원본과 비교해 갱신하는 동기화 모드로 동작한다.

## 전제 확인

1. **현재 폴더가 프로젝트 루트인가** — 프로젝트의 최상위 폴더에서 실행해야 한다.
2. **git repo인가** — 아니면 `git init -b main` 제안 (done-task·new-task·훅 모두 git 전제).
3. **하네스 원본 저장소가 어디 있나** — 아래 [하네스 원본 찾기](#하네스-원본-찾기).

## 하네스 원본 찾기

복사해 올 원본은 **로컬에 clone된 builder-harness 저장소**다. 순서대로 찾는다.

1. **기본 위치 `~/dev/builder-harness`** 를 먼저 본다. `payload/`가 있으면 그게 원본이다.
2. 없으면 사용자에게 경로를 묻는다 — "하네스 저장소를 어디에 받아뒀어?"
3. 아직 안 받았다면 clone을 제안한다:

   ```bash
   git clone git@github.com:youngdonkim/builder-harness.git ~/dev/builder-harness
   ```

   이 저장소는 비공개(private — 외부에 공개되지 않은 저장소)라 https 주소로는 인증이 막힌다. GitHub 계정에 SSH 키가 등록돼 있어야 clone된다.

### 원본 검증 (필수 — 건너뛰지 않는다)

원본을 찾았으면 복사하기 전에 **반드시** 아래 순서를 전부 실행해 검증한다. 제안이 아니라 실행이다.

```bash
git -C <원본경로> rev-parse --abbrev-ref HEAD    # main이어야 한다
git -C <원본경로> status --porcelain             # 출력이 비어 있어야 한다
git -C <원본경로> pull --ff-only origin main     # 반드시 실행
git -C <원본경로> rev-parse HEAD origin/main     # 두 sha가 같아야 한다
```

**어느 하나라도 어긋나면 중단**한다. 무엇이 문제고 사용자가 뭘 하면 되는지 안내한다:

- **main이 아님** → 원본이 지금 어느 브랜치에 있는지 알려준다. 작업 중인 브랜치 내용이 프로젝트로 새어 나가면 안 되니, 원본에서 main으로 옮긴 뒤 다시 불러달라고 안내한다.
- **커밋 안 된 변경이 있음** → 그대로 복사하면 스탬프가 가리키는 커밋과 실제 복사되는 내용이 어긋난다고 짚고, 원본을 정리한(커밋하거나 되돌린) 뒤 다시 불러달라고 안내한다.
- **pull 실패** (네트워크 오류·충돌 등) → 중단한다. 낡은 원본을 복사하면 적용하자마자 뒤처진 상태가 되므로 그냥 진행하지 않는다.
- **HEAD와 origin/main이 다름** → 로컬 원본이 원격과 어긋난 상태라고 알리고 중단한다.

*왜 중단하나*: 검증을 건너뛰고 잘못된 원본을 복사하면 (가) 프로젝트가 조용히 미확정 내용이나 낡은 하네스를 갖게 되고, (나) 스탬프(`.claude/harness-version`의 `commit=`)가 "이 커밋 기준으로 맞췄다"는 거짓 값을 갖게 된다. 스탬프는 다음 동기화에서 프로젝트 파일이 그냥 뒤처진 것인지 프로젝트가 손댄 것인지 가르는 유일한 근거([로컬 수정 흔적 판별](#3-로컬-수정-흔적-판별))라, 한번 거짓이 되면 나중에서야 드러나고 되짚기도 어려운 사고로 이어진다.

검증을 통과했으면 **적용할 커밋을 기록해둔다**. 스탬프 파일에 쓸 값이다:

```bash
git -C <원본경로> rev-parse --short=12 HEAD
```

## 모드 판별

프로젝트 루트에 `CLAUDE.md`가 이미 있거나 `.claude/harness-version`이 있으면 이미 하네스가 적용된 프로젝트다 → **동기화 모드**(아래 [동기화 모드 절차](#동기화-모드-절차))로 진행한다. 없으면 **신규 적용 모드**(아래 [진행 순서](#진행-순서-신규-적용-모드))로 진행한다.

## 진행 순서 (신규 적용 모드)

### 1. 아이디어 인터뷰 (2질문)

사용자에게 묻는다 — 이미 대화에서 나왔으면 생략. 답을 쉽게 꺼내게, 아래 예시를 붙여 안내한다:

- **서비스 이름과 한 줄 정의** (이름은 repo명과 같아도 됨) — 예시: "밥심 — 혼자 사는 직장인을 위한 저녁 메뉴 추천 앱"
- **타겟 — 누가, 어떤 상황에서** — 예시: "야근 잦은 자취 직장인이 퇴근길에 '오늘 뭐 먹지' 고민할 때"

이 두 답은 idea-to-mvp 1단계(UserStory)의 필수 입력 1·2와 같은 항목이다 — CLAUDE.md에 박혀 1단계가 다시 묻지 않는다.

### 2. CLAUDE.md 생성

원본의 `payload/CLAUDE.md.template`을 프로젝트 루트에 `CLAUDE.md`로 복사하고 `{{...}}` placeholder를 1번 답으로 채운다. 템플릿 구조(머리말 + 작업 원칙 + 맨 끝 `@AGENTS.md` 줄)는 **수정하지 않고 그대로** — 하네스 표준이다. **idea-to-mvp 방법론 설명은 CLAUDE.md에 넣지 않는다** — 방법론은 스킬 발동 중에만 필요하고 스킬이 전부 관리한다. CLAUDE.md는 만드는 제품(앱)과 사용자 취향의 자리다.

### 3. AGENTS.md 생성

`AGENTS.md`는 클로드뿐 아니라 그록·Codex 같은 다른 AI 도구도 읽는 규칙 파일이다.

- 프로젝트 루트에 `AGENTS.md`가 **없으면** 원본의 `payload/AGENTS.md.template`을 프로젝트 루트에 `AGENTS.md`로 복사하고 `{{...}}` placeholder를 1번 답으로 채운다 (2단계 CLAUDE.md와 같은 방식). 템플릿 구조는 **수정하지 않고 그대로** — 하네스 표준이다.
- **이미 있으면** 파일을 지우거나 덮어쓰지 않는다. `<!-- BEGIN:project-rules -->` 마커 구역이 없을 때만, 템플릿의 마커 구역(placeholder를 채운 상태)을 파일 맨 끝에 덧붙인다.
- **다른 도구가 자동으로 만든 구역은 절대 건드리지 않고 그대로 둔다** — 예를 들어 `next dev`가 넣는 `<!-- BEGIN:nextjs-agent-rules -->` 구역. 우리 마커 구역만 우리가 관리하고 나머지는 그 도구 몫이다.
- 2단계에서 만든 `CLAUDE.md` **맨 끝**에 `@AGENTS.md` 줄이 있는지 확인하고, 없으면 맨 끝에 붙인다. 맨 끝이어야 하는 이유는 Next.js가 이 줄을 자기가 덧붙이는데, 이미 있으면 다시 안 건드려서다.

### 4. payload 미러 복사

원본의 `payload/` 아래 파일을 프로젝트 루트에 **같은 경로로 통째로 복사**한다 (폴더 없으면 생성). 원본의 구조가 곧 프로젝트에 놓일 모양이라, 무엇을 어디로 옮길지 따로 셀 필요가 없다.

```
<원본>/payload/.claude/  →  <프로젝트>/.claude/   (skills·agents·hooks·rules·templates)
<원본>/payload/docs/     →  <프로젝트>/docs/      (git-workflow.md)
<원본>/payload/.github/  →  <프로젝트>/.github/   (workflows/ci.yml)
```

**복사에서 빼는 파일 셋** — 미러 규칙의 예외는 이 셋뿐이다. 그대로 놓이는 파일이 아니라서 빠진다.

- `payload/CLAUDE.md.template` — 복사 대상이 아니라 가공 대상. [2단계](#2-claudemd-생성)에서 이미 썼다.
- `payload/AGENTS.md.template` — 같은 이유로 가공 대상. [3단계](#3-agentsmd-생성)에서 이미 썼다.
- `payload/.claude/settings-hooks.json` — 복사 대상이 아니라 병합 원본. 다음 단계에서 내용만 합친다.

훅 스크립트에 실행 권한을 준다: `chmod +x <프로젝트>/.claude/hooks/*.sh`

이번에 들어오는 것 중 설명이 필요한 둘 — `docs/git-workflow.md`는 `no-main-push`·`auto-wip-commit` 훅과 `new-task`·`done-task`·`rewind-task` 스킬이 따르는 워크플로를 사람이 읽게 정리해둔 문서고, `.github/workflows/ci.yml`은 lint + build를 도는 CI로 `done-task`가 머지 전에 이 통과를 기다린다.

### 5. 훅 등록 — settings.json 병합

원본의 `payload/.claude/settings-hooks.json`은 **훅 등록 원본**이다. 이 파일의 `hooks` 블록을 프로젝트의 `.claude/settings.json`에 병합한다.

- 프로젝트에 `settings.json`이 없으면 그 내용 그대로 새로 만든다.
- 있으면 **기존 키를 전부 보존한 채** `hooks` 블록만 넣는다. 프로젝트가 이미 자기 훅을 등록해뒀다면 지우지 말고, 같은 이벤트 안에 하네스 훅을 덧붙인다 — 겹치는 하네스 훅(같은 스크립트 경로)은 하나만 남긴다.

경로는 `"$CLAUDE_PROJECT_DIR"/.claude/hooks/<이름>.sh` 형태라 프로젝트를 어디에 두든 그대로 작동한다.

`.claude/settings.json`은 저장소에 커밋되는 파일이라, 이 상태로 main에 합쳐두면 팀원 전원에게 똑같이 적용된다.

### 6. 폴더 정리

```
mvp/                   # 단계 산출물 (market-research.md 등이 단계 진행하며 생김)
docs/                  # 사람이 읽는 문서 (Claude 자동 로드 X)
```

### 7. 버전 스탬프 기록

프로젝트에 `.claude/harness-version` 파일을 만든다. 다음 동기화 때 이 값을 기준으로 프로젝트 쪽 하네스 파일이 그냥 낡은 것인지 로컬에서 손본 것인지 가른다([로컬 수정 흔적 판별](#3-로컬-수정-흔적-판별)).

```
repo=youngdonkim/builder-harness
commit=<하네스 원본 찾기에서 구한 12자리 이상 커밋 sha>
date=<오늘 날짜 YYYY-MM-DD>
```

`repo=`는 원본 저장소 주소다. 포크해서 쓴다면 그 주소로 적는다 — 나중에 이 프로젝트의 하네스가 어디서 왔는지 알아보는 값이다.

### 8. 마무리 안내

사용자에게 알린다:

- 방금 프로젝트에 들어온 것: `CLAUDE.md`, `AGENTS.md`, `.claude/`(skills·agents·hooks·rules·templates·settings.json·harness-version), `docs/git-workflow.md`, `.github/workflows/ci.yml`. **전부 이 프로젝트 저장소에 커밋할 파일**이다 — 커밋해서 main에 합치면 팀원은 프로젝트를 clone하는 것만으로 하네스를 그대로 받는다. 팀원이 하네스 저장소를 따로 받을 필요는 없다.
- 훅 2개가 자동 작동: `no-main-push`(main 직접 push 차단), `auto-wip-commit`(응답 끝날 때마다 feature 브랜치에 wip 커밋 — main에서는 자동으로 건너뛴다). 뭔가 잘못돼서 되돌리고 싶으면 `/rewind-task` 스킬을 쓴다.
- **지금 열린 세션에는 새 스킬·훅이 아직 안 잡힌다** — 새 파일이라서가 아니라 `.claude/` 폴더가 방금 처음 생겨 지금 세션의 감시 대상이 아니라서다. 처음 적용할 때는 **앱을 껐다 켜야** 잡힌다 — 껐다 켜도 대화는 안 날아간다(대화를 버리는 `/clear`와는 다르다). 나중에 하네스를 최신으로 올리는 동기화 때는 `.claude/`가 이미 있어 껐다 켜지 않아도 이 세션에서 바로 잡힌다 — 하네스 원본 저장소에서 `git pull` → 이 프로젝트 세션에서 "하네스 동기화해줘". (스킬이 플러그인이면 그 안 hooks·`.mcp.json`·agents 변경은 `/reload-plugins`가 따로 필요하다(터미널 실행 전용 명령 — 데스크톱 앱엔 없다) — 하네스 자체는 플러그인이 아니다.)
- 다음 단계: `/idea-to-mvp`로 1단계 UserStory 시작. (idea-to-mvp가 `mvp/` 산출물을 보고 현재 단계를 스스로 판별하니, 이미 진행한 프로젝트면 알아서 이어서 시작한다.)

## 동기화 모드 절차

이미 하네스가 적용된 프로젝트에서는 신규 복사 대신, 프로젝트에 있는 파일을 원본과 비교해 갱신한다. 먼저 [하네스 원본 찾기](#하네스-원본-찾기)로 원본 위치를 확인하고 원본 검증을 마친다.

**payload 미러로 온 파일은 전부 하네스 소유물**이고, **`CLAUDE.md`와 `AGENTS.md` 둘만 예외**다.

### 1. 프로젝트 쪽 미커밋 검사

**먼저 지금 프로젝트가 main 브랜치에 있는지 본다.**

```bash
git rev-parse --abbrev-ref HEAD
```

- **main이면 `/new-task`를 직접 호출해 작업 브랜치를 연 뒤 동기화를 이어간다.** 사용자에게 되묻지 말고 클로드가 연다. 이유는 짧게 짚어준다 — `auto-wip-commit`(턴이 끝날 때마다 바뀐 파일을 알아서 커밋해두는 훅)은 작업 브랜치에서만 돈다. main에서 그대로 동기화하면 바뀐 파일이 커밋 안 된 채 쌓여 되돌릴 지점이 안 남고, 나중에 `no-main-push` 훅에 막혀 올리지도 못한다.
- **main이 아니면** — 그대로 다음으로 넘어간다.

동기화는 하네스 소유 파일을 **원본 내용으로 덮어쓴다.** 그 전에 프로젝트 쪽에 커밋 안 된 변경이 있는지도 먼저 본다 — 있는 채로 진행하면 되돌릴 수 없이 사라진다.

```bash
git status --porcelain -- .claude docs/git-workflow.md .github/workflows/ci.yml
```

- **출력이 있으면** 멈추고 사용자에게 묻는다. 이 파일들을 곧 덮어쓸 참이라 커밋하거나 되돌린 뒤 다시 진행해야 한다고 짚고, 걸린 파일 목록을 보여준다.
- **하네스 소유 경로 밖의 미커밋 변경은 상관없다** — 동기화가 안 건드리는 파일이라 그대로 두고 진행한다.

### 2. 하네스 소유물 — 교체가 기본

프로젝트에서 고치지 않는 전제의 파일들이다. 하네스가 관리하니 **원본 내용으로 교체**하는 게 기본이다.

- `payload/.claude/*` ↔ `.claude/*` (skills·agents·hooks·rules·templates)
- `payload/docs/git-workflow.md` ↔ `docs/git-workflow.md`
- `payload/.github/workflows/ci.yml` ↔ `.github/workflows/ci.yml`
- `payload/.claude/settings-hooks.json`의 hooks 블록 ↔ `.claude/settings.json`의 hooks 블록

처리 갈래:

- **동일** → 넘어간다.
- **프로젝트에 없음** (원본에 새로 생긴 파일) → 복사한다.
- **원본에서 사라짐** (이름이 바뀌었거나 폐기된 파일) → 프로젝트에서도 지운다. 지우기 전에 목록으로 보여주고 확인받는다.
- **다름** → 아래 [로컬 수정 흔적 판별](#3-로컬-수정-흔적-판별)로 갈라진다.

`settings.json`은 파일 전체가 아니라 **hooks 블록만** 하네스 소유물이다. 나머지 키(`permissions`·`env` 등 프로젝트가 넣은 것)는 손대지 않는다.

교체한 훅 스크립트에는 실행 권한을 다시 준다: `chmod +x .claude/hooks/*.sh`

### 3. 로컬 수정 흔적 판별

하네스 소유물인데 프로젝트 쪽이 원본과 다를 때, 그냥 뒤처진 것인지 프로젝트가 손댄 것인지 가른다.

- **원본의 옛 버전과 같다** → 그냥 뒤처진 것이다. 조용히 교체한다.
  - 옛 버전은 스탬프의 `commit=` 값으로 꺼낸다: `git -C <원본경로> show <스탬프커밋>:payload/<프로젝트에서의 경로>`
- **원본의 옛 버전과도 다르다** → 프로젝트가 로컬에서 고친 흔적이다. **충돌로 보고 사용자에게 묻는다** — 어디가 어떻게 다른지 짚어주고 (a) 원본으로 교체 (b) 로컬 수정 유지 중 고르게 한다. 임의로 정하지 않는다.
- 스탬프가 없거나 그 커밋에서 파일을 못 찾으면(옛 원본이거나 그때는 payload 안 경로가 달랐으면) 판별할 수 없다 → 안전하게 **충돌로 보고 물어본다**.

### 4. CLAUDE.md·AGENTS.md — 예외 둘, 병합이 기본

`CLAUDE.md`는 프로젝트가 자기 사정에 맞게 채우고 덧붙이는 파일이라 덮어쓰지 않는다. 비교도 파일 전체가 아니라 **템플릿(`payload/CLAUDE.md.template`)에서 온 부분만** 한다.

- **보존 대상 (대조 안 함)** — placeholder가 채워진 프로젝트 고유 내용(서비스 이름·한 줄 정의·타겟 등)과 프로젝트가 스스로 추가한 문장·섹션(디자인 시스템 adapter에 채워진 경로, 앱 개발 컨벤션에 쌓인 규칙 등). 템플릿과 다른 게 정상이고, 병합해도 그대로 남는다.
- **대조 대상** — 템플릿에서 그대로 오는 공용 문구와 구조. 작업 원칙 섹션, 진행 방식·기획 문서 위치 안내문, 섹션 골격과 제목, 그 안에 박힌 단계 번호 같은 것. 신규 적용 모드에서 "수정하지 않고 그대로" 복사하는 부분([2. CLAUDE.md 생성](#2-claudemd-생성))이 곧 이 범위다.

*왜 대조하나*: 공용 문구는 하네스가 바뀌면 같이 낡는다. 예를 들어 `/idea-to-mvp`가 7단계로 개편되면 프로젝트 CLAUDE.md에 남은 "6단계로 검증·개발한다"가 틀린 안내가 되는데, 파일 전체를 비교에서 빼두면 아무도 못 잡는다.

다르면 **병합이 기본 동작이다.** AI가 곧장 병합안을 만든다 — 프로젝트 고유 내용은 그대로 두고 공용 문구만 최신으로 맞춘다. 무엇이 어떻게 합쳐지는지 요지를 한 줄씩 모아 보여주고, 사용자가 확인하면 반영한다.

병합에는 안전 규칙 둘이 있다:

- **진짜 충돌은 AI가 임의로 정하지 않는다** — 같은 대목을 템플릿과 프로젝트가 서로 다르게 고쳤으면, 그 대목만 양쪽 내용을 나란히 짚어 어느 쪽으로 갈지 사용자에게 물어본다. 안 겹치는 나머지는 그대로 합친다.
- **확인 없이 파일에 쓰지 않는다** — 병합도 예외가 아니다. 병합안을 보여주고 사용자 확인을 받은 뒤에만 파일을 고친다.

병합안을 본 사용자가 다른 걸 원하면 (a) 템플릿 공용 문구로 교체 (b) 지금 내용 그대로 유지 중에 고를 수 있다 (기본이 아닌 예외 경로다).

**`AGENTS.md`도 병합이 기본이다** — 대조는 파일 전체가 아니라 **템플릿(`payload/AGENTS.md.template`)에서 온 부분만** 한다.

- **보존 대상 (대조 안 함)** — 프로젝트가 채운 내용. 디자인 시스템 adapter에 적힌 실제 경로, 앱 개발 컨벤션에 쌓인 규칙, 프로젝트가 스스로 추가한 섹션.
- **대조 대상** — 템플릿에서 그대로 오는 공용 문구와 섹션 골격.
- **대조·병합 범위는 `<!-- BEGIN:project-rules -->` 구역 안으로만 한정한다.** 마커 밖과 `<!-- BEGIN:nextjs-agent-rules -->`처럼 다른 도구가 만든 구역은 절대 건드리지 않는다.
- 마커 구역이 아예 없으면 템플릿의 마커 구역을 파일 맨 끝에 덧붙인다. 파일 자체가 없으면 [3. AGENTS.md 생성](#3-agentsmd-생성)대로 템플릿에서 새로 만든다.
- 위 CLAUDE.md 병합 안전 규칙 둘(진짜 충돌은 임의로 정하지 않는다 / 확인 없이 파일에 쓰지 않는다)이 `AGENTS.md`에도 똑같이 적용된다.

`CLAUDE.md` 맨 끝에 `@AGENTS.md` 줄이 있는지도 확인하고, 없으면 맨 끝에 붙인다.

### 5. 폴더 보정

`mvp/`·`docs/` 폴더는 신규 모드와 동일하게, 없으면 채운다.

### 6. 스탬프 갱신

반영이 끝나면 `.claude/harness-version`의 `commit=`을 이번에 적용한 원본 커밋으로, `date=`를 오늘 날짜로 갱신한다. 파일이 없으면 [7. 버전 스탬프 기록](#7-버전-스탬프-기록) 형식으로 새로 만든다.

**사용자가 로컬 수정을 유지하기로 골라서 원본과 다른 파일이 남았어도 스탬프는 갱신한다** — 스탬프는 "언제 기준 원본과 맞춰봤나"를 가리키는 값이지 "모든 파일이 원본과 똑같다"는 보증이 아니다. 다만 남은 차이는 마무리 보고에 반드시 적는다.

### 7. 마무리 보고

**두 갈래가 드러나게** 나눠 보고한다.

- **하네스 소유물** (스킬·에이전트·훅·rules·git-workflow.md·ci.yml·훅 등록) — 교체됨 / 새로 복사됨 / 삭제됨 / 로컬 수정 유지됨(사용자가 고름) / 전부 최신
- **CLAUDE.md** — 병합됨 / 템플릿으로 교체됨(사용자가 고름) / 그대로 유지됨(사용자가 고름) / 최신
- **AGENTS.md** — 병합됨 / 템플릿으로 교체됨(사용자가 고름) / 그대로 유지됨(사용자가 고름) / 최신 / 새로 만듦

끝에 스탬프를 어느 커밋으로 갱신했는지 적는다. 그다음 커밋 안내는 지금 어느 브랜치에 있었는지에 따라 다르게 준다:

- **작업 브랜치에서 진행했으면** — `auto-wip-commit` 훅이 턴마다 알아서 커밋해뒀을 테니, `/clear` 뒤 `/done-task`로 PR을 만들어 main에 합치면 된다고 안내한다.
- **main에 서 있으면** — 동기화 모드는 main에서 멈추니(1단계), 이 갈래는 신규 적용 모드로 하네스를 방금 처음 깐 직후에만 해당한다. 첫 적용은 main에서 하는 게 정상이다. 지금 바뀐 파일이 아직 커밋 안 된 채 main에 남아 있다고 짚어주고, 작업 브랜치를 만들어 그 위에 커밋한 뒤 `/done-task`로 PR을 올리라고 안내한다.

**지금 세션에서도 바뀐 스킬·훅이 바로 잡히니 따로 할 일 없다**는 것도 함께 알린다. 그래도 확실히 하고 싶으면 앱을 껐다 켜면 된다 — 대화는 안 날아간다.

## 안 하는 것 (의도적)

- ❌ 앱 스캐폴딩(`package.json`·`src/`) 생성 — 그건 5단계 FrontendBuild 영역
- ❌ GitHub repo 생성·push — 사용자가 원할 때 별도로
- ❌ 기존 CLAUDE.md·AGENTS.md 무단 덮어쓰기 — 동기화 모드에서도 프로젝트 고유 내용은 병합으로 보존하고, 반영은 사용자 확인 뒤에만. AGENTS.md 안에서 다른 도구가 만든 구역도 손대지 않는다
- ❌ 하네스 원본 저장소를 프로젝트에서 고치기 — 하네스 개선은 builder-harness 저장소에서 PR로. 프로젝트 `.claude/` 안의 복사본을 고쳐봐야 다음 동기화에서 충돌로 잡힌다
- ❌ 프로젝트 `.claude/settings.json`의 hooks 이외 키 건드리기
