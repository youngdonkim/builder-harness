# transfer-ownership — 프로젝트 소유 옮기기

프로젝트가 밖에 만들어 둔 것들 — **저장소·DB·호스팅·소셜 로그인 앱·AI 키** — 을 한 소유에서 다른 소유로 함께 옮긴다. 생애에 한두 번이라 `idea-to-mvp` 본문이 아니라 별도 스킬이다.

**평상시 계정·토큰 관리는 이 스킬이 정하지 않는다.** `docs/account-check.md`(원칙 여섯 + 서비스별 함정)와 `6-0-backend-prep.md`가 정하고, 이 스킬은 그걸 **전제로** 쓴다 — 계정 검문 시점(원칙 ①), 발급 토큰 보관(원칙 ②), 브라우저 작업의 계정 지정(원칙 ④), 한 번만 보이는 값 확보(원칙 ⑤), 카카오 자동화 금지(서비스별 함정). 베껴 적지 않고 가리킨다.

**시작 전 브랜치 확인** — `git rev-parse --abbrev-ref HEAD`. main이면 `/new-task`로 작업 브랜치를 먼저 연다.

> ⚠ 아래 화면 위치·명령·요금제 조건은 쓴 시점 기준이다. 따라 하기 전에 공식 문서로 확인하고, 다르면 공식 문서를 따르고 이 문서를 고쳐야 한다고 보고한다. 반대로 「계획표 승인 전에는 안 옮긴다」·「검증 전에는 옛 토큰을 안 지운다」 같은 우리 규칙은 그대로 지킨다.

## 1. Aside의 역할 — 넷뿐

나머지 실행·검증은 **CLI와 관리 API**로 한다. 호출은 `aside --account <프로필> "<지시>"`.

| | Aside가 하는 일 |
|---|---|
| ① | 양쪽 프로필에서 각 서비스를 훑어 현재 상태 보고 (읽기 전용) |
| ② | 대시보드 전용 클릭 — 조직 초대·수락, 프로젝트 이전, 토큰·키 발급, 호스팅 GitHub 앱 설치·저장소 연결 |
| ③ | 발급된 비밀값을 화면에서 읽어 파일로 저장 |
| ④ | 이메일 인증 코드를 메일함에서 읽어 넣기 |

**비밀값은 대화에 남기지 않는다.** Aside repl에서 세션 폴더에 쓰고(`await fs.writeFile(path.join(pwd, 이름), 값)` — **`/private/tmp`는 거부된다**), 읽어서 제자리에 넣고, 확인하고, 파일을 지운다. 값을 못 읽었으면 살려 두지 않고 바로 폐기 후 재발급(`account-check.md` 원칙 ⑤).

## 2. 0단계 — 입력

- [ ] **프로젝트 `AGENTS.md`의 계정 표는 「옛 상태」로만 읽는다.** 목표를 정하는 근거가 아니다 — 표는 [§7](#7-5단계--마무리)에서 새 소유 기준으로 다시 쓴다.
- [ ] **양쪽 소유의 Aside 프로필을 계정 명부에서 찾고, 없으면 사용자에게 묻고 시작한다.**

`aside account list`로 프로필 목록을 꺼내 **그대로 보여주고 라벨을 받는다** — "u0가 회사, u1이 개인" 식으로.

- **번호로 짐작하지 않는다.** `u0`가 회사라는 규칙은 없다(같은 컴퓨터에서 순서가 뒤바뀐 사례 있음).
- **이메일 도메인으로 단정하지 않는다.** 목록에 보이는 건 Aside 계정 이메일이지 그 프로필 안에 로그인된 저장소·DB·호스팅 계정이 아니다. 판정은 늘 서비스 화면의 계정 표시로 한다(`account-check.md` 원칙 ④).
- **`signed out` 프로필은 못 쓴다.** 사용자가 로그인해야 하고(사람 몫), 그때까지 그 프로필이 맡을 단계는 멈춘다.

**하네스에는 계정 값을 적지 않는다** — `project-init`이 "계정 값은 이 프로젝트 표에만 남는다"고 정해 뒀다. 명부를 새로 만들지 않는다. 사용자가 자기 방식으로 보관하면 그걸 근거로 쓰고, 없으면 물어서 받는다.

## 3. 1단계 — 조사와 이전 계획표

**읽기 전용이다.** 아무것도 만들지 않고 이전·초대 버튼도 누르지 않는다. CLI로 되는 건 CLI로, 대시보드에서만 보이는 건 Aside ①로.

- [ ] 서비스마다 한 줄씩 채운다 — **현재 소유 / 목표 / 방법(이전 vs 재생성) / 도구(CLI vs Aside vs 사람)**. 대상은 DB · 저장소 · 호스팅 · 소셜 로그인 앱(제공사별로 한 줄) · AI 키.
- [ ] **부작용 셋을 서비스마다 점검한다.** 빈칸으로 두지 않는다 — "없음"도 확인한 결과여야 한다.
  1. **주소·식별자가 바뀌는가** — 저장소 주소, DB 참조 아이디(ref), 배포 도메인. 바뀌면 코드·환경변수·콜백이 전부 따라 바뀐다.
  2. **소셜 로그인 앱을 재생성하면 사용자 식별이 갈라지는가** — 제공사 사용자 아이디가 앱 단위면 같은 사람이 새 앱에서 다른 사람으로 보여 기존 계정에 못 들어간다. **이전이 되면 이 문제가 안 생긴다**(id·secret이 따라옴 — [§10](#10-참고--실측-사실)). 제공사마다 **이전 가능 여부부터** 확인하고, 안 되는 곳만 갈라짐을 따진다.
  3. **유료 좌석·결제가 드는가** — 임시로 넣는 멤버도 자리를 차지할 수 있다.

**사용자가 계획표를 승인해야 다음으로 간다.** 되돌리기 비싼 갈림길이다. "이건 나중에"가 나오면 그 줄을 「추후 결정」으로 표시해 [§7](#7-5단계--마무리)에서 남긴다.

## 4. 2단계 — 실행 (순서 고정)

**시작 전에 [§5 정지·금지](#5-3단계--정지금지)를 먼저 읽는다.**

```
DB 조직 → 저장소 → 호스팅 팀 + Git 재연결 → 소셜 로그인 앱 → AI 키
```

- **DB가 맨 앞** — 콜백 주소에 DB 참조 아이디(ref)가 들어가서, DB가 확정돼야 로그인 앱을 건드린다.
- **저장소가 호스팅보다 앞** — 저장소를 옮기면 호스팅 Git 연결이 끊긴다. 호스팅을 먼저 손보면 두 번 잇는다.
- **AI 키가 맨 뒤** — 호스팅 이전 뒤에 해야 환경변수를 한 번에 갈아 끼운다.

- [ ] **단계마다 네 묶음을 탄다** — 전제 확인(명령으로, 말만 믿지 않는다) → 실행 → **API·CLI로 읽어서** 검증(화면의 "됐다"는 검증이 아니다) → 임시 멤버·옛 연결 정리.
- [ ] **공통 패턴** — 새 조직에 옛 소유자를 잠시 멤버로 넣고 → 수락(이메일이면 Aside ④) → **옛 소유자가 이전 실행** → 검증되면 **뺀다**(유료 자리를 차지한다).
  단 **호스팅은 이 패턴을 먼저 쓰지 않는다** — Vercel은 초대 없이 이전을 요청하는 기능이 있다([§10](#10-참고--실측-사실)). 그 기능이 없는 호스팅일 때만 공통 패턴으로 간다.
- [ ] **저장소를 옮기면 호스팅 Git 연결이 끊긴다** — 새 소유에 호스팅 GitHub 앱을 설치하고 저장소를 다시 연결한다(Aside ②). 누르기 전에 **브라우저의 GitHub 로그인 계정도 대조한다** — 연결에는 상대 서비스의 지금 세션이 붙는다(원칙 ④).
- [ ] **새 토큰·키는 발급 즉시 API로 유효성을 확인한 뒤** CLI 전용 파일 · CI Secret · 호스팅 환경변수(Production·Preview 둘 다)에 설치한다. 들어가는 자리는 `6-0-backend-prep.md` §4.1 배선표가 정본이다 — 한 곳만 바꾸면 나머지가 옛 값으로 남아 특정 기능만 조용히 실패한다.
- [ ] **계정 검문은 매 단계 쓰기 작업 직전에 다시 한다**(원칙 ①). gh는 프로젝트 CLI 전용 파일의 `GH_TOKEN`으로 도는지부터 확인한다(`gh api user --jq .login`) — 토큰이 없으면 전역 활성 계정이 저절로 바뀌어 있을 수 있다([§10](#10-참고--실측-사실)). **소유를 옮기면 이 토큰도 새 소유 계정 것으로 갈아 끼운다.**

## 5. 3단계 — 정지·금지

- [ ] **자동화 금지 서비스(카카오)는 사람이 하고 AI는 키 교체만 한다** — 브라우저 에이전트를 붙였다가 계정이 제재된 실사고가 있다(`account-check.md` 서비스별 함정). 조사([§3](#3-1단계--조사와-이전-계획표))에서도 그 화면은 열지 않고 사용자에게 현재 상태를 묻는다.
- [ ] **비밀번호·일회용 코드(OTP)·패스키는 사람 몫이다.** 이메일 인증 코드만 Aside ④가 읽어 넣는다.
- [ ] **옛 토큰·키·앱은 검증([§6](#6-4단계--검증))이 끝날 때까지 폐기를 보류한다.** 되감기가 가능한 이유가 이 보류다.
- [ ] **폐기 전에 같은 계정의 다른 프로젝트가 쓰는지 확인하고 사용자에게 묻는다** — 발급 토큰은 소유 계정당 하나를 여러 프로젝트가 나눠 쓰는 게 기본이라(원칙 ②), 이 프로젝트만 보고 지우면 남의 프로젝트가 멈춘다.

## 6. 4단계 — 검증

**PR 하나로 셋을 한꺼번에 태운다.**

- [ ] **CI가 새 Secret으로 통과하나** — 토큰이 CI Secret에 제대로 들어갔는지 드러난다.
- [ ] **프리뷰가 새 작성자 계정으로 뜨나** — 커밋 작성자의 Git 계정 연결(원칙 ③)이 사는지 드러난다.
- [ ] **머지 뒤 실서비스 배포가 새 팀에서 도나** — Git 재연결이 실제로 붙었는지 드러난다.

**스모크 검사는 시드 순수 상태를 가정한다**([§10](#10-참고--실측-사실)) — 로컬 QA 데이터가 남아 있으면 순위·집계가 어긋난다. 리셋할지 스킵할지는 **사람이 정한다.** AI가 임의로 지우지 않는다.

**화면 판정은 사람 몫이다** — 주소를 건네고 사용자가 로그인·주요 흐름을 직접 확인한다. 확인했다는 말을 들은 뒤에 `/done-task`를 부른다.

## 7. 5단계 — 마무리

- [ ] **계정 표를 새 소유 기준으로 전면 다시 쓴다** — 서비스별 계정·이메일, 커밋 작성자(git), 브라우저 작업 프로필까지. **토큰이 들어간 자리·만료일은 표가 아니라 비밀값 장부**(`mvp/backend-build.md`)에 적는다 — 표는 「누구의 계정인가」만 답한다. **「옛 상태는 이랬다」를 남기지 않는다**(산출물은 매 판이 완결, 옛 값은 git 이력에). 로컬 git 작성자 설정도 표와 맞춘다(전역은 안 건드린다).
- [ ] **「추후 결정」 항목을 표에 `추후 결정:`으로 남긴다** — 지우지 않는다.
- [ ] **계정 명부 갱신 문안을 사용자에게 건넨다** — 하네스에 계정을 안 적으므로([§2](#2-0단계--입력)), 사용자가 자기 보관처에 그대로 붙여 넣을 완성된 문단으로. 담을 것: 프로필↔계정 새 대응, 서비스별 계정·이메일, 토큰이 들어간 자리, 재발급 기한. **값 자체(토큰·키 문자열)는 넣지 않는다.**
- [ ] **메모리를 갱신한다** — 이 프로젝트의 소유가 바뀌었다는 사실과 새 프로필 대응.
- [ ] **마지막으로 옛 토큰·키·앱 폐기 여부를 묻는다**([§5](#5-3단계--정지금지)). "지워도 된다"고 답한 것만 지운다.

## 8. 6단계 — 되감기

되감기도 [§4](#4-2단계--실행-순서-고정)의 네 묶음을 그대로 탄다. 되돌리는 중에도 검증을 건너뛰지 않는다.

| 단계 | 되돌리는 법 | 주의 |
|---|---|---|
| DB | 같은 절차로 반대 방향 프로젝트 이전 | ref가 유지되니 코드·콜백은 안 건드린다 |
| 저장소 | `gh api -X POST /repos/{새owner}/{repo}/transfer -f new_owner=<옛 소유>` | 옛 소유 쪽에 같은 이름 저장소가 있으면 실패 — 먼저 확인 |
| 호스팅 | 반대 방향 이전 + GitHub 앱 재설치·저장소 재연결 | **환경변수는 안 따라온다** — 옛 팀에 다시 등록 |
| 로그인 앱 | 새로 만든 앱이면 옛 앱 값을 배선표대로 되돌린다 | **옛 앱을 안 지웠을 때만** — [§5](#5-3단계--정지금지)의 보류가 이걸 위한 것 |
| AI 키 | 옛 키를 환경변수·CLI 전용 파일에 다시 넣는다 | 폐기 전이어야 한다 |

**저장소 안 파일**(환경변수 이름·계정 표·콜백 주소)은 `/rewind-task`로 되감는다 — 이 표는 **밖에 있는 것**을 되돌리는 법이다.

**옮기다 중간에 멈췄으면 되감기보다 마저 끝내는 쪽이 대개 안전하다.** 절반 상태가 가장 잘 깨진다. 되감기는 계획 자체가 틀렸을 때 고르는 길이고, 어느 쪽으로 갈지는 사용자에게 묻는다.

## 9. 안 하는 것 (범위 밖)

- ❌ 계정 만들기 · 2단계 인증(2FA) 설정 · 사업자 인증 · 유료 플랜 결제·좌석 구매 — 전부 사람 몫. AI는 필요하다는 사실만 [§3](#3-1단계--조사와-이전-계획표) 부작용에 적어 알린다.
- ❌ 카카오 콘솔 조작 — [§5](#5-3단계--정지금지).
- ❌ 화면을 열어 동작 판정 — 사람이 본다(저장소 검증 규칙).

## 10. 참고 — 실측 사실

규칙이 아니라 사실이라 서비스가 바뀌면 낡는다. 어긋나면 공식 문서를 따르고 이 절을 고쳐야 한다고 보고한다.

- **Anthropic API 키는 워크스페이스 범위로 발급해야** 별도 헤더 없이 쓸 수 있다.
- **Vercel 팀 스코프 토큰은 `vercel whoami`가 `Not authorized`로 나와도 정상이다** — 팀 범위 토큰이라 개인 조회 권한이 없을 뿐. 실패로 보고 재발급하지 않는다.
- **`vercel link`는 `.env.local`에 `VERCEL_OIDC_TOKEN` 한 줄을 쓴다.** 다른 값은 안 건드린다.
- **Vercel은 팀 초대 없이 프로젝트 이전을 요청하는 기능이 있다** — 임시 멤버로 유료 자리를 만들 필요가 없다.
- **Supabase 조직 초대 API는 최상위(Enterprise) 요금제 전용**이라 그 아래에서는 대시보드에서만 초대된다.
- **Supabase 프로젝트 이전은 ref·키·인증 설정을 그대로 유지한다** — 그래서 콜백 주소가 안 바뀐다.
- **GitHub 저장소 이전은 `gh api -X POST /repos/{owner}/{repo}/transfer`로 요청하고, 받는 쪽이 이메일 링크로 수락해야 완료된다.** Actions Secrets는 따라온다.
- **GitHub 저장소와 GitHub OAuth 앱은 이전해도 id·secret이 유지된다** — 설정 변경 0건. 그래서 이전되는 앱은 사용자 로그인 식별도 안 갈라진다.
- **구글 로그인 앱이 사는 GCP 프로젝트는 아직 실측이 없다** — 이전 비용이 재생성보다 크다는 기록만 있다(`6-0-backend-prep.md` §2). 실제로 옮겨 보면 여기 적는다.
- **저장소를 옮기면 호스팅의 Git 연결이 끊긴다** — 새 계정에 호스팅 GitHub 앱을 설치하고 다시 연결해야 한다.
- **gh는 환경변수 토큰(`GH_TOKEN`)이 저장된 자격 증명보다 우선한다**(실측: `gh help environment`) — 그래서 프로젝트 CLI 전용 파일의 토큰으로 고정하고, 토큰이 걸린 상태에서는 활성 계정 전환이 아무 효과가 없다. 토큰이 없을 때만 전역 활성 계정이 쓰이고, 계정이 둘이면 그게 저절로 바뀌는 일이 있다. git 자격 증명 도우미가 옛 위치를 가리키면 `gh auth setup-git`으로 잡는다.
- **스모크 검사는 시드 순수 상태를 가정한다** — 로컬 QA 데이터가 남아 있으면 순위·집계가 어긋난다.
