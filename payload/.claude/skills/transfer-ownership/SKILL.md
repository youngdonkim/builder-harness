# transfer-ownership — 프로젝트 소유 계정 옮기기

프로젝트가 밖에 만들어 둔 것들 — **저장소·DB·호스팅·소셜 로그인 앱·AI 키** — 을 한 계정에서 다른 계정으로 함께 옮긴다. 개인 ↔ 회사, 또는 다른 팀으로.

소유 이전은 프로젝트 한평생에 한두 번 있는 일이라 `idea-to-mvp` 본문이 아니라 별도 스킬로 둔다. **평상시 계정·토큰·키를 어떻게 다루는지는 이 스킬의 범위가 아니다** — 그건 `idea-to-mvp`의 `6-0-backend-prep.md`와 `docs/account-check.md`가 정한다. 이 스킬은 그 규칙을 베껴 적지 않고 필요할 때 가리킨다.

**시작 전 브랜치 확인** — 파일을 바꾸기 전에 지금 어느 브랜치인지 먼저 본다.

```bash
git rev-parse --abbrev-ref HEAD
```

**main이면 `/new-task`를 직접 호출해 작업 브랜치를 연 뒤 진행한다.** main에서 파일을 바꾸면 `auto-wip-commit` 훅이 안 돌아 자동 저장이 안 되고(되돌릴 지점이 안 남는다), 나중에 `no-main-push` 훅에 막혀 올리지도 못한다.

> ⚠ 여기 적힌 외부 서비스의 화면 위치·명령·요금제 조건은 이 글을 쓴 시점 기준이다. 따라 하기 전에 공식 문서로 지금도 맞는지 확인하고, 달라졌으면 공식 문서를 따르고 이 문서를 고쳐야 한다고 사용자에게 보고한다. 반대로 「계획표 승인 전에는 아무것도 안 옮긴다」·「검증 전에는 옛 토큰을 안 지운다」 같은 우리 규칙과 실사고 기록은 그대로 지킨다.

## 1. 무슨 스킬인가 — 범위와 경계

**옮기는 것 다섯** — DB(Supabase 등), 저장소(GitHub), 호스팅(Vercel 등), 소셜 로그인 앱, AI 제공사 키. 이 다섯이 서로 주소·키로 얽혀 있어서 하나만 옮기면 나머지가 조용히 끊긴다. 그래서 한 흐름으로 묶어 옮긴다.

**이 스킬이 하지 않는 것**은 [§9](#9-안-하는-것-의도적)에 모아 뒀다. 특히 **평상시 계정 규칙**(어느 CLI가 전환형인지, 토큰을 어디 두는지, 계정 검문을 언제 하는지)은 여기 다시 적지 않는다 — `docs/account-check.md`와 `6-0-backend-prep.md`가 정본이고, 이 스킬은 단계마다 그쪽을 가리킨다.

**이 스킬의 실패 모드는 「덜 옮김」이 아니라 「옮기다 만 상태로 끊김」이다.** 저장소만 옮기고 호스팅 연결을 안 잇거나, 새 키를 넣기 전에 옛 키를 지우면 서비스가 멈춘다. 그래서 순서를 고정하고([§6](#6-실행-순서-고정)), 폐기는 검증 뒤로 미룬다([§5](#5-정지금지-조건)).

## 2. 입력 — 무엇을 근거로 판단하나

**프로젝트 `AGENTS.md`의 「소유와 계정」 표는 「옛 상태」로만 읽는다.** 지금 무엇이 어느 계정에 묶여 있는지를 짐작하는 출발점이지, **목표를 정하는 근거가 아니다.** 표는 이전이 끝난 뒤 새 소유 기준으로 전면 다시 쓴다([§7](#7-마무리--pr-하나로-검증하고-표-다시-쓰기)).

**Aside 프로필과 계정의 대응은 하네스 계정 명부에서 찾고, 없으면 사용자에게 묻는다.**

- **지금 하네스에는 계정 명부가 없는 게 기본이다.** `project-init`이 "계정 값은 이 프로젝트 표에만 남는다 (하네스에는 계정을 적지 않는다)"고 정해 뒀다. **그러니 이 스킬도 하네스에 계정 값을 적지 않는다** — 명부를 새로 만들지도, 하네스 파일에 계정을 써 넣지도 않는다.
- 사용자가 자기 방식(비밀번호 관리자·개인 메모 등)으로 명부를 보관하고 있으면 그걸 근거로 쓴다. 없으면 **물어서 받는다.**

사용자에게 받아야 하는 것 — 이미 대화에 나왔으면 생략하고, 한 번에 묶어 묻는다.

| 받을 것 | 왜 필요한가 |
|---|---|
| 목표 소유 (개인/회사/팀) | 서비스별 목표 계정을 다 가른다 |
| 서비스별 목표 계정·조직·팀 이름 | 이전 대상을 지정할 값 |
| 그 계정이 로그인된 Aside 프로필 (u0·u1…) | 대시보드 작업을 어느 프로필로 열지 |
| 옛 소유 계정이 로그인된 Aside 프로필 | 이전 버튼은 대개 옛 소유자가 누른다([§6](#6-실행-순서-고정)) |

### 2.1 Aside 프로필 라벨 받기

Aside는 **브라우저 프로필 하나 = 계정 묶음 하나**다. 회사면 회사 계정들이, 개인이면 개인 계정들이 그 프로필 안에 다 로그인돼 있고, `--account <프로필>`로 골라 연다. **어느 프로필이 어느 소유인지는 물어서만 알 수 있다.**

목록을 먼저 꺼낸다.

```bash
aside account list
```

프로필 아이디(`u0`·`u1`…), 그 프로필의 Aside 계정 이메일, 로그인 여부가 나온다.

```
* u0  someone@company.co.kr  signed in  profiles: Profile 0
  u1  someone@gmail.com      signed in  profiles: Profile 1
```

**이 목록을 그대로 사용자에게 보여주고 라벨을 받는다** — "u0가 회사, u1이 개인" 식으로. 다음 둘은 하지 않는다.

- **번호로 짐작하지 않는다.** `u0`가 회사라는 규칙은 없다. 같은 컴퓨터에서 순서가 뒤바뀐 사례가 있다.
- **이메일 도메인으로 단정하지 않는다.** 여기 보이는 건 **Aside 계정 이메일**이지 그 프로필 안에 로그인된 저장소·DB·호스팅 계정이 아니다. 회사 프로필에 개인 저장소 계정이 로그인돼 있을 수 있다.

**`signed out`인 프로필은 못 쓴다.** 사용자가 Aside 설정에서 로그인해야 하고(사람 몫), 그때까지 그 프로필이 맡을 단계는 멈춘다.

라벨을 받은 뒤에도 **판정은 늘 서비스 화면의 계정 표시로 한다**(`docs/account-check.md` Aside 항목) — [§3](#3-0단계-조사--이전-계획표) 조사가 그 확인을 겸한다.

## 3. 0단계 조사 — 이전 계획표

**읽기 전용 단계다.** 여기서는 아무것도 만들지 않고, 아무 이전·초대 버튼도 누르지 않는다. 훑어보고 계획표를 만드는 데까지다.

**조사 방법 둘**

- **CLI로 되는 건 CLI로** — 저장소·프로젝트·조직 조회 명령. 화면을 열 필요가 없고 결과가 값으로 남는다.
- **대시보드에서만 보이는 건 Aside로** — 양쪽 프로필에서 각 서비스를 열어 현재 소유·요금제·멤버·연결 상태를 읽는다. 호출은 `aside --account <프로필> "<지시>"`.

**계획표** — 서비스마다 한 줄씩 채운다.

| 서비스 | 현재 소유 | 목표 | 방법 (이전/재생성) | 도구 (CLI/Aside) | 사람 몫 | 부작용 |
|---|---|---|---|---|---|---|
| DB | | | | | | |
| 저장소 | | | | | | |
| 호스팅 | | | | | | |
| 소셜 로그인 앱 (제공사별로 한 줄) | | | | | | |
| AI 키 | | | | | | |

**부작용은 최소 이 셋을 서비스마다 점검한다.** 빈칸으로 두지 않는다 — "없음"이라고 적더라도 확인한 결과여야 한다.

1. **주소·식별자가 바뀌는가** — 저장소 주소, DB 프로젝트 참조 아이디(ref), 배포 도메인. 바뀌면 코드·환경변수·콜백 주소가 전부 따라 바뀌어야 한다.
2. **소셜 로그인 앱을 새로 만들면 기존 사용자의 로그인 식별이 갈라지는가** — 제공사가 주는 사용자 아이디가 앱 단위로 발급되면, 같은 사람이 새 앱에서는 **다른 사람으로 보인다.** 그러면 기존 계정에 다시 못 들어간다. 제공사별로 공식 문서에서 확인한다.
3. **유료 좌석·결제가 필요한가** — 새 팀·조직이 유료 요금제이거나 멤버 자리마다 돈이 붙는지. 임시로 넣는 멤버도 자리를 차지할 수 있다.

**사용자가 계획표를 승인해야 다음으로 간다.** 승인 없이 [§6](#6-실행-순서-고정)을 시작하지 않는다 — 되돌리기 비싼 갈림길이라서다. 승인받을 때 "이건 지금 안 옮기고 나중에"가 나오면 그 줄을 「추후 결정」으로 표시해 두고 [§7](#7-마무리--pr-하나로-검증하고-표-다시-쓰기)에서 남긴다.

## 4. 도구 분담 — CLI와 Aside

**Aside가 맡는 건 딱 넷이다.** 그 밖의 실행·검증은 **서비스별 CLI와 관리 API**(대시보드 대신 명령으로 설정을 읽고 쓰는 통로)로 한다.

| 하는 일 | 도구 |
|---|---|
| 저장소 이전 요청, 이전 결과 확인 | CLI |
| Actions Secrets 확인·재등록 | CLI |
| 팀 초대 (CLI가 지원하는 서비스) | CLI |
| Git 재연결 상태 확인, 배포 확인 | CLI |
| 환경변수 등록·교체 (Production·Preview 둘 다) | CLI |
| DB 인증 설정(사이트 주소·콜백 허용 목록·제공사 값) 읽기·쓰기 | 관리 API |
| ① 양쪽 프로필에서 각 서비스를 훑어 현재 상태 보고 (읽기 전용) | Aside |
| ② 대시보드에서만 되는 클릭 — 조직 초대·수락, 프로젝트 이전, 토큰·키 발급, 호스팅의 GitHub 앱 설치·저장소 연결 | Aside |
| ③ 발급된 비밀값을 화면에서 읽어 파일로 저장 | Aside |
| ④ 이메일로 오는 인증 코드를 메일함에서 읽어 넣기 | Aside |
| 비밀번호·일회용 코드(OTP)·패스키 입력 | 사람 |
| 카카오 계정·카카오 디벨로퍼스 콘솔 작업 전부 | 사람 ([§5](#5-정지금지-조건)) |
| 결제·좌석 구매, 화면 동작 판정 | 사람 |

**비밀값은 대화에 남기지 않는다.** 화면에서 읽은 토큰·키는 Aside repl 안에서 파일로 쓰게 하고, 그 파일을 읽어 제자리에 옮긴 뒤 지운다.

```js
// Aside repl 안에서 — 세션 폴더에 쓴다
await fs.writeFile(path.join(pwd, 'vercel-token.txt'), 값)
```

- **반드시 세션 폴더(`pwd`)에 쓴다. `/private/tmp`는 거부된다.**
- 쓴 다음 흐름은 셋이다 — **읽어서** 제자리(CLI 전용 깃 미추적 파일·환경변수·Secret)에 넣고, **확인하고**, **파일을 지운다.**
- 값을 못 읽었으면 살려 두지 않는다 — 그 자리에서 폐기하고 다시 만든다 (`docs/account-check.md` 원칙 ⑤).

## 5. 정지·금지 조건

**① 카카오 계정·카카오 디벨로퍼스 콘솔에는 Aside를 붙이지 않는다.** 브라우저 에이전트로 카카오에 접근했다가 새 계정이 「비정상적인 가입 시도」로 제재된 실사고가 있다. 그 자리는 **사용자가 직접** 하고, AI는 사용자가 건네준 키로 설정을 갈아 끼우는 **CLI 작업만** 맡는다. 조사([§3](#3-0단계-조사--이전-계획표))에서도 카카오 화면은 열지 않고 사용자에게 현재 상태를 물어 채운다.

**② 비밀번호·일회용 코드(OTP)·패스키는 사람 몫이다.** Aside가 로그인 화면이나 2단계 인증 화면에서 멈추면 거기서 사람에게 넘긴다. **이메일로 오는 인증 코드만** Aside가 메일함에서 읽어 넣는다.

**③ 토큰·키를 지우기 전에, 같은 계정의 다른 프로젝트가 그걸 쓰는지 먼저 확인하고 사용자에게 묻는다.** 발급 토큰은 소유 계정당 하나를 여러 프로젝트가 나눠 쓰는 게 기본이라(`docs/account-check.md` 원칙 ②), 이 프로젝트만 보고 지우면 남의 프로젝트가 멈춘다.

**④ 옛 토큰·키·앱은 검증이 끝날 때까지 폐기를 보류한다.** [§7](#7-마무리--pr-하나로-검증하고-표-다시-쓰기)의 PR 검증까지 통과한 뒤에 사용자에게 묻고 지운다. 되감기([§8](#8-되감기))가 가능한 이유가 이 보류다.

## 6. 실행 순서 (고정)

```
DB 조직 → 저장소 → 호스팅 팀 이전과 Git 재연결 → 소셜 로그인 앱 → AI 키
```

**이 순서는 바꾸지 않는다.**

- **DB가 맨 앞** — 소셜 로그인 콜백 주소에 DB 프로젝트 참조 아이디(ref)가 들어간다. DB가 확정돼야 로그인 앱을 건드릴 수 있다.
- **저장소가 호스팅보다 앞** — 저장소를 옮기면 호스팅의 Git 연결이 끊긴다([§10](#10-참고--실측-사실)). 호스팅을 먼저 손보면 두 번 잇게 된다.
- **AI 키가 맨 뒤** — 어디에도 안 묶여서 언제 해도 되지만, 호스팅 이전이 끝난 뒤에 해야 환경변수를 한 번에 갈아 끼운다.

**단계마다 네 묶음을 그대로 탄다.**

1. **전제 확인** — 이 단계가 기대는 앞 단계 결과와 권한이 실제로 있는지 명령으로 확인한다. 말만 믿지 않는다.
2. **실행** — [§4](#4-도구-분담--cli와-aside) 분담대로.
3. **검증** — 관리 API·CLI로 **읽어서** 확인한다. 화면에서 "됐다"로 보이는 것은 검증이 아니다.
4. **정리** — 임시로 넣은 멤버를 빼고, 옛 연결(협력자 권한·앱 설치·연동)을 걷는다. 단 토큰·키 폐기는 [§5 ④](#5-정지금지-조건)대로 미룬다.

**공통 패턴 — 옛 소유자를 새 조직에 잠시 넣었다 뺀다.**

이전 버튼은 대개 **옛 소유자의 권한**이고, 동시에 **받는 쪽 조직에 대한 권한**도 요구한다. 그래서 이렇게 한다.

1. 새 조직(팀)에 **옛 소유자를 멤버로 초대**한다.
2. 옛 소유자가 초대를 **수락**한다 (이메일 링크면 Aside ④).
3. **옛 소유자가 이전을 실행**한다.
4. 이전이 검증되면 **옛 소유자를 새 조직에서 뺀다.**

임시 멤버도 유료 자리를 차지할 수 있으니([§3](#3-0단계-조사--이전-계획표) 부작용 3), 4번을 잊지 않는다.

**계정 검문은 매 단계 앞에서 다시 한다** — 쓰기 작업 직전에 같은 걸음에서 활성 계정을 확인한다 (`docs/account-check.md` 원칙 ①). 특히 gh는 활성 계정이 저절로 바뀌는 일이 있다([§10](#10-참고--실측-사실)).

### 6.1 DB 조직 이전

- **전제 확인** — 목표 조직이 새 소유 계정에 있나(없으면 사람이 만든다). 옛 소유자가 그 조직 멤버인가. 현재 프로젝트가 어느 조직 것인지 CLI 조직·프로젝트 조회로 확인.
- **실행** — 위 공통 패턴 그대로. **조직 초대 API는 최상위 요금제 전용이라 대시보드에서만 된다**([§10](#10-참고--실측-사실)) → 초대·수락·프로젝트 이전 셋 다 Aside ②로 한다.
- **검증** — CLI로 프로젝트가 새 조직 아래 있는지 읽는다. **참조 아이디(ref)·키·인증 설정이 그대로인지** 관리 API로 읽어 확인한다([§10](#10-참고--실측-사실)에 따르면 그대로여야 한다 — 다르면 멈추고 보고한다). ref가 그대로면 콜백 주소도 그대로라 [6.4](#64-소셜-로그인oauth-앱)가 훨씬 가벼워진다.
- **정리** — 임시 멤버 제거. 새 계정으로 접근 토큰을 발급(Aside ②③)해 CLI 전용 깃 미추적 파일의 값을 교체하고, 깃허브 Secret에 들어간 토큰도 함께 교체한다. **옛 토큰은 아직 지우지 않는다**([§5 ④](#5-정지금지-조건)).

### 6.2 저장소 이전

- **전제 확인** — gh 활성 계정이 **옛 소유자**인지 확인한다(이전을 요청하는 쪽이다). 새 소유 계정·조직에 저장소를 만들 권한이 있는지. 작업 트리가 깨끗한지.
- **실행** — 이전을 요청한다.

  ```bash
  gh api -X POST /repos/{owner}/{repo}/transfer -f new_owner=<새 소유>
  ```

  **받는 쪽이 이메일 링크로 수락해야 끝난다** — 새 소유 계정의 메일함에서 링크를 여는 건 Aside ④(그 계정이 로그인된 프로필)로 한다. 조직으로 옮기는 경우 권한에 따라 수락 없이 바로 처리될 수 있다 — 공식 문서로 확인하고, 안 되면 수락 경로로 간다.
- **검증** — `gh repo view <새owner>/<repo>`로 새 소유 확인. **Actions Secrets는 따라온다**([§10](#10-참고--실측-사실)) — `gh secret list`로 실제로 있는지 읽어 확인하고, 없으면 다시 넣는다. 로컬 원격 주소를 `git remote set-url`로 새 주소에 맞춘다. git 자격 증명 도우미 경로가 옛 위치를 가리키면 `gh auth setup-git`으로 잡는다.
- **정리** — 옛 소유 계정에 남은 협력자 권한·배포 키를 걷는다.

### 6.3 호스팅 팀 이전과 Git 재연결

- **전제 확인** — [6.2](#62-저장소-이전)가 검증까지 끝났나(끝나야 Git 재연결이 의미가 있다). 목표 팀이 있고 요금제·좌석이 [§3](#3-0단계-조사--이전-계획표) 부작용 점검대로인가.
- **실행**
  1. 호스팅 프로젝트를 새 팀으로 이전한다 (대시보드 — Aside ②, 공통 패턴대로).
  2. **새 계정에 호스팅의 GitHub 앱을 설치하고 저장소를 다시 연결한다** (Aside ②). 저장소를 옮기면 이 연결이 끊긴다([§10](#10-참고--실측-사실)). 연결을 누르기 전에 **브라우저의 GitHub 로그인 계정도 목표 계정인지 대조한다** — 연결에는 상대 서비스의 지금 세션이 붙어서, 안 맞추면 다른 계정이 조용히 붙는다 (`docs/account-check.md` 원칙 ④).
  3. 새 팀 스코프(scope — 토큰이 닿는 범위) 토큰을 발급해(Aside ②③) CLI 전용 파일의 값을 교체하고, `vercel link`로 프로젝트를 다시 연결한다. [§10](#10-참고--실측-사실)의 실측 둘을 미리 읽어 둔다 — 정상인데 오류로 보이는 경우가 있다.
  4. 환경변수를 새 프로젝트에 **Production·Preview 둘 다** 등록한다(CLI). 이름은 `.env.example`이 정본이다.
- **검증** — CLI 프로젝트 조회로 새 팀 소속 확인, `.vercel/project.json`의 팀 아이디(orgId) 확인. **커밋 작성자의 Git 계정이 새 소유의 호스팅 계정에 연결돼 있는지** 확인한다 — 연결이 없으면 배포가 조용히 막힌다 (`docs/account-check.md` 원칙 ③). Git 연결이 실제로 사는지는 [§7](#7-마무리--pr-하나로-검증하고-표-다시-쓰기)의 PR에서 최종 확인한다.
- **정리** — 옛 팀에서 프로젝트·GitHub 앱 설치·연동을 걷는다. 옛 토큰은 보류.

### 6.4 소셜 로그인(OAuth) 앱

**[6.1](#61-db-조직-이전) 검증에서 DB 참조 아이디(ref)가 그대로였으면 콜백 주소도 그대로다** — 그러면 앱을 다시 만들 이유는 소유뿐이다. 제공사마다 **「이전되나 / 다시 만들어야 하나」가 [§3](#3-0단계-조사--이전-계획표) 계획표에 이미 적혀 있어야 한다.** 여기서 즉흥으로 정하지 않는다.

- **이전되는 제공사** (GitHub OAuth 앱 등) — 이전하면 client id·secret이 유지돼 설정을 바꿀 일이 없다. 공통 패턴대로 옮기고, 이전 뒤 값이 그대로인지 확인한다.
- **다시 만들어야 하는 제공사** — [§3](#3-0단계-조사--이전-계획표) 부작용 2(사용자 식별이 갈라지는가) 점검 결과를 사용자와 다시 확인한 뒤에만 만든다. 새 앱 값은 `6-0-backend-prep.md` §4.1 자격 증명 배선표대로 **들어가는 자리를 전부** 교체한다 — 한 곳만 바꾸면 나머지가 옛 값으로 남아 특정 기능만 조용히 실패한다.
- **카카오는 AI가 콘솔에 손대지 않는다**([§5 ①](#5-정지금지-조건)). 사용자가 콘솔에서 앱을 옮기거나 새로 만들고 키를 건네면, AI는 그 값을 배선표대로 넣는 CLI 작업만 한다.
- **secret은 항상 제공사 콘솔의 원본에서 온 값을 쓴다** — DB에서 꺼낸 제공사 secret을 다른 곳에 넣지 않는다 (`6-0-backend-prep.md` §4.1 실측).
- **검증** — 관리 API로 DB의 인증 설정(제공사 값·사이트 주소·콜백 허용 목록)에 새 값이 들어갔는지 **읽어서** 확인한다. 값이 맞는지는 그 client id·secret으로 제공사 API를 한 번 호출해 확인한다. **실제 로그인 왕복 판정은 사람 몫이다** — AI가 브라우저로 눌러 보고 "동작 확인 완료"라고 결론 내지 않는다(저장소 검증 규칙).
- **정리** — 옛 앱은 지우지 않고 남겨 둔다([§5 ④](#5-정지금지-조건)). 되감기의 안전망이다.

### 6.5 AI 키

- **전제 확인** — 새 계정에 결제 수단과 월 지출 상한이 걸려 있나(사람 몫). 옛 키가 이 프로젝트 말고 다른 데서도 쓰이는지([§5 ③](#5-정지금지-조건)).
- **실행** — 새 계정에서 키를 발급한다(Aside ②③). **Anthropic API 키는 워크스페이스(workspace — 계정 안에서 프로젝트별로 사용량·권한을 가르는 구획) 범위로 발급해야 헤더 없이 쓸 수 있다**([§10](#10-참고--실측-사실)).
- **교체** — `.env.local`과 호스팅 환경변수(Production·Preview 둘 다)를 새 키로 바꾼다.
- **검증** — 그 키로 제공사 API를 한 번 호출해 실제로 통하는지 본다.
- **정리** — 옛 키는 [§7](#7-마무리--pr-하나로-검증하고-표-다시-쓰기) 검증 뒤 사용자에게 묻고 폐기한다.

## 7. 마무리 — PR 하나로 검증하고 표 다시 쓰기

**PR 하나로 셋을 한꺼번에 검증한다.** 따로따로 확인할 것을 한 번에 태우는 자리다.

1. **CI가 새 Secret으로 통과하나** — 이전으로 바뀐 토큰이 깃허브 Secret에 제대로 들어갔는지가 여기서 드러난다.
2. **프리뷰 배포가 새 작성자 계정으로 뜨나** — 커밋 작성자의 Git 계정 연결([6.3](#63-호스팅-팀-이전과-git-재연결) 검증)이 살아 있는지가 여기서 드러난다.
3. **머지 뒤 실서비스 배포가 새 팀에서 도나** — Git 재연결이 실제로 붙었는지가 여기서 드러난다.

**스모크 검사는 시드 순수 상태를 가정한다**([§10](#10-참고--실측-사실)) — 로컬 QA 데이터가 남아 있으면 순위·집계 검사가 어긋날 수 있다. **리셋할지 스킵할지는 사람이 정한다.** AI가 임의로 데이터를 지우지 않는다.

**화면 판정은 사람 몫이다** — 프리뷰·실서비스 주소를 건네고, 사용자가 직접 들어가 로그인·주요 흐름을 확인한다. 확인했다는 말을 들은 뒤에 `/done-task`를 부른다.

**계정 표를 새 소유 기준으로 전면 다시 쓴다.**

- 프로젝트 `AGENTS.md`의 「소유와 계정」 표를 **새 소유 기준으로 통째로 다시 쓴다.** 서비스별 계정·이메일, 커밋 작성자(git), 토큰이 들어간 자리까지.
- **「옛 상태는 이랬다」를 표에 남기지 않는다** — 산출물은 매 판이 완결이다. 옛 값은 git 이력에 남는다.
- 로컬 git 작성자 설정도 표와 맞춘다(전역 설정은 건드리지 않는다).
- [§3](#3-0단계-조사--이전-계획표)에서 「추후 결정」으로 표시한 줄은 `추후 결정:`으로 남긴다 — 지우지 않는다.

**계정 명부 갱신 문안을 사용자에게 건넨다.** 하네스에는 계정을 안 적으므로([§2](#2-입력--무엇을-근거로-판단하나)), **사용자가 자기 보관처(비밀번호 관리자·개인 메모)에 그대로 붙여 넣을 수 있는 완성된 문단**으로 준다. 담을 것 — Aside 프로필과 계정의 새 대응, 서비스별 계정·이메일, 토큰이 들어간 자리, 재발급 기한이 있으면 그 날짜. 값 자체(토큰·키 문자열)는 문안에 넣지 않는다.

**마지막으로 옛 토큰·키·앱 폐기 여부를 묻는다** ([§5 ③④](#5-정지금지-조건)). 사용자가 "지워도 된다"고 답한 것만 지운다.

## 8. 되감기

**되감기도 [§6](#6-실행-순서-고정)의 네 묶음(전제 확인 → 실행 → 검증 → 정리)을 그대로 탄다.** 되돌리는 중에도 검증을 건너뛰지 않는다.

| 단계 | 되돌리는 법 | 주의 |
|---|---|---|
| [6.1](#61-db-조직-이전) DB | 같은 절차로 **반대 방향** 프로젝트 이전 | 참조 아이디(ref)가 유지되니 코드·콜백은 안 건드린다 |
| [6.2](#62-저장소-이전) 저장소 | `gh api -X POST /repos/{새owner}/{repo}/transfer -f new_owner=<옛 소유>` | 옛 소유 쪽에 같은 이름 저장소가 이미 있으면 실패한다 — 먼저 확인 |
| [6.3](#63-호스팅-팀-이전과-git-재연결) 호스팅 | 반대 방향 프로젝트 이전 + GitHub 앱 재설치·저장소 재연결 | **환경변수는 자동으로 안 따라온다** — 옛 팀에 다시 등록 |
| [6.4](#64-소셜-로그인oauth-앱) 로그인 앱 | 새로 만든 앱이면 옛 앱 값을 배선표대로 되돌린다 | **옛 앱을 안 지웠을 때만 된다** — [§5 ④](#5-정지금지-조건)의 보류가 이걸 위한 것 |
| [6.5](#65-ai-키) AI 키 | 옛 키를 환경변수·`.env.local`에 다시 넣는다 | 폐기 전이어야 한다 |

**코드·문서 쪽 변경**(환경변수 이름, 계정 표, 콜백 주소 등 저장소 안 파일)은 `/rewind-task`로 되감는다 — 이 표는 **밖에 있는 것**을 되돌리는 법이다.

**옮기다 중간에 멈췄으면 되감기보다 마저 끝내는 쪽이 대개 안전하다.** 절반만 옮긴 상태가 가장 잘 깨진다([§1](#1-무슨-스킬인가--범위와-경계)). 되감기는 계획 자체가 틀렸을 때(부작용을 뒤늦게 발견했을 때) 고르는 길이고, 어느 쪽으로 갈지는 사용자에게 묻는다.

## 9. 안 하는 것 (의도적)

## 10. 참고 — 실측 사실

아래는 실제로 해보고 확인한 값이다. 규칙이 아니라 사실이라 서비스가 바뀌면 낡는다 — 어긋나면 공식 문서를 따르고 이 절을 고쳐야 한다고 보고한다.

- **Anthropic API 키는 워크스페이스 범위로 발급해야** 별도 헤더 없이 그대로 쓸 수 있다.
- **Vercel 팀 스코프 토큰은 `vercel whoami`가 `Not authorized`로 나와도 정상이다** — 팀 범위 토큰이라 개인 조회에 권한이 없을 뿐이다. 이걸 실패로 보고 토큰을 다시 만들지 않는다.
- **`vercel link`는 `.env.local`에 `VERCEL_OIDC_TOKEN` 한 줄을 쓴다.** 다른 값은 안 건드린다.
- **Supabase 조직 초대 API는 최상위(Enterprise) 요금제 전용**이라 그 아래 요금제에서는 대시보드에서만 초대할 수 있다.
- **Supabase 프로젝트 이전은 참조 아이디(ref)·키·인증 설정을 그대로 유지한다.** 그래서 콜백 주소가 안 바뀐다.
- **GitHub 저장소 이전은 `gh api -X POST /repos/{owner}/{repo}/transfer`로 요청하고, 받는 쪽이 이메일 링크로 수락해야 완료된다.**
- **GitHub 저장소를 옮겨도 Actions Secrets는 따라온다.**
- **저장소를 옮기면 호스팅의 Git 연결이 끊긴다** — 새 계정에 호스팅 GitHub 앱을 설치하고 저장소를 다시 연결해야 한다.
- **gh CLI에 계정이 둘이면 활성 계정이 저절로 바뀌는 일이 있다** — 작업 전에 확인한다. git 자격 증명 도우미 경로가 옛 위치를 가리키면 `gh auth setup-git`으로 잡는다.
- **스모크 검사는 시드 순수 상태를 가정한다** — 로컬 QA 데이터가 남아 있으면 순위·집계 검사가 어긋날 수 있다. 리셋할지 스킵할지는 사람이 정한다.
