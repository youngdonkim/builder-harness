## 1. 작동 방식 — 단계 진입과 공통 규칙

### 1.1 스킬 범위 — 아이디어에서 MVP까지, 프로젝트당 1회

이 스킬은 아이디어 하나를 MVP 검증까지 끌고 가는 7단계 과정이다. **한 프로젝트(저장소)는 아이디어 하나만 다룬다** — 피봇(같은 문제 영역 안에서 방향을 다듬는 것)은 같은 프로젝트에서 이어간다. 전혀 다른 아이디어로 갈아타는 경우에는 이 프로젝트를 종료하고, 새 프로젝트(폴더를 새로 생성)를 만들어 처음부터 진행하라고 사용자에게 안내한다. 이 구분과 산출물 위치·관리 규칙은 §3.

**AI 빌더 시대라 화면부터 만들고 거른다.** 예전엔 화면 설계가 비싼 작업이라 사람 손으로 그리기 전에 빈손 인터뷰로 먼저 걸렀다. 지금은 Claude Design 같은 AI 도구로 실제 화면처럼 보이는 목업(mockup — 겉모습만 흉내 낸 화면 견본) 하나 만드는 비용이 거의 0에 가깝고, 그걸 진짜로 눌러지는 앱으로 옮기는 비용도 예전 같지 않다. 그래서 이 스킬은 **먼저 돌아가는 화면을 만들어 손에 쥐여주고, 사람들의 반응(행동)으로 거른다** — "이거 어때요?"라는 말보다, 눈앞에서 실제로 도는 화면을 봤을 때 나오는 데모 반응이 훨씬 강한 신호다.

어떤 아이디어가 막 생겨난 시점이 이 스킬의 가장 초기 단계다. 거기서 7단계(UserStory · InformationArchitecture · Prototype · **DemoValidation** · MarketResearch · MvpBuild · **MvpLaunch**)를 거치며 통과 기준 2개로 거른다:

- **통과 기준① 데모 검증 (DemoValidation)**: 3단계가 배포한 **리액트 프로토타입 링크**(목업을 실개발환경으로 옮겨 로컬스토리지로 실제 도는 앱)를 들고 데모 인터뷰를 한다 — 맘 테스트(Mom Test, 사회적으로 좋게 들리는 말이 아니라 과거 행동만 캐묻는 인터뷰 원칙) 질문은 데모를 보여주기 *전에* 먼저 하고, 이어서 프로토타입을 직접 만져보게 한 뒤 반응·Pull 신호(사람들이 자발적으로 "써보고 싶다"고 하는 신호)·UI 피드백을 수집해 painkiller(진통제 — 사람들이 지금 당장 풀고 싶어하는 문제) 신호를 확인한다. 데모 반응에서 구조적 수정사항이 나오면 3단계로 돌아가 **프로토타입 코드를 직접 고치고** 다시 데모하는 **3↔4 순환**을 돈다(목업 재생성이 아니다 — Claude Design은 첫 목업 한 번만 부른다). 프런트엔드가 거의 완성 수준으로 수렴하면 그 시점에 go/no-go 판정 — go 시점엔 최종 확정 아이디어와 함께 **비목표·검증 가설**도 이때 확정한다(구 MarketResearch의 "최종 서비스 기획 요약" 역할을 흡수). 판정 절차는 `references/4-demo-validation.md` §2.9·§2.10.
- **통과 기준② 최종 실측 (MvpLaunch, 구 통과 기준③)**: **광고 집행 전에 동결한 퍼널 기준** vs **실제 사용자 행동**의 실측으로 가설 검증 판정. 중요한 데이터는 사용자가 우리가 의도한 행동(가입·사용·결제)을 실제로 했는지이고, 의도하지 않았지만 의미 있는 다른 행동도 함께 본다. 이 스킬이 진짜로 끝나는 지점. 판정 절차는 `references/7-mvp-launch.md` §2.3.

**MarketResearch(5단계)는 게이트가 아니라 참고 자료다.** 데모로 방향이 굳은 뒤(4단계 go 판정 이후), **검증된 최종 아이디어를 들고** 경쟁 지형과 차별화 축(axis — 우리가 남들과 다르게 잡는 기준)을 조사한다. 조사를 검증 뒤로 미룬 이유는 간단하다 — **검증 전에 조사하면 데모에서 아이디어가 뒤집힐 때 조사가 통째로 버려진다.** 라이트 정찰이 기본이며 필요하면(요금제·한도가 되면) `/deep-research`로 더 깊게 판다. "경쟁이 너무 치열하다" 또는 "시장이 없다·작다"는 판단으로 아이디어를 접을지는 **스킬이 판정하지 않고 유저가 자율로 판단**한다 — 이 단계는 판단에 쓸 정보만 준비해서 보여준다. AI 빌더 시대엔 앞 단계(프로토타입·데모)가 이미 싸서, 판정 관문은 최소로 두고 유저 자율을 넓히는 쪽이 맞다.

(구 통과 기준③ ProtoRetro는 폐지했다 — AI 빌더 시대엔 실물 첫 노출이 이미 4단계(DemoValidation)로 당겨져 여기서 다시 검증하면 중복이고, MvpBuild(6단계)가 이미 도는 프로토타입 코드에 백엔드를 얹는 얇은 작업이라 그 앞에 무거운 게이트를 둘 명분도 사라졌다. "기준은 다음 단계가 비쌀 때만 둔다"는 원칙에 따라 역할을 나눠 이관했다: 치명 결함 거르기는 6단계(MvpBuild) 안 **백엔드·DB·로그인 연동 뒤 베타 공유** 스텝(실데이터가 붙은 배포 링크를 4단계 인터뷰이에게 보내 실사용 반응 확인 — 판정 아닌 확인, `references/6-mvp-build.md` §2.3)으로, 빌드 범위는 `mvp-build.md`로, 런치 기준 후보는 7단계 launch-plan 작성 시 `demo-validation.md`의 Pull 데이터에서 도출하는 걸로. 베타 공유를 백엔드 연동 *뒤*에 두는 이유는, 4단계 데모에서 이미 프런트엔드는 실컷 봤으니 여기서 새로 확인할 값어치가 있는 건 "진짜 데이터가 붙어도 멀쩡히 도는가"뿐이기 때문이다.)

왜 최종 판정이 인터뷰가 아니라 실제 사용자 행동인가 — 인터뷰는 *말*이라, 사람들이 앞에서는 좋게 말해주기 마련이라 실제보다 부풀려진다(맘 테스트가 지적하는 문제). 반면 광고 클릭→가입→사용→결제는 *행동*이라 거짓말을 못 한다. 이건 4단계의 "말보다 데모 반응"이라는 철학과 같은 결이다 — 다만 무게가 다르다. 4단계 Pull 신호는 "데모 본 뒤 관심을 표현"하는 가벼운 행동 신호고, 통과 기준②는 광고 클릭→가입→사용→결제라는 무거운 행동 신호다. 통과 기준①은 가볍게, 통과 기준②가 무겁게.

**6·7단계(MvpBuild·MvpLaunch)는 의도적으로 얇다** — PRD·Architecture 같은 무거운 문서 단계를 두지 않는다. **3단계가 만든 리액트 프로토타입 코드 자체가 화면 스펙**이라서다. 화면·플로우·상태가 이미 도는 코드로 적혀 있으니 그걸 문서로 다시 옮길 이유가 없고, MvpBuild(6단계)는 그 코드에 백엔드·DB·로그인·계측을 얹어 배포까지 완주하면 된다. LLM 시대에 이 수준 빌드는 싸다. 문서는 빌더 자신을 위한 최소(계측 정의·런치 기준·판정 기록)만.

**Production은 이 스킬의 범위 밖** — 통과 기준②에서 가설이 검증되면 production(매출 스케일업·운영 자동화·다채널 확장)으로 졸업한다. 그건 분기별 KPI·실험 추적·운영 도구의 영역이라 이 하네스가 다루지 않는다. (다만 다채널 확장은 **절차로 다루지 않을 뿐 방향은 정해져 있다** — 웹은 이 스택 그대로 두고 그 코드를 옮겨 앱을 만들고, 기본은 React Native다. 절차가 아니라 방향 기록이라 `references/3-prototype.md` §2.4에 적어뒀다.)

### 1.2 현재 단계 판별

- `mvp/`와 프로젝트 루트에서 §2.1 표 산출물의 존재·완성도를 단계 순으로 검사.
- 비거나 미완성인 가장 빠른 단계 = 진행 대상.
- 사용자가 특정 단계를 콕 집어 지시하면 그 단계로 점프 (평가는 "사용자 명시 점프" 사유로 통과).
- **판별 순서**: `user-story.md`(1) → `information-architecture.md`(2) → `mvp/handoff/` + 프로젝트 루트 앱 코드(3, Prototype) → `demo-validation.md`(4) → `market-research.md`(5) → `mvp-build.md`(6) → `launch-plan.md`/`launch-retro.md`(7).
- **Prototype(3단계) 산출물은 `mvp/handoff/` + 루트 앱 코드로 판별**: 3단계는 md 산출물이 없다 — Claude Design에서 받은 꾸러미를 푼 **`mvp/handoff/`**(목업 standalone.html 포함)와, 그걸 옮겨 만든 **프로젝트 루트의 앱 코드**(`package.json`·`src/` 등) **둘 다** 있어야 3단계 완료로 본다 (`references/3-prototype.md`). handoff만 있고 앱 코드가 없으면 마이그레이션 전이라 3단계 진행 중이다.
- **앱 코드는 6단계 구분자가 못 된다**: 앱 코드는 3단계부터 루트에 존재하므로, "루트에 코드가 있으니 6단계까지 끝났다"고 읽으면 안 된다. **6단계 완료 판별은 `mvp/mvp-build.md` 존재 하나로** 한다 — 6단계는 새 코드를 새 자리에 만드는 게 아니라 3단계가 만든 같은 코드에 백엔드·계측을 얹는 단계라, 코드의 유무가 아니라 이 문서의 유무가 경계다.
- **3↔4 순환 중인지는 `demo-validation.md`로 판단**: 3단계 산출물이 갖춰졌다고 곧장 다음 단계로 넘어가는 게 아니다 — `mvp/demo-validation.md`가 없거나 §3 체크리스트를 통과하지 못했으면(=구조적 수정사항이 남아 3단계 복귀가 예정된 상태) 여전히 3·4단계 사이 순환 구간으로 본다. 순환 중엔 "지금 화면 반응이 어땠는지 정리하고, 필요하면 화면 코드부터 고치자"로 이어간다. `demo-validation.md`가 수렴·확정됐으면 5단계(MarketResearch)로 진행.

### 1.3 단계별 안내 문서(references) 읽기 + 응대 톤

- `references/{N}-{name}.md`를 읽고 그 가이드대로 진행. 모든 references는 같은 골격을 가진다: §1 단계 목표 / §2 진행 절차 — 도입부 또는 §2.1의 '단계 시작'에서 이전 정리 보여주기·이번 할 일 안내 (`이전 결론 → 이번 결론` 섹션을 산출물 머리에 박는 건 6단계부터 — §2.2) / §3 완료 체크리스트(+§3.1 다음 단계 핸드오프 — 마지막 7단계엔 없음) / §4 산출물 스펙(+템플릿) / §5 좋은·나쁜 예(있는 문서만) / 마지막 섹션은 사용자 응대 톤. 7단계만 §2가 '3막' 구조라 §2.1~§2.3이 막1~막3이다.
- **응대 톤**: 전 단계 공통 — `CLAUDE.md` 대화 스타일 따름. (references가 §1.3으로 이 줄을 참조.)
- **단계명은 내부 코드명** — 유저에게 `DemoValidation`·`MvpBuild` 같은 코드명을 던지지 않는다. 그 단계 references의 `§1 단계 목표`와 **직전까지 쌓인 산출물 내용**을 바탕으로, 이번 단계에서 뭘 할지를 한국어로 구체적으로 안내한다 (기능·설계처럼 추상적인 단계는 *누가 어떻게 쓰는지*도 곁들임). 고정 문구를 쓰지 않는다 — 매번 그 프로젝트의 실제 맥락에 맞춰 표현한다.
- **UserStory·DemoValidation·Prototype 앞부분 외에는 AI가 먼저 제안** — 안내에 이어 "내가 이전 내용 바탕으로 먼저 정리해볼게, 피드백 주면 수정하고 다시 보여주는 식으로 같이 하자"라고 진행 방식을 밝힌다. **말로 예고만 하지 말고 같은 턴에 실제 초안까지 낸다.** 초안 모드 작업(§1.5)이면 초안을 끝까지 완주해서 낸다. 이후 피드백 → 수정 → 재확인. 예외는 이렇게 갈린다:
  - **DemoValidation(4단계)** — 인터뷰 자체가 소재라 통째로 인터뷰 모드 예외 (§1.5).
  - **Prototype(3단계)은 반반이다** — 앞부분(Claude Design 호출 준비·안내)은 AI가 대신 실행할 수 없는 외부 도구라 **사용자 몫**이고, AI는 첨부할 입력과 권장 프롬프트를 준비해 주는 데까지만 한다. 하지만 꾸러미를 받은 뒤(개발환경 구성 → 리액트 마이그레이션 → 배포)는 **AI가 초안 모드로 끝까지 완주**한다. 이 이중 성격을 안내 때도 그대로 말해준다 — "이 부분은 네가 Claude Design에서 받아와 줘, 받고 나면 나머지는 내가 돌아가는 앱까지 만들어서 링크로 보여줄게".
  - **InformationArchitecture(2단계)·MarketResearch(5단계)**는 화면 인벤토리·조사 정리가 산출물인 초안 모드라 예외가 아니다 — AI가 먼저 정리해 보여주는 게 기본.
  - 예 (MvpBuild 진입): ❌ "MvpBuild 할 차례" / ✅ "데모 반응 좋았으니 이제 진짜 서비스로 만들 차례야 — 지금 앱은 데이터가 브라우저에만 저장되잖아, 그걸 진짜 DB랑 로그인으로 바꾸고 사람들이 어디서 이탈하는지 볼 수 있게 계측 붙여서 다시 배포할게. 붙고 나면 인터뷰했던 분들한테 링크 보내서 크게 깨지는 데 없는지 확인하자."
- **옛 단계 내용은 §2.2 검토 절차를 거친 후 사용** — 어떤 옛 내용을 가져올지는 §2.2의 확인 질문 4개와 표시로 결정한다.

### 1.4 인터뷰 코칭 원칙

각 references의 인터뷰는 **사용자가 처음부터 좋은 답을 만들지 못한다**는 가정으로 작동한다. 기능 명세·가설 같은 산출물은 사람이 처음 써보면 누락·추상·일반론이 섞이는 게 정상이다. AI가 가공·되물음으로 좋은 예 형식까지 끌고 간다.

- **빠진 부분은 배치로 짚어 되묻기.** references의 "좋은 예" 패턴(구체성·검증 가능성·필수 항목 충족)에 사용자 답이 못 미치면 그대로 두지 말고 모자란 항목 체크. **되물음은 주제 단위로 묶어 한 턴에 2~4개** — 하나 묻고 답 받고 또 하나 묻는 직렬 왕복을 피한다. 확인이 잦아지면 사용자가 습관적으로 "응"만 하게 되어 거르는 기능을 잃는다.
- **"잘 모르겠어"는 정상 답.** 사용자가 답을 못하면 AI가 후보 2~3개 제시 → 사용자가 골라서 다듬는 형태로. 빈 칸 채우라고 압박하지 말기.
- **AI가 좋은 예 형식으로 정리해 보여주고 확인 받기.** "이거 맞아? 고칠 데 있어?" — 사용자가 처음부터 형식 갖춰 답할 필요 없음.
- **본질 보존 + 형식만 가공.** 사용자가 답한 의미는 절대 변경 금지. 임의 정보 추가도 금지 — 모르는 부분은 산출물에 `추후 결정: [무엇을 다시 확인할지]`로 명시 후 다음 단계 진입 시 사용자에게 재확인.
- **진행 중 이전 결정 변경 처리.** 단계 진행 중 이전 산출물의 결정이 바뀌어야 함을 감지하면(예: Prototype 만들다 플랫폼이 web → mobile로), AI가 자연어로 영향 범위 짚고 사용자 의향 확인. **영향 작으면**(문서 머리말 한 줄 또는 화면 일부) 자연스럽게 부분 업데이트해 진행. **영향 크면**(여러 단계 산출물 영향) 두 옵션 제시: (a) 영향 부분만 손봐서 이어가기, (b) 처음부터 다시 시작하되 직전 산출물을 base로 보존. 전체 단계 재방문 강제 금지. **반영 위치**: 바뀐 방향은 옛 단계 문서를 고치지 않고 현재(또는 되돌아간) 단계 산출물의 `이전 결론 → 이번 결론` 섹션에 새로 적는다 — 규칙은 §2.2.

### 1.5 작업 모드 — 인터뷰 모드 vs 초안 모드

각 단계의 작업은 두 모드로 나뉜다. 어느 모드인지 의식하고 진행 방식을 바꾼다.

**인터뷰 모드** — 사용자의 암묵지(문제 인식·타겟 지식·취향·전략)가 소재인 작업. DemoValidation 데모 인터뷰(맘 테스트+데모 반응), 플로우 골격 질문, 차별화 결정, 런치 go 선 수치 결정, 통과 기준 go/no-go 판정.
→ 사람과 상호작용이 목적 그 자체다. 배치 질문(§1.4)으로 왕복 횟수만 줄이고, 상호작용 자체를 줄이지 않는다.

**초안 모드** — AI가 산출물을 생산하는 작업. 화면 인벤토리 작성·목업 입력 프롬프트 준비·**개발환경 구성과 리액트 마이그레이션**(3단계 뒷부분)·조사 정리·인터뷰 노트 종합·MVP 빌드·광고 소재·판정 자료 준비.
→ 중간에 잘게 확인받지 않고 **초안을 끝까지 완주한 뒤 완성본으로 한 번에 리뷰**받는다. 이유: 중간 승인은 횟수가 쌓이면 습관 승인이 되어 거르는 기능을 잃고, 사용자 시간만 쪼갠다. 리뷰는 완성본이 구체적이라 피드백 품질도 높다.

**초안 모드의 안전판 4개** — 1~3번은 완주가 폭주로 넘어가지 않게 잡는 장치고, 4번은 완주가 도중에 끊겼을 때 되살리는 장치다:

1. **에스컬레이션 기준** — 다음 셋 중 하나면 완주를 멈추고 물어본다:
   - (a) 이전 단계 산출물과 모순 발견 (예: 목업이 비목표와 충돌)
   - (b) 사용자 암묵지 없이는 방향이 갈리는 결정 (타겟·톤·전략 판단)
   - (c) 결과를 되돌리기 비싼 갈림길 (DB 스키마·구조 전체가 갈리는 선택) — 참고: 스택은 고정이라 3단계 개발환경 구성에서 갈림길 아님(`3-prototype.md` §2.4)

   그 외의 애매함은 합리적 가정을 박고 `추후 결정: [무엇]`으로 마킹 후 계속.
2. **정지 조건** — 같은 산출물의 자율 재작업은 최대 2회. 그 안에 수렴 안 되면 중간 상태 그대로 들고 사용자에게 (오류 복리 방지).
3. **사람 몫 불변** — 통과 기준 판정(go/no-go·피봇), 실사용자 인터뷰, 화면·데모·배포물 클릭 검증은 초안 모드 대상이 아니다. AI는 그 판단의 *자료*까지만 준비한다.
4. **체크포인트** — **다시 만드는 데 비용이 큰 중간 결과**는 본작업에 들어가기 전에 먼저 파일로 저장한다. 초안 모드는 중간 확인 없이 끝까지 달리는 방식이라, 도중에 끊기면(서버 일시 오류 등) 디스크에 아무것도 없어서 재시도가 처음부터가 된다. 해당하는 건 그런 무거운 중간 결과뿐이다 — 인터뷰 노트 종합처럼 가벼운 작업까지 파일로 남기라는 뜻이 아니다. 대표 예가 3단계 `standalone.html` 디코드 결과(`3-prototype.md` §2.5)다. **이 안전판을 3단계 문서가 아니라 여기 두는 이유**는 같은 사고가 6단계 MvpBuild에서도 그대로 나기 때문이다 — 무거운 중간 결과가 생기는 단계라면 어디서나 적용한다.

## 2. 7단계 구성

7단계와 각 단계의 산출물·진실의 원천·안내 문서는 아래 §2.1 표 하나로 본다.

### 2.1 단계 릴레이 표 — 각 단계가 확정하는 것과 진실의 원천(SoT)

7단계는 릴레이다. 각 단계는 이전 단계까지 정리된 내용을 출발점으로 받아 자기 산출물을 만들고, 그 산출물이 다음 단계의 출발점이 된다. 한 번 넘긴 md 산출물은 더 이상 고치지 않는 기록이고, 뒤 단계는 참조만 한다 — **단, 앱 코드만 예외**: 3단계에서 태어난 뒤 3↔4 순환에서 데모 반응대로 고쳐지고, 6단계에서 백엔드·계측이 얹히며 계속 자란다. 코드는 기록이 아니라 살아 있는 산출물이라서다. 그래서 **어떤 내용의 진실의 원천(SoT — Source of Truth)은 곧 그 내용을 확정한 단계의 산출물**이고, 화면 영역만은 3단계 이후 줄곧 앱 코드다(§2.2). 산출물 위치는 프로젝트 루트의 `mvp/` 기준 (3단계는 `mvp/handoff/` + 루트 앱 코드 — §3).

| 7 **MvpLaunch** | `launch-plan.md`(광고 **집행 전** 동결: 퍼널 go 선·예산·기간·채널) → `launch-retro.md`(실측 vs 기준 · 최종 판정 — 통과 기준②, 구 ③) | production의 입력 | `7-mvp-launch.md` |

**중복 금지**: 뒤 단계 문서에 앞 단계가 확정한 내용을 다시 쓰지 않는다 — 필요하면 참조만 한다. 방향이 바뀌면 앞 단계 문서를 고치는 게 아니라, 지금 단계 산출물의 `이전 결론 → 이번 결론` 섹션에 새로 적는다 (§2.2).

### 2.2 단계 간 SoT 검토 절차

원칙: 단계가 진행되며 산출물이 진화하면 **가장 최신 단계 산출물 = 메인 SoT**. 옛 단계 내용은 최신본의 결론·방향에 포함되는지, 어긋나는지를 능동적으로 검토한 뒤에만 근거로 쓴다. *명시 인용 여부*는 보조 신호일 뿐 판정 기준이 아니다. 단계가 쌓이면 새 단계 항목 중 일부가 *신규 작성*이 아니라 *옛 단계 압축·연결* 작업으로 작동한다.

이 절차는 **DemoValidation(go 시점 확정 내용) · MvpBuild · MvpLaunch 모든 단계 공통** — MarketResearch(5단계)는 참고 자료라 이 체인에 넣지 않는다(§1.1). 각 단계 references는 §2.1 단계 릴레이 표와 이 §2.2 검토 절차를 자기가 읽고 쓸 범위의 경계로 삼는다.

#### 이전 결론 → 이번 결론 — 아이디어·가설은 단계마다 새로 기술 (소급 수정 금지)

**대전제 — 변화는 예외가 아니라 기본이다.** 이 스킬은 애자일하게 굴러간다. 빌더가 아이디어가 속한 도메인을 완벽히 아는 게 아니면(대부분 그렇다), 만들면서 도메인을 알게 되고 **아이디어·비목표·검증 가설·타겟이 매 단계에서 통째로 뒤집힐 수 있다** — 프로토타입 고치는 3↔4 순환 중에도, demo-validation → mvp-build 사이에서도, mvp-build 만드는 도중에도, 인터뷰 후에도. 이건 실패가 아니라 이 스킬이 굴러가는 방식 그 자체다. 그러니 "변경 없음"은 여러 케이스 중 하나일 뿐 기본값이 아니다 — 매 단계 "정말 그대로인가?"를 능동적으로 되묻는다.

단계를 진행할수록 아이디어·가설은 이렇게 계속 진화한다. 그 진화를 *옛 단계 문서를 고쳐서* 반영하면, 더 이상 고치지 않기로 한 기록이 계속 바뀌는 문서 역할까지 겸하게 되어 SoT가 오염되고, "본문 재정합 TODO" 같은 부채가 쌓인다. 대신 **각 단계 산출물이 "직전 단계까지의 결론(이전 결론)"과 "이 단계를 지나며 정리된 결론(이번 결론)"을 나란히 새로 기술**한다. 핵심은 *기존엔 이랬는데 이 단계에서 이렇게 정리됐다*가 읽는 순서 그대로 드러나는 것:

- **무엇**: 6단계부터 각 단계의 md 산출물(`mvp-build.md` · `launch-plan.md`) **머리에 `# 이전 결론 → 이번 결론` 섹션**을 박는다. 다루는 내용은 4단계 DemoValidation이 go 시점에 확정하는 4개와 같다 — 최종 아이디어 한 문단 · 비목표 · 검증 가설 · 북극성(선택).
- **작성 룰**: 단계 진입 시 직전 단계의 '이번 결론'과 대조해 —
  - **변경 없으면** 한 줄: `변경 없음 — [직전 단계 산출물 §섹션] 그대로` (중복 방지).
  - **변경 있으면** 세 소제목으로 전(前)→후(後)를 나란히 둔다:
    - `## 이전 결론` — 직전 단계까지의 결론 4개(최종 아이디어·비목표·검증 가설·북극성)를 인용·요약. *어느 문서 어느 섹션 기준*인지 출처를 밝힌다. 이전 단계에 없던 항목(예: 검증 가설 섹션 자체가 없었음)은 "없었음"으로 정직하게 적는다 — 억지로 채우지 않는다.
    - `## 이번 결론` — 이 단계에서 정리된 결론 4개를 새로 기술. **이후 이 4개가 아이디어·가설의 SoT.**
    - `## 무엇이 왜 바뀌었나` — 항목별로 `(옛 → 새)` + 사유를 한 줄씩.
- **불변 원칙**: 이전 단계 문서는 **더 이상 고치지 않는 기록**이다 — 방향이 바뀌어도 소급 수정하지 않는다. 필요하면 옛 문서 *끝에 포인터 한 줄*만 (`→ YYYY-MM-DD 이후 방향은 mvp-build.md 이전 결론 → 이번 결론 섹션 참조`).
- **SoT**: 아이디어·가설의 SoT = **가장 최신 단계의 '이번 결론'** (§2.1 표 4단계 행). 4단계 산출물(demo-validation §go 분기 최종 확정 아이디어·비목표·검증 가설·북극성)이 이 체인의 시작이다 — MarketResearch(5단계)는 참고 자료라 체인에 포함되지 않는다.
- **진행 중 피봇**: 영향받는 가장 빠른 단계로 되돌아가(§1.4) **그 단계 산출물의 `이전 결론 → 이번 결론` 섹션을 갱신**한다. 그보다 앞 단계 문서는 안 건드린다. 가설의 형태 변환(문제 가설 → 검증 가설 → 퍼널 가설)은 기존대로 4·7단계가 담당(문제 가설 → 검증 가설은 4단계, 퍼널 가설은 7단계) — 이 섹션은 그 *사이 구간*에서 방향 전환이 기술될 자리를 보장하는 장치다.

#### 화면 SoT의 진화 — 인벤토리(2단계) → 목업(3단계 앞부분) → 앱 코드(3단계 마이그레이션 직후~끝까지)

화면 영역(플로우·정보 구조·상태·전환 전부)의 SoT는 세 자리를 거친다:

1. **2단계 `information-architecture.md` — *어떤 화면이 있어야 하는지*의 근거로 2단계 완료 시점에 확정되는 기록** — 화면 인벤토리·상태 매트릭스가 여기 남는다. 이 문서가 실제로 스펙으로 읽히는 자리는 3단계 안에서 딱 두 번이다 — Claude Design에 목업 생성 입력으로 첨부될 때, 그리고 마이그레이션 뒤 `MVP 포함 = O` 화면이 코드에 다 있는지 빠짐 검사할 때. 그 두 번을 지나면 이 문서를 스펙으로 읽는 소비자가 더 없다.
2. **3단계 앞부분 목업(`mvp/handoff/`의 standalone.html) — 마이그레이션의 원본** — Claude Design에서 받은 이 파일이 리액트로 옮길 원본이다. 다만 SoT 자리는 잠깐이다.
3. **마이그레이션이 끝나는 순간 앱 코드로 승격 — 이후 끝까지 화면 SoT** — 리액트 워킹 프로토타입이 도는 순간부터 화면의 진실은 코드다. 3↔4 순환의 수정도 코드에 하고, 6단계도 이 코드에 백엔드를 얹는다. `mvp/handoff/`도 2단계 인벤토리도 그 순간부터 **1세대 기록**으로 내려앉는다 — 이후로는 갱신하지도, 작업 근거로 참고하지도 않는다. 코드와 어긋나면 **코드가 기준**이다.

**영역별 SoT 요약 — 살아있는 산출물은 코드 하나뿐, 나머지 md는 전부 단계 완료로 얼려지는 기록이다.**

| 영역 | SoT의 이동 | 마이그레이션 후 |
|---|---|---|
| 아이디어·가설 | 가장 최신 단계의 `이전 결론 → 이번 결론` 체인 | 체인 계속 (문서 릴레이) |
| 화면 목록·구조 | 인벤토리(2단계) → 목업 → 코드 | 코드만 고친다. 인벤토리는 1세대 기록 |
| 화면 생김새·플로우·상태 | 목업(3단계 앞부분) → 코드 | 코드. 목업(standalone.html)은 참고용 |
| 문구(마이크로카피) | user-story.md → screens.md → 코드 | 코드. 문서는 1세대 기록 |
| 규칙·데이터 모델 | rules.md·data-model.md → 코드 | 코드. 문서는 마이그레이션까지만 읽고 이후 참고하지 않는다 |
| 정서·톤·디자인 방향 | user-story.md → 디자인 토큰·컴포넌트(코드) | 코드 |

**"동결"은 없다.** 4단계 수렴 판정은 *화면 구조 변경이 끝났다는 선언*이지 파일을 얼리는 게 아니다. 코드는 6단계에서도 계속 고쳐지므로 얼릴 대상 자체가 없다.

**왜 마이그레이션 직후에 코드로 승격하나**: 코드가 화면에 대해 아는 전부를 담게 된 뒤에도 목업 HTML을 나란히 유지하면 (1) 둘이 어긋날 때마다 어느 쪽이 진실인지 판단하는 세금이 생기고 (2) 실제로 아무도 다시 안 읽는 파일을 계속 고치는 의례가 된다. 승격 시점을 3단계 안으로 당긴 이유도 같다 — 3↔4 순환의 수정이 이미 코드에 들어가는데 SoT만 목업에 남겨두면, 첫 순환부터 두 개가 어긋난다.

- **화면 근거를 찾을 땐 코드부터** — 마이그레이션 이후엔 무조건 현재 앱 코드가 화면 SoT다. `mvp/handoff/`는 "원래 왜 이렇게 생겼나"를 되짚는 참고용일 뿐 근거로 쓰지 않는다.
- **구조 변경이든 문구·생김새 변경이든, 마이그레이션 후엔 코드만 고친다** — 2단계 인벤토리를 먼저 고치는 예외는 없다. 이유는 위 1번과 같고(그 두 공정을 지나면 인벤토리를 스펙으로 읽는 소비자가 없다), 예외 없는 규칙("마이그레이션 후엔 코드만 만진다")이 특수 예외가 있는 규칙보다 AI 실행자에게 더 잘 지켜진다. 화면 구조가 통째로 뒤집히는 대규모 개편은 문서 갱신이 아니라 2단계 재실행(피봇)으로 다룬다.
- 코드엔 추상 4개(최종 아이디어·비목표·검증 가설·북극성)가 문장으로 안 적혀 있으니, **AI가 화면·카피·기능에서 4개를 추론 → 사용자에게 보여주고 확인**받는다(§1.4 코칭).
- 목업 standalone HTML을 읽어야 할 땐 소스가 압축·인코딩돼 있다는 점에 주의한다 — 뚫는 절차는 `references/3-prototype.md` §2.5 참조.
- **상태 변형 점검은 절차로 이관** — 순환·피봇에서 화면을 추가·수정할 땐 빈 상태·오류·로딩 같은 상태 변형을 같이 만들었는지 코드에서 확인한다. 예전엔 2단계 인벤토리의 상태 매트릭스가 하던 점검을, 문서 갱신이 아니라 코드 수정 절차의 체크 항목으로 옮긴 것이다.

**6단계의 '이번 결론' = 백엔드까지 붙은 앱 코드 + `mvp-build.md`.** 백엔드를 붙이며 아이디어·가설이 통째로 뒤집혔어도, 그 뒤집힌 결과는 코드에 그대로 담긴다 — `mvp-build.md`의 `# 이전 결론 → 이번 결론` 섹션이 이걸 문장으로 정리하는 자리다.

**6단계 안에서 피봇(화면·플로우·정보 구조가 바뀌는 경우)이 나오면 기록 방법은 두 가지, 둘 다 한다** — "앞 단계로 되돌아가 옛 문서를 고치기"는 여기 없다:

1. **코드에 직접 반영** — 화면 SoT가 이미 코드니, 바뀐 화면·플로우는 지금 고치고 있는 그 코드에 그대로 넣는다. 별도의 승인 절차나 중간 산출물이 필요 없다.
2. **`mvp-build.md`의 `이전 결론 → 이번 결론`에 문장으로 기록** — 코드만 고치면 *무엇이 왜 바뀌었는지*가 어디에도 안 남는다. 바뀐 최종 아이디어·비목표·검증 가설·북극성을 `## 이전 결론` / `## 이번 결론` / `## 무엇이 왜 바뀌었나`로 적는다. (베타 공유에서 나온 확인 결과도 함께 반영한다 — '이번 결론'은 MvpBuild가 실제로 완성된 뒤 정리되는 자리다.)

이 둘(실코드 + `이전 결론 → 이번 결론` 섹션)이 곧 "피봇이 기록됐다"는 뜻이다. 그 이상 — 옛 문서 본문 소급 재정합, "TODO: 본문 재정합" 같은 부채성 표기 — 은 하지 않는다.

#### 확인 질문 4개 — 옛 문서 내용을 가져와도 되는가

새 단계 산출물을 쓰다 보면 옛 단계 문서의 내용(인터뷰 인용·조사 결과 등)을 근거로 가져오고 싶을 때가 있다. 그런데 옛 문서가 쓰인 뒤 방향이 바뀌었을 수 있다. 그래서 가져오기 전에 아래 4개를 순서대로 확인하고, 결과에 따라 표시를 붙인다.

| 순서 | 확인할 것 | 그렇다면 | 아니라면 |
|---|---|---|---|
| 1 | 그 내용이 **최신 문서에도 그대로 나오나?** (같은 인용·표·사례) | 🔵 가져온다 — 최신 문서의 그 위치를 근거로 적는다 | 2번으로 |
| 2 | 최신 문서가 그 내용을 **버린다고 밝혔나?** | 🟥 가져오지 않는다 — 문서 끝 "버린 내용 목록"에 한 줄 | 3번으로 |
| 3 | 그 내용을 **조금만 넓혀 말해도** 최신 방향과 **어긋나나?** (예: "인터뷰이 A가 그랬다" → "첫 자취생은 그렇다") | 🟥 가져오지 않는다 — 같은 목록에 기록 | 4번으로 |
| 4 | 최신 문서의 **어느 구체 문장·섹션이 그 내용을 품는지 짚을 수 있나?** | 🔵 가져온다 — 넓혀 말한 근거 한 줄 + 그 근거 위치를 함께 적는다 | 🟡 애매함 — 사용자에게 확인 |

**주의**: "버린다고 밝힘"(2번)과 "그냥 언급이 없음"은 다르다. 언급이 없을 뿐이면 3·4번으로 계속 확인한다 — 자동으로 버리지 않는다.

#### 표시 3종 + 버린 내용 목록

산출물 본문에 붙이는 표시:
- **✅ 이번 단계에서 직접** — 지금 단계의 인터뷰·조사에서 직접 얻은 내용
- **🔵 옛 단계에서 가져옴** — 1번 또는 4번 통과. 4번(넓혀 말한 경우)은 근거 한 줄 + 근거 위치 필수 (예: *demo-validation.md §라운드별 데모 노트의 인터뷰이 인용 행*). 위치를 못 대면 자동으로 🟡
- **🟡 애매함** — 사용자 확인 전에는 근거로 쓰지 않는다

문서 끝에 두는 목록:
- **🟥 버린 내용 목록** — 2번·3번으로 걸러진 옛 내용을 한 줄씩 기록 (다음 단계·회고에서 재검토)

#### 단계별 적용 — 각 references에서 보강

각 단계 references는 §2.2 절차를 *그대로* 사용. 단계별로 추가 박는 것:
- **단계 항목 × 옛 단계 표준 섹션 종류 매핑** (예: MvpBuild의 *화면 카피* 항목 → demo-validation의 *최종 확정 아이디어* 톤 검토)
- 단계별 *표시 판정 적용 예시* 1~2개

매핑·예시는 *섹션 종류(역할)* 로만 명시. 특정 프로젝트 인스턴스의 *구체 섹션 이름·내용*은 references에 박지 않음 — 재사용성 유지.

## 3. 산출물 관리

산출물 위치: 프로젝트 루트의 `mvp/` — vN 없음. 한 폴더에 문서 산출물 (`user-story.md` · `information-architecture.md` · `demo-validation.md` · `market-research.md` · `mvp-build.md` · `launch-plan.md` · `launch-retro.md`). 3단계는 md 산출물 대신 `mvp/handoff/` 폴더와 루트 앱 코드를 남긴다 — 아래 참조.

**앱 코드는 프로젝트 루트 폴더에** — **3단계 Prototype에서** `package.json`·`src/` 등이 프로젝트 루트 폴더(이 저장소의 최상위 폴더)에 생긴다. 리액트 워킹 프로토타입(로컬스토리지)까지가 3단계 몫이고, 3↔4 순환에서 데모 반응대로 이 코드를 고치며, **6단계 MvpBuild에서 같은 코드에** 백엔드·DB·로그인·계측을 얹어 최종 배포한다. 새 폴더를 만들지 않는다 — 처음부터 끝까지 앱은 하나다. 여기서 '앱'은 웹사이트·모바일 앱·데스크톱 프로그램 등 만들려는 소프트웨어 전부를 가리킨다 (문서 전체 동일). `mvp/`은 문서 산출물과 `handoff/`만.

**`mvp/handoff/` — Claude Design 꾸러미를 푼 자리**: 사용자가 외부 Claude Design("Mobile app design" 또는 "UI mockups" 모드)에서 받아 온 zip을 여기에 압축 해제한다. 안에는 **목업 standalone.html**(자급자족 단일 파일 — 폰트·이미지·컴포넌트 소스까지 전부 내장)과 문서 다섯 개(제품 정의·데이터 모델·규칙 의사코드·화면별 상태와 문구·디자인 토큰)가 함께 들어 있다. 목업 파일도 루트가 아니라 이 폴더 안에 둔다 — 루트에 따로 두던 예외는 없앴다. **갱신 규칙: 첫 수령분을 그대로 두고 갱신하지 않는다.** Claude Design은 첫 목업 한 번만 부르고, 이후 수정은 전부 리액트 코드에서 하기 때문이다(§2.2). 마이그레이션이 끝난 순간부터 handoff는 *1세대 참고 자료*이고, 코드와 어긋나면 **코드가 기준**이다. 상세는 `references/3-prototype.md` §2.3·§2.7.

핵심 원칙: **한 아이디어 = 한 프로젝트** — 아이디어가 생겨나면 아무것도 없는 새 프로젝트에서 시작한다. 통과 기준①이 no-go거나 통과 기준②가 폐기면 그 아이디어는 거기서 닫히고, 다른 아이디어는 **새 프로젝트(새 레포)**에서 다시 시작한다 — 같은 레포에서 두 번째 아이디어는 진행하지 않는다. 이유: 서로 다른 아이디어의 산출물이 한 폴더에 섞이면 SoT가 오염되고, 닫은 아이디어의 판정 기록도 깨끗하게 보존해야 하기 때문. **단, 피봇은 새 아이디어가 아니다** — 같은 문제 영역 안에서 방향을 다듬는 것이라 같은 프로젝트에서 영향받는 단계로 되돌아가 이어간다. 분기 판정 절차는 `references/4-demo-validation.md` §2.9~2.10(통과 기준①) · `references/7-mvp-launch.md` §2.3(통과 기준②, 구 ③).

### 3.1 영구 의사결정 (ADR)

여러 단계에 걸치는 결정은 **`mvp/adr.md` 단일 파일**에 한 섹션씩 누적한다 — 단계 산출물은 더 이상 고치지 않는 기록이라, 결정의 _이유_와 *변경 이력*은 이 파일에 따로 보존한다. 다음 트리거 감지 시 AI가 한 줄로 확인("이건 ADR감 — 기록할까?"):

- 외부 인프라 선택·교체 (DB·Auth·Storage·Hosting·결제·LLM 등)
- 보안·인증·권한 모델 변경
- 스택 주요 컴포넌트 추가·제거
- 비용 구조에 큰 영향을 주는 결정
- 이전 단계 산출물의 결정을 뒤집는 변경

형식: `## ADR-NNNN: <제목> (날짜)` + 상태·변경·이유 3필드. 뒤집을 땐 옛 섹션은 남겨두고 새 ADR가 그것을 대체한다고 적는다. **ADR 아님**: 진행 중 임시 결정(해당 산출물 안에 바로 적음) · 코드 컨벤션(`.claude/rules/`·`CLAUDE.md`) · 일반 버그·리팩터링.

### 3.2 단계 사이 — `/clear` 후 재호출 권장

매 단계 산출물 저장 직후 (1→2 ~ 6→7 전부), AI는 사용자에게 **`/clear` 후 `/idea-to-mvp` 재호출**을 권장한다. 스킬이 §1.2로 현재 단계를 자동 판별하니 잃는 맥락은 없고, 다음 단계를 깨끗한 대화에서 새로 시작하게 된다 — 대화 맥락이 길게 쌓여 판단이 흐려지는 것을 막기 위해서다. **사용자가 명시 거부하면 그대로 진행.** AI는 자기 대화 맥락의 크기·사용량을 정확히 모르므로 "필요할 때만" 같은 판단을 하지 않는다 — *매 단계 끝에서 예외 없이* 권장한다.

### 3.3 어휘 swap·이름 정합 절차

작업 중 핵심 어휘·단계명·산출물명을 바꿔야 할 때(예: 카탈로그→모음, IdeaValidation→DemoValidation, Mockup→Prototype), 단계 무관 공통 절차:

1. `grep -rn "<옛 단어>" .claude/ mvp/`로 흔적 전부 파악
2. 긴 패턴 먼저, 짧은 패턴 나중 순서로 `sed` 일괄 치환
3. 파일·폴더 rename (`mv`)
4. 다른 문서를 *그대로 인용한 대목*은 원문 보존 — 인용 원본을 같이 swap할 때만 인용문도 swap
5. 다시 `grep`으로 잔재 0 확인
6. 산출물 끝 🟥 버린 내용 목록에 기록 (옛 어휘 + 새 어휘 + 사유)

## 4. 단계 진입 평가와 건너뛰기

각 단계 진입 전 이전 산출물의 **존재**와 **완성도**(해당 references 체크리스트)를 검사. _단계 진입 평가_ = "이전 단계 산출물이 갖춰졌는지 확인하는 잠금장치". 미통과 시 3 옵션:

- (a) 이전 단계 보완 — 안전한 디폴트
- (b) 강행 — 빈 placeholder 산출물 자동 생성 후 진행, 회고에서 재점검
- (c) 산출물 없이 진행 + 회고에서 재점검

선택 사유는 해당 단계 산출물 또는 `launch-retro.md`에 기록.

**단, 7단계(MvpLaunch) 안 "막1 기준 박기 → 막2 광고 집행" 순서는 건너뛸 수 없다** — launch-plan.md 동결 없이 광고 집행 금지 (7-mvp-launch.md §2.1). 사후 기준은 자기합리화가 되기 때문에 이 잠금은 (b)·(c) 예외 없음.
