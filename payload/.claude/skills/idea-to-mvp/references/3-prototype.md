이 단계는 **통과 기준(게이트) 아님** — 거르기는 다음 단계(DemoValidation)에서 이 프로토타입을 들고 진행한다. AI 빌더 시대엔 화면 만드는 비용이 거의 0에 가깝다 — 그래서 빈손 인터뷰 대신, **실제로 돌아가는 것을 먼저 보여주고 반응으로 거르는** 흐름으로 바뀌었다. 이 단계는 그 물건을 준비하는 자리다.

**용어 두 개를 섞지 않는다**:

- **목업(mockup)** — Claude Design이 만들어 준 standalone.html(외부 파일 참조 없이 폰트·이미지·컴포넌트 소스까지 전부 내장된 자급자족 단일 파일). 이 단계 앞부분의 중간 산출물이다.
- **프로토타입(prototype)** — 그 목업을 리액트 코드로 옮겨, 브라우저 로컬스토리지(localStorage — 브라우저가 기기 안에 데이터를 저장해 두는 공간)로 데이터가 도는 워킹 앱. 이 단계의 최종 산출물이다.

## 1. 단계 목표

이 단계의 목표는 **2단계에서 만든 `information-architecture.md`와 `user-story.md`로 목업을 받아, 그걸 리액트 코드로 옮기고 배포해 4단계 데모에 쓸 링크를 만드는 것**이다. 다섯 스텝으로 간다:

1. **Claude Design 호출 준비·안내** (§2.2) — 파일 두 개 첨부 + 권장 프롬프트. **호출 자체는 사용자 몫.**
2. **개발 인계 꾸러미 저장** (§2.3) — 받은 zip을 `mvp/handoff/`에 압축 해제. 목업 파일(standalone.html)도 그 안에 함께 들어간다.
3. **개발환경 구성** (§2.4) — 고정 스택(Next.js(App Router)·React·TypeScript·Supabase·Vercel)의 최신 호환 버전 조합을 조사해 적용.
4. **리액트 마이그레이션 + 검증 관문** (§2.5) — handoff 문서에서 문구·규칙을, standalone.html에서 화면 구조·전환을 읽어 리액트 코드로 옮긴다. **프런트엔드 + 로컬스토리지까지** (백엔드 없음). 완주했다고 바로 배포하지 않고, 관문 두 개(디자인 시스템 감사 · 코드 품질 리뷰)를 통과하고 넘어간다.
5. **배포** (§2.6) — Vercel로 공개 링크를 만든다. 4단계 데모가 이 링크를 쓴다.

산출물은 **`mvp/handoff/` 폴더 + 프로젝트 루트의 앱 코드 + 배포 링크** 셋이다. 목표를 이뤘는지는 §3 완료 체크리스트로 판정한다.

**Claude Design 입력이 두 개인 이유는 맡은 역할이 다르기 때문이다**:

- **`information-architecture.md` — 완전성 담당.** 어떤 화면을 몇 개 만들지, 빈 상태·오류 같은 상태 변형까지 무엇을 빠뜨리지 않을지가 여기서 나온다. 화면 인벤토리 표가 만들 것의 전체 목록이다.
- **`user-story.md` — 정서·톤·마이크로카피 담당.** 화면에 들어갈 말투, 버튼 문구, 어느 장면에 힘을 줄지가 여기서 나온다. 그중 「디자인 방향」 절은 참고 수준이 아니라 레이아웃·타이포·색 같은 **시각 디자인의 원천**이다 — §2.2.3 권장 프롬프트가 이 절을 그렇게 지시한다.

둘 중 하나만 넣으면 안 된다. 인벤토리만 넣으면 빠진 화면은 없는데 말투가 밋밋해지고, 유저 스토리만 넣으면 감은 좋은데 화면이 통째로 빠진다.

**여기서 안 하는 것 (의도적)**:

- ❌ **백엔드** — DB 테이블·RLS·로그인·서버 로직은 전부 6단계(MvpBuild) 몫이다. 이 단계 데이터는 브라우저 로컬스토리지에 담긴다 (§2.4.2에 왜 이렇게 나누는지).
- ❌ **퍼널 계측·실결제** — 6단계.
- ❌ **다크모드·다국어·성능 튜닝** — production 영역. (단 반응형은 4단계 데모를 폰으로 보여줄 수 있어야 하니 챙긴다.)

**작업 모드가 절마다 다르다** (SKILL.md §1.5) — 헷갈리지 않게 미리 정리한다:

| 절 | 모드 | 누가 하나 |
|---|---|---|
| §2.2 Claude Design 호출 | — | **사용자 몫.** AI는 프롬프트 준비·안내까지 |
| §2.4 스택 선택 (React 웹 vs Expo) | 인터뷰 모드 | 사용자에게 확인받고 정한다 |
| §2.4.1 버전 조합 조사·적용 | 초안 모드 | AI가 조사·적용·보고까지 완주 |
| §2.5 리액트 마이그레이션 | 초안 모드 | AI가 끝까지 완주한 뒤 완성본으로 리뷰 |
| §2.6 배포 후 클릭 확인 | — | **사람 몫.** AI가 자동 도구로 사인오프하지 않는다 |

## 2. 진행 절차

### 2.1 단계 시작 — 이전 정리 내용을 보여주고, 이번 단계가 할 일을 안내한다

이전 단계(InformationArchitecture)가 남긴 산출물이 있다. `mvp/information-architecture.md`를 읽고 이걸 짧게 요약해 보여주는 것으로 시작한다:

- **만들 화면 개수** — 인벤토리 표에서 `MVP 포함 = O`인 화면이 몇 개인지 (전체 몇 개 중 몇 개인지 같이).
- **커버리지 자가 점검 결과** — 고아 화면(진입 경로 0개)·막다른 골목(이탈 경로 0개)이 0건인지, 일곱 갈래 점검에서 X가 남아 있는지.

여기서 X나 0건이 아닌 항목이 보이면 목업부터 만들지 말고 **2단계로 잠깐 돌아가 인벤토리를 먼저 채우자고** 안내한다. 인벤토리가 곧 만들 화면 목록이라, 표에 없는 화면은 목업에도 안 생기고 코드에도 안 생긴다.

이어서 `mvp/user-story.md`의 **로그라인**(logline — 서비스의 정서를 담은 한 줄 요약)도 한 줄 보여준다 — 이번 화면의 말투 기준이다.

그다음 **화면 인벤토리를 실제로 돌아가는 앱까지 옮기는 단계**라는 걸 설명한다.

설명 골자 — 그대로 또는 풀어서 전달:

> 2단계에서 만든 화면 인벤토리가 이번에 만들 화면의 전체 목록이야. 유저 스토리만 보고 바로 화면을 만들면 시나리오 주인공이 겪는 성공 경로만 그려져서, 빈 상태·오류 화면·반대편 역할 화면이 통째로 빠져. 그래서 2단계에서 표로 한번 훑고 온 거고, 이번 단계는 그 표를 화면으로 옮기는 자리야. 순서는 이래 — 먼저 Claude Design으로 목업을 받고(이건 네가 직접 눌러야 해), 그다음 내가 개발환경을 깔고 리액트로 옮겨서 배포까지 할게. 데이터는 아직 서버가 아니라 브라우저 안에 저장되는 수준이야. 진짜 DB는 나중(6단계)에 붙여.

이미 `mvp/handoff/`와 루트 앱 코드가 있으면(스킬 중간 재실행 등) §3 체크리스트로 검증해 부족한 부분만 보완하도록 안내한다 — 처음부터 다시 만들지 않는다.

**`이전 결론 → 이번 결론` 섹션은 이 단계엔 없다** (SKILL.md §2.2) — 그 체인은 md 산출물 머리에 박는 건데 이 단계는 md 산출물이 없다. 진행 중 아이디어·가설이 뒤집히면 4단계 `demo-validation.md`에서 정리된다.

### 2.2 Claude Design 안내

목업 제작은 사용자가 외부 [Claude Design](https://support.claude.com/en/articles/14604416-get-started-with-claude-design)에서 직접 진행한다. AI(여기)는 그 호출에 들고 갈 것을 준비해 안내하는 것까지만 한다 — Claude Design은 이 스킬 바깥의 외부 도구라 AI가 대신 호출·실행할 수 없다.

#### 2.2.1 모드 선택

유저 스토리의 플랫폼 맥락과 인벤토리의 네비게이션 구조(탭·스택·모달)를 보고 고른다:
- 모바일 앱이 중심이면 → **Mobile app design**
- 웹이 중심이면 → **UI mockups**
- 애매하면 사용자에게 확인.

(참고: 4단계 데모 검증 단계에선 링크 하나로 공유되는 웹 쪽이 공유 마찰이 적다. 이 단계 배포(§2.6)도 웹 기준이다.)

#### 2.2.2 입력 — 파일 두 개를 첨부

`mvp/information-architecture.md`와 `mvp/user-story.md` **파일 두 개를 Claude Design 대화창에 그대로 끌어다 놓는다**(첨부). 본문을 복사해 붙여넣는 방식은 쓰지 않는다 — 인벤토리 표가 길어서 붙여넣다 잘리기 쉽고, 잘린 만큼 화면이 빠진다. 요약해서 넣는 건 더 안 된다.

첨부가 안 되는 상황이면 그때만 두 문서 **전문**을 통째로 붙여넣되, 인벤토리 표와 상태 매트릭스가 끝까지 다 들어갔는지 확인한다.

#### 2.2.3 권장 프롬프트

두 파일을 첨부한 뒤 아래를 그대로 붙여넣는다. 목업과 개발 인계 문서를 **한 번에**, **zip 하나로** 받는 프롬프트다 — 왜 같이 받는지는 §2.3.

과거엔 "문구는 네가 짓지 말고 user-story.md에 있는 표현을 그대로 써줘" 식으로 그 문서를 문구 창고로만 프레이밍했더니, 디자인 도구가 문서 안 「디자인 방향」 절을 그냥 참고 취급하고 건너뛰어서 목업이 밋밋하게 나온 사고가 있었다. "반응형 웹으로 —" 한 줄만 있고 내비게이션 형태를 못 박지 않았던 것도 문제였다 — 그 틈에 도구가 데스크톱용 사이드바·헤더 메뉴를 멋대로 만들어 붙였다. 아래 프롬프트는 그 두 문제를 고친 버전이다.

```
첨부한 파일 두 개가 입력이야.

- information-architecture.md — 만들 화면의 전체 목록과 구조(정본).
  인벤토리에서 MVP 포함 = O인 화면만 ID 순서대로 하나도 빠짐없이 만들고,
  상태 매트릭스에 표시된 상태 변형(빈 상태·오류 등)도 함께 만들어줘.
  인벤토리에 없는 화면은 만들지 말고, MVP 포함 = X인 화면으로 이동하는 버튼도 그리지 마
  — 눌러도 갈 곳이 없는 죽은 버튼이 된다. 어느 버튼인지는 인벤토리의
  "미룬 화면을 가리키는 버튼" 표에 있어.

- user-story.md — 서비스의 정서·톤·화면 문구를 참고하는 자료다.
  단, 이 문서의 「디자인 방향」 절은 참고가 아니라 시각 디자인의 원천이다 —
  레이아웃·타이포·색·힘 줄 곳(히어로 순간)은 그 절의 지시를 따르고,
  씬 속 화면 묘사는 요소의 존재와 위계로만 읽어라 (배치·크기의 상한이 아니다).

화면 문구는 새로 지어내기보다 user-story.md에 있는 표현을 우선 쓰고,
문서에 없는 문구가 필요할 때만 같은 톤(쉬운 말)으로 최소한 지어라.

반응형 웹으로 만들되, 내비게이션은 웹사이트가 아니라 모바일 앱의 문법으로 해줘:
- 메뉴는 화면 하단 고정 탭바로 (모바일 앱처럼)
- 각 화면 상단은 앱바로 — 좌측 뒤로가기(←), 화면 제목, 우측 액션(아바타 등)
- 데스크톱 폭에서도 이 골격을 그대로 유지해라 — 데스크톱용 헤더 메뉴나
  사이드바를 새로 만들지 마라. 모바일 폭으로 줄여도 배치가 깨지지 않게.
- 탭이 몇 개고 무엇이 들어가는지는 information-architecture.md의
  네비게이션 구조 절이 정본이다

목업 자체는 백엔드 없이 동작하는 프로토타입이면 돼 (가짜 데이터로 화면 전환·인터랙션이
돌아가는 수준).

완성되면 아래 여섯 개를 담은 핸드오프 패키지를 zip 파일 하나로 내보내줘:
1. README — 제품 정의, 핵심 규칙, 우선순위(P0 흐름)
2. data-model — 엔티티/필드/상태 전이. 나중에 Supabase(Postgres)에 옮길 것을 감안한 구조로
3. rules — 핵심 규칙·산정식을 의사코드로
4. screens — 화면별 상태, 빈 상태, 에러 문구(화면에 실제로 들어간 문구 그대로)
5. design-tokens — 색·타이포·간격·라운드를 CSS 변수로 추출
6. 목업 파일 자체 — standalone.html(외부 참조 없이 전부 내장된 단일 파일). 문서들과 같은 zip 안에 넣어줘

없는 규칙을 지어내지 말고, 목업에 실제로 들어간 것만 정리해줘.
이 패키지를 Claude Code가 받아서 Next.js 리액트 앱으로 옮길 거야.
```

- **반응형 웹 블록은 웹 모드에서만** — "반응형 웹으로 만들되 ~"로 시작하는 블록은 §2.2.1에서 웹(UI mockups)을 고른 경우에만 넣는다. 모바일 앱(Mobile app design)은 폭이 하나로 고정이라 해당 없으니 그 블록은 빼고 붙여넣는다. 반대로 웹인데 이 블록을 빼면 데스크톱 폭에만 맞는 화면이 나오기 쉽고, 4단계 데모를 폰으로 보여주거나 6단계에서 광고 유입(대부분 모바일)을 받을 때 그대로 깨진다.
- **프로젝트 얘기를 프롬프트에 덧붙이지 않는다** — 무엇을 만들지는 첨부한 두 파일이 다 말해 준다. 여기에 화면 설명을 덧대면 파일과 어긋난 지시가 섞인다.
- Claude Design이 "개발 스택 정해진 게 있나요?"라고 되물으면 다섯 가지(Next.js·React·TypeScript·Supabase·Vercel)를 그대로 알려준다 — 하네스 고정 스택이라 여기서 다시 고를 게 없다 (§2.4.1).

#### 2.2.4 결과물 받기 — zip 하나 안에 여섯 개

Claude Design이 완성하면 **zip 파일 하나**를 받는다. 그 안에 목업(standalone.html)과 문서 다섯 개가 같이 들어 있어야 한다.

- 목업은 **standalone.html** 하나여야 한다 — 여러 파일로 쪼개진 산출물(컴포넌트 폴더 등)은 받지 않는다.
- 문서는 README·data-model·rules·screens·design-tokens 다섯 개. 목업만 챙기고 문서를 건너뛰지 않는다.
- 빠진 게 있으면 같은 대화에서 이어 요청한다 — 대화를 새로 열지 않는다. 그 대화엔 인벤토리·유저 스토리·방금 만든 화면의 맥락이 이미 다 있어서, 새 대화에서 다시 설명하면 목업과 어긋난 문서가 나온다.

#### 2.2.5 목업 수정 뒤 재추출 — 표준 문안

목업을 수정한 뒤 패키지를 다시 받을 때는 재추출을 명시적으로 지시해야 한다. 실제 사고가 있었다 — 목업에 수정 라운드가 있은 뒤 "기존과 똑같은 방식으로 최종 수정본으로 만들어줘"라고만 요청했더니, 모델이 문서를 처음부터 다시 만드는 비용을 아끼려고 첫 추출 때 만든 옛 문서를 그대로 재사용해 담았다. 그 결과 문서 4개(screens·rules·data-model·design-tokens)가 목업과 어긋났다 — 실측으로 토큰 7건, 문구 8건이 달랐고 랜딩 화면은 구조 전체가 달랐다. 명시적으로 금지하지 않은 지름길은 LLM이 밟는다. 그래서 목업 수정 뒤 패키지를 다시 받을 때는 아래 표준 문안을 그대로 쓴다:

```
핸드오프 패키지를 다시 만들어줘. 단, 이전에 만든 문서를 복사하거나 재사용하지 마 —
지금 목업의 최종 상태를 처음부터 다시 읽고 문서 5개(README·data-model·rules·screens·
design-tokens)를 전부 재생성해. 이전 문서 생성 이후 목업에 수정 라운드가 있었어서,
그때 것을 담으면 틀린 패키지가 돼.

다 만들면 내보내기 전에 자체 검증해: 목업 화면에서 버튼 문구 3개, 색상 값 2개를 골라
screens.md와 design-tokens.css에 정확히 같은 값이 있는지 확인하고, 확인한 항목을
나에게 보여줘.

그다음 목업 standalone.html과 함께 zip 하나로 내보내줘.
```

SoT(Source of Truth — 진실의 원천) 우선순위 원칙 자체는 바뀌지 않는다 — 재추출만 제대로 되면 "문구·규칙은 문서 기준"이라는 원칙은 그대로 유지된다.

#### 2.2.6 역할 분담

Claude Design이 만들어 주는 건 프런트엔드와 가짜 데이터로 도는 목업까지다. 진짜 백엔드(DB·로그인·서버)는 못 만든다. 프롬프트에 Supabase·Next.js 같은 스택 이름이 나오는 건 **문서(data-model 등)를 나중 구현에 맞는 모양으로 정리시키려는 것**이지, 목업을 Next.js 앱으로 만들라는 뜻이 아니다. **실제 리액트 앱으로 옮기는 건 이어지는 §2.4~2.6에서 Claude Code(여기)가 한다** — 단계를 넘기지 않고 같은 3단계 안에서 끝까지 간다.

### 2.3 개발 인계 꾸러미 저장

받은 zip을 **`mvp/handoff/` 폴더에 압축 해제**한다. 폴더가 없으면 만든다.

- 받은 파일 이름 그대로 푼다 (`README.md`·`data-model.md`·`rules.md`·`screens.md`·`design-tokens.css`·`standalone.html` 등).
- zip 안에 폴더가 한 겹 더 있으면 그 안쪽 내용을 `mvp/handoff/` 바로 아래로 꺼낸다 — `mvp/handoff/패키지이름/README.md`처럼 한 칸 깊어지지 않게.
- **버전 폴더를 만들지 않는다.** `handoff-v2/` 같은 걸 두지 않고 한 폴더만 유지한다.

**왜 문서를 목업과 같이 받나.** 목업은 그림이라 **왜 그렇게 생겼는지**는 못 담는다. 어떤 조건에서 다음 화면으로 넘어가는지, 타이머가 몇 초인지, 점수를 어떤 식으로 계산하는지 같은 규칙은 화면을 아무리 들여다봐도 안 읽힌다. 그래서 목업을 만든 **같은 대화에서** 그 규칙 문서를 함께 받는다. 이 문서들이 §2.5 마이그레이션에서 문구·규칙·데이터 모델을 읽는 곳이다 — 쓰임은 거기까지고, 마이그레이션이 끝나면 더 읽지 않는다(아래 '이 폴더의 성격').

**이 폴더의 성격 (중요)** — 마이그레이션(§2.5)이 끝나는 순간부터 `mvp/handoff/`는 **1세대 기록**이다:

- 이후로 갱신하지 않는다. 3↔4 순환에서 화면이 바뀌어도 여기는 그대로 둔다 (§2.7).
- **코드와 어긋나면 코드가 기준이다.** 화면 SoT(Source of Truth — 진실의 원천)는 마이그레이션 완료와 함께 리액트 앱 코드로 넘어간다 (SKILL.md §2.2).
- **문서 다섯 개(README·data-model·rules·screens·design-tokens)는 마이그레이션이 마지막 쓰임이다** — 이후로는 갱신도 참고도 하지 않는다. 코드를 읽다 "왜 이렇게 했더라" 싶어도 근거는 코드에서 찾는다. 폴더를 지우지 않는 건 수령 기록을 보존하는 차원일 뿐이다.
- **`standalone.html`만 예외다** — 코드를 고칠 때 생김새를 눈으로 다시 확인하는 용도로 연다. 이건 md 문서가 아니라 목업 자체라 그 역할은 그대로 남는다.

### 2.4 개발환경 구성

여기서부터 AI(Claude Code)가 직접 만든다.

**스택 선택은 인터뷰 모드다** (SKILL.md §1.5 에스컬레이션 기준 (c) "결과를 되돌리기 비싼 갈림길") — AI가 임의로 정하지 않고 사용자에게 확인받는다. 다만 고를 게 하나뿐이라 길지 않다: **React 웹이냐 Expo냐.**

**기본: React 웹.** 아래 §2.4.1 고정 스택과 그대로 정합되고, 배포하면 링크 하나로 공유돼 4단계 데모의 마찰이 가장 적다. 별다른 이유가 없으면 이걸로 간다.

**웹 우선 — 먼저 이 스택으로 웹 제품을 하나 완성하는 게 기본이다.** 처음부터 여러 플랫폼을 동시에 노리면 어느 쪽도 완성되지 않은 채 3단계만 길어진다. 그래서 기본을 이 스택으로 둔다.

**장기 그림 — 지금 할 일은 없고, 방향만 알아두는 것이다.** **웹은 계속 웹으로 돌린다.** 이 스택 그대로 유지하고, 앱이 필요해지면 **그 웹 코드를 옮겨서(마이그레이션) 앱을 만든다.** 웹을 앱으로 이사시키는 게 아니다 — 웹은 그 자리에서 계속 돌고, 웹 코드가 앱의 출발점이 되는 것이다. 결과는 웹·모바일 앱·데스크톱 앱을 함께 운영하는 그림이고, **Supabase가 그 셋 전부의 공유 등뼈**다 (같은 DB·같은 로그인을 셋이 같이 본다).

**언제 — 7단계(MvpLaunch) 판정을 통과한 *다음*이다.** 사용자가 늘어 사업화 단계로 가거나, 앱이어야만 되는 기능이 필요해질 때. 그 전에 앱을 논하는 건 이르다 — 대부분의 아이디어는 7단계에서 걸러진다. 이건 어디까지나 나중 얘기고, **지금 당장 앱으로 시작해야 하는 경우는 바로 아래 Expo 문단**을 본다.

**무엇으로 — 기본은 React Native다.** 앱이 필요해지면 React Native로 옮긴다 — 화면 층만 다시 쓰면 되고 TypeScript·Supabase 호출·도메인 규칙·타입은 그대로 간다. 데스크톱 네이티브 성능이 제품의 핵심일 때만 Flutter를 검토한다.

**지금 대비 작업은 하지 않는다.** 나중을 위한 추상화 층이나 플랫폼 분기 코드를 MVP에 미리 깔지 않는다.

**Expo/React Native로 갈아타는 경우** — 다음처럼 **네이티브 기능이 검증 가설 자체의 핵심**일 때만:

- 푸시 알림
- 위치(GPS)
- 카메라(QR 스캔 등)
- 오프라인 동작

"나중에 앱으로 낼 거니까"는 이유가 안 된다 — 지금 검증할 가설이 네이티브 기능 없이는 확인이 안 될 때만이다. 이 경우 다음을 사용자에게 명시적으로 짚는다:

- **앱스토어 심사 마찰** — 심사 기간·정책 리스크가 있어 배포가 웹보다 느리다.
- **데모 공유 비용** — 4단계 데모 대상자가 Expo Go 앱을 설치해야 접근 가능하다(링크 하나로 끝나는 웹보다 마찰이 크다). §2.6 배포도 Vercel 링크가 아니라 Expo 공유로 대체된다.
- **고정 스택과의 괴리** — Supabase·Vercel 등 아래 §2.4.1 조합은 웹 기준으로 짜여 있어, Expo를 택하면 그 조사·적용 절차 상당 부분을 스스로 다시 판단해야 한다.

**선택 결과는 ADR로 기록한다** (`mvp/adr.md` — SKILL.md §3.1 "스택 주요 컴포넌트 추가·제거" 트리거). **스택 자체는 이후 에스컬레이션·재논의 대상이 아니다** — 한 번 정하면 끝까지 고정이고, 6단계에서도 다시 고르지 않는다.

**고정 범위는 3단계에서 끝나지 않는다.** React·Next.js·Supabase 스택과 Vercel 배포는 **6단계(MvpBuild)까지 그대로 이어지는 고정**이다. 6단계는 스택을 새로 고르는 자리가 아니라 여기서 만든 같은 코드에 백엔드·계측을 얹는 자리다 (SKILL.md §2.1). 그래서 이 절의 선택은 3단계 한 번만 쓰고 버리는 결정이 아니라, 남은 단계 전부가 올라탈 바닥이다.

#### 2.4.1 고정 core — 최신 호환 버전 조합만 조사·적용 (React 웹 선택 시, 초안 모드)

**React 웹을 택했으면 스택 자체는 고정이다 — 후보 제시·사용자 선택 없음.** idea-to-mvp 웹앱은 무조건 이 조합으로 빌드한다:

| 영역 | 고정 (mandated core) |
|---|---|
| 프레임워크 | Next.js (App Router) |
| 언어 | TypeScript |
| UI | React |
| DB·Auth | Supabase (`@supabase/ssr` + `@supabase/supabase-js`) |
| 호스팅 | Vercel |
| lint | eslint-config-next |
| 패키지 매니저 | npm |

**왜 고정** (매 프로젝트 재결정 안 함): 목업이 React 기반(Claude Design 산출물)이라 Next 이식이 자연스럽고, Supabase는 DB+Auth+소셜 로그인이 붙으면 바로 되는 최단 경로, Vercel은 main 머지→자동 배포+프리뷰. 빌드가 싼 시대엔 *뭘 쓸지*를 매번 고르는 ceremony를 없애고 *뭘 만들지*에 집중한다.

**mandated core 밖**은 프로젝트별 추가 (지도=leaflet, 아이콘=lucide 등) — 검증 가설에 필요할 때만. core에서 빼거나 다른 것으로 갈아타는 건 하지 않는다. (결제 PG는 6단계 — 이 단계엔 결제가 없다.)

**이 절에서 실제로 하는 일 = 고정 스택의 최신 호환 버전 조합을 상호 의존성 고려해 조사·적용** (초안 모드 — AI가 조사·적용·보고, 사용자 선택 없음). **버전 숫자는 휘발성이라 이 references에 박지 않는다.** 조합은 빌드 시점에 조사해 `mvp/adr.md`에 기록한다:

1. Next.js 최신 stable 확인 → 그것이 요구하는 React·Node 버전(peer deps) 파악.
2. TypeScript·eslint-config-next를 그 Next와 호환되는 최신으로.
3. Supabase(`@supabase/ssr`·`@supabase/supabase-js`) 최신.
4. **조합 설치 검증** — `npm install`이 peer-dep 충돌(`ERESOLVE`) 없이 통과하는지. 충돌 시 마지막 호환 조합으로 한 칸 물러선다 (`--force`·`--legacy-peer-deps`로 덮지 말 것).
5. 해소된 정확한 버전을 `package.json`에 핀 + ADR에 조합 기록. 6단계는 이 기록을 참조만 하고 다시 고르지 않는다.

- **조사 소스**: 공식 docs·npm registry·context7 (최신 버전·peer 요구). LLM 학습 시점 이후 버전은 반드시 조사로 확인 — 기억으로 박지 말 것.
- **graceful degradation**: 조사가 불확실하면 마지막 known-good 조합으로 진행하고 `추후 결정: [무엇을 재확인]` 마킹.
- **에스컬레이션**: 고정 스택 자체를 못 쓰는 근본 비호환(예: 목업이 React가 아님)일 때만 멈추고 사용자에게. 그 외엔 조사·적용 완주.

**⚠️ Next.js 16 — CLAUDE.md를 멋대로 바꿔치기한다.** Next.js 16은 `next dev`나 빌드를 돌릴 때 `generate-agent-files.js`가 AGENTS.md를 자동 생성하는데, 이 과정에서 **프로젝트의 CLAUDE.md를 "@AGENTS.md" 한 줄짜리 파일로 통째로 바꿔치기해 버린다.** 실제 사고 사례가 있다 — 그때는 검증 규칙·디자인 시스템 연결 정보(adapter)까지 전부 CLAUDE.md에 있어서 하네스 지침 전체가 그렇게 날아갔고, 거기다 auto-wip-commit 훅이 그 바뀐 상태를 그대로 커밋해 버려서 git 히스토리를 뒤져 복구해야 했다. 지금은 검증 규칙과 adapter가 AGENTS.md로 옮겨가 있어서 이 사고에서 살아남는다 — CLAUDE.md에 남은 건 위임 원칙뿐이라 날아가도 그것만 날아간다. **그래서 여러 AI 도구가 같이 읽어야 하는 공용 규칙은 CLAUDE.md가 아니라 AGENTS.md에 둔다.**

- **스캐폴딩·첫 빌드 직후엔 CLAUDE.md 내용을 반드시 눈으로 확인한다** — "@AGENTS.md" 한 줄만 남아 있으면 바꿔치기당한 것이다.
- **예방책**: CLAUDE.md **맨 끝에 `@AGENTS.md` 참조 줄**이 있으면 next dev가 다시 덮어쓰지 않는다. 이 줄은 project-init이 이미 넣어 뒀으니 **있는지 확인만 하고, 없으면 그때 맨 끝에 넣는다.**
- **AGENTS.md 자체는 지우지 않는다** — Next가 자기 구역(`<!-- BEGIN:nextjs-agent-rules -->`)을 관리하는 정상 파일이라 그대로 둔다. 게다가 이제 이 파일은 Next만의 것이 아니다 — 우리도 `<!-- BEGIN:project-rules -->` 구역을 써서 모든 AI 도구가 읽을 규칙을 담아 두니, 서로의 구역을 건드리지 않고 같이 쓴다.

#### 2.4.2 Supabase·Vercel — 붙일 자리만 잡아둔다

이 단계에서 Supabase는 **프로젝트 생성 + 환경변수 연결까지만** 한다:

- Supabase 프로젝트를 만들고 URL·anon key를 `.env.local`에 넣는다(`.gitignore` 확인 — 키를 커밋하지 않는다). Vercel 프로젝트에도 같은 환경변수를 등록한다.
- 클라이언트 초기화 코드(`@supabase/ssr`)까지만 두고 **테이블은 만들지 않는다.**
- **실제 테이블·RLS(행 단위 보안 규칙)·로그인·데이터 이전은 전부 6단계 몫이다.**

**왜 여기서 끊나.** 두 가지다. (1) 4단계 데모는 사람 앞에서 화면을 눌러 보이는 자리라 백엔드가 필요 없다 — 로컬스토리지로도 "데이터가 쌓이고 다시 보이는" 경험은 똑같이 난다. (2) 데모에서 구조가 뒤집히면 미리 짜둔 DB 스키마 작업이 통째로 버려진다. 화면이 수렴한 다음에 테이블을 뜨는 게 싸다.

그래서 이 단계 데이터는 **브라우저 로컬스토리지**에 담는다 — 저장·조회·수정·삭제가 실제로 돌되, 저장소가 서버가 아니라 브라우저일 뿐이다. 이건 "가짜로 흉내 낸다"는 뜻이 아니다. 사용자가 입력한 값이 새로고침해도 남아 있고 목록에 다시 뜬다 — 데모에서 확인하려는 건 거기까지다.

### 2.5 리액트 마이그레이션

이 절차는 SKILL.md §1.5 **초안 모드** — AI가 `mvp/handoff/`를 스펙 삼아 구현을 끝까지 완주한 뒤 완성본으로 리뷰받는다. 중간에 화면 하나하나 승인받지 않는다.

**입력의 역할 분담**:

- **핸드오프 문서 = 문구·규칙·데이터 모델을 읽는 곳.** `screens.md`(화면별 상태·빈 상태·에러 문구) · `rules.md`(규칙 의사코드) · `data-model.md`(엔티티·필드·상태 전이)에 평문으로 적혀 있으니 여기서 그대로 가져온다. `design-tokens.css`(색·타이포·간격)와 `README.md`(제품 정의·우선순위)도 같이 읽는다.
- **`standalone.html` = 화면 구조 정답지.** 화면 구성·전환·생김새·인터랙션은 이걸 기준으로 옮긴다 — 문서에 안 적히는 것들이라서다.
- **`information-architecture.md` = 빠짐 검사용.** 인벤토리의 `MVP 포함 = O` 화면이 코드에 전부 있는지 ID로 대조한다.

#### 2.5.1 시작 전 — Vercel 플러그인 설치

옮기기 시작하기 전에 **Vercel 플러그인**이 깔려 있는지 확인하고, 없으면 사용자에게 설치를 안내한다. 스택이 Vercel 배포로 고정이라 이 플러그인이 들고 오는 스킬들(`react-best-practices`·`deploy`·`nextjs` 등)을 3단계부터 7단계까지 계속 쓴다 — 아래 관문 ②가 당장 그중 하나를 쓴다.

- **대화 중 설치**: `/plugin install vercel@claude-plugins-official`
- **터미널에서 설치**: `claude plugin install vercel@claude-plugins-official`
- **마켓플레이스를 따로 추가할 필요 없다** — `claude-plugins-official`은 공식 마켓플레이스라 자동으로 등록돼 있다.
- **설치 범위는 사용자 전역(User)을 권한다** — 프로젝트마다 다시 깔지 않아도 된다. 전역으로 깔면 `~/.claude/settings.json`의 `enabledPlugins`에 기록된다.
- **설치 확인**: 대화에서 `/plugin` → Installed 탭, 또는 터미널에서 `claude plugin list`
- **스킬 호출 형식**: `/vercel:react-best-practices`처럼 `플러그인이름:스킬이름`

#### 2.5.2 ⚠️ standalone HTML에서 화면 코드 읽는 법 (grep이 안 먹힌다 — 반드시 이 절차로)

**여기서 HTML을 여는 목적은 문구를 캐내는 게 아니라, 문서에 안 적히는 것(화면 구조·전환 로직·인터랙션)을 확인하는 것이다.** `mvp/handoff/standalone.html`은 자급자족 단일 파일이라 **앱 소스(JSX/JS)가 대개 압축·인코딩되어 들어있다.** 화면에 뻔히 렌더되는 문구를 `grep`/평문 검색하면 **0건이 나온다** — 없는 게 아니라 인코딩돼 있는 것이다. 그러니 `grep 0건`을 "이 파일엔 없다"는 뜻으로 읽지 말고, 아래 절차로 압축부터 푼다.

**입력 우선순위** — 문구·규칙·데이터 모델은 핸드오프 문서(`screens.md`·`rules.md`·`data-model.md`)에서 평문으로 읽고, 화면 구조·전환 로직처럼 문서에 안 적히는 것만 이 HTML에서 찾는다. 같은 내용이 평문으로 이미 있는데 굳이 압축을 풀 이유가 없고, 그쪽이 더 정확하다.

**성공 판정 기준 — 디코드에 성공한 건 목적지가 아니다**

압축을 풀었다는 사실만으로 "소스 확보 완료"라고 결론 내리면 안 된다. 성공 신호는 하나뿐이다 — **디코드해서 나온 내용에 `screens.md`나 화면 인벤토리에 적힌 화면 문구가 실제로 등장하는가.**

- 문구가 잡히면 → 화면 코드를 제대로 찾은 것. 여기가 화면 구조·전환을 읽을 자리다.
- 문구가 안 잡히면 → 프레임워크·라이브러리 코드를 잡은 것이다. 다음 패턴으로 넘어간다.

실제로 어떤 파일에서는 gzip을 다 풀어 21만 자를 얻었는데 그 안에 한글 어절이 **0건**이었다. 나온 건 실행 프레임워크와 React 빌드본, 폰트뿐이었고 화면 문구는 전혀 다른 자리에 평문으로 있었다. 파일 포맷은 Claude Design 버전에 따라 달라지니, **아래 목록에 없는 새 포맷이 나와도 판정 기준은 이것 하나로 똑같이 쓴다.**

**지금까지 관찰된 패턴 두 개** — 어느 쪽이 맞는지는 위 판정 기준으로 가린다. 순서대로 훑되, 문구가 안 잡히면 다음으로 넘어간다.

**패턴 1 — gzip → base64 리소스 맵.** 파일 안에 `{"<uuid>":{"mime":"application/javascript","data":"H4sI…"}}` 형태의 리소스 맵이 있고, `data`가 **`H4sI…`로 시작하면 gzip 시그니처**다. 그 JSON을 파싱 → 각 리소스의 `data`를 **base64 디코드 → gunzip → utf-8 디코드** 한다.

```python
gzip.decompress(base64.b64decode(data)).decode("utf-8")
```

여기 든 게 앱 코드가 아닌 경우가 관찰됐다 — 리소스 95개 중 gzip은 3개뿐이었고 그 셋이 각각 실행 프레임워크·React·ReactDOM 빌드본, 나머지 92개는 폰트였다. 그러니 풀고 나서 반드시 문구로 확인한다.

**패턴 2 — JSON 문자열 템플릿.** `<script type="__bundler/template">` 태그를 찾는다. 내용이 `H4sI`가 아니라 `"<!DOCTYPE html>…`처럼 따옴표로 시작하면 gzip이 아니라 **JSON 문자열 리터럴**이다. 그대로 JSON 파싱하면 평문 HTML이 나온다.

```python
json.loads(re.search(r'<script type="__bundler/template">(.*?)</script>', html, re.S).group(1))
```

그 안에서 찾을 건 두 덩어리다:

- `<x-dc> … </x-dc>` — 화면 마크업.
- `</x-dc>` 바로 뒤의 `<script type="text/x-dc" data-dc-script …>` — 실제 앱 로직. 화면 전환 함수·상태별 조건식·샘플 데이터가 평문 그대로 들어 있다. 별도 인코딩 없이 HTML 엔티티(`&quot;` 등)만 풀면 읽힌다.

**두 패턴 다 문구가 안 잡히면 파일 구조부터 다시 본다.** 형식은 도구/버전마다 다르다. `grep 0건`을 "없음"으로 단정하지 말고 다른 인코딩 가능성을 훑는다: 인라인 `type="text/babel"` 스크립트(평문 JSX), JSON 이스케이프된 HTML 셸 문자열, 유니코드 이스케이프(`\uXXXX`), HTML 엔티티, 별도 base64 data URI 등. 가장 긴 줄들을 뜯어보면 어디에 뭉쳐 있는지 보인다.

**그래도 안 뚫리면** 브라우저 렌더 결과(사용자 스크린샷·DOM)를 근거로 화면 구조를 읽는다. 이때도 **문구는 `screens.md`에서 그대로 가져온다** — 렌더된 화면에서 눈으로 베끼지 않는다.

#### 2.5.3 디코드는 메인 에이전트가 먼저 해서 파일로 넘긴다

마이그레이션은 서브 에이전트에 위임하는 작업이지만(프로젝트 `CLAUDE.md` 위임 원칙), **`standalone.html`처럼 크고 디코딩이 필요한 입력은 통째로 넘기지 않는다.** 일을 나눠 주는 메인 에이전트(orchestrator)가 위 절차로 먼저 디코드해 **평문 파일로 저장**하고, 서브 에이전트에겐 그 파일 경로를 넘긴다.

디코드는 다시 하기 비싼 작업이라서다 — 4MB짜리 파일에서 소스 위치를 찾는 데만 10분 넘게 걸린 사례가 있다. 그걸 서브 에이전트 안에서 하면 결과가 그 에이전트 안에만 남아, 도중에 끊겼을 때 디스크에 아무것도 없어서 재시도가 정말로 처음부터가 된다. 실제로 이 순서로 바꾸고 나서야 화면 코드가 어디 있는지 찾아냈다.

**이미지 리소스도 이때 같이 추출한다.** 목업 마크업의 이미지는 `<img src="(UUID)">`처럼 리소스 맵을 가리키는 참조로만 박혀 있다. 마크업·로직 텍스트만 디코드해 서브 에이전트에 넘기면 이 UUID가 뭘 가리키는지 알 길이 없다 — 실제로 랜딩 히어로의 마스코트+경로 비주얼이 통째로 누락된 사고가 있었다. 그래서 메인 에이전트의 디코드 절차에 한 단계를 더한다:

- `__bundler/manifest`의 리소스 중 mime이 `image/*`인 것을 전부 추출한다 (base64 디코드, `data`가 `H4sI`로 시작하면 gunzip까지 한다).
- 추출한 파일은 `public/` 등 프로젝트 자산 위치에 저장한다.
- **UUID ↔ 저장 파일 경로 매핑표**를 만들어, 디코드된 평문 파일들과 함께 서브 에이전트에 넘긴다.
- 서브 에이전트는 마크업에서 `<img src="(UUID)">`를 만나면 이 매핑표로 실제 자산을 찾는다.

#### 2.5.4 디자인 시스템 baseline

목업의 토큰·컴포넌트·화면을 실코드로 옮기는 작업은 같은 하네스의 `design-system` 스킬을 호출해 그 방법론대로 한다. 시작할 때 토큰 3층(foundation→semantic→component) 구축 + 컴포넌트 인벤토리 생성 + AGENTS.md 연결 정보(adapter) 기록은 스킬의 bootstrap-project.md 절차대로 — 목업 HTML에 내장된 토큰·CSS와 `design-tokens.css`가 이때 foundation·semantic을 채우는 원료다. 이후 모든 화면·컴포넌트 코드는 semantic 토큰만 참조한다 (hex·px 하드코딩 금지 — 스킬 철칙).

목업 화면이 스킬의 안티패턴에 걸리면(예: 목록 항목마다 카드 감싸기·상태색 장식 사용) 그대로 베끼지 않고 **스킬 쪽으로 고쳐서 이식한다** — 목업이 검증할 것은 플로우·구성·첫인상이지 최종 시각이 아니다.

#### 2.5.5 데이터 — 로컬스토리지

- `data-model.md`의 엔티티·필드 모양을 **그대로** 로컬스토리지 저장 구조로 쓴다. 6단계에서 Supabase 테이블로 옮길 때 필드 이름이 달라 다시 짜는 일이 없게.
- 저장·조회·수정·삭제가 실제로 돌아야 한다 — 새로고침해도 데이터가 남는 수준. 화면만 전환되는 껍데기는 이 단계 완료가 아니다.
- 저장·조회 로직은 한 군데(예: `lib/storage.ts`)로 모은다. 6단계에서 이 파일 하나를 Supabase 호출로 갈아끼우면 되게.
- 저장·조회 함수는 처음부터 `Promise`를 반환하게 짠다. 로컬스토리지는 동기라 지금 굳이 이럴 필요가 없어 보이는 게 정상이다 — 그래도 미리 `Promise`로 감싸 두면 6단계에서 진짜 DB 호출(비동기)로 바뀔 때 함수 시그니처가 그대로라 부르는 화면을 하나도 안 고친다.
- 화면(컴포넌트)에서 로컬스토리지 API를 직접 부르면 안 된다 — 반드시 위 한 군데(`lib/storage.ts`)를 거친다. 한 화면이라도 옆길로 새면 그 화면만 6단계에서 따로 찾아 고쳐야 한다. `src/app`·`src/components`에서 저장소 API를 직접 부르는 곳이 있는지 grep으로 세어 확인한다.
- 로그인이 필요한 화면은 **가짜 세션**(로컬스토리지에 현재 사용자 하나)으로 대신한다. 비밀번호·개인정보를 로컬스토리지에 넣지 않는다 — 브라우저에 그대로 노출되는 공간이다.

#### 2.5.6 스코프와 에스컬레이션

- **스코프**: 인벤토리의 `MVP 포함 = O` 화면 전부 + 상태 매트릭스에 `O`로 적힌 상태 변형. `MVP 포함 = X`인 화면으로 가는 버튼은 만들지 않는다.
- **에스컬레이션**: 목업과 handoff 문서가 서로 모순될 때(→ 화면 구조는 목업, 문구·규칙은 문서가 기준. 어긋난 지점은 보고), 인벤토리에 있는데 목업에 없는 화면을 발견했을 때, 외부 서비스 추가가 필요할 때는 멈추고 배치로 질문한다. 그 외 애매함은 합리적 가정 + `추후 결정:` 마킹 후 계속.
- **정지 조건**: 같은 산출물의 자율 재작업은 최대 2회 (SKILL.md §1.5).

#### 2.5.7 마이그레이션이 끝나면 — 화면 SoT가 코드로 넘어온다

마이그레이션이 끝나는 순간부터 **화면 영역(플로우·정보 구조·상태·전환 전부)의 SoT는 리액트 앱 코드**다 (SKILL.md §2.2). 이후 3↔4 순환에서도, 6단계에서도 화면은 이 코드에서 고친다.

- `mvp/handoff/`는 1세대 기록으로 남는다 — 이후 갱신하지도 참고하지도 않는다(standalone.html 눈 확인만 예외 — §2.3). **코드와 어긋나면 코드가 기준.**
- 2단계 `information-architecture.md`도 이 시점부터 1세대 기록이다 — 목업 생성 입력과 방금 끝난 마이그레이션 빠짐 검사로 쓸 용도를 다했다. 이후 화면이 늘거나 빠져도 이 문서는 갱신하지 않는다 — 코드에만 반영한다 (§2.7).

#### 2.5.8 마이그레이션 검증 관문 — 배포 전에 두 개를 통과한다

마이그레이션을 완주했다고 바로 배포하지 않는다. **관문(gate — 통과해야 다음으로 넘어갈 수 있는 검사 지점) 두 개**를 먼저 통과한다. 초안 모드로 중간 확인 없이 끝까지 달린 코드에는 화면을 눌러봐선 안 드러나는 위반이 쌓이기 마련이라, 배포 전에 기계로 한 번 훑는다.

**실행 순서**:

```
마이그레이션 완주 → 관문 ① → 관문 ② → 수정 반영 → 배포(§2.6) → 사람 클릭 검증
```

**관문 ① — 디자인 시스템 감사**

`design-system` 스킬을 호출해 **그 스킬의 철칙과 안티패턴 표를 검사 기준으로 삼는다.** 기준 항목을 이 문서에 베껴 두지 않는 이유는, 스킬이 개정되면 감사 기준도 자동으로 따라가야 하기 때문이다 — 여기 복사해 두면 스킬만 바뀌고 감사는 옛 기준으로 남는다.

다만 **`grep`으로 기계 검증이 되는 항목은 아래 명령을 실제로 돌린다.** 눈대중으로 "괜찮아 보이네" 하고 넘어가는 걸 막는 장치다. 경로는 프로젝트마다 다르니 자리표시자를 자기 프로젝트 경로로 바꿔 쓴다 (`design-system` 도입 기본형은 `src/styles/1-foundation/`·`2-semantic.css`·`3-components.css`).

1. **3층(component·제품 코드)에 색·크기 하드코딩 0건**

```bash
grep -rnE '#([0-9a-fA-F]{3}|[0-9a-fA-F]{4}|[0-9a-fA-F]{6}|[0-9a-fA-F]{8})|rgba?\(|hsla?\(' <3층 CSS 경로> <제품 코드 경로>
grep -rnE '[0-9]+px' <3층 CSS 경로> <제품 코드 경로>
```

걸린 줄은 전부 semantic 토큰으로 바꾼다. `1px` 테두리처럼 남길 값이 있으면 그 줄을 프로젝트 `AGENTS.md`의 디자인 시스템 연결 정보(adapter)에 예외로 적어 둔다 — 적어두지 않으면 다음 라운드에 같은 걸 또 따진다.

2. **3층이 foundation 램프 변수를 직접 참조하는 곳 0건** — semantic 층을 건너뛰면 나중에 브랜드를 갈아끼울 때 3층까지 다 손대야 한다.

```bash
grep -rhoE '^[[:space:]]*--[A-Za-z0-9-]+' <1층 foundation 경로> \
  | sed -E 's/^[[:space:]]*/var(/; s/$/)/' | sort -u > /tmp/foundation-vars.txt
grep -rnFf /tmp/foundation-vars.txt <3층 CSS 경로> <제품 코드 경로>
```

3. **뷰포트 미디어 쿼리는 화면 전환용만** — 뷰포트 미디어 쿼리는 화면 전체가 통째로 바뀌는 전환(예: 좁은 화면에서 상단 내비게이션 → 하단 탭 막대)에만 쓴다. 그 경우 프로젝트 `AGENTS.md`의 디자인 시스템 연결 정보(adapter)에 기록하고 통과. 그 외 용도는 0건이어야 한다 — 부품 크기 대응은 컨테이너 쿼리(container query — 화면 전체 폭이 아니라 그 요소가 실제로 차지한 폭을 보고 규칙을 거는 CSS 기능)로 푼다 (`design-system` 스킬 layout-frames.md §5 반응형 계약). 분기 자체가 필요 없으면 flex 줄바꿈·`auto-fill`·`clamp()`로 푼다. 감사 기준은 스킬이 갖고, 여기서 보는 건 그 기준을 3층 제품 코드에 실제로 적용한 결과다.

```bash
grep -rn '@media' <3층 CSS 경로> <제품 코드 경로>
```

4. **새로 만든 부품·클래스가 컴포넌트 인벤토리에 전부 등록됐는지 대조** — 인벤토리 위치는 프로젝트마다 다르고, 그 프로젝트 `AGENTS.md`의 디자인 시스템 연결 정보(adapter)에 적혀 있다. 흔한 자리는 `docs/components.md`.

```bash
grep -rhoE '^\.[a-z][a-z0-9-]*' <3층 CSS 경로> | sed 's/^\.//' | sort -u > /tmp/classes.txt
while read -r c; do grep -q -- "$c" <컴포넌트 인벤토리 문서 경로> || echo "미등록: $c"; done < /tmp/classes.txt
```

(이 명령은 줄 맨 앞에서 시작하는 클래스 선택자만 집는다. 한 줄에 선택자를 여러 개 늘어놓은 CSS면 놓치는 게 생기니, 결과가 수상하리만치 적으면 눈으로 한 번 더 훑는다.)

**인벤토리 표기와 grep 대조 방식이 어긋나면 오탐이 쏟아진다.** 인벤토리가 "button(변형 9 · 크기 4)"처럼 부품을 블록 단위로 뭉뚱그려 적어 두는 경우가 많은데, 클래스 이름을 문자 그대로 대조하면 `button--l` 같은 변형·하위 요소 클래스가 인벤토리 문구엔 없다는 이유로 줄줄이 미등록으로 잡힌다 — 실측으로 오탐 93건이 나온 사례가 있다. 그래서 대조는 인벤토리 본문이 아니라 **자동 생성한 색인**과 한다: 인벤토리 문서 **끝에 '전체 클래스 색인' 구간을 따로 두고**, 3층 CSS에서 클래스를 추가·삭제할 때마다 재생성한다. 부품 설명 자체는 지금처럼 블록 단위로 써도 되고, grep 대조만 이 색인을 대상으로 한다. 색인 생성은 3층 CSS에서 `^\.클래스` 셀렉터를 전수 추출해 나열하는 것으로 충분하다 (위 grep 명령과 같은 방식).

위반이 나오면 **수정을 반영한 뒤 같은 검사를 다시 돌린다.** 고쳤다는 보고로 끝내지 않는다 — 재검사가 0건이어야 관문 통과다.

**관문 ② — 코드 품질 리뷰**

`/vercel:react-best-practices`를 호출해 마이그레이션 결과 전체를 리뷰하고, 나온 위반을 수정 반영한다. 스택이 React·Next 고정이라 이 스킬은 항상 적용된다. (스킬이 안 보이면 위 §2.5.1 "시작 전 — Vercel 플러그인 설치"로 돌아가 먼저 깔고 온다.)

여기서 실제로 잡히는 결함은 이런 종류다 — 화면을 눌러보는 것만으로는 절대 안 보인다:

- 모달처럼 **조건부로만 쓰는 무거운 컴포넌트가 첫 번들**(bundle — 브라우저가 앱을 열 때 처음 내려받는 코드 뭉치)**에 전부 실림.** 열어보지도 않은 화면 때문에 첫 로딩이 느려진다.
- **`localStorage` 접근에 예외 처리가 없음.** 사생활 보호 모드(private browsing)나 저장 공간이 꽉 찬 브라우저에서 앱 전체가 죽는다. 이 단계 데이터가 전부 로컬스토리지에 있으니 특히 치명적이다.
- **매 렌더마다 새로 만들어지는 함수를 이벤트 리스너**(event listener — 클릭·입력 같은 사건이 났을 때 실행할 함수를 미리 걸어두는 것)**로 등록함.** 글자 하나 칠 때마다 리스너를 뗐다 다시 붙인다.

**관문은 1회성이 아니다 — 코드가 바뀔 때마다 다시 돌린다**

마이그레이션 완주 직후의 1차 실행으로 기준선을 잡고, 그 뒤로도 **ui/ux/bx(디자인 콘셉트) 변경 라운드나 3↔4단계 순환(§2.7)으로 코드가 바뀔 때마다 배포 전에 다시 돌린다.**

감사 없이 변경만 쌓으면 위반과 잔재(아무도 안 쓰는 고아 토큰, 죽은 스타일)가 라운드마다 누적돼서, 나중엔 어느 라운드에서 들어온 건지 추적하는 비용이 고치는 비용보다 커진다. 관문 ①은 grep 기반이라 **반복 비용이 싸다** — 한 번 통과했다고 아끼지 않는다.

**`done-task`의 simplify 게이트와는 축이 다르다**

하네스의 `done-task`에는 이미 simplify 게이트(재사용·단순화·효율·계층 리뷰 — `done-task` §1.5)가 있다. 이 관문 둘과 겹치는 검사가 아니다 — **관문 ①은 디자인 규칙 준수, 관문 ②는 프레임워크 모범 사례(성능·정확성 관례), simplify는 코드 구조·중복**을 본다. 셋이 서로 다른 곳을 보는 상호 보완이라, simplify를 돌렸다고 관문을 건너뛰지 않고 그 반대도 마찬가지다.

### 2.6 배포

**지금 배포하는 건 백엔드 없는 프런트엔드 워킹 프로토타입이다.** Supabase는 §2.4.2대로 붙일 자리만 잡아뒀고, 데이터는 서버가 아니라 브라우저 로컬스토리지에 있다. **그래도 배포에는 아무 문제가 없다** — 서버가 할 일이 없을 뿐이라 그냥 올라간다. "백엔드부터 붙여야 배포할 수 있다"는 건 오해다.

**그래서 얻는 게 공개 URL 하나다.** 링크를 보내면 상대는 아무것도 설치하지 않고 브라우저로 바로 열어본다 — 이 단계에서 굳이 배포까지 하는 이유가 이거다. 쓰임은 두 가지다. (가) 4단계 데모에서 인터뷰이 앞에 띄워 직접 만져보게 하기, (나) **멀리 있는 사람에게 링크만 보내 반응 받기.** 만나지 않고도 반응을 모을 수 있다는 게 실질 이점이다.

**보여주기 전에 상대에게 한계를 한 줄 미리 알린다**: 아직 로그인도 서버 저장도 없어서 기기나 브라우저를 옮기면 넣어둔 데이터가 이어지지 않는다. 미리 말해두지 않으면 상대가 이걸 버그로 읽고, 정작 받아야 할 화면·플로우 반응이 그 얘기에 묻힌다.

1. **Vercel에 배포한다** — 저장소를 Vercel 프로젝트에 연결하고, §2.4.2에서 등록한 환경변수가 배포 환경에도 들어갔는지 확인한다. main 직접 push 금지 — PR 워크플로로 간다 (repo 훅이 막는다).
2. **사이트 전체에 색인 제외(noindex — 검색엔진에게 이 페이지를 검색 결과에 넣지 말라고 알리는 표시)를 건다.** 지금 올리는 건 로컬스토리지로 도는 프로토타입이라 빈 상태 화면과 예시 데이터뿐인데, 이 링크는 4단계 데모와 5단계를 거쳐 6단계까지 몇 주를 떠 있는다. 그동안 검색에 잡히면 서비스가 그 얇은 화면으로 알려진다. 막는 건 검색 색인뿐이고 링크를 보내 여는 건 그대로 되니 데모에는 아무 지장이 없다. Vercel의 preview 배포는 기본으로 막혀 있지만 **여기서 만드는 공개 URL은 production이라 안 막힌다** — 그래서 직접 걸어야 한다. 6단계에서 검색 노출을 켤 때 푼다 (`6-mvp-build.md` §2.2).
3. **사용자가 배포 URL을 브라우저로 직접 클릭해 확인한다** (사람 몫 — SKILL.md §1.5, AI가 자동 도구로 사인오프하지 않는다):
   - 인벤토리의 핵심 플로우가 끝까지 돌아가는지.
   - 데이터를 넣고 **새로고침해도 남아 있는지** (로컬스토리지 동작 확인).
   - 웹 모드면 브라우저 창을 모바일 폭으로 줄여도 안 깨지는지 — 4단계 데모를 폰으로 보여줄 수 있어야 한다.
4. 발견된 문제는 초안 모드로 수정 → 재배포 → 재확인.

(Expo를 택했으면 이 절은 Expo 공유 링크·QR로 대체된다 — 대상자가 Expo Go를 설치해야 한다는 점을 데모 전에 미리 알린다.)

**같은 성질을 데모 *준비* 쪽에서도 한 번 짚어둔다** (위 한 줄은 *상대에게 알릴 것*이고, 이건 *네가 미리 마련해 둘 것*이다): 데이터가 브라우저마다 따로 산다. 데모에서 다른 사람 기기로 열면 빈 상태부터 시작하고, 내가 넣어둔 예시 데이터는 안 보인다. 시연에 예시 데이터가 필요하면 앱 안에 **초기 예시 데이터를 심는 방법**(첫 방문 시 자동 채움 등)을 마련해 둔다. 이때 심는 시드(seed — 미리 채워 넣는 예시 데이터)는 적게 만든다. 빈 상태·몇 개·많은 개수처럼 화면이 보여줘야 할 상태만 확인되면 충분하다 — 수십 명·수백 건을 지어내 봐야 6단계에서 DB용으로 다시 만들며 그만큼 버려진다.

### 2.7 순환 갱신 (4단계에서 복귀 시)

4단계(DemoValidation)의 데모 인터뷰에서 **구조적 수정사항**(플로우·화면 구성·핵심 기능이 바뀌어야 하는 피드백)이 나오면 이 단계로 되돌아온다. **고치는 대상은 리액트 코드다 — Claude Design을 다시 부르지 않는다.** 이미 코드가 화면 SoT라 목업을 새로 받으면 코드와 두 갈래가 되고, 어느 쪽이 진실인지 따지는 비용만 생긴다.

**인벤토리·handoff는 갱신하지 않는다** — 둘 다 마이그레이션 시점에 1세대 기록으로 넘어갔다. 이유는 §2.5.7. 화면 구조가 통째로 뒤집히는 대규모 개편(화면 절반을 새로 짜는 수준)이라면 이건 순환 갱신이 아니라 **피봇**이다 — 2단계로 돌아가 인벤토리를 다시 만드는 재실행으로 다룬다(`SKILL.md` 피봇 규칙).

절차:

1. **코드를 고친다** (초안 모드). 무엇을 왜 바꾸는지 **화면 ID로** 정리해서 시작한다 (예: "S-04(카드 정보 입력)를 온보딩에서 빼고 S-03 다음에 바로 S-05로 — 이유: 인터뷰이 다수가 그 화면에서 이탈"). 화면을 새로 만들 땐 `design-system` 스킬의 semantic 토큰·기존 컴포넌트를 그대로 쓴다.
2. **화면을 추가·수정할 땐 상태 변형도 같이 만들었는지 코드에서 확인한다** — 빈 상태·오류·로딩 같은 변형. 예전엔 2단계 인벤토리의 상태 매트릭스가 하던 점검인데, 인벤토리를 갱신하지 않는 대신 이 자리(코드 수정 절차)로 옮겨왔다.
3. **`mvp/handoff/`는 건드리지 않는다.** 1세대 기록 그대로 둔다 — 새 화면이 거기 없는 건 정상이다.
4. **코드를 고쳤으면 배포 전에 §2.5.8 관문 ①②를 다시 돌린다.** 디자인 시스템 감사와 코드 품질 리뷰는 1회성이 아니다 — 라운드마다 위반·잔재가 쌓이는 걸 막는 장치라, 이번 라운드에 바꾼 코드도 같은 검사를 통과해야 한다.
5. **재배포 + 사용자 클릭 확인** (§2.6).
6. **4단계로 복귀**해 다음 라운드 데모를 진행한다.

4단계가 **수렴**(구조적 수정 0건 — `4-demo-validation.md` §2.8) 판정을 내리면 화면 구조 변경이 끝났다는 뜻이다. 코드는 그대로 6단계로 넘어가 백엔드가 얹힌다 — 파일을 얼려 두는 게 아니라, 더 이상 *구조를* 바꾸지 않는다는 선언이다.

## 5. 사용자 응대 톤

- **톤**: SKILL.md §1.3 따름 — 반말·친근·짧게.
- **진입 안내**: "인벤토리 다 나왔으니 이제 진짜 돌아가는 걸 만들 차례야 — 먼저 Claude Design으로 목업을 받고(이건 네가 눌러야 해), 그다음 내가 개발환경 깔고 리액트로 옮겨서 배포까지 할게. 데이터는 아직 브라우저에 저장되는 수준이고, 진짜 DB는 나중에 붙여."
- **AI는 Claude Design을 대신 실행하지 않는다** — 프롬프트 준비·결과 저장 안내까지만. 사용자가 "네가 대신 만들어줘" 하면 외부 도구라 AI가 못 들어간다는 걸 짚어준다. **대신 그 뒤(개발환경·마이그레이션·배포)는 전부 AI가 한다**는 것도 같이 알린다 — 사용자가 할 일이 얼마나 남았는지 헷갈리지 않게.
- **목업 품질 불만**: "화면이 별로다", "이상하게 나왔다" 하면 다시 만들어달라고만 던지지 말고, §2.2.3 프롬프트를 더 구체화(빠진 화면 ID·상태 변형 짚기)해서 **마이그레이션 전에** 같은 대화에서 보완하자고 안내한다. 마이그레이션이 끝난 뒤라면 목업이 아니라 코드를 고친다 (§2.7).
- **모드 선택 애매**: 억지로 정하지 말고 사용자에게 확인.
- **화면이 너무 많다고 할 때**: **마이그레이션 전(목업 단계까지)이면** 인벤토리에서 임의로 화면을 빼지 말고, 2단계로 돌아가 `MVP 포함` 칸을 다시 정하자고 안내한다 — 목록에서 지우는 게 아니라 이번엔 안 만든다고 표시하는 거다. **마이그레이션 후라면** 이 안내는 해당 없다 — 데모 근거를 들어 코드에서 그 화면을 바로 빼면 된다. 인벤토리는 그 시점엔 이미 1세대 기록이라 고치지 않는다 (§2.3).
- **3단계에서 DB까지 붙이자고 할 때**: 4단계 데모엔 백엔드가 필요 없고, 데모에서 구조가 뒤집히면 미리 만든 테이블·RLS가 통째로 버려진다고 짚어준다 (§2.4.2). 지금은 붙일 자리(프로젝트·환경변수)만 잡아두고, 화면이 수렴한 뒤 6단계에서 로컬스토리지를 Supabase로 갈아끼운다.
- **백엔드까지 목업으로 만들어 달라고 할 때**: Claude Design은 가짜 데이터로 도는 프런트엔드까지가 한계라고 짚는다 (§2.2.6). 실제 데이터가 도는 건 §2.5 마이그레이션에서 로컬스토리지로, 진짜 DB는 6단계에서.
- **순환 때 목업을 다시 받자고 할 때**: 이제 화면 SoT가 코드라, 목업을 새로 받으면 코드와 두 갈래가 돼서 어느 쪽이 진짜인지 따지는 비용만 생긴다고 짚어준다. 순환 수정은 코드에서 한다 (§2.7). 화면이 늘거나 빠지는 변경도 코드에만 반영한다 — 인벤토리는 이미 1세대 기록이다 (§2.3).
- **`mvp/handoff/`도 같이 고쳐 달라고 할 때**: 갱신 대상도 참고 대상도 아니라고 짚어준다 — 마이그레이션 이후엔 읽지 않는 1세대 기록이라 지금 코드와 달라도 정상이고, 근거는 코드에서 찾는다 (§2.3). 문서를 코드에 맞춰 계속 손보면 아무도 안 읽는 파일에 비용만 든다.
- **빌드 중**: 잘게 확인 요청 금지 (초안 모드). 에스컬레이션 기준 해당 시에만 멈추고 배치로 질문. 스택 버전 조합은 어떤 조합으로 갔는지 끝나고 한 번 보고.
- **배포·클릭 검증 안내**: "배포까진 내가 하는데, 실제로 눌러보고 확인하는 건 네 몫이야 — 자동 검증 도구로 대신 사인오프 안 해" (SKILL.md §1.5 사람 몫). 새로고침해도 데이터가 남는지 같이 봐 달라고 짚는다.
