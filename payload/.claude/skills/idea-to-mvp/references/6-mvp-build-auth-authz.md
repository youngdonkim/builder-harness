| | [6-mvp-build-auth-consent.md](6-mvp-build-auth-consent.md) | 이 문서 |

## 1. 손대기 전에 정본부터 받아온다 — 이 문서에서 제일 중요한 절

**이 절이 나머지 셋보다 중요하다.** 실제로 하루를 태운 실패의 1번 원인이 여기라서다.

> 공식 참조 구현을 베껴놓고 시작한 게 아니라 **처음부터 우리 식으로 짰다.** 문제는 "달랐다"가 아니라 **"다른 줄도 몰랐다"**는 것이다. 정책도 함수 호출도 전부 공식 권고와 어긋나 있었는데 아무도 몰랐다.

그리고 **"최신인지 확인해라"라는 지시는 안 먹힌다.** AI는 확인하지 않고 기억으로 짠다. 그래서 지시가 아니라 **절차**로 적는다 — 아래를 실제로 실행한다.

**① 참조 구현을 받아와 그대로 둔다** **[공식]**

`supabase/supabase` 저장소의 `examples/auth/nextjs/lib/supabase/`에서 세 파일을 받아온다.

| 파일 | 무엇 |
|---|---|
| `proxy.ts` | 미들웨어 정본 |
| `client.ts` | 브라우저 클라이언트 정본 |
| `server.ts` | 서버 클라이언트 정본 |

**문서 사이트가 저장소 샘플을 끌어다 쓰는 구조라 샘플이 먼저다.** 문서 페이지에 적힌 코드와 다르면 저장소 쪽이 정본이다.

**② AI용 공식 규칙 파일도 같이 받아 읽는다** **[공식]**

`examples/prompts/nextjs-supabase-auth.md`와 `examples/prompts/database-rls-policies.md` — **Supabase가 AI에게 주라고 직접 만든 규칙 파일**이다. 사람이 요약해 옮기지 말고 받은 그대로 읽는다.

**③ 어긋나는 자리에만 주석을 남긴다** **[우리 결정]**

우리 사정 때문에 공식과 다르게 간 줄에만 이 모양으로 적는다.

```
// 공식은 X, 우린 Y, 이유는 Z
```

기준선 설명 문서는 만들지 않는다 — **코드가 정본**이다.

> **⚠ 위 경로는 오늘(2026-08-20) 기준이다.** 없으면 저장소에서 찾아라. 이 판은 자주 바뀐다 — `auth-helpers`는 폐기됐고, 미들웨어 정본은 `getUser()`에서 `getClaims()`로 옮겨갔다.

## 2. 역할 표를 처음부터 만든다

**근거는 "모든 프로젝트에 역할이 둘 이상 필요하다"가 아니다.** 그건 확인된 게 아니다. 근거는 **추가 부담이 작다**는 것이다 — 실제 부담은 RLS 규율(모든 표에 RLS·grant 회수·정책 4개로 쪼개기·테스트)인데, 그건 역할을 나누든 안 나누든 **공식이 요구하는 필수**다. 그 위에 역할 구조를 얹는 비용은 표 하나와 함수 하나뿐이다. **[우리 결정]**

```sql
create type app_role as enum ('operator');   -- 늘어나면 값만 추가
create table user_roles (
  user_id uuid references auth.users on delete cascade not null,
  role app_role not null,
  unique (user_id, role)
);
alter table user_roles enable row level security;   -- 이 표도 예외 없음
```

### 2.1 규칙 넷

**규칙 1 — 역할은 `user_roles` 표에 담는다.** 불리언 컬럼(`is_operator`)으로 시작하지 않는다. 스위치는 예·아니오뿐이라 셋째 역할이 생기면 컬럼을 또 만들어야 하고, 한 사람이 여러 역할을 갖지도 못한다. 표면 enum 값 추가로 끝난다. **[우리 결정]**

**규칙 2 — 일반 회원은 행을 만들지 않는다.** `user_roles`에는 **특별한 역할만** 담는다. 회원 전원이 "나는 회원입니다" 행을 하나씩 갖는 건 같은 말의 반복이고, `to authenticated`가 이미 "로그인한 사람"을 걸러준다. 공식 예제도 `admin`·`moderator`만 담는다. **[공식]**

**규칙 3 — 정책은 신분이 아니라 권한 이름으로 묻는다.** ← **넷 중 제일 중요하다** **[우리 결정]**

원칙과 이유는 `security-baseline.md` 2부에 있다. 여기선 실제로 만들 모양만 적는다.

```sql
-- 판정 함수: 권한 이름을 받아 예/아니오를 돌려준다
create function public.authorize(required text) returns boolean
language plpgsql stable security definer set search_path = ''
as $$
declare ok boolean;
begin
  select case required
           when 'reports.resolve' then exists (
             select 1 from public.user_roles
             where user_id = (select auth.uid()) and role = 'operator'
           )
           else false
         end into ok;
  return coalesce(ok, false);
end;
$$;

revoke execute on function public.authorize(text) from public;
grant   execute on function public.authorize(text) to authenticated;

-- 정책: 문에 신분이 아니라 권한 이름을 쓴다
create policy reports_resolve on public.reports
  for update to authenticated
  using ( (select public.authorize('reports.resolve')) );
```

**규칙 4 — 매핑은 함수 안 `case`로 시작하고, 관리가 필요해지면 표로 옮긴다.** 위 `case` 갈래를 `role_permissions` 표 조회로 바꾸는 건 `create or replace function` 하나다. **규칙 3을 지켰으면 이때 정책은 한 줄도 안 바뀐다.** **[우리 결정]**

**바깥 모양(계약)은 처음부터 고정하고, 안쪽 구현은 자라게 둔다** — 이게 규칙 3·4의 요지다.

### 2.2 미루는 것 셋

| 미루는 것 | 왜 |
|---|---|
| `role_permissions` 매핑 표 | 역할이 적을 땐 함수 안 `case`가 더 단순하다. 나중에 붙이기 싸다 (규칙 4) |
| Custom Access Token Auth Hook (JWT에 역할 심기) | 아래 함정 |
| 역할 부여 화면 | 6단계 범위 밖. 부여는 마이그레이션·수동 경로로 |

**Auth Hook을 미루는 진짜 이유 — 공식이 안 적어둔 함정** **[우리 결정]**: JWT에 역할을 심으면 **역할을 바꿔도 토큰을 새로 받기 전까진 안 바뀐다.** 운영자 권한을 회수했는데 옛 토큰으로 계속 처리되는 상태가 생긴다. 역할이 적으면 **표를 직접 읽는 `security definer` 함수가 더 단순하고 즉시 반영된다.** 성능 때문에 필요해지면 그때 함수 안만 바꾸면 된다.

### 2.3 표를 만들 때 같이 정해둘 것

**① 역할 표 자신에게도 RLS를 건다.** `user_roles`는 권한의 근거라 오히려 더 조여야 한다. 셋을 정한다 **[공식]**:

| 정할 것 | 흔한 답 |
|---|---|
| 누가 읽나 | 자기 줄만? 운영자는 전부? |
| 누가 쓰나 | 앱에서는 아무도. 부여는 별도 경로 |
| 비로그인은 | grant 자체를 안 준다 |

**② 권한 이름은 `표.동작` 꼴로 통일한다.** 정책에 쓰는 이름(표 단위 읽기·쓰기)과 RPC 이름(행동)을 섞으면 **정책에서 존재하지 않는 권한을 부르게 된다.** 정책에서 실제로 쓸 것만 만든다. **[우리 결정]**

**③ `auth.uid()`를 직접 쓸지 프로젝트 헬퍼를 쓸지 한 줄로 정해두고 일관되게 간다.** 판정 함수 안에서는 `auth.uid()`, 정책 안에서는 헬퍼 — 이렇게 갈리면 다음 사람이 매번 고민한다. **[우리 결정]**

**④ 기본 키를 둘지 정한다.** `unique (user_id, role)`만으로도 동작하지만, 행을 하나씩 가리켜야 할 일(부여 취소 화면 등)이 생기면 대리 키가 필요하다. **미루기로 했으면 미룬다고 적어둔다.** **[우리 결정]**

**⑤ ⚠ 불리언 컬럼에서 옮겨오는 경우, 데이터 이관을 같은 마이그레이션에 넣는다.** 구조만 바꾸고 기존 값을 안 옮기면 **권한이 통째로 사라지는데 에러가 안 난다.** **[우리 결정]**

```sql
insert into public.user_roles (user_id, role)
select id, 'operator' from public.profiles where is_operator;
```

## 3. 권한은 테스트로 고정한다

공식이 강하게 권하는 자리다 — Supabase는 pgTAP(`supabase test db`) 방식을 안내한다. **[공식]**

**① 최소 셋은 반드시 쓴다.** 표를 전부 다 쓰면 유지가 안 되니 범위를 셋으로 고정한다.

1. 공개여야 하는 것이 **비로그인에게 보이는가**
2. 역할 표가 **남에게 안 보이는가**
3. 권한이 필요한 일이 **일반 회원에게 막히는가**

**② 정체성 전환은 두 줄을 다 넣는다.** `auth.uid()` 구현이 버전에 따라 둘 중 하나를 보므로 둘 다 넣는 게 안전하다. **[우리 결정]**

```sql
set local role authenticated;
set local request.jwt.claim.sub = '<uuid>';
set local request.jwt.claims    = '{"sub":"<uuid>"}';
```

**③ ⚠ 거절 판정이 두 가지다 — 다르게 테스트해야 한다.** **[공식]**

| 무엇이 막았나 | 어떻게 나타나나 | 어떻게 검사하나 |
|---|---|---|
| grant 없음 | `42501` **에러가 난다** | 에러가 나는지 본다 |
| 정책이 걸렀음 | **에러 없이 빈 결과** | 결과 개수가 0인지 본다 |

이걸 모르면 **통과하는데 아무것도 안 검사하는 테스트**가 된다. 에러를 기다리는 검사에 정책 거름을 물리면 영원히 초록불이다.

**④ 문서에 "이 표는 공개"라고 적지 않는다 — 테스트가 그 기록이다.** **[우리 결정]** 글로 적으면 코드와 어긋나는 날이 온다. 테스트로 적어두면 실수로 닫았을 때 깨지고, 실수로 열어도 "공개 아님" 테스트가 깨진다.

```sql
set local role anon;
select is(count(*), 8::bigint, '비로그인이 공개 프로젝트를 본다') from public.eggs;
```

> **⚠ 남은 숙제 — CI 연결은 별도 작업이다.** `supabase test db`(pgTAP)를 돌리는 단계가 **하네스 CI 워크플로에 아직 없다.** 규칙만 있고 실행 장치가 없으면 테스트가 안 돌아도 아무도 모른다. 이 프로젝트에서 테스트를 썼다면 **로컬에서 직접 돌려 통과를 확인**하고, CI에 붙이는 건 하네스 쪽 별도 작업으로 남겨둔다.

## 4. 세션 층 — 라이브러리가 이미 하는 것을 다시 만들지 않는다

**① supabase-js가 이미 해주는 것** **[공식]**: 만료 90초 전 갱신 · 30초 타이머 · 요청 직전 재확인 · 동시 갱신 병합 · 복구 불가 시 `SIGNED_OUT` 발생.

**② 그래서 "만료 때문에 나는 401"은 라이브러리가 거의 다 막는다.** 남는 401은 서버 시계 어긋남·서명키 회전·사용자 삭제인데, **이건 갱신해도 대부분 또 실패한다.** 401을 받아 재시도하는 층은 **선택 항목이지 표준이 아니다** — 공식에 찬성도 반대도 없다. 붙이려면 재귀 방지·1회 제한·본문 재전송 판정 셋을 갖춘다. **[우리 결정]**

**③ 세션 상태를 앱이 따로 캐시하지 마라.** 라이브러리가 이미 캐시하고 있다. 없어도 될 층이 **"세션이 죽었는데 화면은 로그인처럼 보이는"** 버그를 낳는다. **[실측 1건]**

**④ 로그인 전에 입력을 받아도 된다.** 왕복 너머로 나르는 표준이 둘로 갈린다. **[공식]**

| 무엇을 | 어떻게 |
|---|---|
| **돌아갈 경로** | `redirectTo`에 `?next=`로 싣고, 콜백에서 `startsWith("/")`로 상대 경로인지 검증 (공식 예제 그대로) |
| **입력값 자체** | URL이 아니라 브라우저 저장소에 맡겼다가 콜백 이후 **한 지점에서만** 복구 |

**복구 지점이 둘 이상으로 흩어지면 이 패턴은 반드시 깨진다** — 저장과 복구를 각각 한 함수에만 둔다.

**⑤ ⚠ `sessionStorage`는 쓰지 마라 — 탭 단위다.** **[실측 1건]** 모바일 인앱 브라우저처럼 OAuth가 새 탭이나 외부 앱으로 튀면 값이 통째로 사라진다. `localStorage`나 짧은 만료를 건 쿠키를 쓴다.

**⑥ 돌아올 주소에서는 모달 파라미터만 지운다.** **[실측 1건]** `?modal=login`이 살아 돌아와 로그인 창이 다시 열리는 걸 막으려고 **쿼리 전체를 버리면 `?step=3` 같은 멀쩡한 화면 상태까지 잃는다.**

```ts
url.searchParams.delete(MODAL_PARAM);   // 이 한 줄이면 나머지 쿼리는 산다
```
