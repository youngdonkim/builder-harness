## 1. 단계 목표

이 단계의 목표는 **아이디어의 초기 맥락(필수 입력 4개)을 사용자에게서 걷고, `user-scenario-writer` 서브 에이전트에 위임해 영화 시나리오 형식의 유저 스토리를 만드는 것**이다. 산출물은 `mvp/user-story.md` 한 파일 — 위임 프롬프트 그대로 입력 4개 원문(§4.1)과 에이전트가 생성한 시나리오 본문을 담는다.

이 산출물은 **2단계(InformationArchitecture)의 도출 원천이자 3단계(Prototype)의 입력, 4단계(DemoValidation)의 자동 도출 원천**이다 — 2단계는 이 문서에서 화면 인벤토리·객체 지도를 뽑아내고(`2-information-architecture.md`), 3단계는 그 인벤토리와 이 문서를 함께 Claude Design에 입력해 목업의 톤·문구를 잡고(`3-prototype.md`), 4단계는 여기서 아이디어 한두 문장을 도출해 사용자에게 다시 묻지 않는다 (`4-demo-validation.md` §2.2). 뒤쪽의 5단계(MarketResearch)도 이 문서의 대안·타겟 정보를 조사의 출발점 중 하나로 삼는다 (`5-market-research.md`). 목표를 이뤘는지는 §3 완료 체크리스트로 판정한다.

## 2. 진행 절차

### 2.1 단계 시작 — 이번 단계가 할 일을 안내한다 (7단계의 첫 단계라 이전 정리는 없음)

이 단계는 7단계의 첫 단계라 "이전 단계까지 정리된 내용"이 없다 — 대신 사용자에게 **왜 유저 스토리부터 쓰는지**를 짧게 설명하는 것으로 시작한다.

설명 골자 — 그대로 또는 풀어서 전달:

> 서비스를 영화 한 편처럼 구체적인 그림으로 먼저 그려두면, 이후 단계에서 AI에게 넘길 맥락의 해상도가 올라가.

이미 `mvp/user-story.md`가 있으면(스킬 중간 재실행 등) 읽고 §3 체크리스트로 검증해 부족한 부분만 보완한다 — 처음부터 다시 받지 않는다.

### 2.2 필수 입력 4개 받기 (인터뷰 모드)

이 절차는 SKILL.md §1.5의 **인터뷰 모드** — 사용자의 암묵지(아직 아무도 모르는 자기 아이디어)가 소재라 상호작용 자체가 목적. 아래 4개를 그대로 또는 풀어서 사용자에게 안내:

```
서비스를 시작하기 전에 네 가지만 알려줘:

1. 서비스 이름과 한 줄 정의
2. 타겟 — 누가, 어떤 상황에서
3. 현재의 대안과 그 불편함 (문제)
4. 해결책의 핵심 아이디어
```

**입력 1·2는 CLAUDE.md로 미리 채운다** — 프로젝트 CLAUDE.md 상단에 프로젝트 정의(서비스 이름·한 줄 정의·타겟)가 이미 있으면(project-init 인터뷰가 채워둠), 입력 1·2를 그 내용으로 채워 보여주고 맞는지 확인만 받는다. 새로 묻는 건 3·4다. 타겟의 "어떤 상황에서"가 CLAUDE.md에 없으면 그 부분만 보충해 받는다.

코칭 규칙 (SKILL.md §1.4):

- **빠짐·모호는 배치로 되묻기** — 하나씩 직렬로 왕복하지 말고 모자란 항목 2~4개를 한 턴에 묶어 확인.
- **"잘 모르겠어"는 정상 답** — AI가 후보 2~3개 제시하고 사용자가 골라 다듬게 한다.

**4개가 확정되기 전에는 에이전트에 위임하지 않는다.** `user-scenario-writer`는 빠진 입력을 임의로 가정해 채우는 폴백을 갖고 있지만, 그건 강행 진입용 안전판이지 기본 경로가 아니다 — 4개 다 사용자 확인을 받은 뒤에만 §2.3으로 넘어간다.

### 2.3 에이전트 위임

입력 4개가 확정되면 `user-scenario-writer` 서브 에이전트를 호출해 위임한다. 위임 프롬프트에 반드시 포함할 것:

- **(a) 확정된 입력 4개 원문 전부** — 요약·재구성 없이 사용자가 확인한 그대로 전달.
- **(b) 저장 경로 명시** — `mvp/user-story.md` (에이전트 기본 경로와 동일 — `.claude/agents/user-scenario-writer.md` §출력).
- **(c) 문서 상단 `# 입력 (확정)` 섹션 보존 지시** — 4개 입력 원문을 문서 최상단에 그 섹션으로 남기라고 명시. 4단계(DemoValidation)가 여기서 아이디어를 도출한다 (`4-demo-validation.md` §2.2).

이미 `mvp/user-story.md`가 있으면 에이전트 자체 규칙대로 `user-story-v2.md`처럼 버전을 올려 저장된다 — 스킬 쪽에서 별도 처리 안 함.

### 2.4 결과 보고·리뷰

에이전트가 반환하는 세 가지 — **저장 경로 · 로그라인(logline — 서비스의 정서를 담은 한 줄 요약) · 장면 목록** — 를 사용자에게 그대로 보여주고 피드백을 받는다.

이건 SKILL.md §1.5의 **초안 모드** — AI(서브 에이전트)가 산출물을 완주해서 만든 뒤 완성본으로 한 번에 리뷰받는 작업이다. 중간에 장면 하나하나 승인받지 않는다. 수정 요청이 오면 무엇을 바꿀지 구체화해 에이전트 재위임으로 반영하고, 다시 세 가지를 보여준다.

## 3. 완료 체크리스트

- [ ] **필수 입력 4개 확정** (§2.2) — 사용자 확인 완료, 배치 되묻기로 빠짐·모호 해소.
- [ ] **`user-story.md` 저장** (§2.3) — `mvp/`, 상단 `# 입력 (확정)` 섹션에 입력 원문 4개 포함.
- [ ] **로그라인·장면 목록 사용자 확인** (§2.4) — 수정 요청 있으면 재위임까지 반영 완료.
- [ ] **디자인 방향 절 포함** — 3단계 권장 프롬프트가 이 절을 "시각 디자인의 원천"으로 가리킨다. 없으면 디자인 도구가 씬 묘사를 문자 그대로 그려 밋밋한 목업이 나온다 (실제 사고 있었음).

### 3.1 다음 단계 핸드오프

산출물 저장 직후, 매 단계 공통대로 **`/clear` 후 `/idea-to-mvp` 재호출**을 권장한다 (SKILL.md §3.2). 다음 단계인 2단계(InformationArchitecture)는 이 문서를 읽어 화면 인벤토리·객체 지도·상태 매트릭스를 뽑아낸다 (`2-information-architecture.md`) — 유저 스토리는 주인공 한 명의 성공 경로 하나라, 거기서 안 그려진 화면(빈 상태·실패 분기·설정 등)까지 2단계가 채워 서비스 전체 지도를 만든다. 이어지는 3단계(Prototype)는 그 인벤토리와 `user-story.md`를 함께 외부 Claude Design에 입력해 목업을 만들고, 이를 리액트로 옮겨 워킹 프로토타입으로 배포한다 (`3-prototype.md`). 아이디어 한두 문장은 4단계(DemoValidation)가 이 문서에서 **직접 도출**한다 (`4-demo-validation.md` §2.2).

## 4. 산출물 스펙

위치: 프로젝트 루트의 `mvp/user-story.md`

본문 구조는 `user-scenario-writer` 에이전트의 필수 구조 — 타이틀+로그라인 · 주인공 페르소나 · 장면(S#) 구성 · "시나리오에 심어둔 UX 장치 정리" 표 · 디자인 방향 — 를 그대로 따른다 (`.claude/agents/user-scenario-writer.md` §필수 구조). 여기서 중복 정의하지 않는다. 이 스킬이 그 위에 추가로 요구하는 건 문서 최상단 `# 입력 (확정)` 섹션 하나뿐 — §2.3(c).

### 4.1 `# 입력 (확정)` 섹션 템플릿

```markdown
# 입력 (확정)

1. **서비스 이름과 한 줄 정의**: {§2.2에서 받은 원문}
2. **타겟**: {누가, 어떤 상황에서}
3. **현재의 대안과 불편함 (문제)**: {원문}
4. **해결책의 핵심 아이디어**: {원문}
```

이 뒤로 `user-scenario-writer`가 생성한 시나리오 본문이 이어진다.

## 5. 사용자 응대 톤

- **톤**: SKILL.md §1.3 따름 — 반말·친근·짧게.
- **흐름**: 필수 입력 4개 받기(§2.2) → 에이전트 위임(§2.3) → 결과 리뷰(§2.4). 단계 건너뛰지 않기 — 특히 입력 4개가 다 확정되기 전에 위임부터 하는 점프 금지.
- **솔루션 함정 주의**: 입력 ④(해결책의 핵심 아이디어)는 받되, 그 검증은 4단계(DemoValidation) 인터뷰의 몫이다. 유저 스토리는 아직 검증 전의 그림일 뿐 — 사용자가 "이 시나리오대로 확정됐다"고 오해하지 않도록, 결과 리뷰(§2.4) 때 "이건 이후 인터뷰 단계에서 검증할 가설을 구체화한 그림"이라고 짚어준다.
- **시나리오 품질 불만**: 사용자가 "장면이 별로다", "와닿지 않는다" 하면 에이전트한테 "다시 잘 써줘"만 던지지 말고, 입력 4개 중 무엇이 모호했는지 되짚어 더 구체화한 뒤 재위임한다.
