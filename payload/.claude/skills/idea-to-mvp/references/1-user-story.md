## 1. 단계 목표

이 단계의 목표는 **아이디어의 초기 맥락(필수 입력 — 단면 4개, 양면 시장이면 5개)을 사용자에게서 걷고, `user-scenario-writer` 서브 에이전트에 위임해 영화 시나리오 형식의 유저 스토리를 만드는 것**이다. **단계는 하나인데 산출물은 두 파일이다**:

- **`mvp/user-story.md` — UX 서사.** 입력 원문(§4.2) + 로그라인·주인공·장면(S#) + UX 장치 표 + 프로토타이핑 우선순위 + 화면 묘사를 읽는 법·힘줄 곳. 에이전트가 쓴다.
- **`mvp/design-brief.md` — 디자인·콘텐츠 정본.** 브랜드 인상 · 보이스 앤 톤 · 「문자 그대로」 고정 문구 표 · 확정 브랜드 자산 · UI 패턴 지정 · 주 사용 맥락 · 피할 것 · 모션 · 접근성 바닥선 · 가치 우선순위. **메인 클로드가 직접 쓰고 제자리에서 누적한다** (§4.3).

**왜 나누나.** 하나였을 땐 두 문제가 났다. 첫째, 서사는 1↔2 순환에서 자주 다시 쓰이는데(실측: v8까지) 그때마다 안 바뀐 브랜드 확정값까지 전량 다시 쓰여 매번 변형 위험을 지불했다. 둘째, 장면 인용문과 고정 문구 표가 같은 사실을 따로 적다 서로 어긋난 사고가 실제로 났다. 그래서 **변경 주기로 갈랐다** — 재생성마다 다시 쓰는 것은 서사에, 확정돼 쌓이는 것은 브리프에. 파일이 커져 소비자마다 몇 번씩 나눠 읽던 문제(실측: 1,373줄)도 함께 풀린다.

**정본 경계는 파일 경계다.** 화면 문구·미감·UI 패턴의 정본은 브리프 하나이고, 스토리의 장면 묘사·인용 블록은 요소의 존재·위계·정서를 보여주는 **예시**다. 두 파일이 어긋나면 브리프가 이긴다. 이 선언을 두 파일 머리에 각각 박는다 (§4.1).

**바로 다음 단계는 2단계(Mockup)다.** 2단계는 `user-story.md`에서 기능 목록을 뽑고, 스토리·기능 목록·브리프 셋을 입력으로 목업 캔버스를 만든다 (`2-mockup.md`). 그 캔버스를 보다 이 문서들의 결함이 드러나면 되돌아와 고친다 — 그래서 둘 다 2단계 왕복이 수렴할 때까지 살아 있는 산출물이다 (§2.5).

2단계를 지나도 두 파일은 뒤 단계로 계속 이어진다 — 3·4·5·7단계가 어떻게 쓰는지는 SKILL.md §2.1 단계 릴레이 표에 있다. 목표를 이뤘는지는 §3 완료 체크리스트로 판정한다.

## 2. 진행 절차

### 2.1 단계 시작 — 이번 단계가 할 일을 안내한다 (7단계의 첫 단계라 이전 정리는 없음)

이 단계는 7단계의 첫 단계라 "이전 단계까지 정리된 내용"이 없다 — 대신 사용자에게 **왜 유저 스토리부터 쓰는지**를 짧게 설명하는 것으로 시작한다.

설명 골자 — 그대로 또는 풀어서 전달:

> 서비스를 영화 한 편처럼 구체적인 그림으로 먼저 그려두면, 이후 단계에서 AI에게 넘길 맥락의 해상도가 올라가.

이미 `mvp/user-story.md`(또는 `mvp/design-brief.md`)가 있으면(스킬 중간 재실행 등) 읽고 §3 체크리스트로 검증해 부족한 부분만 보완한다 — 처음부터 다시 받지 않는다.

### 2.2 필수 입력 받기 (인터뷰 모드)

받을 입력은 **기본 4개**다. 파는 쪽·사는 쪽이 따로 있는 **양면 시장**일 때만 갈라진다 — 그건 아래 "양면 시장이면 여기서 갈린다"에서 다룬다.

이 절차는 SKILL.md §1.5의 **인터뷰 모드** — 사용자의 암묵지(아직 아무도 모르는 자기 아이디어)가 소재라 상호작용 자체가 목적. 아래 4개를 그대로 또는 풀어서 사용자에게 안내:

```
서비스를 시작하기 전에 네 가지만 알려줘:

1. 서비스 이름과 한 줄 정의
2. 타겟 — 누가, 어떤 상황에서
3. 현재의 대안과 그 불편함 (문제)
4. 해결책의 핵심 아이디어
```

**입력 1·2는 CLAUDE.md로 미리 채운다** — 프로젝트 CLAUDE.md 상단에 프로젝트 정의(서비스 이름·한 줄 정의·타겟)가 이미 있으면(project-init 인터뷰가 채워둠), 입력 1·2를 그 내용으로 채워 보여주고 맞는지 확인만 받는다. 새로 묻는 건 3·4다. 타겟의 "어떤 상황에서"가 CLAUDE.md에 없으면 그 부분만 보충해 받는다.

코칭 규칙 (SKILL.md §1.4):

- **빠짐·모호는 배치로 되묻기** — 하나씩 직렬로 왕복하지 말고 모자란 항목 2~4개를 한 턴에 묶어 확인.
- **"잘 모르겠어"는 정상 답** — AI가 후보 2~3개 제시하고 사용자가 골라 다듬게 한다.

**양면 시장이면 여기서 갈린다** — 쓰는 사람이 두 종류이고 **한쪽이 있어야 다른 쪽이 쓸 수 있는** 서비스가 양면 시장이다 (중고 거래 — 파는 사람·사는 사람 / 배달 — 가게·손님 / 강의 마켓 — 강사·수강생). 판별은 **입력 1(한 줄 정의)에서 감지**한다. 질문을 하나 더 늘리지 말고, 위 배치 되묻기에 얹어 확인만 받는다:

```
이거 쓰는 사람이 두 종류 맞지? — {A 역할}이랑 {B 역할}.
맞으면 2·3·4번은 양쪽 각각 받을게.
```

- **단면이면** 위 4개 그대로다. 아무것도 안 바뀐다.
- **양면이면** 2·3·4를 역할별로 받고, 입력 5를 하나 더 받는다:

```
양쪽이 있으니 이렇게 받을게:

2. 타겟 — {A 역할}은 누가·어떤 상황에서 / {B 역할}은 누가·어떤 상황에서
3. 현재의 대안과 그 불편함 — {A 역할}은 지금 어떻게 때우는지 / {B 역할}은 지금 어떻게 때우는지
4. 해결책의 핵심 아이디어 — {A 역할}에게 뭘 해주는지 / {B 역할}에게 뭘 해주는지
5. 초기 공급을 어떻게 채울 건가 — 어느 쪽부터 채울지, 그 한쪽을 직접 채울 건지
```

역할이 둘이어도 **되묻기는 한 턴에 묶는다** — 왕복을 두 배로 늘리지 않는다. 칸이 6개(2·3·4 × 두 역할)라 한꺼번에 답하기 버거워하면 "2·3번 먼저, 4·5번 다음"처럼 두 턴까지만 나눈다.

**왜 2·3·4를 쪼개나** — 파는 쪽 고민과 사는 쪽 고민은 아예 다른 얘기다. 한쪽만 적혀 있으면 화면도 그 한쪽만 생기고, 결국 7단계에서 그 한쪽만 검증하게 된다.

**왜 5번을 묻나 — "닭이 먼저냐 달걀이 먼저냐"** — 양면 시장의 제일 큰 위험은 한쪽이 없으면 다른 쪽도 안 온다는 것이다. 살 사람이 없으면 파는 사람이 안 올리고, 올라온 게 없으면 살 사람이 안 온다. 그래서 초기엔 보통 **한쪽을 만드는 사람이 직접 채운다** — 물건을 직접 구해다 올리거나, 공급자를 발로 뛰어 섭외하거나, 한 동네·한 학교로 범위를 좁혀 양쪽을 동시에 채우거나. 이건 조사로 알아낼 일이 아니라 만드는 사람이 정할 일이라 여기서 묻는다. "잘 모르겠어"면 위 코칭 규칙대로 후보 2~3개를 제시해 고르게 한다.

**입력이 다 확정되기 전에는 에이전트에 위임하지 않는다** (단면 4개·양면 5개). `user-scenario-writer`는 빠진 입력을 임의로 가정해 채우는 폴백을 갖고 있지만, 그건 강행 진입용 안전판이지 기본 경로가 아니다 — 전부 사용자 확인을 받은 뒤에만 §2.3으로 넘어간다.

### 2.3 산출물 두 개 만들기 — 브리프 초판 + 에이전트 위임

순서가 있다. **브리프 초판을 먼저 만들고, 그 다음 에이전트에 위임한다** — 에이전트가 브리프를 읽어 확정을 지켜야 하기 때문이다.

**(1) `mvp/design-brief.md` 초판을 메인 클로드가 직접 쓴다.** §4.3 템플릿 그대로 만들고, **인터뷰(§2.2)에서 이미 나온 확정만** 해당 칸에 날짜와 함께 채운다. 나머지는 전부 `추후 결정`으로 둔다 — 여기서 브랜딩 인터뷰를 새로 열지 않는다. 서체·로고·마스코트가 `추후 결정`인 채로 다음 단계에 가는 게 정상이다.

**(2) `user-scenario-writer` 서브 에이전트에 위임한다.** 위임 프롬프트에 반드시 포함할 것:

- **(a) 확정된 입력 원문 전부** — 요약·재구성 없이 사용자가 확인한 그대로 전달 (단면 4개·양면 5개, 양면이면 2·3·4의 역할별 답 전부).
- **(b) 저장 경로 명시** — `mvp/user-story.md` (에이전트 기본 경로와 동일 — `.claude/agents/user-scenario-writer.md` §출력).
- **(c) 문서 상단 `# 입력 (확정)` 섹션 보존 지시** — 입력 원문을 문서 최상단에 그 섹션으로 남기라고 명시. 뒤 단계들이 여기를 아이디어의 출발점으로 읽는다 (3단계 경쟁자 조사, 7단계 최종 확정).
- **(d) 양면이면 그 사실과 두 역할 이름** — 어느 쪽이 수요(사는 쪽)이고 어느 쪽이 공급(파는 쪽)인지 적어 넘긴다. 에이전트는 주인공을 수요 쪽으로 잡고 반대편 장면을 2~3개 그린다 (`.claude/agents/user-scenario-writer.md` §필수 구조).
- **(e) 브리프 경로와 읽기 전용 지시** — `mvp/design-brief.md`를 먼저 읽고 확정 사항을 지키되 **쓰지는 말라**고 명시. 브리프에 올릴 것은 최종 메시지에 제안으로 담아 돌려보내게 한다.
- **(f) 두 파일 머리의 정본 선언** — `user-story.md` 머리에 §4.1의 선언 문단을 넣으라고 명시.

이미 `mvp/user-story.md`가 있으면 에이전트 자체 규칙대로 `user-story-v2.md`처럼 버전을 올려 저장된다 — 스킬 쪽에서 별도 처리 안 함. **`design-brief.md`는 반대다** — 판올림 없이 같은 파일을 제자리에서 고쳐 누적한다 (SKILL.md §3).

### 2.4 결과 보고·리뷰

에이전트가 반환하는 다섯 가지 중 앞의 셋 — **저장 경로 · 로그라인(logline — 서비스의 정서를 담은 한 줄 요약) · 장면 목록** — 을 사용자에게 그대로 보여주고 피드백을 받는다.

이건 SKILL.md §1.5의 **초안 모드** — AI(서브 에이전트)가 산출물을 완주해서 만든 뒤 완성본으로 한 번에 리뷰받는 작업이다. 중간에 장면 하나하나 승인받지 않는다. 수정 요청이 오면 무엇을 바꿀지 구체화해 에이전트 재위임으로 반영하고, 다시 세 가지를 보여준다.

**나머지 둘은 브리프로 간다.** 에이전트가 함께 돌려주는 **보이스·톤 확인 요청**과 **브리프에 올릴 제안 목록**(새로 판정한 고정 문구·UI 패턴 지정 제안·확정 헤드카피 등)을 사용자에게 묻고, **확인받은 것만** 메인 클로드가 `design-brief.md`의 해당 칸에 지위(`사용자 확정`)와 날짜를 붙여 적는다. 확인 못 받은 건 `가정` 지위로 남기거나 `추후 결정`으로 둔다.

**에이전트가 "브리프와 어긋난다"고 보고하면** 임의로 한쪽을 고르지 말고 사용자에게 무엇이 어떻게 어긋나는지 보여주고 어느 쪽이 맞는지 확인받는다 — 브리프를 고칠 일이면 브리프를 고치고, 스토리를 고칠 일이면 재위임한다.

### 2.5 목업에서 되돌아온 경우

**2단계 Mockup에서 이 단계 산출물의 결함이 드러나면 이 절차로 되돌아온다.** 목업 캔버스로 화면을 늘어놓고 보면 글로만 읽을 땐 안 보이던 것들이 드러난다. 돌아오는 길은 결함의 성격 따라 둘로 갈린다:

- **이야기 결함**(사족 문구, 장면과 장면 사이에 빠져 있던 화면, 성립하지 않는 전제) → `user-scenario-writer` 에이전트를 **재위임**해 `user-story.md`를 고친다 (§2.3(2)와 같은 방식, 무엇을 왜 바꾸는지를 위임 프롬프트에 적는다). 새 판본은 `user-story-v2.md`처럼 번호가 올라가고 옛 판본은 남는다 (SKILL.md §3).
- **문구·미감 확정**(눌러보다 "이 버튼 이름은 이걸로 가자", "메인 컬러는 이걸로") → 재위임이 아니라 **메인 클로드가 `design-brief.md`의 해당 칸을 제자리에서 고친다.** 날짜와 `사용자 확정` 지위를 붙인다. 판올림하지 않는다.

(기능·범위 문제는 여기가 아니라 `feature-list.md` 몫이다 — `2-mockup.md` §2.5의 3갈래 라우팅 참고.)

브리프를 고쳤으면 다음 재위임 때 에이전트가 그 확정을 읽어 장면 인용을 맞춘다 — 스토리와 브리프가 어긋난 채로 남지 않게 하는 장치다.

고친 뒤에는 2단계로 돌아가 기능 목록과 캔버스를 다시 맞춘다. 이 왕복이 **1↔2 순환**이고, 4단계 IA가 이 문서들을 읽어 가는 순간 순환이 끝나며 두 파일 다 기록으로 얼려진다.

`design-brief.md`는 이 스킬이 통째로 정의한다 — 골격은 §4.3.

### 4.1 두 파일의 정본 선언 (둘 다 필수)

두 파일 머리에 각각 한 단락씩 박는다. 서로를 가리키는 상호 참조라 **한쪽만 넣으면 안 된다** — 어느 파일을 먼저 연 사람이든 자기가 지금 뭘 보고 있는지 알아야 한다.

`user-story.md` 머리 (제목 바로 아래, `# 입력 (확정)` 앞):

```markdown
> **이 문서의 자리** — 이 문서는 UX 서사(사용자 여정)의 정본입니다. 화면 문구·미감(색·서체·모션)·UI 패턴의 정본은 `mvp/design-brief.md`입니다. 여기 장면 속 화면 묘사와 인용 블록은 **어떤 요소가 있고, 위계가 어떻고, 어떤 정서인지를 보여주는 예시**이지 문구·배치의 스펙이 아닙니다. 두 문서가 어긋나면 **브리프가 이깁니다** — 어긋남을 발견하면 조용히 한쪽을 고르지 말고 결함으로 보고해 주세요 (1↔2 순환에서 고칠 대상입니다).
```

`design-brief.md` 머리 (§4.3 템플릿에 이미 들어 있다):

```markdown
> **이 문서의 자리** — 이 문서는 화면 문구·미감(색·서체·모션)·UI 패턴의 정본이자 **결정 대장(ledger — 확정된 결정을 날짜와 함께 쌓아 두는 장부)** 입니다. 사용자 여정·장면의 정본은 `mvp/user-story.md`이고, 거기 적힌 화면 묘사·인용 문구는 예시이지 문구의 스펙이 아닙니다. 두 문서가 어긋나면 **이 문서가 이깁니다** — 어긋남을 발견하면 조용히 한쪽을 고르지 말고 결함으로 보고해 주세요.
>
> **갱신 규칙** — 판올림(`-v2`)을 하지 않습니다. 확정이 나올 때마다 해당 칸을 제자리에서 고쳐 누적합니다. 뒤집힌 결정은 지우지 않고 새 확정이 대체한다고 적습니다. 쓰는 사람은 메인 클로드입니다.
```

### 4.2 `# 입력 (확정)` 섹션 템플릿

**단면(기본)**:

```markdown
# 입력 (확정)

1. **서비스 이름과 한 줄 정의**: {§2.2에서 받은 원문}
2. **타겟**: {누가, 어떤 상황에서}
3. **현재의 대안과 불편함 (문제)**: {원문}
4. **해결책의 핵심 아이디어**: {원문}
```

**양면 시장**: 번호는 그대로 두고 2·3·4 안에서만 역할별로 갈라 적는다. 뒤 단계들이 이 섹션을 번호로 읽으니 번호 체계를 바꾸지 않는다.

```markdown
# 입력 (확정)

> 양면 시장 — 수요 쪽: {B 역할} / 공급 쪽: {A 역할}

1. **서비스 이름과 한 줄 정의**: {원문}
2. **타겟**
   - {A 역할}: {누가, 어떤 상황에서}
   - {B 역할}: {누가, 어떤 상황에서}
3. **현재의 대안과 불편함 (문제)**
   - {A 역할}: {원문}
   - {B 역할}: {원문}
4. **해결책의 핵심 아이디어**
   - {A 역할}: {원문}
   - {B 역할}: {원문}
5. **초기 공급을 채우는 방법**: {어느 쪽부터, 직접 채울지 — 원문}
```

이 뒤로 `user-scenario-writer`가 생성한 시나리오 본문이 이어진다.

### 4.3 `design-brief.md` 초판 템플릿

위치: `mvp/design-brief.md`. 열 개 절을 순서대로 담는다. **모든 칸에 값이 있어야 한다** — 안 정한 칸은 빈칸으로 두지 말고 `추후 결정`이라고 적는다. 빈칸은 빠뜨린 것인지 일부러 안 정한 것인지 구분이 안 된다.

**지위 칸 표기 네 가지**:

- `사용자 확정` — 사람이 확인해 준 것. 확정일 필수.
- `가정` — AI가 근거를 대고 제안했고 아직 확인 전.
- `기본값` — 하네스가 깔아 주는 바닥선. 프로젝트가 덮어써도 된다.
- `추후 결정` — 아직 안 정함. 디자인 도구는 이 칸에서만 자유롭게 정한다.

````markdown
# 디자인 브리프

_1단계 UserStory 산출물. 화면 문구·미감·UI 패턴의 정본._

> **이 문서의 자리** — (§4.1의 브리프용 선언 문단을 그대로)

## 1. 브랜드 인상

| 항목 | 내용 | 지위 | 확정일 |
|---|---|---|---|
| 브랜드 인상 한 줄 | 추후 결정 — 이 서비스가 유저에게 줘야 할 정서 한 줄 (예: "조용한 확신") | 추후 결정 | |

## 2. 보이스 앤 톤

**보이스(voice)** 는 브랜드가 말하는 성격이라 상황이 바뀌어도 안 변하고, **톤(tone)** 은 그 성격이 자리마다 입는 말투입니다. 자리마다 톤이 달라도 되지만 보이스를 벗어나면 안 됩니다.

| 항목 | 내용 | 지위 | 확정일 |
|---|---|---|---|
| 보이스 | 추후 결정 — 「브랜드 인상 한 줄」을 몇 줄로 편 것 | 추후 결정 | |
| 기본 말투 | 추후 결정 — 종결 어미(해요체·합쇼체·반말)와 사용자를 부르는 말 | 추후 결정 | |

자리별 톤:

| 자리 | 톤 | 예시 문구 | 지위 | 확정일 |
|---|---|---|---|---|
| 히어로 타이틀 | | | 추후 결정 | |
| 본문 안내 | | | 추후 결정 | |
| 에러 | | | 추후 결정 | |
| 완료 | | | 추후 결정 | |

(자리는 서비스에 맞게 더하거나 뺍니다.)

**보이스와 톤은 각각 따로 확정받습니다** — 기본값으로 톤을 깔지 않습니다.

## 3. 「문자 그대로」 고정 문구

확정돼서 다른 에이전트가 손대면 안 되는 문구입니다. 기능이 실리는 텍스트(메뉴·내비게이션, 동작 버튼, 카테고리명, 상태 표시, 폼 라벨)와 확정된 헤드카피·슬로건이 여기 옵니다. 판별 기준은 `user-scenario-writer` 에이전트 §작법 규칙의 「BX가 닿는 곳과 닿지 않는 곳」을 따릅니다.

| 자리 | 확정 문구 | 지위 | 확정일 |
|---|---|---|---|

**여기 오른 문구는 글자 단위로 그대로 씁니다** — 유저 스토리의 장면 인용, 목업 캔버스, 프로토타입 캔버스, 앱 코드 어디서나 조사·띄어쓰기·문장부호까지 같아야 합니다. 아직 하나도 없으면 "없음" 한 줄.

| 완전성 | 누르는 요소엔 눌렸다는 반응, 기다리는 동안엔 로딩 표시, 마우스로 쓰는 화면이면 올렸을 때 반응까지 빠짐없이. 어떤 모양으로 넣을지는 디자인 도구 자유 | 기본값 | |
| 금지 | 자동으로 넘어가는 배너는 광고 배너보다 느리게, 스크롤을 가로채는 효과는 쓰지 않기 | 기본값 | |

이 셋에 안 걸리는 자잘한 움직임은 디자인 도구 재량입니다 — 비워두는 재량이 아니라 채워 넣는 재량입니다.
````

## 5. 사용자 응대 톤

- **톤**: SKILL.md §1.3 따름 — 반말·친근·짧게.
- **흐름**: 필수 입력 받기(§2.2) → 브리프 초판 + 에이전트 위임(§2.3) → 결과 리뷰와 브리프 반영(§2.4). 단계 건너뛰지 않기 — 특히 입력이 다 확정되기 전에 위임부터 하는 점프 금지.
- **브리프를 브랜딩 인터뷰로 키우지 않는다** — `design-brief.md`는 결정을 담는 그릇이지 브랜딩 단계가 아니다. 서체·로고·마스코트가 `추후 결정`인 채로 다음 단계에 가는 게 정상이니, 칸을 채우려고 질문을 늘리지 않는다. 확정은 눌러보는 2단계에서 자연스럽게 쌓인다.
- **솔루션 함정 주의**: 입력 ④(해결책의 핵심 아이디어)는 받되, 그 검증은 마지막 7단계(MvpLaunch) 광고 실측의 몫이다. 유저 스토리는 아직 검증 전의 그림일 뿐 — 사용자가 "이 시나리오대로 확정됐다"고 오해하지 않도록, 결과 리뷰(§2.4) 때 "이건 앞으로 만들면서 다듬어갈 그림이고, 맞는지는 마지막에 실제 사용자 반응으로 확인한다"고 짚어준다.
- **시나리오 품질 불만**: 사용자가 "장면이 별로다", "와닿지 않는다" 하면 에이전트한테 "다시 잘 써줘"만 던지지 말고, 입력 중 무엇이 모호했는지 되짚어 더 구체화한 뒤 재위임한다.
