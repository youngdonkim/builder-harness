## 1. 단계 목표

이 단계의 목표는 **아이디어의 초기 맥락(필수 입력 — 단면 4개, 양면 시장이면 5개 — 과 사용자의 실제 경험)을 사용자에게서 걷고, `user-scenario-writer` 서브 에이전트에 위임해 영화 시나리오 형식의 유저 스토리를 만드는 것**이다. **단계는 하나인데 산출물은 두 파일이다**:

- **`mvp/user-story.md` — UX 서사.** 입력 원문(§4.2) + 로그라인·주인공·장면(S#) + UX 장치 표 + 프로토타이핑 우선순위 + 화면 묘사를 읽는 법·힘줄 곳. 에이전트가 쓴다.
- **`mvp/design-brief.md` — 디자인·콘텐츠 정본.** 브랜드 인상 · 보이스 앤 톤 · 「문자 그대로」 고정 문구 표 · 확정 브랜드 자산 · UI 패턴 지정 · 주 사용 맥락 · 피할 것 · 모션 · 접근성 바닥선 · 가치 우선순위. **메인 클로드가 직접 쓰고 제자리에서 누적한다** (§4.3).

**왜 나누나.** 하나였을 땐 두 문제가 났다. 첫째, 서사는 1↔2 순환에서 자주 다시 쓰이는데(실측: v8까지) 그때마다 안 바뀐 브랜드 확정값까지 전량 다시 쓰여 매번 변형 위험을 지불했다. 둘째, 장면 인용문과 고정 문구 표가 같은 사실을 따로 적다 서로 어긋난 사고가 실제로 났다. 그래서 **변경 주기로 갈랐다** — 재생성마다 다시 쓰는 것은 서사에, 확정돼 쌓이는 것은 브리프에. 파일이 커져 소비자마다 몇 번씩 나눠 읽던 문제(실측: 1,373줄)도 함께 풀린다.

**정본 경계는 파일 경계다.** 화면 문구·미감·UI 패턴의 정본은 브리프 하나이고, 스토리의 장면 묘사·인용 블록은 요소의 존재·위계·정서를 보여주는 **예시**다. 두 파일이 어긋나면 브리프가 이긴다. 이 선언을 두 파일 머리에 각각 박는다 (§4.1).

**바로 다음 단계는 2단계(Mockup)다.** 2단계는 `user-story.md`에서 기능 목록을 뽑고, 스토리·기능 목록·브리프 셋을 입력으로 목업 캔버스를 만든다 (`2-mockup.md`). 그 캔버스를 보다 이 문서들의 결함이 드러나면 되돌아와 고친다 — 그래서 둘 다 2단계 왕복이 수렴할 때까지 살아 있는 산출물이다 (§2.6).

2단계를 지나도 두 파일은 뒤 단계로 계속 이어진다 — 3·4·5·7단계가 어떻게 쓰는지는 SKILL.md §2.1 단계 릴레이 표에 있다. 목표를 이뤘는지는 §3 완료 체크리스트로 판정한다.

## 2. 진행 절차

### 2.1 단계 시작 — 이번 단계가 할 일을 안내한다 (7단계의 첫 단계라 이전 정리는 없음)

이 단계는 7단계의 첫 단계라 "이전 단계까지 정리된 내용"이 없다 — 대신 사용자에게 **왜 유저 스토리부터 쓰는지**를 짧게 설명하는 것으로 시작한다. 그 설명은 §2.2 첫 턴 질문의 첫머리에 들어 있다 — 따로 한 번 더 하지 않고 첫 턴 질문과 한 메시지로 낸다.

이미 `mvp/user-story.md`(또는 `mvp/design-brief.md`)가 있으면(스킬 중간 재실행 등) 읽고 §3 체크리스트로 검증해 부족한 부분만 보완한다 — 처음부터 다시 받지 않는다.

### 2.2 필수 입력과 실제 경험 받기 (인터뷰 모드)

받을 입력은 **기본 4개**다. 파는 쪽·사는 쪽이 따로 있는 **양면 시장**일 때만 갈라진다 — 그건 아래 "양면 시장이면 여기서 갈린다"에서 다룬다. **실제 경험은 따로 묻지 않는다** — 3번 안에서 「최근에 실제로 있었던 한 번」으로 함께 받는다. 4번까지 받으면 AI가 도메인 지식으로 빠진 기능 후보를 얹어 **기능 씨앗 목록**까지 만든다 (아래 「AI 도메인 보완 제안」).

이 절차는 SKILL.md §1.5의 **인터뷰 모드** — 사용자의 암묵지(아직 아무도 모르는 자기 아이디어)가 소재라 상호작용 자체가 목적이다.

**질문마다 「왜 묻는지」 한 줄을 붙인다.** 사용자가 질문의 쓸모를 알아야 제대로 답한다 — 이유 없이 "현재의 대안과 그 불편함"을 물으면 "이걸 왜 묻지?"에서 멈춘다. **양식도 말로만 시키지 않는다** — 어떤 칸인지 양식을 보여 주고 채운 예를 붙인다.

**두 턴에 나눠 묻는다** — 첫 턴에 1·2·3, 3번 답을 받은 뒤 둘째 턴에 4번. 넷을 한 번에 내면 너무 길고, 3번 답을 봐야 4번에서 어느 일로 흐름을 그릴지와 어느 분야 예시를 보여 줄지 고를 수 있다. 첫 턴 답에 되물을 것이 있으면 둘째 턴에 4번과 함께 묶어 낸다 — 단 3번에서 어떤 일이 문제인지조차 안 잡혔으면 4번에서 그릴 일을 고를 수 없으니, 그 되묻기를 먼저 하고 4번은 답을 받은 뒤에 낸다. 되묻기 배치 규칙(한 턴에 2~4개, 항목당 최대 2번)은 아래 코칭 규칙 그대로다.

**첫 턴 — 1·2·3** (말투는 `AGENTS.md` 응답 톤에 맞춰 풀어서 전달):

```
이제 유저 스토리를 쓸 차례야. 서비스를 영화 한 편처럼 구체적인 장면으로 먼저 그려 두면, 뒤에서 화면을 만들 때 AI에게 넘기는 맥락이 또렷해져. 그러려면 먼저 세 가지를 알려 줘. 네 번째는 이 답을 받고 이어서 물어볼게.

1. 서비스 이름과 한 줄 정의
   이걸 묻는 이유: 한 줄로 말할 수 있어야 뒤의 모든 단계가 같은 것을 가리켜.

2. 누가, 어떤 상황에서 쓰나
   이걸 묻는 이유: 쓰는 사람과 그 사람이 처한 상황이 정해져야 장면의 주인공이 생겨.
   예를 들면 "월말 마감에 쫓기는 회계 담당자", "아이 병원비 영수증이 쌓여 가는 부모"처럼
   사람과 상황을 같이 적어 줘.

3. 지금 무엇이 문제고, 그걸 지금은 어떻게 때우고 있어?
   이걸 묻는 이유: 지금 때우는 방법이 곧 이 서비스가 이겨야 할 상대야.
   그 방법보다 확실히 나아야 쓸 이유가 생겨.
   - 문제: 어떤 일에서 무엇이 걸려?
   - 그래서 불편한 점: 시간이 드는지, 실수하거나 놓치는지, 자꾸 미루게 되는지
   - 지금 때우는 방법: 손으로 복사해 붙이기, 엑셀에 따로 정리, 달력 알림 걸기, 다른 사람에게 부탁하기 같은 것
   - 최근에 실제로 있었던 한 번: 언제, 무슨 일이었는지 겪은 그대로 (없으면 "없음"이라고 적어도 돼)
```

1·2에 `AGENTS.md`의 초안이 있으면 그 자리에서 새로 묻지 않고 초안을 보여 주며 다듬게 한다 (아래 「입력 1·2는 여기서 묻고 확정한다」).

**둘째 턴 — 4** (말투는 `AGENTS.md` 응답 톤에 맞춰 풀어서 전달). `{ }`는 프로젝트마다 바뀌는 자리다:

````
4. {서비스 이름}에서 일이 어떻게 흘러가는지 적어 줘.
   이걸 묻는 이유: 누가 무엇을 넣고, 그게 무엇이 되어 누구에게 가는지가 정해져야
   장면도 화면도 빠짐없이 그릴 수 있어.
   {여러 일을 맡는 서비스일 때만: 여러 가지 일을 맡는 서비스니까 대표 일 하나만 적어 줘.
   방금 얘기한 {3번 답의 일}이면 돼. 성격이 다른 일이 하나 더 있으면 그것도 적어도 좋아.}

「누가」에는 사람만 들어가는 게 아니야. {서비스 이름}이 알아서 처리하는 단계,
상대방이나 외부 사이트가 받는 단계도 한 줄씩 적어 줘.

「무엇을 넣나」는 일마다 달라. 예를 들면
- {다른 분야 짝 예시 1 — 예: 리모델링 견적을 받는 일이면 → 평수·원하는 공사·예산을 적고 현장 사진을 올린다}
- {다른 분야 짝 예시 2 — 예: 블로그에 글을 올리는 일이면 → 글을 쓰고 사진을 골라 넣는다}
- {다른 분야 짝 예시 3 — 예: 휴가를 신청하는 일이면 → 날짜와 사유를 고른다}

「무엇이 되어, 어디에 남나」도 여러 모습이야. 예를 들면 견적 요청 한 건으로 접수됨 /
블로그 포스트 한 편이 올라감 / 팀장 결재함에 신청서 한 건이 들어감 / 상대 메일함에 메일 한 통이 도착함.

아래 양식에 적어 줘. 단계는 필요한 만큼 늘려도 돼.

```
[1] 누가, 언제                :
    무엇을 넣나                :
    → 무엇이 되어, 어디에 남나  :
[2] 그걸 누가 받아서           :
    무엇을 하나(넣나)           :
    → 무엇이 되어, 어디에 남나  :
(끝날 때까지 이어서)
[끝] 처음 시작한 사람에게 무엇이 돌아오나 :
```

채운 예 (분야가 다르니 모양만 참고해)
{예시 모음에서 고른 흐름 하나}
````

**4번은 「일이 흘러가는 길」로 받는다.** 구호("AI가 도와준다")로는 장면도 화면도 못 뽑는다. 「사진을 찍으면 → 답이 나온다」처럼 화살표 한 줄로 끝나도 부족하다 — 누가 무엇을 하게 되는지, 결과가 어디로 가는지가 그려지지 않는다. 실제 서비스의 일은 데이터가 사람과 사람(또는 사이트·시스템) 사이를 거쳐 간다. 그래서 단계마다 같은 세 줄을 반복해, 처음 시작한 사람에게 결과가 돌아올 때까지 잇는다:

1. **누가(언제)** — 그 단계를 하는 쪽. 사람만 들어가지 않는다 — **서비스 자신이 자동으로 처리하는 단계, 외부 사이트·기관·시스템이 받는 단계도 한 줄씩 적는다.** 안 적으면 흐름이 끊긴다.
2. **무엇을 넣나** — 그 단계의 입력 데이터다. 사용자가 고르는 것, 올리는 파일, 직접 쓰는 글, 다른 곳에서 가져오는 자료. 설명할 때 데이터 이름만 던지지 말고 「이런 일이면 → 이걸 넣는다」 짝으로 보여 준다. 넣는 게 없는 단계(정해진 때가 되면 서비스가 스스로 시작하는 단계 등)는 `무엇을 넣나 : 없음 — {언제} 스스로 시작`처럼 적는다.
3. **→ 무엇이 되어, 어디에 남나** — 결과물이 세상에 남는 모습이다. 견적 요청 한 건으로 접수됨, 블로그 포스트 한 편, 피드 게시물 한 건, 결재함의 신청서 한 건, 상대 메일함의 메일 한 통, 기관 사이트의 접수 한 건처럼. 서비스 화면 안에서 그 결과가 카드인지 목록인지 같은 모양은 4·5단계 몫이라 여기서 묻지 않는다.

흐름을 받을 때 챙길 셋:

- **사람이 끼어드는 자리를 빠뜨리지 않는다** — 흐름 중간에 사람이 확인·승인·본인확인으로 끼어드는 자리가 드러나면 그 단계를 따로 적는다. 뒤 단계 화면 목록이 가장 잘 빠뜨리는 자리다.
- **여러 가지 일을 맡는 서비스(플랫폼형·도구 모음형)는 대표 일 1~2개만** 흐름으로 받는다. 전부 받으려 하면 인터뷰가 끝나지 않는다. 나머지 일은 2단계 기능 목록이 채운다.
- **예시는 사용자 분야가 아닌 것에서 고른다** — 4번 질문에 붙이는 채운 예는 `1-user-story-examples.md`(예시 모음)에서 사용자 아이디어와 다른 분야 하나만 골라 "분야가 다르니 모양만 참고해"라고 붙인다. 같은 분야 예시는 답을 그쪽으로 끌고 간다. 「무엇을 넣나」「무엇이 되어, 어디에 남나」 설명에 붙이는 짝 예시도 사용자 분야가 아닌 것에서 3개 안팎을 고른다.

AI가 판단의 기준으로 삼는 나쁜 예와 좋은 예 (사용자에게 내미는 예시는 예시 모음에서 고른다):

나쁜 예:

> 사진을 찍으면 → 문제와 해설과 답이 나온다

좋은 예 — 같은 아이디어를 흐름으로:

```
[1] 오답 노트를 정리하던 학생이 → 틀린 문제가 찍힌 시험지 사진을 올린다 → 오답 한 건으로 접수된다
[2] 서비스가 → 문제를 글자로 옮기고 풀이·정답·비슷한 유형 문제를 붙인다 → 풀이가 붙은 오답 한 건이 학생의 오답 노트에 쌓인다
[끝] 학생에게 → 정리된 오답이 돌아오고, 주말에 모아 다시 풀거나 시험 전날 한꺼번에 인쇄한다
```

**4번 답을 받은 뒤 확인** — AI가 사용자 답을 흐름 양식으로 고쳐 써서 확인받는다 (말투는 `AGENTS.md` 응답 톤에 맞춰 풀어서 전달):

```
이렇게 이해했는데 맞아? 고칠 데 있으면 말해 줘.

{사용자 답을 흐름 양식으로 고쳐 쓴 것. AI가 끼워 넣은 단계는 "(내가 끼워 넣음)" 표시}

{모르는 것이 있으면: 모르는 게 하나 있어 — {무엇}. 일단 {가정}으로 할게.}
```

- **고쳐 쓸 때는 한 단계를 한 줄로 줄여도 된다** — `[n] 누가 → 무엇을 넣고 → 무엇이 되어 어디에 남나` (예시 모음의 모양). 사용자가 쓴 뜻은 바꾸지 않는다.
- **흐름상 빠진 단계가 보이면 AI가 끼워 넣되 끼워 넣었다고 표시한다** — 사용자가 적지 않았지만 앞뒤가 이어지려면 있어야 하는 단계(서비스가 알아서 처리하는 단계, 상대가 받는 단계, 사람이 승인하는 단계 등). `# 입력 (확정)`에는 그 단계 끝에 `(AI가 끼워 넣음)`을 붙여 적는다 (§4.2).
- **모르는 것은 "일단 이렇게 가정할게"라고 밝힌다** — 몰래 채우지 않는다. 사용자가 "맞아"라고 하면 확정으로 친다. 아직 모르는 채로 가기로 한 것은 `# 입력 (확정)`의 해당 항목 끝에 `추후 결정: {무엇을 다시 확인할지}`로 적는다 (SKILL.md §1.4). 되묻기 2번 뒤에 AI가 고른 해석은 아래 코칭 규칙의 `가정` 표시를 따른다.

**입력 1·2는 여기서 묻고 확정한다** — project-init은 이 둘을 묻지 않는다. 설치 때 코칭 없이 받은 답을 여기서 확인만 하고 넘기면 그 답에 닻이 내린 채 확정되기 때문이다. 먼저 프로젝트 `AGENTS.md` 상단의 프로젝트 정의 줄(`이 저장소는 **…**를 만든다. 타겟: **…**.`)을 본다:

- **빈 자리 표시 `(1단계 유저 스토리에서 채움)`이면** 여기서 새로 묻는다 — 3과 함께 위 첫 턴 질문으로.
- **초안 표시 `(초안 — 1단계에서 확정)`가 붙어 있거나 이미 채워져 있으면** 초안으로 보여주되 확인만 받고 넘기지 않는다 — 아래 코칭 규칙(되묻기·고쳐 써서 확인받기·한 항목당 최대 2번)대로 다듬는다. 2번의 "어떤 상황에서"가 비어 있으면 그 부분을 채워 받는다.

확정한 입력 1·2는 §2.3 (3)에서 `AGENTS.md`에 써넣는다.

코칭 규칙 (SKILL.md §1.4):

- **빠짐·모호는 그냥 넘어가지 말고 배치로 되묻기** — 답이 부족하거나 뜻이 두 갈래로 읽히면 받아 적고 넘어가지 않는다. 하나씩 직렬로 왕복하지 말고 모자란 항목 2~4개를 한 턴에 묶어 확인. 되묻는 방식은 둘이다:
  - **예를 들어 다시 묻기** — "예를 들면 A처럼 ~인 거야, 아니면 B처럼 ~인 거야?" A·B는 그 사람이 이미 한 답에서 뽑는다.
  - **고쳐 써서 확인받기** — "이런 뜻으로 이해했는데 맞아? — {사용자 답을 더 구체적으로 고쳐 쓴 문장}". 4번이면 위 「4번 답을 받은 뒤 확인」처럼 흐름 양식으로 고쳐 써서 보여준다.
- **되묻기는 한 항목당 최대 2번** — 배치 한 턴에 들어간 항목은 각각 한 번씩 센다. 2번 되물어도 부족하면 **3번째는 묻지 않는다.** 그때까지 나온 답으로 가장 그럴듯한 해석을 AI가 고르고, 사용자에게 "이렇게 가정하고 갈게"라고 말한 뒤 다음으로 넘어간다. 그 항목은 `# 입력 (확정)`에 `(가정 — 되묻기 2번 뒤 AI가 고른 해석)`을 붙여 적는다 (§4.2). 되묻기가 끝없이 늘면 인터뷰가 심문이 된다 — 부족한 채로 가도 뒤 단계(목업·스토리보드 검토)에서 다시 드러나 고쳐진다.
- **"잘 모르겠어"는 정상 답** — AI가 후보 2~3개 제시하고 사용자가 골라 다듬게 한다. 이것도 되묻기 한 번으로 센다.
- **「무엇을 넣나」「무엇이 되어」 자리에 명사가 없으면 뭉개진 답이다** ("AI가 알아서 해 준다") — 예시를 볼지 되묻지 않는다(왕복만 는다). **그 사람의 3번 답에서 뽑아** 흐름 후보 2~3개를 만들어 그 턴에 내고 고르게 한다. 예시 모음으로 채우지 않는다 — 남의 예시를 들이밀면 아이디어가 그쪽으로 끌려간다.
- **결과에서 거꾸로 입력을 검산한다** — 어떤 단계의 결과를 내는 데 **없으면 안 되는데** 그 단계나 앞 단계의 「무엇을 넣나」에 빠진 것을 찾아 되묻기 배치에 묶는다 (예: "사진을 올리면 → 부족한 영양소가 나온다"라면 키·몸무게·목표가 어느 단계에서 들어오는지). 「있으면 좋은」 데이터는 여기서 묻지 않는다 — 그건 아래 「AI 도메인 보완 제안」에서 채택/보류로 다룬다. 수준은 "무엇을 받아야 하나"까지다 — 필드 형식은 4·6단계 몫이다.

**양면 시장이면 여기서 갈린다** — 쓰는 사람이 두 종류이고 **한쪽이 있어야 다른 쪽이 쓸 수 있는** 서비스가 양면 시장이다 (중고 거래 — 파는 사람·사는 사람 / 배달 — 가게·손님 / 강의 마켓 — 강사·수강생). 판별은 **입력 1(한 줄 정의)에서 감지**한다. 질문을 하나 더 늘리지 말고, 되묻기 배치에 얹어 확인만 받는다:

```
이거 쓰는 사람이 두 종류 맞지? — {A 역할}이랑 {B 역할}.
맞으면 2·3번은 양쪽 각각 받을게.
```

- **단면이면** 위 4개 그대로다. 아무것도 안 바뀐다.
- **양면이면** 2·3을 역할별로 받고, 입력 5를 하나 더 받는다. **4번은 흐름 하나로 받는다** — 두 역할이 흐름 안에 차례로 다 드러나기 때문이다 (중고 거래라면 파는 사람이 올리고 → 사는 사람이 문의하고 → 파는 사람이 약속을 잡는다).

```
양쪽이 있으니 이렇게 받을게:

2. 누가, 어떤 상황에서 쓰나 — {A 역할}은 누가·어떤 상황에서 / {B 역할}은 누가·어떤 상황에서
3. 지금 무엇이 문제고, 그걸 지금은 어떻게 때우고 있어? — {A 역할}·{B 역할} 각각
   (문제 / 그래서 불편한 점 / 지금 때우는 방법 / 최근에 실제로 있었던 한 번)
5. 초기 공급을 어떻게 채울 건가 — 어느 쪽부터 채울지, 그 한쪽을 직접 채울 건지
   이걸 묻는 이유: 한쪽이 비어 있으면 다른 쪽도 안 와서, 처음엔 누군가 한쪽을 직접 채워야 해.
```

역할이 둘이어도 **턴을 늘리지 않는다** — 첫 턴 1·2·3, 둘째 턴 4·5 그대로다. 1에서 양면이 미리 보이면(`AGENTS.md` 초안 등) 첫 턴부터 2·3을 역할별로 묻고, 첫 턴 답을 받고서야 드러나면 둘째 턴에 양면 확인을 얹어 나머지 역할의 2·3을 4·5와 함께 묻는다. 되묻기도 한 턴에 묶는다 — 왕복을 두 배로 늘리지 않는다.

**왜 2·3을 쪼개나** — 파는 쪽 고민과 사는 쪽 고민은 아예 다른 얘기다. 한쪽만 적혀 있으면 화면도 그 한쪽만 생기고, 결국 7단계에서 그 한쪽만 검증하게 된다.

**왜 5번을 묻나 — "닭이 먼저냐 달걀이 먼저냐"** — 양면 시장의 제일 큰 위험은 한쪽이 없으면 다른 쪽도 안 온다는 것이다. 살 사람이 없으면 파는 사람이 안 올리고, 올라온 게 없으면 살 사람이 안 온다. 그래서 초기엔 보통 **한쪽을 만드는 사람이 직접 채운다** — 물건을 직접 구해다 올리거나, 공급자를 발로 뛰어 섭외하거나, 한 동네·한 학교로 범위를 좁혀 양쪽을 동시에 채우거나. 이건 조사로 알아낼 일이 아니라 만드는 사람이 정할 일이라 여기서 묻는다. "잘 모르겠어"면 위 코칭 규칙대로 후보 2~3개를 제시해 고르게 한다.

#### 「실제 경험」 — 3번 안에서 받는다

유저 스토리가 지어낸 이야기 위에 서지 않고 **실제 경험 위에 서게** 하려고 사용자가 실제로 겪은 일을 걷는다 **(사용자 확정 2026-09-01)**. 따로 묻지 않고 3번의 「최근에 실제로 있었던 한 번」으로 받는다 — 문제·불편·때우는 방법을 말하다 보면 그 한 번이 함께 나온다.

- **3번의 「최근에 실제로 있었던 한 번」 답을 「실제 경험」에 원문 그대로 옮긴다** (§4.2) — 요약하면 장면의 뼈대가 될 세부가 날아간다.
- **3번 답이 추상적이어서 실제 한 번이 안 나왔을 때만 한 번 되묻는다** — "최근에 있었던 한 번 들려줄래?" 그 이상은 묻지 않는다.
- **경험이 없으면 "없음"으로 적고 넘어간다** — 본인이 안 써본 분야일 수 있다. 없는 경험을 지어내 채우면 스토리가 거기서부터 거짓이 된다.
- **대표 일을 2개 받았으면 일마다 한 줄씩 목록으로 적는다** — 일이 하나면 원문 한 덩어리다. 3번 답에 그 일의 실제 한 번이 없으면 그 줄은 "없음"이다.
- **양면 시장이면 역할별로 받는다** — 한쪽만 겪어봤으면 겪은 쪽만 적고 반대쪽은 "없음"이다.

#### 「AI 도메인 보완 제안」 — 4번 흐름까지 확인받으면 한 번에

사용자 혼자서는 주요 기능(메뉴)을 구멍 없이 다 뽑기 어렵다. 그래서 4번 흐름까지 확인받으면 AI가 도메인 지식으로 **이런 종류의 서비스에 보통 있는 메뉴·기능** 중 아직 언급 안 된 것을 후보로 내민다. 여기서 채워 두면 뒤 단계가 빨라진다 **(사용자 확정 2026-09-01)**.

- **한 번에 목록으로 낸다** — SKILL.md §1.5의 **초안 모드**다. 후보를 하나씩 "이건 어때?" 묻지 않고 목록을 통째로 보여주고, 사용자가 **채택/보류**를 표시하게 한다. 후보마다 왜 보통 있는 기능인지 한 줄 근거를 붙인다.
- **결과에 꼭 필요한 입력은 이미 4번 검산에서 받았다** — 여기서는 「있으면 좋은」 것만 낸다. 없으면 안 되는 입력이 이제야 보이면 보완 제안이 아니라 4번으로 되돌아가 되묻는다.
- **여기서 "다 뽑았다"고 보지 않는다** — 이건 씨앗을 늘리는 자리이지 완전성을 판정하는 자리가 아니다. 완전성의 최종 책임은 2단계의 역할 × 단계 격자(`2-mockup.md` §2.3)와 4단계 커버리지 자가 점검이 계속 진다. 여기에 새 검토 장치를 만들지 않는다.

**기능 씨앗 목록은 흐름에서 먼저 뽑는다** — 흐름의 단계마다 기능 후보가 하나씩 나온다 (예: 인테리어 견적 흐름이면 견적 요청 작성·접수, 요청 목록, 견적서 작성·보내기). 여기에 3번 답(실제 경험·때우는 방법)에서 나온 메뉴와 채택된 보완 후보를 합쳐 **「기능 씨앗 목록」**으로 적고, 항목마다 출처(`흐름` / `경험` / `제안 채택`)를 붙인다 (§4.2). 이 목록이 2단계 기능 목록의 출발 입력이다. 양면 시장처럼 씨앗 목록에 역할 칸이 있으면, 흐름에서 서비스 자신이 하는 단계에서 나온 기능은 역할 칸에 `서비스`로 적는다 — 사람 역할이 아니라도 화면·작업이 필요한 기능이라 빠뜨리면 안 된다.

**입력이 다 확정되기 전에는 에이전트에 위임하지 않는다** (단면 4개·양면 5개). `user-scenario-writer`는 빠진 입력을 임의로 가정해 채우는 폴백을 갖고 있지만, 그건 강행 진입용 안전판이지 기본 경로가 아니다 — 전부 사용자 확인을 받은 뒤에만 §2.3으로 넘어간다. 되묻기 2번 뒤 AI가 고른 해석(`가정` 표시)도 사용자에게 그렇게 가정한다고 말했으면 확정으로 치고 넘어간다.

### 2.3 산출물 두 개 만들기 — 브리프 초판 + 에이전트 위임

순서가 있다. **브리프 초판을 먼저 만들고, 그 다음 에이전트에 위임한다** — 에이전트가 브리프를 읽어 확정을 지켜야 하기 때문이다.

**(1) `mvp/design-brief.md` 초판을 메인 클로드가 직접 쓴다.** §4.3 템플릿 그대로 만들고, **인터뷰(§2.2)에서 이미 나온 확정만** 해당 칸에 날짜와 함께 채운다. 나머지는 전부 `추후 결정`으로 둔다 — 여기서 브랜딩 인터뷰를 새로 열지 않는다. 서체·로고·마스코트가 `추후 결정`인 채로 다음 단계에 가는 게 정상이다 — 색·서체·둥글기 같은 값은 2단계 입구에서 참고 디자인을 받아 채운다(`2-mockup.md` §2.2).

**(2) `user-scenario-writer` 서브 에이전트에 위임한다.** 위임 프롬프트에 반드시 포함할 것:

- **(a) 확정된 입력 원문 전부** — 요약·재구성 없이 사용자가 확인한 그대로 전달 (단면 4개·양면 5개, 양면이면 2·3의 역할별 답 전부와 4번 흐름). `가정` 표시·`(AI가 끼워 넣음)` 표시가 붙은 항목은 표시째로 넘긴다.
- **(b) 저장 경로 명시** — `mvp/user-story.md` (에이전트 기본 경로와 동일 — `.claude/agents/user-scenario-writer.md` §출력).
- **(c) 문서 상단 `# 입력 (확정)` 섹션 보존 지시** — 입력 원문을 문서 최상단에 그 섹션으로 남기라고 명시. 뒤 단계들이 여기를 아이디어의 출발점으로 읽는다 (3단계 경쟁자 조사, 7단계 최종 확정).
- **(d) 양면이면 그 사실과 두 역할 이름** — 어느 쪽이 수요(사는 쪽)이고 어느 쪽이 공급(파는 쪽)인지 적어 넘긴다. 에이전트는 주인공을 수요 쪽으로 잡고 반대편 장면을 2~3개 그린다 (`.claude/agents/user-scenario-writer.md` §필수 구조).
- **(e) 브리프 경로와 읽기 전용 지시** — `mvp/design-brief.md`를 먼저 읽고 확정 사항을 지키되 **쓰지는 말라**고 명시. 브리프에 올릴 것은 최종 메시지에 제안으로 담아 돌려보내게 한다.
- **(f) 두 파일 머리의 정본 선언** — `user-story.md` 머리에 §4.1의 선언 문단을 넣으라고 명시.
- **(g) 「실제 경험」 원문과 「기능 씨앗 목록」** — 경험담(3번의 「최근에 실제로 있었던 한 번」)은 요약하지 말고 원문 그대로 넘기고, **경험이 덮는 자리는 그 경험을 장면의 뼈대로 쓰라**고 명시한다 (`.claude/agents/user-scenario-writer.md` §작법 규칙). 씨앗 목록도 함께 넘겨 어떤 기능이 이미 사용자 손에 있는지 알게 한다. 경험이 "없음"이면 그 사실도 그대로 적어 넘긴다.

**(3) 확정된 입력 1·2를 프로젝트 `AGENTS.md`의 프로젝트 정의 줄에 써넣는다.** `<!-- BEGIN:project-rules -->` 구역 첫 문단의 `이 저장소는 **…**를 만든다. 타겟: **…**.` 한 줄만 고친다 — 빈 자리 표시 `(1단계 유저 스토리에서 채움)`·초안 표시 `(초안 — 1단계에서 확정)`를 확정 문구로 바꾸고 표시는 지운다. 그 밖의 줄·제목·다른 도구가 만든 구역(`<!-- BEGIN:nextjs-agent-rules -->` 등)은 건드리지 않는다. *왜*: `AGENTS.md`는 매 세션 자동으로 읽혀서, 여기가 비어 있으면 이후 세션이 이 프로젝트가 무엇인지 모른 채 돈다. 입력 1·2가 나중에 바뀌면(§2.6 되돌아옴 포함) 다시 써넣고, 7단계가 최종 확정 아이디어로 한 번 더 덮어쓴다(`7-mvp-launch.md` §2.1.1 4번).

같은 단계 안의 재위임(§2.4 리뷰 반영·§2.5 스토리보드 반복)은 지시서에 「`mvp/user-story.md`에 제자리 덮어쓰기, 판올림 금지」를 넣는다. 2단계에서 되돌아와 다시 받을 때(§2.6)만 `-v2`. **`design-brief.md`는 반대다** — 판올림 없이 같은 파일을 제자리에서 고쳐 누적한다 (SKILL.md §3).

### 2.4 결과 보고·리뷰

에이전트가 반환하는 다섯 가지 중 앞의 셋 — **저장 경로 · 로그라인(logline) · 장면 목록** — 을 사용자에게 그대로 보여주고 피드백을 받는다.

이건 SKILL.md §1.5의 **초안 모드** — AI(서브 에이전트)가 산출물을 완주해서 만든 뒤 완성본으로 한 번에 리뷰받는 작업이다. 중간에 장면 하나하나 승인받지 않는다. 수정 요청이 오면 무엇을 바꿀지 구체화해 에이전트 재위임으로 반영하고(제자리 덮어쓰기 — §2.3 끝), 다시 세 가지를 보여준다.

**나머지 둘은 브리프로 간다.** 에이전트가 함께 돌려주는 **보이스·톤 확인 요청**과 **브리프에 올릴 제안 목록**(새로 판정한 고정 문구·UI 패턴 지정 제안·확정 헤드카피 등)을 사용자에게 묻고, **확인받은 것만** 메인 클로드가 `design-brief.md`의 해당 칸에 지위(`사용자 확정`)와 날짜를 붙여 적는다. 확인 못 받은 건 `가정` 지위로 남기거나 `추후 결정`으로 둔다.

**확인 요청에서 묻는 건 보이스와 「톤을 기본값으로 갈지」 둘이다.** 화면 문구 톤은 브리프에 하네스 기본값(합쇼체 — §4.3 「2. 보이스 앤 톤」)으로 이미 깔려 있어서, 톤은 그대로 갈지 한 번만 묻는다. 그대로 가면 「기본 말투」 행의 지위만 `사용자 확정`과 날짜로 바꾸고 내용은 그대로 둔다. 다른 말투를 원하면(작가가 근거를 대고 다른 톤을 제안한 경우 포함) 「기본 말투」와 자리별 톤 행의 내용까지 덮어쓰고 `사용자 확정`과 날짜를 붙인다.

**에이전트가 "브리프와 어긋난다"고 보고하면** 임의로 한쪽을 고르지 말고 사용자에게 무엇이 어떻게 어긋나는지 보여주고 어느 쪽이 맞는지 확인받는다 — 브리프를 고칠 일이면 브리프를 고치고, 스토리를 고칠 일이면 재위임한다.

### 2.5 스토리보드로 검토하기 — ChatGPT에서 그려 보고 되돌린다

`user-story.md`는 글이라 읽기 싫고, 읽어도 흐름의 구멍이 잘 안 보인다. **그림으로 바꿔 보면 보인다.** 사용자가 ChatGPT에 파일과 아래 프롬프트를 넣어 UX 스토리보드를 만들고, 거기서 어긋난 점을 찾아 `user-story.md`에 되돌린다. **문서가 사용자 의도를 정확히 담을 때까지 반복한다.**

**AI 몫과 사람 몫** — AI는 프롬프트를 그대로 건네고, 돌아온 수정사항을 문서에 반영한다. ChatGPT에 넣고 그림을 보고 판정하는 건 사람 몫이다 — AI가 그림을 보고 "맞다"고 결론 내지 않는다(저장소 검증 규칙).

**한 회차 절차**

1. §2.4 리뷰가 끝나면 사용자에게 안내한다 — "`mvp/user-story.md`를 ChatGPT에 첨부하고 아래 프롬프트를 그대로 넣어 스토리보드를 만들어 봐. 보고 나서 문서와 다른 데, 빠진 데, 순서가 이상한 데를 말해줘."
2. 프롬프트는 **아래 블록을 글자 그대로** 보여준다 — 줄이거나 고쳐 쓰지 않는다.
3. 사용자가 수정사항을 말하면 §2.6과 같은 갈래로 반영한다 — **이야기 결함**(빠진 화면·순서·전제)은 `user-scenario-writer` 재위임, **문구·미감 확정**은 메인이 `design-brief.md`에. 기능·범위 문제는 2단계 몫이라 여기서 다루지 않는다.
4. 반영이 끝나면 다시 1로. **마지막 회차에 수정사항이 0건이면 끝**이다. 횟수 상한은 없다.

**제자리 덮어쓰기 — 판올림이 아니다.** 이 반복은 같은 판을 다듬는 것이라 `user-story.md`를 **같은 파일명으로 덮어쓴다.** `-v2`로 올리지 않고 별도 문서도 만들지 않는다. 재위임 지시서에 「`mvp/user-story.md`를 제자리에서 덮어써라 — 판올림(-v2) 금지」를 **반드시** 넣는다 — 저장 경로가 없으면 에이전트는 기존 파일을 덮어쓰지 않고 멈춰 보고한다 (`.claude/agents/user-scenario-writer.md` §출력). 판올림은 §2.6처럼 **2단계에서 되돌아올 때**만 한다(SKILL.md 판올림 규칙). 회차 이력은 git이 보존한다.

**ChatGPT에 넣을 프롬프트** (그대로 복사):

```
첨부한 `user-story.md`를 읽고, 그 내용을 바탕으로 UX Storyboard를 만들어라.
목적은 광고나 브랜드 영상을 만드는 것이 아니라, 사용자가 서비스에 유입되는 순간부터 첫 화면, 주요 기능의 발견과 사용, 핵심 행동, 결과, 이후 재사용·공유까지의 전체 UX를 한눈에 검토하는 것이다.
`user-story.md`의 사용자 여정과 내용을 바탕으로 중요한 장면과 전환점을 스스로 선별하여 여러 개의 스토리보드 패널로 구성하라.
각 패널에는:

* 사용자의 실제 상황을 보여주는 스케치
* 사용자가 사용하는 디바이스와 해당 시점의 UI
* 사용자의 행동과 그에 따른 제품의 변화
* 필요한 경우 대사나 생각

을 함께 표현하라.
최종 결과물은 사용자 상황 + UI + 인터랙션이 연결된 가로형 UX Storyboard여야 한다. 단순한 UI 화면 모음이나 플로우차트가 아니라, 실제 사용자가 서비스를 어떻게 경험하는지 이야기처럼 이어지는 형태로 만들어라.
`user-story.md`에 없는 기능이나 내용을 임의로 추가하지 말고, 문서의 UX 흐름과 의도를 우선하라.
그림은 광고 일러스트가 아니라 제품 기획·UX 검토에 사용하는 콘티형 스케치 느낌으로 구성하고, 전체 여정이 한 장에서 자연스럽게 읽히도록 하라.
```

### 2.6 목업에서 되돌아온 경우

**2단계 Mockup에서 이 단계 산출물의 결함이 드러나면 이 절차로 되돌아온다.** 목업 캔버스로 화면을 늘어놓고 보면 글로만 읽을 땐 안 보이던 것들이 드러난다. 돌아오는 길은 결함의 성격 따라 둘로 갈린다:

- **이야기 결함**(사족 문구, 장면과 장면 사이에 빠져 있던 화면, 성립하지 않는 전제) → `user-scenario-writer` 에이전트를 **재위임**해 `user-story.md`를 고친다 (§2.3(2)와 같은 방식, 무엇을 왜 바꾸는지를 위임 프롬프트에 적는다). 지시서에 번호를 올린 저장 경로(예: `mvp/user-story-v2.md`)를 적는다 — 새 판본은 번호가 올라가고 옛 판본은 남는다 (SKILL.md §3).
- **문구·미감 확정**(눌러보다 "이 버튼 이름은 이걸로 가자", "강조색은 이걸로") → 재위임이 아니라 **메인 클로드가 `design-brief.md`의 해당 칸을 제자리에서 고친다.** 날짜와 `사용자 확정` 지위를 붙인다. 판올림하지 않는다.

(기능·범위 문제는 여기가 아니라 `feature-list.md` 몫이다 — `2-mockup.md` §2.6의 3갈래 라우팅 참고.)

브리프를 고쳤으면 다음 재위임 때 에이전트가 그 확정을 읽어 장면 인용을 맞춘다 — 스토리와 브리프가 어긋난 채로 남지 않게 하는 장치다.

고친 뒤에는 2단계로 돌아가 기능 목록과 캔버스를 다시 맞춘다. 이 왕복이 **1↔2 순환**이고, 4단계 IA가 이 문서들을 읽어 가는 순간 순환이 끝나며 두 파일 다 기록으로 얼려진다.

## 3. 완료 체크리스트

- [ ] **필수 입력 확정** (§2.2) — 단면 4개·양면 5개(양면은 2·3이 역할별로 갈리고 4는 흐름 하나). 질문마다 왜 묻는지를 붙였고, 첫 턴 1·2·3 → 둘째 턴 4로 나눠 물음. 사용자 확인 완료, 배치 되묻기로 빠짐·모호 해소(한 항목당 최대 2번, 그래도 부족하면 `가정` 표시). 3번은 문제·불편한 점·지금 때우는 방법이 다 참. 4번은 흐름 — 단계마다 누가(언제)·무엇을 넣나·무엇이 되어 어디에 남나가 차 있고, 처음 시작한 사람에게 결과가 돌아올 때까지 이어짐(서비스 자신·외부가 받는 단계, 사람이 확인·승인으로 끼어드는 단계 포함. 여러 일을 맡는 서비스면 대표 일 1~2개). 흐름을 고쳐 써서 확인받았고, AI가 끼워 넣은 단계는 `(AI가 끼워 넣음)` 표시.
- [ ] **실제 경험** (§2.2) — 3번의 「최근에 실제로 있었던 한 번」을 원문 그대로 옮김(답이 추상적일 때만 한 번 되물음). 대표 일이 둘이면 일마다 한 줄. 경험이 없으면 "없음"으로 명시.
- [ ] **AI 도메인 보완 제안 + 기능 씨앗 목록** (§2.2) — 후보를 한 번에 목록으로 제안했고, 흐름 단계에서 뽑은 기능·경험에서 나온 메뉴·채택분을 출처 표기(`흐름`/`경험`/`제안 채택`)와 함께 씨앗 목록으로 정리.
- [ ] **`AGENTS.md` 프로젝트 정의 줄 써넣음** (§2.3 (3)) — 빈 자리 표시 `(1단계 유저 스토리에서 채움)`·초안 표시 `(초안 — 1단계에서 확정)`가 확정된 입력 1·2로 바뀌었고, 그 줄 말고는 `AGENTS.md`를 건드리지 않음.
- [ ] **`user-story.md` 저장** (§2.3) — `mvp/`, 상단 `# 입력 (확정)` 섹션에 입력 원문 + 「실제 경험」 + 「기능 씨앗 목록」 포함.
- [ ] **`design-brief.md` 저장** (§2.3·§4.3) — `mvp/`, 열 개 절이 순서대로 있고 값이 없는 칸 0개(안 정한 칸은 `추후 결정`). 인터뷰에서 나온 확정은 지위·날짜와 함께 채워짐.
- [ ] **두 파일 머리에 정본 선언** (§4.1) — 서로를 가리키는 상호 참조 포함. 브리프가 이긴다는 우선순위와 "장면 묘사는 예시"가 양쪽에 다 적혀 있음.
- [ ] **로그라인·장면 목록 사용자 확인** (§2.4) — 수정 요청 있으면 재위임까지 반영 완료.
- [ ] **보이스·톤 확인 + 브리프 반영** (§2.4) — 에이전트가 제안한 보이스를 사용자에게 물었고, 톤은 하네스 기본값(합쇼체)으로 갈지 한 번 물었음. 확인받은 것만 브리프에 `사용자 확정`으로 기록.
- [ ] **스토리보드 검토 반복** (§2.5) — 사용자가 ChatGPT 스토리보드로 최소 1회 검토했고, 마지막 회차 수정사항 0건. 반영은 `user-story.md` 제자리 덮어쓰기(`-v2` 아님).
- [ ] **화면 묘사를 읽는 법 + 힘줄 곳 절 포함** — `user-story.md` 마지막 섹션. 씬 묘사가 예시 층이라는 선언과 3층 구분(2층 정본은 브리프)이 들어 있어야 한다. 없으면 디자인 도구가 씬 묘사를 문자 그대로 그려 밋밋한 화면이 나온다 (실제 사고 있었음 — `5-frontend-build.md` §2.2.3).

## 4. 산출물 스펙

위치: 프로젝트 루트의 `mvp/user-story.md`와 `mvp/design-brief.md`.

`user-story.md`의 본문 구조는 `user-scenario-writer` 에이전트의 필수 구조 — 타이틀+로그라인 · 주인공 페르소나 · 장면(S#) 구성 · "시나리오에 심어둔 UX 장치 정리" 표 · 화면 묘사를 읽는 법과 힘줄 곳 — 를 그대로 따른다 (`.claude/agents/user-scenario-writer.md` §필수 구조). 여기서 중복 정의하지 않는다. 이 스킬이 그 위에 추가로 요구하는 건 둘 — 문서 최상단 `# 입력 (확정)` 섹션(§4.2)과 그 위의 정본 선언(§4.1)이다.

### 4.1 두 파일의 정본 선언 (둘 다 필수)

두 파일 머리에 각각 한 단락씩 박는다. 서로를 가리키는 상호 참조라 **한쪽만 넣으면 안 된다** — 어느 파일을 먼저 연 사람이든 자기가 지금 뭘 보고 있는지 알아야 한다.

`user-story.md` 머리 (제목 바로 아래, `# 입력 (확정)` 앞):

```markdown
> **이 문서의 자리** — 이 문서는 UX 서사(사용자 여정)의 정본입니다. 화면 문구·미감(색·서체·모션)·UI 패턴의 정본은 `mvp/design-brief.md`입니다. 여기 장면 속 화면 묘사와 인용 블록은 **어떤 요소가 있고, 위계가 어떻고, 어떤 정서인지를 보여주는 예시**이지 문구·배치의 스펙이 아닙니다. 두 문서가 어긋나면 **브리프가 이깁니다** — 어긋남을 발견하면 조용히 한쪽을 고르지 말고 결함으로 보고해 주세요 (1↔2 순환에서 고칠 대상입니다).
```

`design-brief.md` 머리 (§4.3 템플릿에 이미 들어 있다):

```markdown
> **이 문서의 자리** — 이 문서는 화면 문구·미감(색·서체·모션)·UI 패턴의 정본이자 **결정 대장(ledger — 확정된 결정을 날짜와 함께 쌓아 두는 장부)** 입니다. 사용자 여정·장면의 정본은 `mvp/user-story.md`이고, 거기 적힌 화면 묘사·인용 문구는 예시이지 문구의 스펙이 아닙니다. 두 문서가 어긋나면 **이 문서가 이깁니다** — 어긋남을 발견하면 조용히 한쪽을 고르지 말고 결함으로 보고해 주세요.
>
> **갱신 규칙** — 판올림(`-v2`)을 하지 않습니다. 확정이 나올 때마다 해당 칸을 제자리에서 고쳐 누적합니다. 뒤집힌 결정은 지우지 않고 새 확정이 대체한다고 적습니다. 쓰는 사람은 메인 클로드입니다.
```

### 4.2 `# 입력 (확정)` 섹션 템플릿

**단면(기본)**:

````markdown
# 입력 (확정)

1. **서비스 이름과 한 줄 정의**: {§2.2에서 받은 원문}
2. **타겟**: {누가, 어떤 상황에서}
3. **현재의 대안과 불편함 (문제)**
   - 문제: {원문}
   - 불편한 점: {원문}
   - 지금 때우는 방법: {원문}
4. **일이 흘러가는 길 (해결책의 핵심 아이디어)** — {§2.2에서 확인받은 흐름 원문. 대표 일이 둘이면 일마다 하나씩}

   ```
   [1] {누가, 언제} → {무엇을 넣나} → {무엇이 되어, 어디에 남나}
   [2] {누가 받아서} → {무엇을 하나(넣나)} → {무엇이 되어, 어디에 남나}
   [끝] {처음 시작한 사람에게 무엇이 돌아오나}
   ```

**실제 경험**

{3번 「최근에 실제로 있었던 한 번」 답 원문 — 요약하지 않는다. 대표 일이 둘이면 일마다 한 줄씩 목록. 없으면 "없음"}

**기능 씨앗 목록**

| 기능·메뉴 | 출처 |
|---|---|
| {이름} | 흐름 |
| {이름} | 경험 |
| {이름} | 제안 채택 |
````

**`가정` 표시** — 되묻기 2번 뒤에도 부족해 AI가 해석을 고른 항목은 그 항목 끝에 `(가정 — 되묻기 2번 뒤 AI가 고른 해석)`을 붙인다 (§2.2). 단면·양면 공통이다.

**`추후 결정` 표시** — 확인 때 "일단 이렇게 가정할게"라고 밝혔지만 아직 모르는 채로 가기로 한 것은 해당 항목 끝에 `추후 결정: {무엇을 다시 확인할지}`를 붙인다 (§2.2).

**끼워 넣음 표시** — 사용자가 적지 않았지만 흐름상 빠져 있어 AI가 끼워 넣은 단계는 그 단계 끝에 `(AI가 끼워 넣음)`을 붙인다 (§2.2 「4번 답을 받은 뒤 확인」). 이 표시는 이 섹션에만 남는다 — 에이전트는 표시를 시나리오 본문에 옮기지 않고, 끼워 넣은 단계라는 사실을 문서의 "※ 가정한 내용"에만 적는다 (`.claude/agents/user-scenario-writer.md` §입력 확인).

**양면 시장**: 번호는 그대로 두고 2·3 안에서만 역할별로 갈라 적는다. 4번은 두 역할이 다 드러나는 흐름 하나다. 뒤 단계들이 이 섹션을 번호로 읽으니 번호 체계를 바꾸지 않는다.

````markdown
# 입력 (확정)

> 양면 시장 — 수요 쪽: {B 역할} / 공급 쪽: {A 역할}

1. **서비스 이름과 한 줄 정의**: {원문}
2. **타겟**
   - {A 역할}: {누가, 어떤 상황에서}
   - {B 역할}: {누가, 어떤 상황에서}
3. **현재의 대안과 불편함 (문제)**
   - {A 역할}: {문제 / 불편한 점 / 지금 때우는 방법 — 원문}
   - {B 역할}: {문제 / 불편한 점 / 지금 때우는 방법 — 원문}
4. **일이 흘러가는 길 (해결책의 핵심 아이디어)** — {확인받은 흐름 원문. 두 역할이 차례로 나온다}

   ```
   [1] {A 역할}이 → {무엇을 넣나} → {무엇이 되어, 어디에 남나}
   [2] {B 역할}이 → {무엇을 하나(넣나)} → {무엇이 되어, 어디에 남나}
   [끝] {처음 시작한 사람에게 무엇이 돌아오나}
   ```

5. **초기 공급을 채우는 방법**: {어느 쪽부터, 직접 채울지 — 원문}

**실제 경험**

- {A 역할}: {3번 「최근에 실제로 있었던 한 번」 원문 — 없으면 "없음"}
- {B 역할}: {3번 「최근에 실제로 있었던 한 번」 원문 — 없으면 "없음"}

**기능 씨앗 목록**

| 기능·메뉴 | 역할 | 출처 |
|---|---|---|
| {이름} | {A 또는 B 역할} | 흐름 |
| {이름} | 서비스 | 흐름 |
| {이름} | {A 또는 B 역할} | 경험 |
| {이름} | {A 또는 B 역할} | 제안 채택 |
````

씨앗 목록의 역할 칸에는 사람 역할 말고 `서비스`도 온다 — 흐름에서 서비스 자신이 하는 단계(자동 분류, 정해진 때 스스로 시작 등)에서 나온 기능이다 (§2.2).

**「실제 경험」·「기능 씨앗 목록」에 번호를 붙이지 않는 이유** — 뒤 단계들이 1~4번(양면은 5번까지)을 번호로 읽어서다. 새 항목에 번호를 이어 붙이면 단면과 양면에서 같은 번호가 다른 뜻이 된다. 그래서 번호 없는 소제목으로 붙인다.

판올림 규칙은 AGENTS.md 「판올림 문서는 매 판이 완결된 한 편이다」 그대로 — 씨앗 목록도 지금 확정된 목록 전량을 적는다.

이 뒤로 `user-scenario-writer`가 생성한 시나리오 본문이 이어진다.

### 4.3 `design-brief.md` 초판 템플릿

위치: `mvp/design-brief.md`. 열 개 절을 순서대로 담는다. **모든 칸에 값이 있어야 한다** — 안 정한 칸은 비워 두지 말고 `추후 결정`이라고 적는다. 비어 있는 칸은 빠뜨린 것인지 일부러 안 정한 것인지 구분이 안 된다.

**지위 칸 표기 다섯 가지**:

- `사용자 확정` — 사람이 확인해 준 것. 확정일 필수.
- `가정` — AI가 근거를 대고 제안했고 아직 확인 전.
- `기본값` — 하네스가 깔아 주는 바닥선. 프로젝트가 덮어써도 된다.
- `추후 결정` — 아직 안 정함. 디자인 도구는 이 칸에서만 자유롭게 정한다.
- `표준` — 접근성처럼 바깥 기준에서 온 바닥선. 프로젝트가 덮어쓰지 않는다. 디자인 도구도 고치지 않는다.

````markdown
# 디자인 브리프

_1단계 UserStory 산출물. 화면 문구·미감·UI 패턴의 정본._

> **이 문서의 자리** — (§4.1의 브리프용 선언 문단을 그대로)

## 1. 브랜드 인상

| 항목 | 내용 | 지위 | 확정일 |
|---|---|---|---|
| 브랜드 인상 한 줄 | 추후 결정 — 이 서비스가 유저에게 줘야 할 정서 한 줄 (예: "조용한 확신") | 추후 결정 | |

## 2. 보이스 앤 톤

**보이스(voice)** 는 브랜드가 말하는 성격이라 상황이 바뀌어도 안 변하고, **톤(tone)** 은 그 성격이 자리마다 입는 말투입니다. 자리마다 톤이 달라도 되지만 보이스를 벗어나면 안 됩니다.

| 항목 | 내용 | 지위 | 확정일 |
|---|---|---|---|
| 보이스 | 추후 결정 — 「브랜드 인상 한 줄」을 몇 줄로 편 것 | 추후 결정 | |
| 기본 말투 | 합쇼체. 사용자를 부르는 말은 쓰지 않습니다. 자리마다 쓰는 어미는 아래 표에 있습니다. | 기본값 | |

자리별 톤:

| 자리 | 톤 | 예시 문구 | 지위 | 확정일 |
|---|---|---|---|---|
| 제목 — 할 일을 말할 때 | 「~해주세요」 | 결제 수단을 등록해주세요 | 기본값 | |
| 제목 — 상태를 알릴 때 | 「~습니다」 | 결제가 완료됐습니다 | 기본값 | |
| 설명 문장 | 「~입니다」「~합니다」 | 영수증은 이메일로 보내 드립니다 | 기본값 | |
| 첫 화면 제목 (히어로가 있는 유형만 — SaaS·O2O·해외형 커뮤니티 랜딩) | 추후 결정 — 브랜드 문구라 보이스와 함께 정합니다 | 추후 결정 | 추후 결정 | |
| 본문 안내 | 설명 문장과 같음 — 「~입니다」「~합니다」 | 입력한 주소는 배송에만 사용합니다 | 기본값 | |
| 에러 | 제목은 상태(「~습니다」) + 할 일(「~해주세요」), 설명은 「~입니다」「~합니다」 | 결제하지 못했습니다 / 카드 한도를 확인해주세요 / 이번 달 한도를 넘은 결제입니다 | 기본값 | |
| 완료 | 「~습니다」 | 신청이 접수됐습니다 | 기본값 | |

(자리는 서비스에 맞게 더하거나 뺍니다.)

**보이스는 따로 확정받습니다.** 톤은 하네스 기본값(합쇼체)으로 시작하고, AI가 스스로 바꾸지 않습니다. 프로젝트가 다른 말투를 원하면(예: 어린이 대상 서비스라 해요체) 사용자 확인을 받아 해당 행을 `사용자 확정`과 확정일로 덮어씁니다. `기본값` 행도 따라야 할 규정이라, 디자인 도구는 이 톤을 그대로 씁니다.

## 3. 「문자 그대로」 고정 문구

확정돼서 다른 에이전트가 손대면 안 되는 문구입니다. 기능이 실리는 텍스트(메뉴·내비게이션, 동작 버튼, 카테고리명, 상태 표시, 폼 라벨)와 확정된 헤드카피·슬로건이 여기 옵니다. 판별 기준은 `user-scenario-writer` 에이전트 §작법 규칙의 「BX가 닿는 곳과 닿지 않는 곳」을 따릅니다.

| 자리 | 확정 문구 | 지위 | 확정일 |
|---|---|---|---|

**여기 오른 문구는 글자 단위로 그대로 씁니다** — 유저 스토리의 장면 인용, 목업 캔버스, 프로토타입 캔버스, 앱 코드 어디서나 조사·띄어쓰기·문장부호까지 같아야 합니다. 아직 하나도 없으면 "없음" 한 줄.
````

## 5. 사용자 응대 톤

- **톤**: SKILL.md §1.3 따름 — `AGENTS.md` 응답 톤(~입니다 체)·친근·짧게.
- **흐름**: 필수 입력 받기 — 첫 턴 1·2·3, 둘째 턴 4(§2.2) → 브리프 초판 + 에이전트 위임(§2.3) → 결과 리뷰와 브리프 반영(§2.4) → 스토리보드 검토 반복(§2.5). 단계 건너뛰지 않기 — 특히 입력이 다 확정되기 전에 위임부터 하는 점프 금지.
- **질문엔 이유를, 양식엔 채운 예를 붙인다** — "이걸 묻는 이유" 한 줄 없이 질문만 던지거나, 양식을 보여 주지 않고 "몇 칸으로 적어 줘"라고 말로만 시키지 않는다. 사용자는 무엇을 왜 적는지 알아야 제대로 답한다.
- **"빈칸"이라는 말을 쓰지 않는다** — 비어 있는 항목은 "아직 안 정한 것", "이 부분"처럼 가리킨다.
- **브리프를 브랜딩 인터뷰로 키우지 않는다** — `design-brief.md`는 결정을 담는 그릇이지 브랜딩 단계가 아니다. 서체·로고·마스코트가 `추후 결정`인 채로 다음 단계에 가는 게 정상이니, 칸을 채우려고 질문을 늘리지 않는다. 확정은 눌러보는 2단계에서 자연스럽게 쌓인다.
- **솔루션 함정 주의**: 입력 ④(일이 흘러가는 길 — 해결책의 핵심 아이디어)는 받되, 그 검증은 마지막 7단계(MvpLaunch) 광고 실측의 몫이다. 유저 스토리는 아직 검증 전의 그림일 뿐 — 사용자가 "이 시나리오대로 확정됐다"고 오해하지 않도록, 결과 리뷰(§2.4) 때 "이건 앞으로 만들면서 다듬어갈 그림이고, 맞는지는 마지막에 실제 사용자 반응으로 확인한다"고 짚어준다.
- **시나리오 품질 불만**: 사용자가 "장면이 별로다", "와닿지 않는다" 하면 에이전트한테 "다시 잘 써줘"만 던지지 말고, 입력 중 무엇이 모호했는지 되짚어 더 구체화한 뒤 재위임한다.
