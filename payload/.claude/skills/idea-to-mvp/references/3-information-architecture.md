## 1. 단계 목표

이 단계의 목표는 **`user-story.md`와 `feature-list.md`에서 정보 구조(IA, information architecture — 서비스 안의 모든 화면과 정보를 어떤 순서·계층으로 놓을지 정한 지도)를 뽑아내, 빠진 화면이 없는 목록을 만드는 것**이다. 산출물은 `mvp/information-architecture.md` 한 파일 — §2.3의 6개 절을 담는다.

**입력은 둘이고 역할이 다르다.** `user-story.md`는 동선과 진입 경로의 원천이다 — 사람이 어떤 순서로 무엇을 거쳐 목적을 이루는지가 여기에만 있다. `feature-list.md`는 완전성 체크리스트다 — 이 서비스가 무엇을 하기로 했는지의 전체 목록이라, 화면을 다 뽑았는지 대조하는 데 쓴다. **기능 목록이 스토리를 대체하지는 않는다** — 기능만 보고 화면을 뽑으면 목록은 채워져도 사람이 지나갈 길이 안 그려진다.

**왜 필요한가.** 유저 스토리는 **한 사람의 성공 경로 하나**다 — 발견→온보딩→첫 사용→아하 모먼트→에필로그로 이어지는 영화 한 편의 서사지 서비스 전체가 아니다. 그런데 4단계 Prototype의 프롬프트는 "인벤토리에 없는 화면은 추가하지 마"라고 못 박는다. 여기서 빠진 화면은 영원히 안 생긴다. 그래서 **기억에 의존하지 말고, 빠지면 표에 빈칸이 남게** 만든다. 목표를 이뤘는지는 §3 완료 체크리스트로 판정한다.

## 2. 진행 절차

### 2.1 단계 시작 — 이전 정리 내용을 보여주고, 이번 단계가 할 일을 안내한다

`mvp/user-story.md`와 `mvp/feature-list.md`를 읽고 **로그라인**(logline — 서비스의 정서를 담은 한 줄 요약)·**장면(S#) 목록**·**기능 목록의 역할별 기능 수와 범위 결정(만든다/안 만든다)**을 짧게 요약해 보여준 뒤, 왜 이 단계를 거치는지 설명한다.

설명 골자 — 그대로 또는 풀어서 전달:

> 유저 스토리는 주인공 한 명이 술술 성공하는 이야기야. 근데 실제 서비스엔 데이터가 하나도 없는 첫 화면, 로그인 실패, 설정, 삭제 확인이 다 있어야 해. 시나리오엔 안 나오지. 그래서 목업 전에 화면 목록을 훑어 빠진 걸 채운다.

이미 `mvp/information-architecture.md`가 있으면(스킬 중간 재실행 등) 읽고 §3 체크리스트로 검증해 부족한 부분만 보완한다 — 처음부터 다시 만들지 않는다.

### 2.2 일곱 갈래 훑기 — 누락 체크리스트

초안 전에 아래 일곱 갈래를 **하나씩 훑는다**. 유저 스토리에 없어도 그 갈래의 화면이 이 서비스에 필요하면 넣고, **왜 넣었는지 한 줄 근거**를 단다. 근거를 못 쓰겠으면 넣지 말고 사용자에게 물어본다.

이 갈래 중 일부(반대편 역할·계정·설정 등)는 2단계 기능 목록에서 이미 나왔을 수 있다 — 겹치면 새로 만들지 말고 **대조만 한다**.

| 갈래 | 빠지는 것 | 왜 치명적인가 |
|---|---|---|
| 상태 변형 | 빈 상태(데이터 0개)·로딩·오류·항목 과다·긴 텍스트 | **빈 상태가 신규 사용자의 첫 화면이다.** 이탈이 여기서 제일 많이 난다 |
| 분기·실패 | 로그인 실패·검색 결과 0건·권한 거부·결제 실패·중복 가입 | 시나리오 주인공은 절대 실패하지 않는다 |
| 반대편 역할 | 공급자·운영자의 **완결된** 여정 | 시나리오엔 관점 전환 장면 한두 개(양면 시장이면 2~3개)뿐 — 여정이 아니라 장면이다 |
| 진입점 | 알림 눌러 진입·공유 링크 진입(비로그인)·딥링크(deep link — 앱 안 특정 화면으로 바로 꽂히는 링크)·재방문 | 시나리오는 항상 처음부터 순서대로 온다 |
| 계정·설정 | 로그인·비밀번호 찾기·로그아웃·프로필 편집·알림 설정·탈퇴 | 시나리오는 "가입"만 그린다 |
| 되돌리기 | 취소·수정·삭제 확인·되돌리기 | 지우는 행동엔 확인 화면이 필요하다 |
| 시스템 | 권한 요청·오프라인·점검 중·강제 업데이트 | 없으면 앱이 멈춘 것처럼 보인다 |

### 2.3 초안 만들기 (초안 모드)

SKILL.md §1.5의 **초안 모드** — AI가 아래 6개 절을 통째로 채운 뒤 완성본으로 한 번에 리뷰받는다. 화면 하나하나 승인받지 않는다.

**① 객체 지도**(OOUX, object-oriented UX — 서비스를 명사 단위로 쪼개 보는 방법) — 시나리오는 동사(행동) 중심이라 빠뜨리기 쉽지만, 명사는 유한하고 셀 수 있다. 명사 하나마다 목록·상세·만들기·수정·삭제 화면이 기계적으로 나온다. 객체끼리의 관계(무엇이 무엇에 속하는지)도 적는다.
> 예: 모임 앱 → 객체는 `모임`·`사용자`·`후기`·`알림`. `모임` 하나에서 목록/상세/만들기/수정/참가자 관리 5개가 나온다.

**② 역할 목록** — 비로그인 방문자 / 소비자 / 공급자 / 운영자 등. 이 서비스에 실제로 있는 역할만.

**③ 화면 인벤토리 표** — 이 단계의 핵심 산출물. ①②와 §2.2에서 나온 화면을 전부 한 표에 모은다. 형식은 §4.1.

**④ 상태 매트릭스** — 화면 × 상태 격자. 형식은 §4.2.

**⑤ 네비게이션 구조**(navigation — 화면 사이를 오가는 길) — 탭 · 스택(stack — 화면이 쌓였다 뒤로가기로 벗겨지는 구조) · 모달(modal — 지금 화면 위에 덮어 뜨는 창) 계층. 어떤 화면이 어디에 속하는지.

**⑥ 커버리지 자가 점검** — 고아 화면 0건 / 막다른 골목 0건 확인(§4.1) + 일곱 갈래가 인벤토리에 반영됐는지 갈래별 O/X + **기능 목록 대조**. X면 근거 한 줄.

기능 목록 대조는 `feature-list.md`의 `만든다` 기능을 하나씩 짚어 *그 기능이 드러날 화면이 인벤토리에 있는지* 확인하는 일이다. **1:1 매핑이 아니다** — 기능 하나가 화면 여럿에 걸리기도 하고, 화면 하나에 기능 여럿이 얹히기도 한다. **화면이 없는 기능은 "없음"이 정답이다** — 뒤에서 도는 자동화나 정책은 눈에 보이는 화면이 없는 게 정상이라, 억지로 화면을 만들지 않는다.

### 2.4 MVP 경계선 긋기

**전체를 그리되, 이번에 만들 것만** 인벤토리의 `MVP 포함` 칸에 O로 표시한다. 안 만들 화면도 목록엔 X로 남긴다 — 그래야 나중에 "이거 왜 없지?"가 아니라 "의도적으로 뺐지"가 된다. 어디에 그을지는 사용자 판단이니, 애매하면 AI가 후보를 제시하고 고르게 한다 (SKILL.md §1.4). 단, `MVP 포함` 판단은 **2단계 기능 목록의 범위 결정(만든다/안 만든다)을 따른다** — 여기서 범위를 새로 정하지 않는다. 기능 목록과 어긋나는 판단이 필요해 보이면 그것부터 사용자에게 짚어 확인한다.

경계선을 그은 뒤, `MVP 포함 = O`인 화면 안에 `MVP 포함 = X` 화면으로 이동하는 버튼·링크가 생길 자리가 있으면 **"미룬 화면을 가리키는 버튼" 표**로 정리한다. 형식·용도는 §4.3.

### 2.5 결과 보고·리뷰

완성한 초안 앞에 셋을 짧게 붙인다 — **화면 개수**(전체 N개 중 MVP 포함 M개) · **새로 넣은 화면**(갈래별 개수와 근거) · **자가 점검 결과**(고아 0 / 막다른 골목 0 / 일곱 갈래 O·X).

수정 요청이 오면 표를 고치고 자가 점검을 다시 돌려 보여준다. 자율 재작업은 최대 2회 — 수렴 안 되면 중간 상태 그대로 들고 간다 (SKILL.md §1.5).

## 3. 완료 체크리스트

- [ ] **객체 지도·역할 목록** (§2.3①②) — 명사마다 나오는 화면이 인벤토리에 반영됨.
- [ ] **화면 인벤토리 표 완성** (§4.1) — 모든 화면에 7개 칸이 다 채워짐.
- [ ] **고아 화면 0건 / 막다른 골목 0건** (§4.1) — 진입·이탈 경로가 0개인 화면 없음.
- [ ] **상태 매트릭스 빈칸 0개** (§4.2) — 안 만들 칸은 `해당없음`.
- [ ] **일곱 갈래 O/X 기록** (§2.3⑥) — X인 갈래엔 근거 한 줄.
- [ ] **기능 커버리지 대조** (§2.3⑥) — `feature-list.md`의 `만든다` 기능마다 드러날 화면을 짚음. 화면 없는 기능은 "없음"으로 명시.
- [ ] **MVP 경계선 사용자 확인** (§2.4)
- [ ] **미룬 화면을 가리키는 버튼 표 작성** (§4.3) — 해당 버튼 없으면 "없음" 명시.

### 3.1 다음 단계 핸드오프

산출물 저장 직후, 매 단계 공통대로 **`/clear` 후 `/idea-to-mvp` 재호출**을 권장한다 (SKILL.md §3.2). 다음 단계는 4단계(Prototype) — 이 문서와 `user-story.md`를 **함께** 외부 Claude Design에 입력한다 (`4-prototype.md`). 역할이 갈린다 — **이 문서가 완전성**(빠진 화면 없음), **유저 스토리가 정서와 방향**(톤·마이크로카피·버튼 문구).

**이 문서의 수명**: 4단계에서 두 번 쓰이고 끝난다 — Claude Design에 목업 생성 스펙으로 첨부될 때, 그리고 마이그레이션 뒤 코드에 빠진 화면이 없는지 대조할 때. 마이그레이션이 끝나면 이 문서는 **1세대 기록**으로 얼려진다 — 이후 피드백을 반영해 화면 구조가 바뀌어도 이 문서는 갱신하지 않고 코드에만 반영한다 (`4-prototype.md` §2.7).

## 4. 산출물 스펙

위치: 프로젝트 루트의 `mvp/information-architecture.md`. §2.3의 6개 절 + §2.4의 미룬 화면 버튼 표를 순서대로 담는다.

### 4.1 화면 인벤토리 표

| ID | 화면 이름 | 역할 | 목적 | 진입 경로 | 이탈 경로 | MVP 포함 |
|---|---|---|---|---|---|---|
| S-01 | 홈 | 소비자 | 모임 목록 보기 | 앱 실행, 하단탭 | S-02(상세), S-10(검색) | O |
| S-02 | 모임 상세 | 소비자 | 참가할지 결정 | S-01, 공유 링크(비로그인) | S-03(참가 신청), 뒤로 → S-01 | O |
| S-31 | 신고 처리 | 운영자 | 신고 검토·조치 | 운영자 알림, S-30(신고 목록) | S-30 | X (2차) |

- **ID**(`S-01` 형식)로 4단계에서 목업 화면과 대조한다.
- **진입 경로 0개 = 고아 화면** — 만들었는데 갈 수가 없다. *그리로 가는 버튼이 있는 화면*이 빠진 것.
- **이탈 경로 0개 = 막다른 골목** — 들어가면 못 나온다. *되돌아갈 길*이 빠진 것.
- 이 두 검사가 자동 누락 탐지기다.

### 4.2 상태 매트릭스

화면 × 상태(정상 / 빈 / 로딩 / 오류 / 권한없음) 격자다.

| 화면 | 정상 | 빈 상태 | 로딩 | 오류 | 권한없음 |
|---|---|---|---|---|---|
| S-01 홈 | O | O "아직 모임이 없어요" + 만들기 버튼 | O 뼈대 화면 | O 재시도 버튼 | 해당없음 |
| S-02 모임 상세 | O | 해당없음 | O | O 삭제된 모임 안내 | O 비공개 모임 안내 |
| S-03 참가 신청 | O | 해당없음 | O | O 정원 초과 안내 | O 로그인 유도 |

- **빈칸을 남기지 않는다.** 안 만들 칸엔 반드시 `해당없음`이라고 적는다. 그래야 *빠뜨린 것*과 *일부러 뺀 것*이 구분된다.
- 다섯 상태를 다 만들 필요는 없지만 **모든 칸에 판단은 적혀 있어야 한다.**
- `O` 옆에 뭘 보여줄지 한 줄 적어두면 4단계 목업 프롬프트가 그대로 써먹는다.

### 4.3 미룬 화면을 가리키는 버튼 표

`MVP 포함 = O`인 화면 안에서 `MVP 포함 = X`인 화면으로 이동하는 버튼·링크 자리를 전부 모은 표다. 4단계 목업 프롬프트(§2.2.3)가 이 표를 근거로 해당 버튼을 그리지 않는다 — 표에 없으면 눌러도 갈 곳이 없는 죽은 버튼이 생긴다.

| 있는 화면(ID) | 버튼·링크 자리 | 가리키는 미룬 화면(ID) | 비고 |
|---|---|---|---|
| S-02 모임 상세 | "신고하기" 버튼 | S-31 신고 처리 (X, 2차) | 이번 목업·코드에선 그리지 않음 |
| S-02 모임 상세 | "후기 작성" 버튼 | S-20 후기 작성 (X, 2차) | 1차엔 후기 기능 미포함이라 버튼 자체를 안 그림 |

해당하는 버튼이 하나도 없으면 표 대신 "없음" 한 줄로 남긴다.

## 5. 사용자 응대 톤

- **톤**: SKILL.md §1.3 따름 — 반말·친근·짧게.
- **초안 모드다** — 화면 하나씩 "이거 넣을까?" 묻지 않는다 (§2.3).
- **표가 길어도 다 보여준다** — 화면이 30개면 30줄 다. 요약해서 접으면 *빠진 걸 찾는다*는 이 단계의 목적이 사라진다.
- **"이렇게 많이 필요해?"**: 정상 반응이다. 목록에 있다고 이번에 다 만드는 게 아니라고 짚어준다 (§2.4).
- **"잘 모르겠어"는 정상 답** — AI가 후보 2~3개 제시하고 고르게 한다 (SKILL.md §1.4). 역할 목록과 MVP 경계선에서 특히 자주 나온다.
