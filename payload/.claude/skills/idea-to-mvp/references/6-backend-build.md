5단계가 만든 프로토타입은 화면도 돌고 클릭도 되지만, 데이터가 **브라우저 로컬스토리지(localStorage — 그 브라우저 안에만 저장되는 공간)**에만 쌓인다. 다른 기기로 열면 아무것도 없고, 여러 사람이 같은 데이터를 나눠 쓸 수도 없다. 이 단계는 그 앱에 **진짜 백엔드·DB·auth를 붙여 실서비스로 완성**하고, 퍼널 계측을 심어 배포하는 자리다. 산출물은 실서비스가 된 앱 코드 + `backend-build.md` 하나.

**이 문서는 단계 전체의 허브다.** 실제 작업 절차 중 둘은 주제 문서가 담당한다 — **DB·스키마는 [`backend-db-schema.md`](backend-db-schema.md)**, **로그인·동의·권한은 [`auth-and-consent.md`](auth-and-consent.md)**.

## 1. 단계 목표

- **배포된 실서비스** — 5단계 프로토타입(로컬스토리지로 도는 리액트 앱)에서 로컬스토리지를 걷어내고 Supabase(DB·auth)를 붙여, 실데이터가 흐르는 서비스로 완성해 공개 URL로 배포.
- **(선택) 베타 공유** — 5단계에서 프로토타입을 같이 본 지인·팀 동료가 있으면 실데이터가 붙은 링크를 보내 크게 깨지는 데가 없는지 확인한다 (판정 아닌 확인). **마땅한 사람이 없으면 건너뛴다.**
- **퍼널 계측 심기** — 유입·가입·핵심행동·재방문·결제 5종 이벤트가 실제로 찍힘. 7단계(MvpLaunch) 판정의 데이터 원천.
- **(지불이 이 서비스의 핵심 교환이면) 실결제** — 판단 기준은 코드다. **5단계 화면에 결제 흐름이 있으면** 실제로 돈이 오가게 붙인다 (fake door 아님). 화면에 없으면 만들지 않는다.
- **`backend-build.md`** — 스택 추가분·베타 공유 관찰(해당 시)·배포 정보·추후 결정·빌드 중 발견 기록. **코드를 서술하는 내용은 적지 않는다.**
- **실서비스 개통은 이 6단계에서 끝난다** — 실 DB·개인정보 수집·결제·공개 배포가 전부 여기 안에 들어간다. 7단계(MvpLaunch)는 광고를 돌려 숫자로 판정하고 회고하는 단계지, 인프라를 새로 세우는 단계가 아니다.

**SoT 책임** (SKILL.md §2.1): **이 단계의 스펙은 5단계 앱 코드 하나다.** 화면에 구현된 것을 백엔드로 실물화하고, 화면에 없는 건 만들지 않는다. 백엔드 스키마의 SoT는 마이그레이션 파일, 계측 이벤트의 SoT는 이벤트 테이블 스키마와 추적 코드다.

**그래서 `backend-build.md`에는 코드에 실을 수 없는 것만 남긴다.** 코드를 서술하는 내용 — 스키마 표, 계측 이벤트 정의, "어느 파일에 뭐가 있다" 식의 포인터 — 은 **어떤 형태로도 적지 않는다.** 낡은 문서가 코드와 충돌해 그걸 읽은 다음 작업이 엉뚱한 결과를 낳기 때문이다. 남기는 건 이 단계에서 새로 추가한 스택(결제 PG 등, ADR 링크)·베타 공유 관찰·배포 정보·추후 결정·빌드 중 발견이다. 스택 조합(Next.js·React·TypeScript·Supabase·Vercel과 핀한 버전)은 5단계에서 확정·기록됐으니 여기선 참조만 한다.

**여기서 안 하는 것 (의도적)**:

- ❌ 스택 선택·개발환경 구성·프런트 신규 구현 — 전부 5단계 몫. 그 절차가 필요하면 `5-frontend-build.md`를 본다. 여기선 **이미 있는 코드에 백엔드를 얹는다**.
- ❌ 화면 구조 갈아엎기 — 코드를 고치는 건 정상이지만, 화면이 늘거나 빠지는 구조 변경은 5단계로 돌아가 프로토타입을 고친 뒤 다시 오는 일이다 (§5). 이 단계에서 새로 생기는 화면은 동의 온보딩 하나뿐이다 (§2.2 범위 가드).
- ❌ PRD·Architecture·Design·**DB 설계** 문서 작성 — 앱 코드와 마이그레이션 파일이 스펙 (`backend-db-schema.md` §2.1). 문서 ceremony 금지.
- ❌ 명세 밖 기능·화면 추가 — `추후 결정:` 마킹만.
- ❌ 다크모드·다국어·반응형 정교화·성능 튜닝·부하 대비 — production 영역. (단, 광고 유입 랜딩 경로(랜딩→가입→핵심행동)는 모바일 화면 확인이 필수 — 7단계 소액 광고 유입은 대부분 모바일이라, 이 경로가 모바일에서 깨져 있으면 퍼널 실측이 제품 반응이 아니라 깨진 화면을 재는 꼴이 돼 통과 기준이 오염된다.)
- ❌ CI·테스트 스위트 정교화 — 검증 가설과 무관한 인프라 투자는 production에서.
- ❌ 광고·채널 준비 — 7단계(MvpLaunch) 영역 (단 결제 PG 심사처럼 리드타임 긴 것만 병렬 시작 OK).

**헷갈리기 쉬운 하나 — 검색 노출(SEO)은 이 목록에 없다. 여기서 한다** (§2.3). 위 항목들은 나중에 해도 같은 크기의 일이지만, 검색 노출은 서버가 데이터를 채워 보내는 구조에 얹히는 거라 나중에 하면 그 구조부터 다시 뜯는 더 큰 일이 된다.

## 2. 진행 절차

### 2.1 단계 시작 — 이전 정리 내용을 보여주고, 이번 단계가 할 일을 안내한다

이 단계에 들어오면 가장 먼저 사용자와 "지금까지 어디까지 왔고, 이제 무엇을 할지"를 맞춘다:

1. **이전 단계까지 정리된 내용을 먼저 보여준다.** 입력이 둘이다:
   - **프로젝트 루트의 앱 코드** (5단계 산출물) — **이 단계의 스펙이자 화면·플로우의 SoT.** 정답지로 모셔두는 게 아니라 이 단계에서 이어서 고칠 실코드다. 지금 데이터가 어디에(로컬스토리지 어느 키에) 어떤 모양으로 쌓이는지, 각 데이터의 소유자 주석(`5-frontend-build.md` §2.5.5)이 뭐라고 적혀 있는지부터 읽는다.
   - **3단계 `market-research.md`의 조사 요약** (경쟁 지형·차별화 힌트) — 무엇부터 만들지·무엇을 미룰지 판단할 때 쓰는 참고 맥락 (없으면 없는 대로 진행).

   둘 다 짧게 요약해 보여준다.
2. **그 내용을 기반으로 이번 단계가 무엇을 하는지 설명한다.** 지금 앱은 데이터가 브라우저 안에만 쌓여서 다른 기기로 열면 비어 있다고 짚고 — 이제 로컬스토리지를 걷어내고 실 DB·로그인을 붙여서 → 실데이터가 도는 상태로 베타 공유해 치명 결함 확인 → 퍼널 계측을 심고 → 최종 배포까지 완주하는 단계라고 안내한다.
3. **이미 `backend-build.md`가 있으면**(스킬 중간 재실행 등) 읽고 §3 체크리스트로 검증해 부족한 부분만 보완한다. 앱 코드는 5단계부터 있으니 이 단계를 했다는 표시가 못 된다 — 6단계 진행 여부는 `backend-build.md`로 판단한다.

**진입 조건**: 프로젝트 루트에 5단계가 만든 앱 코드(`package.json`·`src/` 등)가 있고, **사용자가 5단계를 완료로 선언한 상태**여야 한다. 아직 화면을 고치는 중이면 강행하지 말고 5단계에서 마무리하자고 안내한다. 3단계 `market-research.md`는 있으면 참고하고 없으면 없는 대로 간다 — 그 단계는 게이트가 아니다.

### 2.2 백엔드·DB·auth 연동 (이 단계의 첫 일)

이 절차는 SKILL.md §1.5 **초안 모드** — AI가 끝까지 완주한 뒤 완성본으로 리뷰받는다. 중간에 테이블 하나하나 승인받지 않는다.

**5단계에서 Supabase는 "붙일 자리만 잡아둔" 상태다** — 프로젝트 생성 + 환경변수 연결까지만 돼 있고, **테이블·RLS·auth는 여기서 처음 만든다.** 그래서 이 단계의 첫 일은 로컬스토리지를 걷어내고 그 자리를 Supabase로 채우는 것이다.

**절차는 주제 문서 둘이 나눠 담당한다** — 이 절은 순서와 경계만 잡는다:

- **DB·스키마** — 로컬 스택 준비, 마이그레이션 파일 작성, 로컬·클라우드 검증, 백업까지: [`backend-db-schema.md`](backend-db-schema.md)
- **로그인·동의·권한** — 동의 흐름, 온보딩, 약관 페이지, 역할·세션 구현 표준: [`auth-and-consent.md`](auth-and-consent.md)

**환경은 2단이다 — 로컬(도커) 하나, 클라우드 하나**

손대기 전에 이것부터 정해 둔다. **로컬(도커)이 개발과 마이그레이션 검증을 맡고, 클라우드 Supabase 프로젝트 1개가 실서비스를 맡는다.** 그 사이에 스테이징(staging — 실서비스에 올리기 전 똑같이 만들어 두는 연습용 환경)을 하나 더 두지 않는다.

- **클라우드 DB를 두는 이유는 "한 번 더 검증"이 아니다** — 배포된 앱이 내 컴퓨터 주소(127.0.0.1)에 접속할 수 없어서다. 검증하려고 두는 게 아니라, 배포된 앱이 붙을 곳이 필요해서 두는 것.
- **마이그레이션 검증은 오히려 로컬이 더 강하다** — `db reset`은 전체 마이그레이션을 0부터 다시 재생하지만, 클라우드에 미는 건 이미 있는 상태 위에 새것만 얹는 것이라 검증력이 약하다.
- **클라우드를 개발용·실서비스용 둘로 쪼개면 손해가 크다** — OAuth 앱(콜백 주소가 앱당 하나라 두 개를 따로 만들어야 한다)·Storage 정책·마이그레이션 푸시가 전부 두 벌이 된다. **밀 곳이 늘어나는 만큼 두 곳이 서로 어긋나는(드리프트) 사고 확률이 커진다** — 드리프트(drift — 같아야 할 두 곳의 상태가 서로 어긋나는 것). 얻는 것보다 잃는 게 크다.
- **미리보기 배포에도 DB가 필요해지면** 프로젝트를 하나 더 만들지 말고 Supabase 브랜치 기능(`supabase branches`)을 먼저 검토한다.

**작업 순서**:

1. **지금 상태 모양 파악** — 앱 코드가 로컬스토리지에 무엇을 어떤 모양으로 저장하는지 읽는다. 여기가 스키마의 실측 근거다.
2. **스키마 설계** — 1에서 읽은 실제 저장 모양을 그대로 테이블로 옮긴다. 5단계가 로컬스토리지 구조를 데이터 모델 그대로 만들어뒀기 때문에 **코드가 곧 데이터 모델이다** — `mvp/handoff/` 문서를 다시 열지 않는다. 만드는 절차는 `backend-db-schema.md`.
   - **마이그레이션 파일을 쓰기 전에, 어떤 표를 만들고 각 표의 소유자를 무엇으로 잡을지 대화로 요약해 보여주고 승인받는다.** 되돌리기 비싼 갈림길이라 초안 모드 예외다 (SKILL.md §1.5 에스컬레이션 (c)). **이 요약을 파일로 남기지 않는다** — 승인 뒤 바로 마이그레이션 파일을 쓰고, 그 파일이 곧 설계 문서다.
3. **auth 붙이기** — Supabase Auth로 가입·로그인. 로컬스토리지 시절엔 "사용자"가 없었으니, 소유자 기준(어느 행이 누구 것인지)을 이때 처음 정한다. 절차·표준은 `auth-and-consent.md`.
4. **읽기·쓰기 경로 교체** — 로컬스토리지 호출을 Supabase 클라이언트 호출로 바꾼다.
5. **로컬스토리지 코드 제거** — 남겨두고 폴백으로 쓰지 않는다. 두 갈래로 남으면 어느 쪽이 진짜 데이터인지 알 수 없어져, 베타 공유·계측 숫자가 전부 오염된다. (기기 간 이어쓰기용 마이그레이션도 하지 않는다 — 5단계에서 브라우저에 쌓인 데이터는 버리는 데이터다.)

**RLS는 필수다** — 모든 표에 RLS 활성화 + 정책 작성. Supabase 공개 키(anon key)가 브라우저에 그대로 노출되는 구조라, RLS가 없으면 그 키 하나로 모든 테이블이 열린다 — Supabase 프로젝트에서 가장 흔하고 치명적인 사고 지점이다.

**보안 baseline**: auth·API·업로드·`supabase/` 코드를 만지면 `.claude/rules/security-baseline.md`가 자동 로드된다 — 1부 외부 도달 baseline(http-only cookie·민감정보·업로드 검증·rate limit·에러에 stack 미노출)과 2부 Supabase 권한 baseline(기본 비공개·grant와 정책 두 겹·정책 모양 다섯 줄·하지 말 것 아홉) 준수. 광고로 모르는 사람들이 실제로 들어오는 코드다.

**범위 가드 (강제)**:

- 5단계 앱 코드에 없는 화면·기능을 추가하지 않는다. 이 단계에서 새로 생기는 화면은 **동의 온보딩 하나뿐**이다 (동의 온보딩의 정의는 `auth-and-consent.md`). "이것도 있으면 좋겠는데" 신호는 `추후 결정:`으로 `backend-build.md`에 마킹만.
- 5단계에서 화면만 있고 동작은 비워둔 영역이 있다면 — 이번에 *실제로 작동*시켜야 하는지는 **핵심 플로우(랜딩 → 가입 → 핵심행동)가 돌아가는 데 필요한가**로 판단한다. 그 흐름에 안 걸리면 그대로 둔다.
- 다크모드·다국어·반응형 정교화·성능 튜닝·CI 정교화는 범위 밖 (§1 "여기서 안 하는 것").

**이 단계에서 새로 추가하는 스택만 ADR로 기록한다** (`mvp/adr.md` — SKILL.md §3.1 "스택 주요 컴포넌트 추가·제거" 트리거). 여기서 ADR 대상이 되는 건 결제 PG(토스페이먼츠·Stripe 등)처럼 이 단계에 와서 붙이는 것들이다 — 결제는 심사 리드타임이 있어 백엔드 연동과 병렬로 시작한다.

**에스컬레이션**: 명세와 모순 발견·스키마가 크게 갈리는 선택·외부 서비스 추가 필요 시 멈추고 배치 질문. 그 외 애매함은 합리적 가정 + `추후 결정:` 마킹 후 계속.

### 2.3 검색 노출(SEO) — 이 시점에 같이 한다

로컬스토리지 시절엔 데이터를 서버가 모르니 검색엔진에 보여줄 HTML을 애초에 만들 수가 없었다. 그래서 검색 노출은 위에서 읽기·쓰기 경로를 Supabase로 갈아끼우는 **바로 그때 같이** 한다. 따로 떼어두면 잊히고, 나중에 하려면 서버가 데이터를 채워 보내는 구조부터 다시 뜯게 된다.

1. **기본 세트 적용** — 페이지별 제목·설명, 공유 미리보기(OG — 링크를 카톡·슬랙에 붙였을 때 뜨는 제목·설명·이미지), sitemap·robots, 없는 콘텐츠에 404 상태코드. 구체적인 방법은 여기 적지 않는다 — 널리 알려진 일반 지식이라 그때그때 최신 방식으로 하면 된다.
2. **5단계에서 걸어둔 색인 제외를 여기서 푼다** — `5-frontend-build.md` §2.6에서 프로토타입 전체를 검색에 안 잡히게 막아뒀다. 검색 노출을 켠다는 건 그걸 푸는 일이다. 단 **전부 푸는 게 아니다** — `.claude/rules/security-baseline.md` 1부가 말하는 대로 검색엔진은 외부 도달 경로라, 공개할 페이지만 열고 운영 콘솔·개인 전용 화면은 계속 막아둔다. 어느 화면이 공개인지는 4단계 인벤토리의 역할 열을 **출발점으로 참고**하되, 판정은 **현재 코드에 실제 있는 화면 기준**으로 한다 — 인벤토리는 1세대 기록이라 5단계 이후 코드에서 바뀐 화면이 반영돼 있지 않다.
3. **함정: 빈 상태가 200으로 나간다** — 4단계 상태 매트릭스대로 화면마다 빈 상태를 만들어 뒀기 때문에, 없는 콘텐츠 주소로 들어와도 "아직 없어요" 화면이 정상(200) 응답으로 나가기 쉽다. 검색엔진은 그걸 내용 없는 페이지로 색인한다. **데이터가 0개인 것(빈 상태, 200)과 그 주소가 아예 없는 것(404)을 갈라서** 처리한다.
4. **함정: `loading.tsx`가 404를 200으로 바꿔 놓는다 (Next.js)** — 라우트에 `loading.tsx`를 두면 그 라우트는 **스트리밍**(화면 뼈대를 먼저 보내고 내용은 준비되는 대로 이어 보내는 방식)으로 바뀐다. 뼈대를 먼저 보내는 순간 **응답 상태코드가 200으로 확정**되고, 그 뒤에 `notFound()`를 불러도 상태 줄은 이미 나간 뒤다. 결과는 없는 주소가 **200 + "불러오는 중"**으로 응답하는 것 — 검색엔진이 없는 페이지를 빈 내용으로 색인한다. 라우터가 아예 모르는 주소는 그대로 404가 나오니 **눈치채기 어렵다.**
   - **해법**: 있는지 없는지만 확인하는 **가벼운 조회 하나를 먼저 `await`** 한다 — 아직 아무것도 안 보낸 시점이라 여기서 부르는 `notFound()`는 진짜 404를 낸다. 무거운 나머지 조회는 `<Suspense>`로 감싸 흘려보낸다. `loading.tsx`는 **존재 확인이 필요 없는 화면**(목록·홈)에만 둔다.
   - **메타데이터도 같이 가른다** — `generateMetadata`는 가벼운 조회만 쓰게 한다. 제목·설명·OG는 한 줄이면 되는데 무거운 조회를 기다리면 첫 응답이 그만큼 늦어진다.
5. **판정** — `curl <배포 URL> | grep <화면에 보이는 콘텐츠 문구>`가 잡혀야 통과. 안 잡히면 서버가 데이터를 안 채워 보낸 것이라 나머지가 전부 무의미하다. **브라우저를 안 여는 검사라 AI가 직접 끝까지 확인한다** (SKILL.md §1.5 "사람 몫"은 화면을 눈으로 보는 검증 얘기고, 이건 응답 본문을 확인하는 일이라 해당 없다).

**연동이 끝나면 배포해 링크를 갱신한다** — §2.5 베타 공유에 쓸 링크가 실데이터로 돌아야 한다. 5단계 배포 링크는 그대로 두고 재배포하면 된다.

### 2.4 스모크 테스트 — 밖에서 보이는 계약만

여기서 **스모크 테스트(smoke test — 크게 깨진 데가 없는지 빠르게 훑는 최소 검사)**를 처음 도입한다.

**5단계에는 테스트를 쓰지 않는다** — 화면을 만들고 고치는 동안 구조가 매일 뒤집히는데 테스트를 쓰면 매번 다시 쓰게 되고, 싸야 할 검증 루프가 비싸진다. 그 구간이 싼 건 의도된 설계다. 거기선 깨지면 화면에 바로 보이니 사람 눈이 제일 싸고 빠르다.

**6단계에서 시작한다** — 백엔드와 검색 노출이 붙는 순간 **깨져도 눈에 안 보이는 것**이 생기기 때문이다. 실제로 있었던 일 셋: ① `loading.tsx`를 붙였더니 없는 주소가 404 대신 200으로 나갔는데 화면은 멀쩡해서 사람이 상태 코드를 손으로 재고서야 발견 ② 로그인 토큰이 만료되자 로그인과 상관없는 공개 화면이 통째로 죽었는데 사용자 신고로 발견 ③ 서버 렌더로 옮기며 조회 경로가 두 벌로 갈라진 것은 따로 검토를 돌려서야 발견. 상태 코드·크롤러가 받는 HTML·색인 제외·권한은 브라우저로 눌러봐선 안 보인다.

거창한 테스트 피라미드를 세우자는 게 아니다. **밖에서 보이는 계약만** 확인한다.

**기본 세트** — 도는 서버에 실제 요청을 넣어 확인한다:

| 확인 | 왜 |
|---|---|
| 공개 화면이 200 + **내용이 HTML에 실려 있음** | 검색 노출의 전제 (§2.3 5번 `curl` 판정을 테스트로 굳힌 것) |
| 목록→상세가 **진짜 `<a href>`** | 크롤러가 따라갈 길 |
| 낱개 제목·공유 미리보기(OG) 태그 | 링크를 붙였을 때 페이지마다 다 같아 보이면 안 됨 |
| **없는 주소는 404, 빈 상태는 200** | §2.3 3·4번이 못 박은 것 — 브라우저로는 절대 안 보임 |
| `robots.txt`·사이트맵이 열리고, 막을 것을 막음 | |
| **색인 제외 상태** — 아직 공개 전인 5단계 상태면 켜져 있어야 | 공개하는 날 이 테스트를 뒤집는다. 코드와 짝이라 한쪽만 고치면 걸린다 |
| **로그인 토큰이 만료돼도 공개 화면이 열림** | 공개 데이터는 로그인 상태와 무관해야 함 |

**만드는 법 — 도구를 늘리지 않는다**:

- **Node 내장 테스트 러너(`node:test`)면 충분하다** — 새로 깔 게 0개. vitest·jest는 컴포넌트를 하나하나 테스트할 필요가 생겼을 때 판단할 일이지, 이 목적으로 새로 깔지 않는다.
- **대상 주소는 사이트맵에서 뽑는다** — DB에 붙지 않아도 되고, 주소만 바꾸면 로컬이든 배포본이든 같은 테스트가 그대로 돈다.
- `package.json`에 실행 항목 하나 (예: `"smoke": "node --test ..."`).

**⚠ CI에서 도는 것과 안 도는 것을 갈라 쓴다**:

- **스모크 테스트는 깃허브 CI에서 못 돌 수 있다** — CI에는 로컬 DB가 없다. `done-task` 전에 **로컬에서 돌리는 검사**로 두거나, 배포된 미리보기 주소를 향해 쏜다. **CI에 넣었다고 착각하게 쓰지 마라 — 안 도는 검사는 없는 검사보다 나쁘다** (있다고 믿게 되니까).
- **반면 라우트 정적 검사는 CI에서 돈다** — `notFound()`를 부르는 `page.tsx`가 있는 라우트 갈래에 `loading.tsx`가 있으면 실패시키는 검사다. 파일만 읽으면 되니 서버도 DB도 필요 없다. §2.3 4번 함정을 빌드 전에 기계로 막는 자리다.

**새 검사를 언제 늘리나** — 사람 손으로 한 번 확인한 것이 **두 번째로 필요해지면** 그때 테스트로 옮긴다. 위 기본 세트도 손으로 열 번 넘게 반복한 `curl` 묶음이 그대로 굳은 것이다.

### 2.5 베타 공유

**이 절은 건너뛸 수 있다.** 5단계에서 프로토타입을 같이 본 지인·팀 동료가 있으면, 배포된 링크를 그 사람들에게 보내 **실제 사용 반응**을 확인한다. **마땅한 사람이 없으면 이 절을 통째로 건너뛰고 §2.6(퍼널 계측)으로 간다** — 이걸 하려고 사람을 새로 구하러 다니지 않는다.

**왜 백엔드 연동 뒤인가**: 5단계에서 이미 화면은 보여줬으니 화면 반응은 새로 볼 게 없다. 이 시점 공유가 볼 값어치가 있는 건 **실데이터가 흐를 때의 행동**이다 — 진짜로 계정을 만드는지, 자기 데이터가 남는 걸 확인하고 다시 들어오는지, 핵심 플로우에서 어디서 이탈하는지.

**판정 아님**: 계속/중단을 가르는 관문이 아니라 치명 결함(가입 실패·데이터 유실·핵심 플로우 이탈·심각한 오해) 확인용이다. 발견되면 수정 후 재공유, 없으면 §2.6(퍼널 계측)으로 진행. 관찰 내용은 `backend-build.md`에 짧게 기록한다.

**사용자가 직접 클릭하며 검증한다** — AI가 Playwright 같은 도구로 자동 사인오프하지 않는다 (SKILL.md §1.5 "사람 몫 불변"). AI는 배포까지 준비하고, 실제로 눌러보고 확인하는 건 사람 몫.

### 2.6 퍼널 계측

7단계(MvpLaunch) 판정은 **여기서 심은 이벤트가 전부다** — 계측이 빠지면 광고비를 쓰고도 판정 불능. 5종 기본 이벤트:

| # | 이벤트 | 정의 (예시 — 서비스에 맞게 구체화) | 퍼널 위치 |
|---|---|---|---|
| 1 | 유입 | 랜딩 도착 (유입 채널 구분 파라미터 포함 — 발품 vs 광고 vs 기타) | 최상단 |
| 2 | 가입 | 계정 생성 완료 | 전환 1 |
| 3 | 핵심행동 | *이 서비스의 aha 순간* 1회 완료 (예: 매물 진단 1회) — 무엇으로 할지 사용자와 결정 | 활성화 |
| 4 | 재방문 | 가입 후 7일 내 재방문 | retention |
| 5 | 결제 | (지불 가설 있으면) 결제 완료 / (없으면) 가격 페이지 도달 등 지불 의사 프록시 | 수익 |

- **채널 구분이 필수** — 발품 유입과 광고 유입을 구분 못 하면 7단계(MvpLaunch) 이중 채널 판정이 무너진다. UTM 파라미터 등으로 구분.
- **기본 5종 말고 이 서비스에만 필요한 이벤트가 있으면 AI가 먼저 제안한다** — 예: 중고 거래의 '채팅 시작', 강의 마켓의 '미리보기 재생'처럼 그 서비스의 성패를 가르는 행동. 5단계 화면을 읽어 후보를 1~2개 뽑아 사용자에게 보여주고, **승인받은 것만** 심는다. 승인 없이 늘리지 않는다 — 이벤트가 늘수록 7단계 판정이 흐려진다.
- 계측 도구는 **Supabase 자체 이벤트 테이블 기본** (고정 스택에 이미 있음 — 별도 analytics SaaS 없이 테이블에 적재, 퍼널 쿼리를 SQL로). 무거운 SaaS는 지양. 이벤트 테이블도 §2.2와 같은 기준으로 RLS를 건다.
- **이벤트 정의는 코드에만 둔다** — 이벤트 테이블 스키마와 추적 코드가 정의의 SoT다. `backend-build.md`에 표로 옮겨 적지 않는다. 7단계 launch-plan은 **코드에서 직접 읽어** 퍼널을 짠다 (문서와 코드가 어긋나 이름이 달라지는 사고를 원천에서 막는다).

#### 2.6.1 에러 관측

퍼널 계측과 별개로 에러를 감지할 수단도 확보한다 — 최소 배포 후 Vercel 대시보드의 런타임 로그(Runtime Logs, 서버 실행 중 발생한 에러·로그를 모아 보여주는 화면)를 확인하는 방법을 알아둔다. 원하면 Sentry류 경량 에러 추적 도구를 붙여도 되지만 필수는 아니다. 7단계 측정 기간에 가입 실패·결제 에러 같은 버그가 조용히 나면 퍼널 숫자가 나쁜 게 제품 탓인지 버그 탓인지 구분을 못 해 판정이 오염된다 — "버그는 즉시 고친다"는 룰(7단계)이 있어도 버그가 났다는 걸 아는 수단이 없으면 소용없다.

### 2.7 배포·완료

**Vercel 함수 리전은 DB 리전에 맞춘다** — `vercel.json`의 `regions`로 명시한다. 기본값(iad1, 미국 동부)으로 두면 DB가 멀 경우 질의마다 대륙 왕복이 곱해진다. [실측 1건: 상세 페이지 첫 응답 566→188ms] 프로젝트별 구체 리전 값은 각 프로젝트 AGENTS.md에 적는다.

성능 참고 하나 더 — **스켈레톤(skeleton — 본문이 오기 전 잠깐 보여주는 뼈대 화면)은 공짜가 아니다.** 페이지 안 `<Suspense fallback>`이든 라우트 `loading.tsx`든, 스켈레톤이 화면에 한번 그려지면 React가 깜빡임 방지용 공개 지연(`FALLBACK_THROTTLE_MS` = 300ms)을 걸어서 **본문이 준비돼도 300ms를 채울 때까지 안 보여준다.** 조회가 그보다 빠르면 스켈레톤 없이 다 기다렸다 한 번에 보내는 쪽이 오히려 빠르다. 어느 쪽이 이득인지는 실측으로 정한다. [실측 2건: 페이지 안 Suspense 제거로 클릭→본문 380ms→60ms / 라우트 `loading.tsx`가 남은 화면은 스켈레톤→본문 간격이 정확히 ~300ms] 단 `useSearchParams()`처럼 프레임워크가 Suspense를 강제하는 자리는 예외다. (강제 규칙이 아니라 참고 지식이다 — §2.3의 `loading.tsx` 404 함정과는 별개 축이니 거기 해법과 함께 판단한다.)

1. 최종 배포 (5단계에서 붙여둔 Vercel 그대로). main 직접 push 금지 — PR 워크플로 (repo 훅이 막음).
2. **사용자가 배포 URL을 브라우저로 직접 클릭** — 핵심 시나리오 끝까지 통과 + 가입·핵심행동 이벤트가 실제로 찍히는지 확인 (AI가 자동 도구로 검증·사인오프하지 않음 — SKILL.md §1.5 사람 몫).
3. 실결제 연동했으면 **실결제 테스트 1건** (결제 → 환불) — 사용자가 직접.
4. 발견된 문제는 초안 모드로 수정 → 재배포 → 재확인 (자율 재작업 상한 2회 — SKILL.md §1.5).

백엔드 연동·베타 공유·계측·배포가 모두 끝나면 7단계(MvpLaunch)로 넘어간다.

### 2.8 옛 단계 내용 가져오기 — SKILL.md §2.2 검토 절차 적용

이 단계 산출물에 옛 문서 내용을 근거로 가져올 땐 SKILL.md §2.2의 **확인 질문 4개**를 순서대로 거친다. 통과한 내용엔 표시 3종(**✅ 이번 단계에서 직접** / **🔵 옛 단계에서 가져옴** / **🟡 애매함**)을 붙이고, 4번(넓혀 말한 경우)으로 통과한 건 넓혀 말한 근거 한 줄 + 근거 위치를 함께 적는다. 2·3번에 걸린 내용은 가져오지 않고 문서 끝 `# 🟥 버린 내용 목록`에 한 줄씩 남긴다 (§4.1).

**단계 항목 × 옛 단계 표준 섹션 종류 매핑** — 옛 단계의 *섹션 종류(역할)* 기준이다:

| 이 단계 항목 | 가져오는 옛 단계 섹션 종류 | 비고 |
| --- | --- | --- |
| 화면 카피 조정 (§2.2) | `user-story.md`의 *입력 (확정)* — 서비스 한 줄 정의·로그라인 | 톤이 맞는지만 본다 |
| 빌드 스코프 판단 (§2.2) | `market-research.md`의 *조사 요약* | 참고 맥락 — 게이트 아님 |

**표시 판정 적용 예시**:

- **(가) `market-research.md` 조사 요약의 빈틈 정보를 빌드 스코프 근거로 가져올 때** — **5단계 앱 코드에 그 화면·기능이 실제로 있는지**부터 본다. 코드에 없으면 이 단계에서 만들지 않는다 — **🟥**로 버린 내용 목록에 남기고, 필요하면 `추후 결정:`으로 마킹한다. 코드에 있으면 **🔵**로 쓰고 근거 위치를 병기한다.
- **(나) `user-story.md`의 표현을 랜딩 화면 카피 근거로 넓혀 쓸 때** — 지금 앱 코드의 어느 화면이 그 내용을 품는지 짚을 수 있어야(확인 질문 4번) **🔵**로 쓰고, 못 짚으면 **🟡**로 두고 사용자에게 확인받는다.

## 3. 완료 체크리스트

다음이 모두 충족되어야 다음 단계(MvpLaunch)로 진입.

- [ ] **백엔드·DB·auth 연동 완료** (§2.2) — 테이블·auth 생성, Supabase RLS 활성화·정책 확인 포함.
- [ ] **스키마가 마이그레이션 파일로 남아 있음** ([backend-db-schema.md](backend-db-schema.md) §2.1) — 대시보드로 직접 만든 것도, 따로 만든 DB 설계 문서도 없음. 로컬 리셋(래퍼가 있으면 래퍼로) 통과 + **함수·트리거를 실제로 불러 확인**한 뒤 `db push`로 클라우드에 반영. 새로 만든 함수마다 실행 권한도 회수됨. **올린 뒤 클라우드에서 권한·storage·auth 관련이 실제로 걸렸는지 확인** (같은 문서 §2.4).
- [ ] **마이그레이션을 클라우드에 실제로 밀었음** (`backend-db-schema.md` §2.6) — 마이그레이션이 든 PR을 머지했다고 자동으로 올라가지 않는다. `npx supabase db push --linked`를 따로 돌렸고, `npx supabase migration list --linked`에 안 올라간 게 없음. CI가 이걸 잡아주도록 깃허브 Secret 셋(`SUPABASE_ACCESS_TOKEN`·`SUPABASE_PROJECT_REF`·`SUPABASE_DB_PASSWORD`)도 넣어뒀음.
- [ ] **백업 상태 확인** (`backend-db-schema.md` §2.7) — `npx supabase backups list --linked`로 확인. 자동 백업·시점 복구(PITR)가 꺼져 있으면 켜거나, `db dump`로 파일 백업을 정기적으로 남기는 방법을 정해뒀음.
- [ ] **로그인·동의 처리 완료** ([auth-and-consent.md](auth-and-consent.md)) — 받는 정보를 필수/선택으로 갈랐음. 선택 정보를 받으면 인증 뒤 신규 가입자만 온보딩으로 보내 동의를 받고(필수·선택 체크박스 분리, 거부해도 가입 가능, 선택 칸 nullable), 필수만 받으면 고지문 한 줄. 약관·개인정보처리방침 페이지가 실제로 있고 로그인 화면 밖에서도 접근됨.
- [ ] **로컬스토리지 저장 경로 제거 확인** (§2.2) — 폴백으로도 남아 있지 않음.
- [ ] **5단계 앱 코드의 핵심 플로우(랜딩 → 가입 → 핵심행동)가 실제로 동작** (§2.2) — 로컬스토리지가 아니라 실 DB로 데이터가 흐름.
- [ ] **(추가 스택 있으면) ADR 기록** (§2.2) — 결제 PG 등 이 단계에서 새로 붙인 것만. 고정 스택 조합·버전은 5단계 기록 참조.
- [ ] **검색 노출 기본 세트 + curl 판정 통과** (§2.3) — 제목·설명·OG·sitemap/robots·404 상태코드. 5단계 색인 제외를 공개 페이지만 풀었고 비공개 화면은 계속 막힘. `curl`로 콘텐츠 문구가 잡힘.
- [ ] **스모크 테스트 기본 세트 통과** (§2.4) — 상태 코드·HTML 내용·링크·OG·robots/사이트맵·색인 제외·토큰 만료 시 공개 화면. 베타 공유(§2.5) 전에 갖춰 둔다.
- [ ] (해당 시) **베타 공유·치명 결함 확인** (§2.5) — 5단계에서 프로토타입을 같이 본 사람에게 실데이터 붙은 링크 공유, 가입 실패·데이터 유실·핵심 플로우 이탈·심각한 오해 없음(또는 발견분 수정·재공유 완료). **마땅한 사람이 없어 건너뛰었으면 그렇게 기록.**
- [ ] **퍼널 이벤트가 실제로 찍힘** (§2.6) — 기본 5종 + (승인받았으면) 서비스 전용 이벤트. 사용자가 직접 클릭해 발화 확인. 채널 구분 동작.
- [ ] **에러 로그 확인 수단 확보** (§2.6.1) — 최소 Vercel 런타임 로그 확인 방법 숙지.
- [ ] **(화면에 결제 흐름이 있으면) 실결제 1건 테스트 완료** (§2.7, 결제 → 환불).
- [ ] **공개 URL 접속 가능** (§2.7) — 배포 완료, 핵심 시나리오가 실데이터로 끝까지 돈다.
- [ ] **`backend-build.md` 작성됨** (§4) — 스택 추가분·베타 공유 관찰(해당 시)·배포 정보·추후 결정·빌드 중 발견. **스키마 표·이벤트 정의·화면 구현 현황 같은 코드 서술은 안 적혀 있음.**
- [ ] **옛 단계에서 가져온 내용에 표시가 붙음** (§2.8) — 확인 질문 4개를 거쳐 🔵(또는 ✅·🟡)를 달았고, 걸러진 내용은 문서 끝 🟥 버린 내용 목록에 기록됨.
- [ ] (사용자 검증) **사람이 브라우저로 배포물 클릭 검토 완료** (§2.7) — 광고 유입 랜딩 경로(랜딩→가입→핵심행동)는 모바일 화면에서도 확인.

체크리스트 미충족 시 SKILL.md §4 단계 진입 평가 정책에 따라 사용자에게 선택지 제시.

산출물 저장 직후, 매 단계 공통대로 **`/clear` 후 `/idea-to-mvp` 재호출**을 권장한다 (SKILL.md §3.2). 다음 단계는 7단계(MvpLaunch) — 이 배포본과 **계측 코드(이벤트 테이블·추적 코드)**를 입력으로, 확정 4개와 퍼널 기준을 광고 집행 전에 동결하고 실사용자 검증을 시작한다.

### 4.2 frontmatter 규칙

- `name`: `backend-build`
- `created_at` / `updated_at`: ISO 날짜

## 5. 사용자 응대 톤 + 코칭

- **톤**: SKILL.md §1.3대로 반말·친근·짧게.
- **진입 안내**: "지금 앱은 데이터가 네 브라우저 안에만 쌓여서 다른 기기로 열면 텅 비어 있어. 이제 진짜 DB랑 로그인 붙여서 실서비스로 만들 차례야 — 백엔드 붙이고, 퍼널 계측 심어서 배포 완주할게. 만드는 기준은 지금 화면 그대로야 — 화면에 있는 걸 진짜로 돌게 만들고, 화면에 없는 건 안 만들어. 스택도 5단계에서 이미 정해놔서 새로 고를 건 없어."
- **빌드 중**: 잘게 확인 요청 금지 (초안 모드). 에스컬레이션 기준 해당 시에만 멈추고 배치로 질문.
- **베타 공유 안내**: "이번엔 진짜 데이터가 도는 링크야 — 프로토타입 같이 봐준 사람들한테 보내서 실제로 가입하고 쓰는지 보자. 판정이 아니라 치명적인 거 있는지 확인이야. 보낼 사람 없으면 건너뛰어도 돼."
- **화면 구조를 다시 뒤집자는 요청**: 코드를 고치는 건 이 단계에서도 정상이다 — 백엔드 붙이며 화면이 조금씩 바뀌는 건 당연. 다만 **화면이 늘거나 빠지는 구조 변경**이면 5단계로 돌아가 프로토타입을 고친 뒤 다시 오는 게 순서라고 짚는다. 화면 절반을 새로 짜는 수준이면 그건 피봇이라 4단계 재실행으로 다루고(SKILL.md §2.2 — 인벤토리는 1세대 기록이라 갱신하지 않는다), 급하지 않으면 7단계(MvpLaunch) 이후 production으로 넘기자고 안내한다.
- **범위 압박 대응**: 사용자가 "이 기능도 넣자" 하면 — **5단계 앱 코드에 그 화면이 있는지**부터 짚고, 없으면 핵심 플로우(랜딩→가입→핵심행동)에 꼭 필요한지 확인. 필요 없으면 "런치 검증(7단계) 끝나고 production에서" 권유 (강제는 아님 — 사용자가 원하면 명세 먼저 갱신 후 빌드).
- **완료 시**: 배포 URL + "핵심 시나리오대로 클릭해봐 + 이벤트 찍히는 것도 같이 확인하자" + 체크리스트 현황.
- **배포·클릭 검증 안내**: "배포까진 내가 하는데, 실제로 눌러보고 확인하는 건 네 몫이야 — 자동 검증 도구로 대신 사인오프 안 해" (SKILL.md §1.5 사람 몫).
