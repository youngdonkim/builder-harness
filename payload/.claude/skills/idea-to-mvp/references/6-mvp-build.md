3단계가 만든 프로토타입은 화면도 돌고 클릭도 되지만, 데이터가 **브라우저 로컬스토리지(localStorage — 그 브라우저 안에만 저장되는 공간)**에만 쌓인다. 다른 기기로 열면 아무것도 없고, 여러 사람이 같은 데이터를 나눠 쓸 수도 없다. 이 단계는 그 앱에 **진짜 백엔드·DB·auth를 붙여 실서비스로 완성**하고, 퍼널 계측을 심어 배포하는 자리다. 산출물은 실서비스가 된 앱 코드 + `mvp-build.md` 하나.

## 1. 단계 목표

- **배포된 실서비스** — 3단계 프로토타입(로컬스토리지로 도는 리액트 앱)에서 로컬스토리지를 걷어내고 Supabase(DB·auth)를 붙여, 실데이터가 흐르는 서비스로 완성해 공개 URL로 배포.
- **베타 공유로 치명 결함 거르기** — 실데이터가 붙은 링크를 4단계(DemoValidation) 인터뷰이에게 보내 실사용 반응 확인 (판정 아닌 확인).
- **퍼널 계측 심기** — 유입·가입·핵심행동·재방문·결제 5종 이벤트가 실제로 찍힘. 7단계(MvpLaunch) 판정의 데이터 원천.
- **(지불 가설 있으면) 실결제** — `demo-validation.md` 검증 가설에 지불 검증이 포함되면 실결제 연동 (fake door 아님).
- **`mvp-build.md`** — 데이터 모델(표 목록)·연동 결정·계측 이벤트 정의·배포 정보·베타 공유 관찰 기록.
- **실서비스 개통은 이 6단계에서 끝난다** — 실 DB·개인정보 수집·결제·공개 배포가 전부 여기 안에 들어간다. 7단계(MvpLaunch)는 광고를 돌려 숫자로 판정하고 회고하는 단계지, 인프라를 새로 세우는 단계가 아니다.

**SoT 책임** (SKILL.md §2.1): 연동 결정·퍼널 계측 이벤트 정의·배포 정보 = `mvp-build.md`. **백엔드 스키마의 SoT는 마이그레이션 파일**이고 `mvp-build.md`엔 표 목록과 그게 어느 파일에 있는지만 적는다 (§2.2.2). 화면·플로우 명세의 SoT(Source of Truth — 진실의 원천)는 **3단계부터 앱 코드**다 — 문서에 옮겨 적지 않는다. 스택 조합(Next.js·React·TypeScript·Supabase·Vercel과 핀한 버전)도 3단계에서 확정·기록됐으니 여기선 참조만 하고, **이 단계에서 새로 추가한 것(결제 PG 등)만** `mvp-build.md`와 ADR에 적는다.

**여기서 안 하는 것 (의도적)**:

- ❌ 스택 선택·개발환경 구성·프런트 신규 구현 — 전부 3단계 몫. 그 절차가 필요하면 `3-prototype.md`를 본다. 여기선 **이미 있는 코드에 백엔드를 얹는다**.
- ❌ 화면 구조 갈아엎기 — 코드를 고치는 건 정상이지만, 화면이 늘거나 빠지는 구조 변경은 4단계 go 판정을 되돌리는 일이다 (§5).
- ❌ PRD·Architecture·Design·**DB 설계** 문서 작성 — 앱 코드와 마이그레이션 파일이 스펙 (§2.2.2). 문서 ceremony 금지.
- ❌ 명세 밖 기능·화면 추가 — `추후 결정:` 마킹만.
- ❌ 다크모드·다국어·반응형 정교화·성능 튜닝·부하 대비 — production 영역. (단, 광고 유입 랜딩 경로(랜딩→가입→핵심행동)는 모바일 화면 확인이 필수 — 7단계 소액 광고 유입은 대부분 모바일이라, 이 경로가 모바일에서 깨져 있으면 퍼널 실측이 제품 반응이 아니라 깨진 화면을 재는 꼴이 돼 통과 기준②가 오염된다.)
- ❌ CI·테스트 스위트 정교화 — 검증 가설과 무관한 인프라 투자는 production에서.
- ❌ 광고·채널 준비 — 7단계(MvpLaunch) 영역 (단 결제 PG 심사처럼 리드타임 긴 것만 병렬 시작 OK).

**헷갈리기 쉬운 하나 — 검색 노출(SEO)은 이 목록에 없다. 여기서 한다** (§2.2.3). 위 항목들은 나중에 해도 같은 크기의 일이지만, 검색 노출은 서버가 데이터를 채워 보내는 구조에 얹히는 거라 나중에 하면 그 구조부터 다시 뜯는 더 큰 일이 된다.

## 2. 진행 절차

### 2.1 단계 시작 — 이전 정리 내용을 보여주고, 이번 단계가 할 일을 안내한다

이 단계에 들어오면 가장 먼저 사용자와 "지금까지 어디까지 왔고, 이제 무엇을 할지"를 맞춘다:

1. **이전 단계까지 정리된 내용을 먼저 보여준다.** 입력이 셋이다:
   - **프로젝트 루트의 앱 코드** (3단계 산출물) — 화면·플로우의 SoT. 정답지로 모셔두는 게 아니라 **이 단계에서 이어서 고칠 실코드**다. 지금 데이터가 어디에(로컬스토리지 어느 키에) 어떤 모양으로 쌓이는지부터 읽는다.
   - **`demo-validation.md` § 최종 확정 아이디어** (+비목표·검증 가설·북극성 — 4단계 go 분기에서 확정된 4개) — 무엇을 만들지 정하는 스펙.
   - **5단계 `market-research.md`의 조사 요약** (경쟁 지형·차별화 힌트) — 무엇부터 만들지·무엇을 미룰지 판단할 때 쓰는 참고 맥락 (없으면 없는 대로 진행).

   셋 다 짧게 요약해 보여준다.
2. **그 내용을 기반으로 이번 단계가 무엇을 하는지 설명한다.** 지금 앱은 데이터가 브라우저 안에만 쌓여서 다른 기기로 열면 비어 있다고 짚고 — 이제 로컬스토리지를 걷어내고 실 DB·로그인을 붙여서 → 실데이터가 도는 상태로 베타 공유해 치명 결함 확인 → 퍼널 계측을 심고 → 최종 배포까지 완주하는 단계라고 안내한다.
3. **`mvp-build.md` 머리에 `# 이전 결론 → 이번 결론` 섹션을 적는다** (SKILL.md §2.2). 체인의 직전 결론은 4단계(DemoValidation)의 '이번 결론'(최종 확정 아이디어·비목표·검증 가설·북극성)이다 — 5단계 MarketResearch는 참고 자료라 이 체인에 들어가지 않는다. 그 결론과 대조해 변경 여부를 확인한다 — 프로토타입 순환(3↔4단계) 중이나 5단계 조사 중에 방향이 바뀌었다면 그 델타를 여기서 기술한다. 변경 없으면 `변경 없음 — demo-validation.md §최종 확정 아이디어 그대로` 한 줄로 충분.
4. **이미 `mvp-build.md`가 있으면**(스킬 중간 재실행 등) 읽고 §3 체크리스트로 검증해 부족한 부분만 보완한다. 앱 코드는 3단계부터 있으니 이 단계를 했다는 표시가 못 된다 — 6단계 진행 여부는 `mvp-build.md`로 판단한다.

**진입 조건**: 프로젝트 루트에 3단계가 만든 앱 코드(`package.json`·`src/` 등)가 있고, 4단계(DemoValidation) go 판정(구조적 수정 0건 수렴)을 통과한 상태여야 한다. 아직 순환 중이면 강행하지 말고 4단계로 돌아가 마무리를 안내한다. 5단계 `market-research.md`는 있으면 참고하고 없으면 없는 대로 간다 — 그 단계는 게이트가 아니다.

### 2.2 백엔드·DB·auth 연동 (이 단계의 첫 일)

이 절차는 SKILL.md §1.5 **초안 모드** — AI가 끝까지 완주한 뒤 완성본으로 리뷰받는다. 중간에 테이블 하나하나 승인받지 않는다.

**3단계에서 Supabase는 "붙일 자리만 잡아둔" 상태다** — 프로젝트 생성 + 환경변수 연결까지만 돼 있고, **테이블·RLS·auth는 여기서 처음 만든다.** 그래서 이 단계의 첫 일은 로컬스토리지를 걷어내고 그 자리를 Supabase로 채우는 것이다.

**환경은 2단이다 — 로컬(도커) 하나, 클라우드 하나**

손대기 전에 이것부터 정해 둔다. **로컬(도커)이 개발과 마이그레이션 검증을 맡고, 클라우드 Supabase 프로젝트 1개가 실서비스를 맡는다.** 그 사이에 스테이징(staging — 실서비스에 올리기 전 똑같이 만들어 두는 연습용 환경)을 하나 더 두지 않는다.

- **클라우드 DB를 두는 이유는 "한 번 더 검증"이 아니다** — 배포된 앱이 내 컴퓨터 주소(127.0.0.1)에 접속할 수 없어서다. 검증하려고 두는 게 아니라, 배포된 앱이 붙을 곳이 필요해서 두는 것.
- **마이그레이션 검증은 오히려 로컬이 더 강하다** — `db reset`은 전체 마이그레이션을 0부터 다시 재생하지만, 클라우드에 미는 건 이미 있는 상태 위에 새것만 얹는 것이라 검증력이 약하다.
- **클라우드를 개발용·실서비스용 둘로 쪼개면 손해가 크다** — OAuth 앱(콜백 주소가 앱당 하나라 두 개를 따로 만들어야 한다)·Storage 정책·마이그레이션 푸시가 전부 두 벌이 된다. **밀 곳이 늘어나는 만큼 두 곳이 서로 어긋나는(드리프트) 사고 확률이 커진다** — 드리프트(drift — 같아야 할 두 곳의 상태가 서로 어긋나는 것). 얻는 것보다 잃는 게 크다.
- **미리보기 배포에도 DB가 필요해지면** 프로젝트를 하나 더 만들지 말고 Supabase 브랜치 기능(`supabase branches`)을 먼저 검토한다.

**작업 순서**:

1. **지금 상태 모양 파악** — 앱 코드가 로컬스토리지에 무엇을 어떤 모양으로 저장하는지 읽는다. 여기가 스키마의 실측 근거다.
2. **스키마 설계** — 1에서 읽은 실제 저장 모양을 그대로 테이블로 옮긴다. 3단계가 로컬스토리지 구조를 데이터 모델 그대로 만들어뒀기 때문에(`3-prototype.md` §2.5.5) **코드가 곧 데이터 모델이다** — `mvp/handoff/` 문서를 다시 열지 않는다.
3. **auth 붙이기** — Supabase Auth로 가입·로그인. 로컬스토리지 시절엔 "사용자"가 없었으니, 소유자 기준(어느 행이 누구 것인지)을 이때 처음 정한다. **로그인에 딸려오는 동의·약관 처리는 [6-mvp-build-auth-consent.md](6-mvp-build-auth-consent.md)를 따른다** — 받는 정보에 따라 화면과 스키마가 갈린다.
4. **읽기·쓰기 경로 교체** — 로컬스토리지 호출을 Supabase 클라이언트 호출로 바꾼다.
5. **로컬스토리지 코드 제거** — 남겨두고 폴백으로 쓰지 않는다. 두 갈래로 남으면 어느 쪽이 진짜 데이터인지 알 수 없어져, 베타 공유·계측 숫자가 전부 오염된다. (기기 간 이어쓰기용 마이그레이션도 하지 않는다 — 프로토타입 단계 데이터는 버리는 데이터다.)

**RLS는 필수다.** Supabase 연동 시 **RLS(행 단위 보안 규칙, Row Level Security — 테이블마다 "누가 어느 행을 읽고 쓸 수 있나"를 DB가 직접 강제하는 규칙) 활성화 + 정책 작성**을 반드시 한다. Supabase의 공개 키(anon key)는 브라우저에 그대로 노출되는 구조라, RLS를 안 걸면 그 키만으로 아무나 모든 테이블을 읽고 쓸 수 있다 — Supabase 프로젝트에서 가장 흔하고 치명적인 사고 지점이다.

**보안 baseline**: auth·API·업로드 코드를 만지면 `.claude/rules/threat-model.md`가 자동 로드된다 — 그 baseline(http-only cookie·권한 검사·IDOR 회피·rate limit·에러에 stack 미노출 등) 준수. 광고로 모르는 사람들이 실제로 들어오는 코드다.

**범위 가드 (강제)**:

- 3단계 앱 코드에 없는 화면·기능 추가 금지. "이것도 있으면 좋겠는데" 신호는 `추후 결정:`으로 `mvp-build.md`에 마킹만.
- `demo-validation.md` §비목표 화면·기능은 빌드에도 없음.
- 3단계에서 화면만 있고 동작은 비워둔 영역이 있다면 — 이번에 *실제로 작동*시켜야 하는지 `demo-validation.md`(핵심 플로우·검증 가설) 기준으로 판단. 가설 검증에 불필요하면 그대로 둔다.
- 다크모드·다국어·반응형 정교화·성능 튜닝·CI 정교화는 범위 밖 (§1 "여기서 안 하는 것").

**이 단계에서 새로 추가하는 스택만 ADR로 기록한다** (`mvp/adr.md` — SKILL.md §3.1 "스택 주요 컴포넌트 추가·제거" 트리거). 여기서 ADR 대상이 되는 건 결제 PG(토스페이먼츠·Stripe 등)처럼 이 단계에 와서 붙이는 것들이다 — 결제는 심사 리드타임이 있어 백엔드 연동과 병렬로 시작한다.

**에스컬레이션**: 명세와 모순 발견·스키마가 크게 갈리는 선택·외부 서비스 추가 필요 시 멈추고 배치 질문. 그 외 애매함은 합리적 가정 + `추후 결정:` 마킹 후 계속.

#### 2.2.1 로컬 스택 준비 — 시작 전에 갖춰 둔다

**① 로컬 스택엔 Docker Desktop이 필요하다**

공식 문서:

> "A container manager compatible with Docker APIs is a prerequisite"
> — https://supabase.com/docs/guides/local-development

컨테이너(container — 프로그램을 실행 환경째로 담아 돌리는 방식)를 관리하는 프로그램이 먼저 깔려 있어야 한다는 뜻이다. **Docker Desktop을 쓴다.** 공식 문서가 preferred option(권장 선택지)으로 적어둔 것이고, 화면으로 상태를 볼 수 있어 문제가 생겼을 때 원인을 찾기 쉽다.

설치 후 앱을 한 번 실행해서 권한을 준 다음, 돌고 있는지 확인한다:

```bash
docker info      # 정보가 나오면 준비된 것
```

> Docker Desktop은 직원 250명 미만 **그리고** 연 매출 1000만 달러 미만이면 무료다. 넘는 조직에서 업무용으로 쓰면 유료 라이선스가 필요하다 (https://docs.docker.com/subscription/desktop-license/). 여기 걸리는 조직이면 공식 문서가 같이 적어둔 Rancher Desktop·Podman·OrbStack 중 하나를 쓴다.

**② CLI는 전역이 아니라 프로젝트 개발 의존성으로 깐다**

```bash
npm i supabase --save-dev      # 그다음 npx supabase ...
```

이유: 스키마를 다루는 도구라 **버전이 사람마다 다르면 사고가 난다.** `package.json`에 박아두면 팀원이 같은 버전을 쓴다. 전역(global — 컴퓨터 전체에 하나만 까는 방식)으로도 깔려 있으면 어느 쪽이 실행되는지 헷갈리니 **둘 중 하나만 남긴다.**

**③ `gh` CLI — PR을 만들고 머지하는 데 쓴다**

```bash
brew install gh    # 맥 기준. 다른 OS면 https://cli.github.com 의 설치법을 따른다
gh auth login      # 깔고 나서 한 번 로그인
gh auth status     # 준비됐는지 확인
```

이유: `done-task` 스킬이 이 명령으로 PR을 만들고 머지한다 — **없으면 그 스킬이 아예 안 돈다.** 이건 프로젝트가 아니라 깃허브 계정에 붙는 도구라 전역으로 깐다.

**④ Vercel CLI — 배포와 환경변수에 쓴다**

```bash
npm i vercel --save-dev    # 그다음 npx vercel ...
npx vercel login
```

배포(`npx vercel deploy`)와 환경변수 내려받기(`npx vercel env pull`)에 쓴다.

**3단계에서 깐 Vercel "플러그인"과는 다른 것이다** (`3-prototype.md` §2.5.1) — 플러그인은 클로드 코드 안에서 쓰는 스킬 묶음이고, 이건 터미널에서 직접 치는 명령이다. 이름만 같지 하는 일이 다르니 둘 다 갖춰 둔다.

**⑤ 시작 전 하드웨어를 확인한다 — 숫자를 잘못 읽지 않게**

로컬 스택은 컨테이너를 여러 개 띄운다. **Supabase 공식 문서에 권장 사양이 없으니** 직접 재고 판단해야 한다. 아래 명령은 **맥 기준**이다 — 다른 OS면 같은 것을 재는 그 OS 도구를 쓰면 되고, 판정 기준(아래 표)은 OS와 상관없이 같다.

```bash
memory_pressure | tail -4      # 메모리 압박 정도 — 핵심 지표
df -h /                        # 디스크 여유
sysctl vm.swapusage            # 디스크로 밀려난 양
ps -Ao rss,comm -r | head -20  # 메모리 많이 쓰는 앱
```

**판정 기준**

| 보는 것 | 괜찮음 | 빠듯함 |
|---|---|---|
| `System-wide memory free percentage` | 40% 이상 | 20% 아래 |
| 스왑(swap — 메모리가 모자랄 때 디스크로 밀어내 두는 공간) 사용량 | 거의 안 늘어남 | 계속 커짐 |
| 디스크 여유 | 20GB 이상 | 10GB 아래 |

**⚠ 흔한 오해 — "메모리 압축"은 압박의 증거가 아니다**

맥은 여유가 있어도 안 쓰는 데이터를 **미리 눌러 담아 둔다**(대략 절반 크기로). 디스크로 밀어내는 것보다 훨씬 빨라서 일부러 먼저 하는 동작이다. `vm_stat`의 "Pages occupied by compressor"가 몇 GB로 보여도 **그것만으로는 메모리가 모자란다는 뜻이 아니다.** 압박 여부는 위 표의 두 지표로 판단한다.

**⚠ 숫자 함정 — 앱별 메모리 합계는 부풀려진다**

`ps`의 RSS는 앱끼리 공유하는 메모리를 **각각 중복으로 센다.** 앱별 사용량을 더하면 실제 총량보다 훨씬 커진다. **순위를 보는 데만 쓰고 절대값은 믿지 않는다.**

**빠듯하면**

1. 브라우저 탭 정리가 대개 제일 효과가 크다 (브라우저가 최대 소비자인 경우가 흔하다)
2. Docker Desktop 설정에서 메모리 할당을 줄인다
3. **안 쓸 땐 내린다** — `npx supabase stop`

실제 사용량은 **한 번 띄워 보고 다시 재는 게 정확하다.** 위 명령을 띄우기 전과 띄운 뒤에 각각 돌려 비교한다.

#### 2.2.2 스키마 만들기 — 파일로 남기고 로컬에서 검증한다

§2.2 작업 순서 2~4(스키마 설계·auth·경로 교체)에 손대기 전에 **어디서 어떻게 만들지**부터 정한다. 이걸 안 정하고 설계 문서부터 쓰거나 웹 대시보드에서 손으로 테이블부터 만들기 시작하면 나중에 되돌리기 어려운 상태가 된다.

**① 스키마는 마이그레이션 파일로 남긴다 — 설계 문서도, 대시보드도 아니다**

§1의 "앱 코드가 스펙"은 **DB에도 그대로 적용된다.** 스키마가 크면 어딘가 정리해 두고 싶어지는데, 답이 `docs/db-design.md` 같은 문서면 안 된다 — 마크다운 안의 SQL은 **실행할 수가 없어서 검증이 안 되고**, 마이그레이션과 늘 같이 고쳐야 하는 두 번째 정본이 된다. 자리를 이렇게 나눈다:

- **무엇을 만드나 → 마이그레이션 파일.** 실행 가능한 형태라야 검증된다.
- **왜 그렇게 정했나 → `mvp/adr.md`.** 결정은 마이그레이션 파일에 안 남는다 — 나중에 다른 클라우드로 옮길 때를 대비한 조치, 컬럼에 파일 전체 주소를 담을지 경로만 담을지, 접근 권한을 자동 노출에 맡길지 직접 쓸지 같은 것들. 코드만 봐서는 안 나오고, 코드 쓰기 전에 정해야 한다.

Supabase 공식 문서가 원격(클라우드) DB에 대해 못 박는다:

> "Making schema changes directly on your remote database (via the SQL editor or Table Editor) bypasses the migration history and will cause `db push` to fail with sync errors."
> — https://supabase.com/docs/guides/deployment/database-migrations

클라우드 DB를 SQL 편집기나 테이블 편집기로 직접 고치면 **마이그레이션(migration — 스키마를 어떻게 바꿨는지 순서대로 적어 둔 파일) 이력을 건너뛰게 돼서**, 나중에 `db push`가 "안 맞는다"는 오류로 실패한다는 뜻이다.

공식 문서는 **로컬 DB에 한해** 대시보드로 만지고 `supabase db diff`(지금 DB와 파일의 차이를 뽑아 주는 명령)로 파일을 뽑는 길도 열어둔다. 하지만 diff는 publication(다른 DB로 내보낼 목록) 변경, storage 버킷(파일 저장소) 변경, `security_invoker` 속성을 가진 뷰를 놓칠 수 있다고 공식 문서가 밝혀 뒀다 (https://supabase.com/docs/reference/cli/supabase-db-diff). 그래서 **기본은 마이그레이션 파일을 직접 쓰는 것으로 하고**, RLS 정책이 여러 개거나 뷰·함수를 직접 정의하는 스키마면 더더욱 diff에 기대지 않는다. 대시보드는 결과를 눈으로 확인하는 용도로만 쓴다.

**② 함수를 만들 때마다 하는 두 가지 — `search_path` 비우기 + 실행 권한 회수**

`search_path`(표 이름만 적었을 때 어느 스키마에서 찾을지 정해 둔 목록)를 비워 두는 건 Supabase 함수의 기본 안전장치다. 비웠으면 함수 안의 표 이름엔 `public.` 접두를 붙여야 한다.

함정은 **트리거 함수(표에 값이 들어오거나 바뀔 때 DB가 자동으로 부르는 함수)는 자기 `search_path`가 없으면 부른 쪽 것을 물려받는다**는 점이다. 빠뜨린 트리거 함수는 평소엔 멀쩡하다가 `search_path`를 비운 함수 안에서 불릴 때만 `relation "..." does not exist`로 터져서 찾기 어렵다.

**실행 권한은 함수마다 이름과 인자를 적어 회수한다.** Postgres는 함수를 만들면 모두에게 실행 권한을 자동으로 주므로, `revoke execute on function 이름(인자…) from public, anon, authenticated;`로 거두지 않으면 비로그인 방문자도 그 함수를 부를 수 있다. **한 번에 막으려는 시도는 안 통한다** — `alter default privileges … revoke execute on functions from public`으로 앞으로 만들 함수까지 미리 막아도, Supabase 마이그레이션에서는 `pg_default_acl`에 줄만 들어가고 그 뒤에 만든 함수는 권한이 열린 채로 태어난다(`for role`을 붙여도 같다 — 재현해 확인한 동작). 실제로 이렇게 뚫린 함수를 비로그인 상태로 불러 데이터가 굳은 사고도 있었다.

여기서 회수한 권한이 클라우드에서도 실제로 걸리는지는 로컬로 확인이 안 된다 — 아래 ④에서 다시 본다.

**③ 로컬에서 검증한다 — `db reset` 통과는 "문법이 맞다"까지다**

흐름은 이렇다: **마이그레이션 파일 작성 → 로컬에서 `db reset` → 함수를 실제로 불러 보기 → 클라우드에 `db push` → 클라우드에서 확인(④)**

| 명령 | 하는 일 |
|---|---|
| `supabase migration new <이름>` | 빈 마이그레이션 파일을 만든다 |
| `supabase db reset` | 로컬 DB를 밀고 마이그레이션을 처음부터 다시 적용한다 |
| `supabase db push` | 로컬 마이그레이션을 클라우드에 올린다 |

`db reset`은 **순서 문제·문법 오류를 드러내는 도구**고, 이 단계에선 수십 번 돌리게 된다. 쓰려면 로컬 스택이 떠 있어야 한다(`npx supabase start`). 같은 걸 클라우드에서 하면 느리고, 시험 데이터가 쌓인 뒤엔 되돌리는 비용도 커진다(⑧) — 그래서 고쳐 가며 반복하는 자리는 로컬이다.

검증은 시점을 셋으로 나눠서 한다:

| 언제 | 무엇을 | 왜 |
|---|---|---|
| 덩어리 하나 쓸 때마다 | `db reset` — 표까지 쓰고 한 번, 함수까지 쓰고 한 번 | 다 쓰고 마지막에 한 번만 돌리면 깨진 자리를 좁힐 수 없다 |
| 함수·트리거를 쓴 뒤 (제일 빠뜨리기 쉬운 자리) | 로컬 DB에 표 몇 줄을 손으로 넣고 **직접 불러서** 의도대로 도는지 본다 | `db reset` 통과는 문법만 맞다는 뜻이라 문법이 멀쩡한 논리 오류는 그대로 통과한다 — 어떤 프로젝트에선 스키마 버그 넷 중 셋이 이렇게 `db reset`을 통과했고, 함수를 직접 호출하고 나서야 드러났다 |
| `db push` 직후 | 클라우드에서 다시 본다 (④) | 로컬은 권한 관련을 아예 못 재는 자리다 |

**RLS 정책과 `security definer` 함수(만든 사람 권한으로 도는 함수)는 `auth.uid()`(지금 로그인한 사람이 누구인지 알려주는 함수)가 실제로 동작하는 환경이 아니면 검증이 안 된다.** 맨 PostgreSQL을 따로 깔아서는 반쪽만 된다 — `auth.uid()`도 파일 저장소도 Supabase가 넣어주는 것이라 그냥 Postgres엔 없다.

**④ 로컬 통과가 곧 클라우드 통과는 아니다 — 경계는 "그 표의 주인이 누구냐"다**

③이 *같은 DB 안에서 문법과 동작이 다르다*는 얘기였다면, 이건 *로컬과 클라우드가 다르다*는 얘기다. 로컬은 내가 DB 주인이라 뭐든 되지만, 클라우드에는 Supabase가 정해 둔 다른 주인이 있는 영역이 있다. `auth.*`, `storage.*` 같은 데 손대는 건 올려 봐야 안다. `db push` 직후 클라우드에서 아래를 한 번 더 확인한다:

| 로컬로는 확인 안 되는 것 | 왜 |
|---|---|
| 위 ②에서 회수한 함수 실행 권한이 실제로 걸리는지 | 마이그레이션을 돌리는 계정이 로컬과 다르다 |
| `storage.objects`에 정책을 만들 수 있는지 | 그 표의 주인이 따로 있다 |
| `auth.users`에 트리거를 걸 수 있는지 | 같은 이유 |
| 파일 삭제 정책 | 로컬 스택엔 직접 삭제를 막는 장치가 따로 있어 시험 자체가 안 된다 |
| 주기 작업의 시간대 | 로컬 설정이 클라우드와 같다는 보장이 없다 |

**⑤ 로컬이 못 잡는 건 딱 하나 — 실데이터에 걸려 실패하는 마이그레이션**

로컬과 클라우드는 **같은 Postgres에 같은 마이그레이션 파일**을 돌린다. 그래서 문법·순서·RLS·권한·함수 컴파일·제약 정의는 로컬에서 통과하면 클라우드에도 그대로 옮겨간다. 다른 건 **담긴 데이터뿐**이다. 그러니 로컬이 못 잡는 것도 데이터에 걸려 실패하는 마이그레이션뿐이다:

| 이런 마이그레이션 | 왜 실데이터에서만 실패하나 |
|---|---|
| `alter column set not null` | 실제 데이터에 빈 값(NULL)이 하나라도 있으면 실패 |
| `create unique index` | 실제로 중복된 값이 있으면 실패 |
| `add constraint check` | 그 규칙을 어기는 줄이 이미 있으면 실패 |
| 데이터를 바꾸는 `update` | 실제 데이터 형식을 잘못 가정했을 때 엉뚱하게 바뀐다 |

대응은 두 가지다.

**첫째, 밀기 전에 무엇이 나갈지 미리 본다:**

```bash
npx supabase db push --linked --dry-run   # 실제로 밀지 않고, 나갈 내용만 보여준다
```

**둘째, 사용자가 생긴 뒤에는 실데이터를 받아 로컬에서 먼저 돌려본다:**

```bash
npx supabase db dump --linked --data-only -f supabase/seed-from-cloud.sql
```

> **⚠ 이 파일에는 진짜 개인정보가 들어 있다.** 커밋하지 말고 `.gitignore`에 넣고, 이름·이메일처럼 누구인지 알아볼 수 있는 정보는 가짜 값으로 바꿔 쓴다.

**⑥ 마이그레이션은 자동으로 안 올라간다**

**마이그레이션 파일이 든 PR을 머지해도 클라우드 DB는 그대로다.** 코드는 배포가 알아서 되지만 DB는 아니다 — `npx supabase db push --linked`를 **따로 돌려야** 반영된다.

하네스가 넣어주는 `.github/workflows/ci.yml`이 main에 올라온 뒤 밀린 게 있으면 CI를 실패시켜 알려준다. 알려주기만 하고 자동으로 밀지는 않는다 — 지워진 데이터는 되돌릴 수 없어서, 미는 건 사람 눈을 거친다.

이 확인이 돌게 하려면 깃허브 저장소에 **Secret(비밀값 — 저장소 설정에 숨겨 두는 값) 세 개**를 넣는다. Settings → Secrets and variables → Actions에서 넣는다.

| Secret 이름 | 무엇 |
|---|---|
| `SUPABASE_ACCESS_TOKEN` | Supabase 계정 접근 토큰 |
| `SUPABASE_PROJECT_REF` | 클라우드 프로젝트 참조 아이디 |
| `SUPABASE_DB_PASSWORD` | 그 프로젝트의 DB 비밀번호 |

**DB 비밀번호까지 필요한 이유** — `migration list --linked`는 관리 API를 부르는 게 아니라 **원격 DB에 직접 붙어 마이그레이션 이력 테이블을 읽기** 때문이다. 비밀번호가 없거나 틀리면 `password authentication failed for user "postgres"`로 실패한다.

셋 중 하나라도 없으면 이 확인은 조용히 건너뛴다 — 아직 Supabase를 안 붙인 프로젝트에서 CI가 깨지지 않게 하려는 것이다. 바꿔 말하면 **Secret을 안 넣으면 밀린 마이그레이션을 아무도 안 잡아준다.** 클라우드를 붙이는 이 시점에 같이 넣어 둔다.

**⑦ 실사용자를 받기 전에 백업 상태를 확인한다**

```bash
npx supabase backups list --linked
```

`backups`가 비어 있고 `pitr_enabled: false`로 나오면 **복구 수단이 아예 없는 상태**다. 요금제를 올려 자동 백업을 켜거나, 최소한 위 ⑤의 `db dump`를 정기적으로 돌려 파일로 남긴다 — 같은 명령이 백업과 로컬 검증용 데이터를 겸한다. 여기 나오는 PITR은 시점 복구(PITR, Point In Time Recovery — 원하는 과거 시각의 상태로 되돌리는 기능)를 말한다.

**왜 7단계가 아니라 6단계에서 하나** — 이 단계가 끝나는 시점엔 이미 개인정보 동의를 받은 실사용자 데이터가 쌓여 있기 때문이다. 광고를 돌리는 7단계까지 기다릴 일이 아니다.

되돌릴 수 있는 것과 없는 것도 갈라 둔다:

- **더하기(`create`·`add`)는 되돌리기 쉽다** — 잃을 데이터가 없다.
- **지우기(`drop column`·`drop table`)는 못 되돌린다** — 백업 없이는 끝이다.
- **마이그레이션 파일을 git에서 되돌려도 이미 실행된 DB는 안 바뀐다** — git은 파일만 되돌린다.

**⑧ `db push` 했다고 `db reset`을 못 쓰게 되는 게 아니다**

"클라우드에 올리면 이제 `db reset`을 못 하니 큰일"은 흔한 오해다. 클라우드도 리셋할 수 있고, 초기엔 마음껏 해도 된다. 언제부터 조심해야 하는지가 안 적혀 있어 생기는 오해라 표로 정리한다:

| 대상 | 리셋 | 그래서 |
|---|---|---|
| 로컬 스택 | 언제나 | `db push` 여부와 무관하게 계속 된다 |
| 클라우드, 아직 실사용자 없고 데이터도 없음 | 자유 | 마이그레이션 파일을 제자리에서 고치고 리셋하면 된다 |
| 클라우드, 시험 데이터만 쌓임 | 가능하지만 귀찮음 | 이때부터 새 파일 덧붙이기로 옮겨 갈 때다 |
| 클라우드, 실사용자 데이터 있음 | 금지 | 무조건 덧붙이기 |

전환 기준은 파일 개수나 날짜가 아니라 **"날아가면 아까운 데이터가 생겼을 때"**다. 시험용 데이터를 SQL로 만들어 두면(다시 채우는 게 명령 한 번이면 되면) 클라우드를 리셋하는 비용이 계속 싸게 유지돼서, 제자리 수정 단계를 훨씬 오래 끌고 갈 수 있다.

#### 2.2.3 검색 노출(SEO) — 이 시점에 같이 한다

로컬스토리지 시절엔 데이터를 서버가 모르니 검색엔진에 보여줄 HTML을 애초에 만들 수가 없었다. 그래서 검색 노출은 위에서 읽기·쓰기 경로를 Supabase로 갈아끼우는 **바로 그때 같이** 한다. 따로 떼어두면 잊히고, 나중에 하려면 서버가 데이터를 채워 보내는 구조부터 다시 뜯게 된다.

1. **기본 세트 적용** — 페이지별 제목·설명, 공유 미리보기(OG — 링크를 카톡·슬랙에 붙였을 때 뜨는 제목·설명·이미지), sitemap·robots, 없는 콘텐츠에 404 상태코드. 구체적인 방법은 여기 적지 않는다 — 널리 알려진 일반 지식이라 그때그때 최신 방식으로 하면 된다.
2. **3단계에서 걸어둔 색인 제외를 여기서 푼다** — `3-prototype.md` §2.6에서 프로토타입 전체를 검색에 안 잡히게 막아뒀다. 검색 노출을 켠다는 건 그걸 푸는 일이다. 단 **전부 푸는 게 아니다** — `.claude/rules/threat-model.md`가 말하는 대로 검색엔진은 외부 도달 경로라, 공개할 페이지만 열고 운영 콘솔·개인 전용 화면은 계속 막아둔다. 어느 화면이 공개인지는 2단계 인벤토리의 역할 열을 **출발점으로 참고**하되, 판정은 **현재 코드에 실제 있는 화면 기준**으로 한다 — 인벤토리는 1세대 기록이라 3↔4 순환에서 바뀐 화면이 반영돼 있지 않다.
3. **함정: 빈 상태가 200으로 나간다** — 2단계 상태 매트릭스대로 화면마다 빈 상태를 만들어 뒀기 때문에, 없는 콘텐츠 주소로 들어와도 "아직 없어요" 화면이 정상(200) 응답으로 나가기 쉽다. 검색엔진은 그걸 내용 없는 페이지로 색인한다. **데이터가 0개인 것(빈 상태, 200)과 그 주소가 아예 없는 것(404)을 갈라서** 처리한다.
4. **판정** — `curl <배포 URL> | grep <화면에 보이는 콘텐츠 문구>`가 잡혀야 통과. 안 잡히면 서버가 데이터를 안 채워 보낸 것이라 나머지가 전부 무의미하다. **브라우저를 안 여는 검사라 AI가 직접 끝까지 확인한다** (SKILL.md §1.5 "사람 몫"은 화면을 눈으로 보는 검증 얘기고, 이건 응답 본문을 확인하는 일이라 해당 없다).

**연동이 끝나면 배포해 링크를 갱신한다** — §2.3 베타 공유에 쓸 링크가 실데이터로 돌아야 한다. 3단계 배포 링크는 그대로 두고 재배포하면 된다.

### 2.3 베타 공유

배포된 링크를 **4단계(DemoValidation) 인터뷰이(와 타겟 명단)**에게 보내 **실제 사용 반응**을 확인한다.

**왜 백엔드 연동 뒤로 왔나**: 3단계에서 이미 프로토타입을 배포해 4단계 데모까지 돌렸으니, 여기서 또 공유해봐야 화면 반응은 새로 볼 게 없다. 이 시점 공유가 볼 값어치가 있는 건 **실데이터가 흐를 때의 행동**이다 — 진짜로 계정을 만드는지, 자기 데이터가 남는 걸 확인하고 다시 들어오는지, 핵심 플로우에서 어디서 이탈하는지.

**판정 아님**: go/no-go 게이트가 아니라 치명 결함(가입 실패·데이터 유실·핵심 플로우 이탈·심각한 오해) 확인용. 발견되면 수정 후 재공유, 없으면 §2.4(퍼널 계측)로 진행. 관찰 내용은 `mvp-build.md`에 짧게 기록한다.

**사용자가 직접 클릭하며 검증한다** — AI가 Playwright 같은 도구로 자동 사인오프하지 않는다 (SKILL.md §1.5 "사람 몫 불변"). AI는 배포까지 준비하고, 실제로 눌러보고 확인하는 건 사람 몫.

### 2.4 퍼널 계측

7단계(MvpLaunch) 판정은 **여기서 심은 이벤트가 전부다** — 계측이 빠지면 광고비를 쓰고도 판정 불능. 5종 기본 이벤트:

| # | 이벤트 | 정의 (예시 — 서비스에 맞게 구체화) | 퍼널 위치 |
|---|---|---|---|
| 1 | 유입 | 랜딩 도착 (유입 채널 구분 파라미터 포함 — 발품 vs 광고 vs 기타) | 최상단 |
| 2 | 가입 | 계정 생성 완료 | 전환 1 |
| 3 | 핵심행동 | *이 서비스의 aha 순간* 1회 완료 (예: 매물 진단 1회) — 무엇으로 할지 사용자와 결정 | 활성화 |
| 4 | 재방문 | 가입 후 7일 내 재방문 | retention |
| 5 | 결제 | (지불 가설 있으면) 결제 완료 / (없으면) 가격 페이지 도달 등 지불 의사 프록시 | 수익 |

- **채널 구분이 필수** — 발품 유입과 광고 유입을 구분 못 하면 7단계(MvpLaunch) 이중 채널 판정이 무너진다. UTM 파라미터 등으로 구분.
- 계측 도구는 **Supabase 자체 이벤트 테이블 기본** (고정 스택에 이미 있음 — 별도 analytics SaaS 없이 5종을 테이블에 적재, 퍼널 쿼리를 SQL로). 무거운 SaaS는 지양. 이벤트 테이블도 §2.2와 같은 기준으로 RLS를 건다.
- **이벤트 정의를 `mvp-build.md`에 표로 기록** — 7단계(MvpLaunch) launch-plan이 이 정의를 그대로 참조한다 (이름·정의 drift 방지).

#### 2.4.1 에러 관측

퍼널 계측과 별개로 에러를 감지할 수단도 확보한다 — 최소 배포 후 Vercel 대시보드의 런타임 로그(Runtime Logs, 서버 실행 중 발생한 에러·로그를 모아 보여주는 화면)를 확인하는 방법을 알아둔다. 원하면 Sentry류 경량 에러 추적 도구를 붙여도 되지만 필수는 아니다. 7단계 측정 기간에 가입 실패·결제 에러 같은 버그가 조용히 나면 퍼널 숫자가 나쁜 게 제품 탓인지 버그 탓인지 구분을 못 해 판정이 오염된다 — "버그는 즉시 고친다"는 룰(7단계)이 있어도 버그가 났다는 걸 아는 수단이 없으면 소용없다.

### 2.5 배포·완료

1. 최종 배포 (3단계에서 붙여둔 Vercel 그대로). main 직접 push 금지 — PR 워크플로 (repo 훅이 막음).
2. **사용자가 배포 URL을 브라우저로 직접 클릭** — 핵심 시나리오 끝까지 통과 + 가입·핵심행동 이벤트가 실제로 찍히는지 확인 (AI가 자동 도구로 검증·사인오프하지 않음 — SKILL.md §1.5 사람 몫).
3. 실결제 연동했으면 **실결제 테스트 1건** (결제 → 환불) — 사용자가 직접.
4. 발견된 문제는 초안 모드로 수정 → 재배포 → 재확인 (자율 재작업 상한 2회 — SKILL.md §1.5).

백엔드 연동·베타 공유·계측·배포가 모두 끝나면 7단계(MvpLaunch)로 넘어간다.

### 2.6 옛 단계 내용 가져오기 — SKILL.md §2.2 검토 절차 적용

이 단계 산출물에 옛 문서 내용을 근거로 가져올 땐 SKILL.md §2.2의 **확인 질문 4개**를 순서대로 거친다. 통과한 내용엔 표시 3종(**✅ 이번 단계에서 직접** / **🔵 옛 단계에서 가져옴** / **🟡 애매함**)을 붙이고, 4번(넓혀 말한 경우)으로 통과한 건 넓혀 말한 근거 한 줄 + 근거 위치를 함께 적는다. 2·3번에 걸린 내용은 가져오지 않고 문서 끝 `# 🟥 버린 내용 목록`에 한 줄씩 남긴다 (§4.1).

**단계 항목 × 옛 단계 표준 섹션 종류 매핑** — 옛 단계의 *섹션 종류(역할)* 기준이다:

| 이 단계 항목 | 가져오는 옛 단계 섹션 종류 | 비고 |
| --- | --- | --- |
| `# 이전 결론 → 이번 결론` (§2.1) | `demo-validation.md`의 *최종 확정 아이디어* 섹션 | 체인의 직전 결론 — 5단계는 체인 밖 |
| 화면 카피 조정 (§2.2) | `demo-validation.md`의 *최종 확정 아이디어* 톤 검토 | 톤이 확정 아이디어와 맞는지만 본다 |
| 빌드 스코프 판단 (§2.2) | `market-research.md`의 *조사 요약* | 참고 맥락 — 게이트 아님 |

**표시 판정 적용 예시**:

- **(가) `market-research.md` 조사 요약의 빈틈 정보를 빌드 스코프 근거로 가져올 때** — 최신 문서(`demo-validation.md` §비목표)와 어긋나지 않는지 확인 질문을 거쳐 **🔵**로 쓰고 근거 위치를 병기한다. 비목표와 어긋나면 **🟥**로 가져오지 않고 버린 내용 목록에 남긴다.
- **(나) 4단계 인터뷰 인용을 랜딩 화면 카피 근거로 넓혀 쓸 때** — 최신 문서의 어느 문장이 그 내용을 품는지 짚을 수 있어야(확인 질문 4번) **🔵**로 쓰고, 못 짚으면 **🟡**로 두고 사용자에게 확인받는다.

## 3. 완료 체크리스트

다음이 모두 충족되어야 다음 단계(MvpLaunch)로 진입.

- [ ] **백엔드·DB·auth 연동 완료** (§2.2) — 테이블·auth 생성, Supabase RLS 활성화·정책 확인 포함.
- [ ] **스키마가 마이그레이션 파일로 남아 있음** (§2.2.2) — 대시보드로 직접 만든 것도, 따로 만든 DB 설계 문서도 없음. 로컬 `supabase db reset` 통과 + **함수·트리거를 실제로 불러 확인**한 뒤 `db push`로 클라우드에 반영. 새로 만든 함수마다 실행 권한도 회수됨. **올린 뒤 클라우드에서 권한·storage·auth 관련이 실제로 걸렸는지 확인** (§2.2.2 ④).
- [ ] **마이그레이션을 클라우드에 실제로 밀었음** (§2.2.2 ⑥) — 마이그레이션이 든 PR을 머지했다고 자동으로 올라가지 않는다. `npx supabase db push --linked`를 따로 돌렸고, `npx supabase migration list --linked`에 안 올라간 게 없음. CI가 이걸 잡아주도록 깃허브 Secret 셋(`SUPABASE_ACCESS_TOKEN`·`SUPABASE_PROJECT_REF`·`SUPABASE_DB_PASSWORD`)도 넣어뒀음.
- [ ] **백업 상태 확인** (§2.2.2 ⑦) — `npx supabase backups list --linked`로 확인. 자동 백업·시점 복구(PITR)가 꺼져 있으면 켜거나, `db dump`로 파일 백업을 정기적으로 남기는 방법을 정해뒀음.
- [ ] **로그인·동의 처리 완료** ([6-mvp-build-auth-consent.md](6-mvp-build-auth-consent.md)) — 받는 정보를 필수/선택으로 갈랐음. 선택 정보를 받으면 인증 뒤 신규 가입자만 온보딩으로 보내 동의를 받고(필수·선택 체크박스 분리, 거부해도 가입 가능, 선택 칸 nullable), 필수만 받으면 고지문 한 줄. 약관·개인정보처리방침 페이지가 실제로 있고 로그인 화면 밖에서도 접근됨.
- [ ] **로컬스토리지 저장 경로 제거 확인** (§2.2) — 폴백으로도 남아 있지 않음.
- [ ] **demo-validation에서 확인된 핵심 플로우가 실제로 동작** (§2.2) — 로컬스토리지가 아니라 실 DB로 데이터가 흐름.
- [ ] **(추가 스택 있으면) ADR 기록** (§2.2) — 결제 PG 등 이 단계에서 새로 붙인 것만. 고정 스택 조합·버전은 3단계 기록 참조.
- [ ] **검색 노출 기본 세트 + curl 판정 통과** (§2.2.3) — 제목·설명·OG·sitemap/robots·404 상태코드. 3단계 색인 제외를 공개 페이지만 풀었고 비공개 화면은 계속 막힘. `curl`로 콘텐츠 문구가 잡힘.
- [ ] **베타 공유·치명 결함 확인** (§2.3) — 4단계 인터뷰이(와 타겟 명단)에게 실데이터 붙은 링크 공유, 가입 실패·데이터 유실·핵심 플로우 이탈·심각한 오해 없음(또는 발견분 수정·재공유 완료).
- [ ] **퍼널 이벤트 5종이 실제로 찍힘** (§2.4) — 사용자가 직접 클릭해 이벤트 발화 확인. 채널 구분 동작.
- [ ] **에러 로그 확인 수단 확보** (§2.4.1) — 최소 Vercel 런타임 로그 확인 방법 숙지.
- [ ] **(지불 가설 있으면) 실결제 1건 테스트 완료** (§2.5, 결제 → 환불).
- [ ] **공개 URL 접속 가능** (§2.5) — 배포 완료, 핵심 시나리오가 실데이터로 끝까지 돈다.
- [ ] **`mvp-build.md` 작성됨** (§4) — 데이터 모델·연동 결정·계측 이벤트 정의 표·배포 정보·베타 공유 관찰·3단계 프로토타입 대비 조정 사항.
- [ ] **옛 단계에서 가져온 내용에 표시가 붙음** (§2.6) — 확인 질문 4개를 거쳐 🔵(또는 ✅·🟡)를 달았고, 걸러진 내용은 문서 끝 🟥 버린 내용 목록에 기록됨.
- [ ] (사용자 검증) **사람이 브라우저로 배포물 클릭 검토 완료** (§2.5) — 광고 유입 랜딩 경로(랜딩→가입→핵심행동)는 모바일 화면에서도 확인.

### 4.2 frontmatter 규칙

- `name`: `mvp-build`
- `created_at` / `updated_at`: ISO 날짜
- `status`: `draft` (연동 중) → `confirmed` (백엔드 연동·베타 공유·계측·배포 완료)
- 스택 필드는 두지 않는다 — 스택은 3단계에서 확정되므로 여기 frontmatter의 몫이 아니다. 이 단계에서 추가한 것만 본문 `# 스택`에 적는다.

## 5. 사용자 응대 톤 + 코칭

- **톤**: SKILL.md §1.3대로 반말·친근·짧게.
- **진입 안내**: "지금 앱은 데이터가 네 브라우저 안에만 쌓여서 다른 기기로 열면 텅 비어 있어. 이제 진짜 DB랑 로그인 붙여서 실서비스로 만들 차례야 — 백엔드 붙이고, 실데이터 도는 상태로 베타 공유해보고, 퍼널 계측까지 심어서 배포 완주할게. 스택은 3단계에서 이미 정해놔서 새로 고를 건 없어."
- **빌드 중**: 잘게 확인 요청 금지 (초안 모드). 에스컬레이션 기준 해당 시에만 멈추고 배치로 질문.
- **베타 공유 안내**: "이번엔 진짜 데이터가 도는 링크야 — 4단계에서 만난 사람들한테 보내서 실제로 가입하고 쓰는지 보자. 판정이 아니라 치명적인 거 있는지 확인이야."
- **화면 구조를 다시 뒤집자는 요청**: 코드를 고치는 건 이 단계에서도 정상이다 — 백엔드 붙이며 화면이 조금씩 바뀌는 건 당연. 다만 **화면이 늘거나 빠지는 구조 변경**은 4단계 go 판정(구조적 수정 0건 수렴)을 되돌리는 일이라고 짚는다. 정말 필요하면 옛 문서를 고치는 게 아니라 2단계를 다시 실행하는 피봇으로 다루는 게 순서고(SKILL.md §2.2 — 인벤토리는 1세대 기록이라 갱신하지 않는다), 아니면 7단계(MvpLaunch) 이후 production으로 넘기자고 안내한다.
- **범위 압박 대응**: 사용자가 "이 기능도 넣자" 하면 — 3단계 앱 코드에 있는 범위·`demo-validation.md` §비목표와 대조해 짚고, 검증 가설에 필요한지 확인. 필요 없으면 "런치 검증(7단계) 끝나고 production에서" 권유 (강제는 아님 — 사용자가 원하면 명세 먼저 갱신 후 빌드).
- **완료 시**: 배포 URL + "핵심 시나리오대로 클릭해봐 + 이벤트 찍히는 것도 같이 확인하자" + 체크리스트 현황.
- **배포·클릭 검증 안내**: "배포까진 내가 하는데, 실제로 눌러보고 확인하는 건 네 몫이야 — 자동 검증 도구로 대신 사인오프 안 해" (SKILL.md §1.5 사람 몫).
