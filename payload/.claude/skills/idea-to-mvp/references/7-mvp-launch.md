이 단계는 **말이 아니라 행동으로 가설을 판정하는** 이 스킬의 **유일한** 통과 기준이다. 사람을 구해 앉혀놓고 묻는 인터뷰는 앞에서 좋게 말해주기 마련이라 실제보다 부풀려지지만, 광고 클릭→가입→사용→결제는 거짓말을 못 한다. 그래서 앞 단계들은 거르지 않고 만들며 다듬기만 했고, 거르기는 여기 한 번뿐이다.

**이 단계의 생명은 순서다** — 기준을 광고 집행 *전에* 동결한다. 숫자를 보고 나서 기준을 정하면 창업자 뇌는 무조건 자기한테 유리하게 해석한다(사후 자기합리화). 합격선은 시험 전에 그어놔야 의미가 있다.

**소액 광고의 한계를 알고 쓴다** — 소액 예산의 퍼널 숫자는 광고 소재·타겟팅 실력에 흔들린다 ("광고가 구려서 죽었는지 제품이 필요 없어서 죽었는지" 구분 어려움). 그래서 채널은 반드시 **이중**: 발품(정성 — *왜* 쓰는지/안 쓰는지 들림) + 광고(정량 — 퍼널 숫자). 하나로만 판정하지 않는다.

## 1. 단계 목표

- **`launch-plan.md`** — 광고 집행 *전* 동결: **확정 4개**(최종 아이디어 · 비목표 · 검증 가설 · 북극성) + 퍼널 go 선 · 예산 · 측정 기간 · 채널 계획.
- **이중 채널 집행** — 발품(커뮤니티·직접 아웃리치) + 소액 광고. 측정 기간 동안 퍼널 데이터 + 정성 voice 수집.
- **`launch-retro.md`** — 실측 vs 기준 + 정성 종합 → **가설 검증 / 피봇 / 폐기** 최종 판정 (통과 기준).

**SoT 책임** (SKILL.md §2.1): 확정 4개와 런치 기준 = `launch-plan.md` (동결 후 불변), 실측·판정 = `launch-retro.md`. 계측 이벤트 *정의*의 SoT는 **코드**(이벤트 테이블 스키마·추적 코드)다 — 여기서 재정의하지 않고 코드에서 직접 읽어 쓴다.

## 2. 진행 절차 — 3막 (순서 강제)

**단계 시작** — 막1에 들어가기 전에 사용자와 "지금까지 어디까지 왔고, 이제 무엇을 할지"를 맞춘다: ① 이전 단계까지 정리된 내용을 먼저 보여준다 — 배포 URL이 살아 있고 퍼널 이벤트가 실제로 찍히는 상태(`backend-build.md` + **코드의 이벤트 테이블·추적 코드**), 실제 앱 코드가 무엇을 하는 서비스인지, `market-research.md`의 조사 요약과 `backend-build.md`의 베타 공유 관찰(있으면)에서 나온 채널 힌트를 짧게 요약. ② 그 내용을 기반으로 이번 단계가 무엇을 하는지 설명한다 — **아이디어·안 만들 것·검증할 가설을 여기서 문장으로 못 박고**, 기준을 동결하고, 발품+소액 광고로 실제 사용자를 불러와서, 그들의 행동 실측 숫자로 최종 판정하는 단계. ③ `launch-plan.md` 머리에 `# 이전 결론 → 이번 결론`을 적는다 — **확정 4개는 여기서 처음 확정되므로 첫 판은 "이 단계에서 처음 확정" 한 줄이다** (SKILL.md §2.2). 이미 launch-plan·launch-retro가 있으면(중간 재실행) §3 체크리스트로 검증해 이어간다.

### 2.1 막1 — 기준 박기 (광고 집행 전, 강제 잠금)

**launch-plan.md를 쓰고 사용자가 확정하기 전에는 광고 집행 금지.** SKILL.md §4의 건너뛰기 옵션도 이 잠금엔 적용 안 됨.

#### 2.1.1 최종 확정 — 아이디어·비목표·검증 가설·북극성 동결

**퍼널 숫자를 정하기 전에 이 4개부터 못 박는다.** 광고를 켜는 순간부터는 "무엇을 검증하려던 거였지"가 흔들리면 안 되기 때문이다. 여기까지 오는 동안 아이디어는 어디에도 문장으로 확정된 적이 없다 — 1단계 `user-story.md`는 *출발점 입력*이고, 5단계 이후 진실은 *코드*였다. 그러니 **지금 실제로 만든 것을 근거로 4개를 문장으로 확정하고, 광고 집행과 함께 얼린다.**

절차:

1. **AI가 후보를 만들어 제시한다.** 근거는 셋 — `user-story.md`(서비스 한 줄 정의·타겟·현재의 대안), `feature-list.md`(무엇을 만들고 무엇을 안 만들기로 했나), **실제 앱 코드**(화면·카피·기능에서 지금 이 서비스가 실제로 무엇인지). 셋이 어긋나면 **코드가 기준**이다 (SKILL.md §2.2).
2. **사용자에게 4개를 순서대로 보여주고 확인받는다.** (2)(3)(4)는 founder 의지라 추정하지 말고 후보 2~3개를 내서 고르게 한다 (SKILL.md §1.4).

   **(1) 최종 확정 아이디어** (한 문단):
   > "**[누구]가 [상황]에서 [문제] 겪는 걸 [어떻게] 풀어준다**"

   1단계 한 줄 정의와 달라졌으면 무엇이 왜 이동했는지 한 줄 붙인다 (타겟·문제·해결 방식 중 어디).

   **(2) 비목표 (안 만들 것)** — 형식 `[X] 안 함 — [이유]`. **최소 1개.** 광고를 켜면 "이것도 있어야 하지 않나" 요청이 몰려오는데, 그때 브레이크가 될 문장이다.

   **(3) 검증 가설** — 형식 `[조건]하면 [예측]할 것이다`. **1~2개.** 아래 퍼널 go 선이 이 가설을 숫자로 옮긴 것이므로, 가설이 없으면 go 선의 근거도 없다.

   **(4) 북극성** (1줄, 선택) — 2~3년 방향 한 줄(행동·규모·포지셔닝 중 하나). 이번 검증에 묶인 수치는 쓰지 않는다 — 그건 아래 go 선의 몫이다. 생략 가능.
3. **`launch-plan.md`의 `# 이전 결론 → 이번 결론`에 4개를 박는다.** 첫 판이면 `## 이전 결론`은 "이 단계에서 처음 확정"이고, 4개는 `## 이번 결론`에 적는다. 동결 시점부터 이 4개가 아이디어·가설의 SoT다.
4. **`CLAUDE.md`·`AGENTS.md`의 프로젝트 정의 줄을 갱신한다.** 두 파일 상단에 같은 프로젝트 정의 줄(한 줄 정의·타겟, project-init이 채운 것)이 각각 있다. **둘 다** 최종 확정 아이디어와 일치하게 덮어쓴다. 한쪽만 고치면 도구마다 다른 정의를 읽는다. 이 둘은 매 세션 자동으로 함께 로드되는 파일이라, 안 고치면 이후 모든 세션이 낡은 정의를 계속 읽는다.

여기까지 확정한 뒤에 아래 퍼널 기준으로 넘어간다.

AI가 초안 모드로 launch-plan 초안을 완주해서 제시 — 단 **go 선 수치는 인터뷰 모드** (사용자 결정 영역, SKILL.md §1.5). AI는 §2.1.1에서 방금 확정한 검증 가설 + **코드에서 읽은 이벤트 정의**를 base로 *후보 수치 + 업계 통상 범위 + 이유*를 제시하고, 사용자가 정한다.

**옛 문서에서 가져오는 내용은 SKILL.md §2.2 검토 절차를 거친다** — launch-plan에 근거로 끌어오는 것들(`user-story.md`의 대안·불편함, `market-research.md`의 조사 요약, `backend-build.md`의 베타 공유 관찰)은 확인 질문 4개를 순서대로 확인한 뒤 **🔵 옛 단계에서 가져옴** 표시와 근거 위치를 함께 적고, 걸러진 내용은 문서 끝 `# 🟥 버린 내용 목록`에 한 줄씩 남긴다 (§4). 계측 이벤트 *정의*만은 예외 없이 **코드**(이벤트 테이블·추적 코드)에서 직접 읽는다 — 문서에서 옮겨 적지 않는다. 예시: 1단계에 적힌 불편함 한 줄을 go 선 근거로 넓혀 쓸 땐, 지금 앱 코드의 어느 화면이 그 내용을 품는지 짚을 수 있어야(확인 질문 4번) 🔵로 쓴다 — 못 짚으면 🟡로 두고 사용자에게 확인받는다.

**퍼널 기준으로 박을 4개**:

1. **퍼널 go 선** — 코드의 이벤트 테이블·추적 코드에서 이벤트 이름과 정의를 직접 확인해 그대로 쓴다 (여기서 재정의 금지):

   | 퍼널 | 측정 | go 선 | 이유 |
   |---|---|---|---|
   | 유입→가입 | 랜딩 전환율 | __% | (후보 제시 시 통상 범위 병기) |
   | 가입→핵심행동 | 활성화율 | __% | |
   | 재방문 | 7일 내 재방문율 | __% | |
   | 지불 | 결제 전환율 (또는 프록시) | __% | |

   모든 선이 넘어야 go는 아님 — **어떤 조합이면 go / 어떤 조합이면 피봇 검토**인지 판정 룰도 함께 박는다 (예: "가입·활성화 통과 + 지불 미달 = 가격 피봇 검토"). 표본이 작으므로 판정 룰은 단순하게.

2. **예산·기간** — 광고비 상한 (예: 30만원) + 측정 기간 (예: 2주). 기간 전 조기 종료 조건(예산 소진·명백한 무반응)도 명시.

3. **채널 계획** —
   - **발품**: 어디 커뮤니티·어떤 방식(글·DM)·목표 접촉 수. 정성 voice 수집 방법 (댓글·DM 대화 기록).
   - **광고**: 매체(예: Meta·네이버)·타겟·소재 방향. 채널 구분 파라미터는 **코드에서** 확인 (6단계에서 심은 것).
   - **검색 유입 분리**: 6단계에서 검색 노출을 켰으면(`6-backend-build.md` §2.3) 검색으로 들어오는 사람이 생긴다. 이건 발품도 광고도 아니라서 그냥 두면 광고 성과로 오해된다. 유입 이벤트에서 검색 유입을 **제3의 채널로 갈라서** 집계하고, 판정은 발품·광고 두 축으로만 한다.

4. **동결 선언** — "이 기준은 집행 후 변경하지 않는다. 변경이 불가피하면 *변경 전에* 사유를 launch-plan.md 하단에 기록한다." frontmatter `status: frozen` + 동결 날짜.

### 2.2 막2 — 이중 채널 집행 + 수집

**광고 소재·랜딩 카피는 초안 모드로 생산** — AI가 소재 후보 여러 벌 완주 (카피는 `ux-writing-reviewer` 에이전트 통과). 집행(광고 계정 세팅·게시)은 사용자가.

**발품도 계획대로** — 커뮤니티 글·DM은 AI가 초안, 게시·대화는 사용자. 대화에서 나온 정성 voice는 그때그때 기록 (launch-retro 입력).

**측정 기간 중 룰**:

- **퍼널에 영향 주는 변경 금지** — 랜딩 카피 수정·가격 변경·기능 추가는 측정을 오염시킨다. 발견한 개선 아이디어는 `추후 결정:`으로 기록만.
- **명백한 버그 fix는 OK** — 퍼널이 *깨진* 것(결제 에러·가입 불능)은 즉시 수정하고 수정 시점을 기록 (판정 시 참작).
- **에러 확인 루틴** — 측정 기간 중 주기적으로(예: 매일 한 번) 에러 로그(6단계에서 확보한 관측 수단 — `backend-build.md` 배포 정보 참조)를 확인한다. 버그로 인한 퍼널 왜곡을 늦게 발견할수록 오염된 기간이 길어진다.
- AI는 주기적으로 퍼널 중간 숫자를 정리해 보여줄 수 있으나, **중간 숫자로 기준을 흔들지 않는다** — go 선 재론은 금지.

### 2.3 막3 — launch-retro (통과 기준, 최종 판정)

측정 기간 종료 후:

1. **AI가 판정 자료를 초안 모드로 완주** — 퍼널 실측 vs go 선 표 (채널 구분 포함) + 발품 정성 voice 종합 + 판정 룰 적용 결과 + 버그 fix·특이사항 타임라인.
2. **판정은 사람** (SKILL.md §1.5 사람 몫 불변). 3분기:

   - **가설 검증 (go)** → **production 졸업** — 이 하네스의 범위 밖 (매출 스케일업·운영 자동화·다채널 확장은 분기별 KPI·운영 도구 영역). 7단계 전부 완주. launch-retro에 production 입력(검증된 채널·남긴 `추후 결정` 목록) 정리.
     - **여기서 말하는 "production 졸업"은 사업 단계 얘기지 인프라 얘기가 아니다** — 실서비스 개통(실 DB·개인정보·결제·공개 배포)은 이미 6단계(BackendBuild)에서 끝나 있다. 졸업한다는 건 검증된 아이디어를 매출로 키우는 운영 단계로 넘어간다는 뜻이지, 이제서야 실서비스용 DB를 새로 만든다는 뜻이 아니다.
   - **피봇** → 무엇이 죽고 무엇이 살았는지로 되돌아갈 단계를 정한다. 갈래는 아래 표대로. 영향 범위 처리 원칙은 SKILL.md §1.4 "이전 결정 변경 처리".
   - **폐기 (no-go)** → 이 아이디어는 닫음. 학습을 launch-retro에 보존. 새 아이디어는 새 프로젝트에서 처음부터.

**실패 갈래 표** — 어떤 신호가 죽었는지로 다음 행동이 갈린다:

| 실패 신호 | 성격 | 다음 행동 |
|---|---|---|
| 지불 전환만 미달, 나머지 통과 | 가격·과금 모델 | 가격만 손질 후 재런치 (단계 이동 없음) |
| 가입은 되는데 활성화·재방문 미달 | 기능·완성도 | 6단계(BackendBuild)로 — 핵심행동 UX·온보딩 재작업 |
| 유입은 되는데 가입이 낮음 | 구조·UX | 5단계(FrontendBuild)로 — 랜딩·온보딩 플로우 재설계 |
| 전 지표 약함 + 발품 정성 반응도 없음 | 아이디어 자체 | 폐기 — 새 아이디어는 새 프로젝트 (같은 프로젝트에서 1단계 재실행이 아니다, SKILL.md §3 원칙) |

**Use·Love·Pay 매핑** (판정 자료에 이 3축으로도 요약):

| 축 | 측정 |
|---|---|
| Use (쓰는가) | 활성화율 + 재방문율 |
| Love (좋아하는가) | 발품 정성 voice (자발 추천·재문의) — 표본이 충분히 쌓이면 Sean Ellis 설문("없어지면 매우 실망" 40%)을 *보조*로 |
| Pay (지불하는가) | 실결제 전환 (또는 지불 프록시) |

Sean Ellis 40%는 소액 광고 표본으론 통계가 안 서는 경우가 많다 — **주 판정은 launch-plan의 퍼널 go 선**, Sean Ellis는 표본 될 때만 보조.

## 5. 좋은 예 vs 나쁜 예

- **기준 박기** — 좋은: "가입 전환 5%·활성화 40%·재방문 20%, 판정 룰까지 집행 3일 전 동결". / 나쁜: "일단 광고 돌려보고 숫자 보고 판단하자" (사후 기준 = 자기합리화 문).
- **채널** — 좋은: "광고 가입 31명(전환 4.2%) + 발품 대화 14건에서 '중개사 말을 못 믿겠다' 7회 반복". / 나쁜: 광고 숫자만 놓고 "전환 낮음 = 폐기" (소재 문제인지 제품 문제인지 미구분).
- **측정 기간 대응** — 좋은: "결제 에러 발견 즉시 fix + 타임라인 기록, 랜딩 카피 개선안은 추후 결정으로 보류". / 나쁜: 중간 숫자 보고 랜딩 카피 교체 (측정 오염).
- **판정** — 좋은: "가입·활성화 통과, 지불 미달 → 판정 룰대로 가격 피봇 검토, 근거 표 첨부". / 나쁜: "느낌상 반응 나쁘지 않으니 go".

## 6. 사용자 응대 톤 + 코칭

- **톤**: SKILL.md §1.3대로 반말·친근·짧게.
- **진입 안내**: "이제 진짜 시장에 내보내서 검증할 차례야. 순서가 중요해 — 광고 켜기 *전에* 두 가지를 못 박자. 하나는 '이게 결국 누구의 무슨 문제를 푸는 건지, 뭘 안 만들 건지'고, 다른 하나는 '얼마면 합격'인지 선이야. 내가 지금 만든 코드 보고 초안 만들어올게 — 최종 판단은 네가 해."
- **go 선 코칭**: 사용자가 수치를 못 정하면 후보 2~3개 + 통상 범위 제시 (SKILL.md §1.4). "모르겠으면 보수적인 쪽으로 — 낮은 선으로 통과하는 것보다 높은 선에 못 미치는 걸 아는 게 싸."
- **동결 후 흔들림 대응**: 측정 중 "기준 좀 낮출까?" 신호 — "그게 이 단계가 막으려는 바로 그거야. 낮출 이유가 진짜면 *변경 이력에 사유 먼저* 쓰고 바꾸자 — 근데 웬만하면 기간 끝까지 보고 판정에서 얘기하자."
- **판정 안내**: 자료를 표로 보여주고 — "판정은 네 몫이야. 자료 기준으로는 [요약]. 어느 쪽?"
