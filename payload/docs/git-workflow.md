# git 워크플로

이 저장소에서 브랜치를 어떻게 만들고, 작업을 어떻게 main에 합치고, 뭔가 잘못됐을 때
어떻게 되돌리는지를 정리한 문서입니다. `new-task`·`done-task` 스킬이 이 흐름을 자동으로
돌려 주므로 평소에는 이 문서를 몰라도 되지만, **되돌리기가 필요한 순간**에는 여기부터 보셔야 합니다.
특히 §4~§6은 실제로 사고가 났을 때 참고할 수 있게 써 놓았습니다.

## 1. 전체 흐름

작업 단위는 **브랜치 하나**입니다. 폴더는 맨 처음 내려받은 저장소 하나뿐이고, 작업을 새로
시작할 때마다 그 안에서 브랜치만 새로 팝니다. 이 브랜치 단위로 아래 순환을 돕니다.

```
new-task → 작업 → done-task → new-task → 작업 → ...
```

- **`new-task`**: main을 최신으로 당겨 오고, 새 feature 브랜치를 만들어 줍니다. (머지 끝난
  옛 브랜치가 로컬에 남아 있으면 이때 같이 지웁니다 — 평소에는 `done-task`가 이미 지워 두어서
  지울 것이 없지만, 정리가 실패했을 때를 위한 안전망으로 남아 있습니다.)
- **작업**: 코드를 고치는 동안, 응답이 끝날 때마다 `auto-wip-commit` 훅이 변경된 파일을
  자동으로 `wip: ...` 커밋으로 저장합니다. **main 브랜치에서는 이 훅이 돌지 않습니다** — main을
  wip 커밋으로 더럽히지 않으려는 안전장치입니다. 그래서 wip 커밋은 항상 feature 브랜치에만 쌓입니다.
- **`done-task`**: 안에서 simplify 판단을 먼저 하고, git 절차는 내부 스킬 ship-task(fork)에 넘깁니다 — 사용자께서 알아 두실 이름은 done-task뿐입니다. 그 절차가 쌓인 wip 커밋들을 push하고, PR(코드 합치기 요청)을 만들고, 머지
  권한이 있으면 CI(자동 검사 — push된 코드가 빌드·린트를 통과하는지 GitHub이 자동으로
  돌려 보는 것)가 끝날 때까지 기다렸다가, 통과했을 때만 **뭉쳐서 합치기(squash merge)**
  — PR 안의 여러 커밋을 하나로 뭉쳐서 main에 합치는 방식 — 로 main에 반영합니다. 그다음
  원격 브랜치를 지우고, 로컬도 main으로 옮겨 앉은 뒤 방금 머지한 브랜치를 지워서
  마무리합니다. CI가 실패하면 머지하지 않고 멈춥니다.
- 다시 `new-task`로 돌아가서 다음 작업을 시작합니다.

한 가지 헷갈리기 쉬운 점이 있습니다 — `new-task`는 **main에 서 있을 때** 도는 단계입니다. 이미 feature 브랜치를 열고 작업 중이라면 `new-task`를 또 돌리는 것이 아니라 그냥 이어서 작업하시면 됩니다. 지금 어디 서 있는지는 `git branch --show-current`로 확인합니다.

누가 부르는지도 갈립니다. `new-task`는 클로드가 알아서 부릅니다 — main에서 일을 시작하면 브랜치를 직접 열고 진행합니다. `done-task`는 **사용자께서 "보내줘"라고 말씀하신 뒤에만** 부릅니다. 머지는 곧 실서비스 배포라, 화면을 직접 본 사람의 승인이 한 번은 있어야 하기 때문입니다. 그래서 작업이 끝나면 클로드가 "화면을 확인하셨다면 보내도 되겠습니까?"라고 먼저 물어볼 것입니다.

main에 머지되면 Vercel이 그 커밋을 자동으로 배포합니다. 즉 **main에 무언가 들어가는 순간 =
서비스가 바뀌는 순간**이라고 생각하시면 됩니다.

결과적으로 두 종류의 기록이 남습니다.

- **feature 브랜치**: 작업하는 동안의 wip 커밋들이 촘촘하게 쌓입니다 (한 턴에 하나씩).
- **main**: PR 하나당 뭉쳐진 커밋 딱 1개만 남습니다.

여기까지는 혼자 작업하는 것을 전제로 한 흐름입니다. 여러 명이 같이 작업할 때는 몇 가지가
달라지는데, §8에 정리해 두었습니다.

### 1.1 처음 시작 — 저장소 만들기는 한 번만

새 폴더에서 "하네스 적용해줘"라고 하시면 첫 커밋과 첫 push는 자동입니다. `project-init`이
하네스 파일을 main에 첫 커밋으로 넣고, 이어서 `github-connect`가 GitHub 저장소를 만들고
main을 올립니다. git·gh 설치나 GitHub 로그인처럼 사람만 할 수 있는 일이 나오면 한 단계씩
화면 이름·버튼 이름으로 알려 드립니다.

이 첫 커밋·첫 push만 main에 직접 들어갑니다 — §3 "main 직접 push 금지"의 유일한 예외입니다. 빈
저장소라 리뷰할 화면도 배포도 없기 때문입니다. 그다음부터는 위 흐름대로 `new-task` → 작업 →
`done-task`입니다.

push는 HTTPS + 토큰으로 합니다. 토큰은 프로젝트의 `.env.cli`(git에 올라가지 않는 파일)에 있고,
자세한 내용은 `docs/account-check.md` gh 항목에 있습니다. GitHub 연결을 미루셨다면 나중에 "깃헙
연결해줘"라고 하시면 됩니다 — 그 전에는 원격 저장소가 없어서 `new-task`·`done-task`가 돌지 않습니다.

## 2. 왜 뭉쳐서 합치기(squash merge)인가

두 가지를 동시에 얻고 싶기 때문입니다.

- **main 기록은 PR 단위로 깨끗하게** — `git log`를 봤을 때 "이 PR에서 무엇을 했다"가 한 줄로
  보여야 나중에 찾기 쉽습니다.
- **wip 커밋은 버리지 않고 PR 페이지에 보존** — auto-wip-commit이 남긴 커밋들은 그 작업을
  하면서 사용자가 말한 의도의 흔적(무슨 요청으로 무엇이 바뀌었는지)이라 함부로 지우면 아깝습니다.
  나중에 "그때 그 시점"으로 돌아가고 싶을 때 이 wip 커밋들이 유일한 단서가 될 수 있습니다.

**로컬에서 미리 뭉쳐서(local squash) PR을 올리는 방식은 쓰지 않습니다** — 그렇게 하면 뭉치는 순간
wip 커밋이 통째로 사라져서 위에서 말한 두 번째 이득을 잃습니다. GitHub이 PR을 머지할 때
뭉쳐 주면(squash merge), 뭉치기 전 원본 커밋들이 그 PR 페이지의 Commits 탭에 그대로
남습니다 — 로컬에서 미리 뭉치는 것보다 이 방법이 두 이득을 다 챙깁니다.

**병합 커밋(merge commit)이나 재배치 병합(rebase merge)도 쓰지 않습니다.** 병합 커밋은 main
로그에 브랜치 갈래가 그대로 남아 지저분해지고, 재배치 병합은 브랜치의 커밋들을 하나씩
main 위에 다시 쌓는 방식이라 wip 커밋 하나하나가 main 로그에 그대로 노출됩니다 — 원하는
"main은 깨끗하게, wip은 PR 페이지에만"이라는 분리가 되지 않습니다. 그래서 **뭉쳐서 합치기 하나만
씁니다.**

### 2.5 작업 단위 끊기 가이드

작업은 **PR 하나로 묶을 수 있는 크기**로 끊는 것이 좋습니다. 너무 큰 PR은 세 가지가 힘들어집니다.

- **리뷰**: 변경이 너무 많으면 무엇을 왜 바꿨는지 한눈에 들어오지 않습니다.
- **되돌리기**: §5에서 보겠지만 main에서 되돌리는 단위가 PR 하나입니다. PR이 여러 목적을
  섞어서 크면, 그중 하나만 잘못됐어도 되돌릴 때는 PR 전체를 되돌려야 합니다 — 문제없던 부분까지
  같이 사라지는 것입니다.
- **기록 추적**: main 로그에서 "이 기능이 언제 들어갔지"를 찾을 때, PR 하나가 여러 목적을
  섞고 있으면 제목만 봐서는 무엇이 들어 있는지 짐작하기 어렵습니다.

**좋은 예** — `배포 설정 정리 + 이미지 교체` (파일 5개, 20줄 안팎 변경). 배포 설정
손보기와 이미지 교체라는 목적이 뚜렷하고 크기도 작아서, 무언가 잘못됐을 때 이 PR 하나만
되돌리면 영향 범위가 명확합니다.

**크기가 큰 예** — `개발환경 구축 + 화면 마이그레이션` (파일 십수 개, 수천 줄 변경).
제목부터 "개발환경 구축"과 "마이그레이션"이라는 서로 다른 두 목적이 붙어 있습니다. 이
경우처럼 프로젝트 초기 세팅을 한 번에 끝내야 하는 상황도 있긴 하지만, 이후 이 PR에서
문제가 생기면 환경 구축과 마이그레이션 둘 다 한꺼번에 되돌아가야 해서 영향 범위가 큽니다.
가능하면 "환경 구축"과 "마이그레이션"을 나눠서 두 개의 PR로 올리는 쪽이 되돌리기에는
더 안전했을 것입니다.

판단 기준: **"이 PR이 잘못됐을 때, 되돌려도 괜찮은 크기인가?"** 를 스스로 물어보고 애매하면
쪼갭니다.

## 3. main 직접 push 금지

이 저장소는 모든 변경이 PR을 거쳐야 합니다. `.claude/hooks/no-main-push.sh` 훅이 이것을 막아 줍니다 —
main에 직접 push하는 `git push` 명령을 감지하면 실행을 차단합니다. 예외는 맨 처음 저장소를
만들 때의 첫 push 하나뿐입니다(§1.1) — 훅은 원격에 main이 아직 없고 강제 push가 아닐 때만
그 push를 통과시킵니다. `env X=1 git push ...`처럼 앞에 환경변수를 붙여도 똑같이 검사합니다.

**단, 이 훅이 막는 것은 Claude가 이 저장소 안에서 Bash로 실행하는 push뿐입니다.** 사용자가
자기 터미널에서 직접 `git push origin main`을 치는 것은 이 훅이 관여할 수 없습니다 — 훅은
Claude Code 안에서만 동작하는 안전장치이지, 저장소 자체의 규칙이 아니기 때문입니다.

원래는 GitHub의 브랜치 보호 규칙(branch protection rule)으로 "main에는 PR 없이 직접
push 못 함"을 서버 쪽에서도 강제하고 싶었는데, **저장소가 private(비공개) + 무료
플랜이면 그 기능 자체를 켤 수 없습니다** (GitHub API가 403으로 거절합니다). 그러니 서버
쪽에는 main을 지켜 주는 안전망이 없다고 보시는 것이 맞습니다.

이제 PR마다 CI가 돌고, `done-task`가 머지 전에 그 통과를 기다립니다. **다만 이것은 브랜치
보호 규칙이 강제하는 것이 아닙니다** — 브랜치 보호는 여전히 켤 수 없으므로, "CI를 통과해야
머지한다"는 `done-task` 스킬이 지키는 관례일 뿐 GitHub이 서버 쪽에서 막아 주는
규칙은 아닙니다. §8.2에서 보는 "머지는 팀장만" 관례와 성격이 같습니다.

그래서 이 워크플로는 "잘못된 push를 막는다"보다 **"잘못돼도 되돌릴 수 있게 해 둔다"**는
쪽에 기대고 있습니다. 막을 방법이 완벽하지 않으니, 대신 §4~§6에서 되돌리는 방법을 확실히
알아 두는 것이 중요합니다.

## 4. wip 커밋 하나로 되돌아가기

feature 브랜치에서 작업하다가 "몇 턴 전 그 시점으로 돌아가고 싶다" 싶을 때 쓰는 절차입니다.
아래 흐름을 따라가시면 됩니다.

```
돌아가고 싶은 wip이 있다
  → 그 브랜치가 아직 살아있나?
      ├ 예 (아직 작업 중, done-task 전) — wip이 git log에 그대로 보임
      └ 아니오 (이미 ship함, done-task가 로컬 브랜치까지 지운 뒤)
                              → main 로그에서 PR 번호 찾기
                              → git fetch origin pull/N/head:recover-N
  → 어느 wip인지 고르기 (git log로 커밋 메시지·시점 확인)
  → 되돌리는 방법 고르기
      ├ 파일 하나만 필요:        git checkout <sha> -- <파일>
      ├ 새 브랜치로 되살리기:     git switch -c <새이름> <sha>
      └ 통째로 그 시점으로 되감기: git reset --hard <sha>   (push 전에만 안전)
```

**브랜치가 아직 살아있는 경우** (아직 `done-task` 전) — `git log`로 wip 커밋들이 그대로
보입니다. 원하는 시점의 커밋 해시(sha)를 찾아서 바로 아래 방법 중 하나를 쓰시면 됩니다.

**이미 ship한 경우** (`done-task`가 로컬 브랜치까지 지운 뒤) — 원격 브랜치는
사라졌어도, **GitHub은 `refs/pull/<PR번호>/head`라는 이름으로 그 PR 브랜치의 끝점을
영구 보존합니다.** 브랜치 끝점이라 거기서 거슬러 올라가는 wip 커밋 전부가 딸려 옵니다.
실제로 확인된 동작입니다: 머지된 PR들의 브랜치가 전부 삭제됐는데도

```bash
git ls-remote origin 'refs/pull/*/head'
```

를 돌리면 삭제된 브랜치들이 전부 살아 있습니다. main 로그(`git log --oneline`)에서 커밋 메시지 끝에
`(#N)`으로 PR 번호를 확인한 다음, 이렇게 로컬로 가져오면 그 PR에서 쌓인 wip 커밋이
전부 다시 살아납니다.

```bash
git fetch origin pull/<N>/head:recover-<N>
```

이렇게 가져온 `recover-<N>` 브랜치 안에서 `git log`로 원하는 wip 커밋을 찾으시면 됩니다
(예: 어떤 PR은 wip 3개가 그대로 딸려 옵니다).

**되돌리는 방법 3가지, 언제 쓰는지:**

- **파일 하나만**: `git checkout <sha> -- <파일>` — 지금 브랜치는 그대로 두고, 특정
  파일만 그 시점 내용으로 가져오고 싶을 때.
- **새 브랜치로 살리기**: `git switch -c <새이름> <sha>` — 그 시점부터 다시 작업을 이어가고
  싶을 때. 지금 브랜치는 건드리지 않습니다.
- **통째로 되감기**: `git reset --hard <sha>` — 지금 브랜치를 그 시점으로 완전히 되돌리고
  싶을 때. **주의: 이미 push한 브랜치에서 쓰면 원격과 어긋나서 강제 push(force push) —
  원격 기록을 통째로 덮어써 그 이후 커밋들이 보이지 않게 만드는 명령 — 가 필요해지므로,
  아직 push하지 않은 로컬에서만 안전합니다.**

이 전체 과정(브랜치 생존 확인 → PR 번호 찾기 → 복구 → 되돌리기)을 자동으로 해 주는
`/rewind-task` 스킬이 있습니다. 되돌리기 자체가 목적이면 이 문서의 절차를 손으로 따라가는
대신 `/rewind-task`를 부르셔도 됩니다.

## 5. PR 단위로 되돌리기 (main)

main에 이미 뭉쳐서 합쳐진(squash merge된) PR 하나를 통째로 되돌리고 싶을 때는
**되돌리기(`git revert`)가 기본입니다** — 문제가 된 커밋의 변경을 거꾸로 적용하는 새
커밋을 만드는 방식입니다. `git reset --hard` + 강제 push는 쓰지 마세요 — main의 기록 자체를
지워 버려서, 그 사이에 다른 사람이나 다른 컴퓨터가 이미 그 커밋을 기준으로 작업하고
있었다면 그 작업이 통째로 어긋나거나 사라질 수 있습니다. `git revert`는 기록을 지우지
않고 "취소하는 커밋"을 새로 쌓는 방식이라 안전합니다.

- **파일 하나만 되돌리기**: `git checkout <되돌리려는 PR 이전 sha> -- <파일>` 로 그
  파일만 이전 상태로 가져온 다음 새 커밋으로 만들면 됩니다.
- **일부만 살리기(cherry-pick)**: PR 안의 변경 중 일부 커밋만 골라서 가져오고 싶을 때
  `git cherry-pick <sha>`. 문제 있는 부분은 빼고 괜찮은 부분만 살릴 때 유용합니다.
- **둘 다 합치기**: 되돌리기로 PR 전체를 취소한 다음, 그중 살리고 싶은 부분만
  일부만 살리기(cherry-pick)로 다시 가져오는 조합.

**원칙: 임시 브랜치에서 먼저 해 보고, 결과가 마음에 들 때 main에 반영하세요.** `git revert`나
`cherry-pick` 모두 `new-task`로 새 브랜치를 만들어서 먼저 시도해 보고, 원하는 상태가
맞는지 확인한 다음 PR로 올리는 것이 안전합니다 — main 위에서 바로 시도하다 꼬이면 되돌리기가
더 복잡해집니다.

## 6. 잃어버린 커밋 찾기

wip 커밋을 찾을 수 없게 됐을 때, 안전한 순서대로 확인해 보세요.

1. **`refs/pull` (PR을 거친 것 — 영구 보존)**: §4에서 본 것처럼 `done-task`로 PR까지
   갔던 작업은 `git fetch origin pull/<N>/head:recover-<N>`로 언제든 되살릴 수 있습니다.
   **가장 믿을 수 있는 방법입니다.**

2. **로컬 참조 기록(reflog)** — git이 로컬에서 브랜치·HEAD가 움직인 이력을 따로 저장해 두는
   내부 기록입니다. `git reflog`로 확인할 수 있습니다. 다만 보존 기간이 있습니다:
   - 지금 어딘가에서 도달 가능한(다른 브랜치·태그에서 이어지는) 커밋은 90일
     (`gc.reflogExpire`).
   - 어디서도 도달할 수 없는 커밋(예: 뭉쳐서 합치기 후 남은 원본 wip들)은 **30일**
     (`gc.reflogExpireUnreachable`). 따로 설정하지 않았다면 git 기본값이 그대로 적용됩니다
     (`git config --get gc.reflogExpireUnreachable`로 확인 가능 — 빈 값이면 기본값을 쓰는 중).
   - 단, 이 기간이 지나도 자동 정리(`git gc`)가 loose object(느슨하게 떠 있는, 아직
     정리 안 된 커밋 데이터) 개수가 일정 임계치를 넘어야 실제로 실행됩니다. 저장소 규모가
     작으면 그 임계치를 넘지 않아서 30일이 지나도 더 오래 남아 있는 경우가 있습니다.
     **하지만 이것은 보장된 안전망이 아니라 운에 가깝습니다** — "30일 지나도 혹시 있을 수도"
     정도로만 기대하시고, 확실한 복구 수단으로 믿지는 마세요.

3. **도달 불가능한 커밋 찾기(`git fsck --unreachable`)**: reflog에도 없는 커밋을 마지막으로
   뒤지는 명령입니다. 이것도 위 2번과 같은 이유로 **운에 가까운 수단**입니다 — git이 아직 그
   데이터를 지우지 않았으면 걸리고, 지웠으면 없습니다.

4. **태그로 미리 박아 두기**: 브랜치는 계속 앞으로 움직이는 표시라 지우면 그 브랜치가
   가리키던 위치 정보도 같이 사라집니다. 반면 **태그는 특정 커밋에 고정된 이름표**라 브랜치를
   지워도 남습니다. **PR을 거치지 않은 브랜치를 지울 때만** 이것이 필요합니다 — PR을 거친 것은 이미
   `refs/pull`이 영구 보존해 주므로 태그가 필요 없습니다. 하지만 로컬에서만 실험하다 지울
   브랜치라면, 지우기 전에 `git tag <이름> <sha>`로 찍어 두면 나중에도 찾을 수 있습니다.
   예를 들어 `backup/before-revert-YYYYMMDD` 같은 이름으로, 되돌리기 전 시점이나
   지우려는 브랜치의 wip 지점에 손으로 태그를 박아 두는 식으로 쓰면 됩니다.

**정리하면**: PR을 거친 작업은 `refs/pull`로 영구히 안전합니다. **PR을 거치지 않은 브랜치를
`git branch -D`로 지우는 것이 이 워크플로에서 wip을 영구히 잃을 수 있는 유일한 지점입니다**
— `git branch -D`는 그 브랜치의 reflog까지 같이 지워 버리기 때문입니다. 그런 브랜치를 지울 때는
미리 태그부터 찍으세요. (참고로 지금 올라타 있는 브랜치는 `git branch -D` 자체가 먹히지 않습니다 —
`error: Cannot delete branch 'X' checked out at ...`로 막히므로, 지우려면 다른 브랜치로
먼저 옮겨야 합니다.)

## 7. 코드 복구와 서비스 복구는 다르다

main이 잘못된 상태로 배포돼서 **서비스가 지금 당장 정상으로 돌아와야 하는 상황**이면,
순서가 중요합니다.

1. **먼저 Vercel 대시보드에서 즉시 되돌리기(Instant Rollback)** — 문제 생기기 전의
   배포를 그 자리에서 바로 지금 서비스로 승격시키는 기능입니다. 코드를 되돌리는 것보다 훨씬
   빠르게 서비스를 정상으로 되돌릴 수 있습니다.
2. **그다음에 코드 되돌리기** — §5의 되돌리기 절차로 main의 커밋 자체를 정리합니다. 이것은
   서비스가 이미 안정된 뒤에 여유를 갖고 처리해도 됩니다.

서비스가 급할 때는 "코드부터 고쳐야지"보다 "일단 이전 배포로 되돌려서 사용자 피해부터
막자"가 먼저입니다.

## 8. 팀으로 일할 때

여기까지는 혼자 작업하는 것을 전제로 썼습니다. 팀원이 들어오면 몇 가지가 달라지는데, 그
차이만 정리한 절입니다. §1의 `new-task → 작업 → done-task` 순환 자체는 그대로이고,
`done-task`가 하는 일과 판단 기준이 역할에 따라 갈릴 뿐입니다.

팀원은 자기 복제본(fork)이 아니라 **이 저장소에 직접** 브랜치를 올리는 협업자
(collaborator)입니다. 그리고 **저장소 오너 = 팀장**이라는 전제를 깔고 있습니다.

### 8.1 역할에 따라 무엇이 달라지나

`done-task`가 어디까지 하는지가 역할별로 갈립니다.

| | 팀장 (오너) | 팀원 (협업자) |
|---|---|---|
| push, PR 생성 | O | O |
| PR 머지 | O (직접 머지까지) | X — 머지는 팀장 몫 |
| `done-task`가 끝나는 지점 | main 머지 + 원격·로컬 브랜치 삭제까지 (로컬은 main으로 이동) | PR 생성까지 |

역할은 미리 어딘가에 설정해 두는 것이 아니라, 그때그때 GitHub 권한을 조회해서 자동으로
정해집니다.

```bash
gh api repos/{owner}/{repo} --jq '.permissions'
```

실제로 돌려 보면 오너는 이렇게 나옵니다.

```
{"admin":true,"maintain":true,"pull":true,"push":true,"triage":true}
```

쓰기 권한만 있는 팀원 계정으로 돌리면 `admin`과 `maintain`이 `false`이고 `push`만
`true`입니다. `done-task`는 이 값을 보고 실행하는 사람이 팀장인지 팀원인지 판단합니다.

### 8.2 강제가 아니라 관례입니다

§3에서 봤듯 저장소가 비공개 + 무료 플랜이면 브랜치 보호 규칙을 켤 수 없습니다. 그
말은 "팀원은 PR만 만들고 머지는 팀장이 한다"는 규칙도 **서버가 지켜 주는 것이 아니라는
뜻**입니다. 쓰기 권한이 있는 팀원이면 GitHub 웹 화면에서 Merge 버튼을 누르거나
`gh pr merge`를 직접 실행해서 그냥 머지해 버릴 수 있습니다 — `done-task` 스킬이 그
동작을 하지 않도록 짜여 있을 뿐, 저장소 자체가 막아 주는 것은 아닙니다.

진짜로 막고 싶다면 두 갈래입니다. 저장소를 공개로 바꾸면 브랜치 보호 규칙이 무료로
켜지고, 비공개를 유지하고 싶으면 GitHub Team 플랜으로 올려야 그 기능을 쓸 수 있습니다.
지금은 둘 다 하고 있지 않으니, "팀원은 머지하지 않는다"는 순전히 다 같이 지키기로 한
약속이라고 보시면 됩니다.

### 8.3 다른 사람 PR이 먼저 들어갔을 때 — 조건부 합치기(merge)

팀으로 작업하면 내가 브랜치를 올리는 사이 다른 사람 PR이 먼저 main에 들어가는 일이
흔해집니다. `done-task`는 이 상황을 감지해서 조건에 따라 다르게 움직입니다.

먼저 아래 명령으로 충돌 여부를 미리 확인합니다.

```bash
git merge-tree --write-tree origin/main HEAD
```

이 명령은 실제로 병합하지 않고, 병합했다면 어떻게 됐을지만 계산해 보는 모의 병합이라
지금 작업 트리를 건드리지 않습니다 (git 2.50.1에서 지원 확인함). 이 결과로 이렇게 판단합니다.

- **origin/main이 앞서 있지 않음** → 맞출 것이 없으니 그냥 진행합니다.
- **앞서 있고 + 충돌 없음** → `git merge origin/main`으로 합쳐서 맞춘 뒤 진행합니다.
  합치기는 두 갈래를 한 번에 붙여서 병합 커밋 하나로 마무리하는 방식입니다. **이미
  push한 브랜치여도 똑같이 합니다** — 아래에서 설명하듯 합치기는 강제 push가 필요 없기 때문입니다.
- **앞서 있고 + 충돌 있음** → 합치기를 시작하지 않고 멈춥니다. 사람이 직접 풀어야 하는
  상황이라, `done-task`가 무엇을 할지 물어보고 끝냅니다.

**왜 재배치(rebase)가 아니라 합치기일까요?** 재배치는 내 커밋들을 origin/main 최신
위로 하나씩 다시 쌓는 방식입니다. 예전에는 `done-task`가 충돌이 없으면 재배치를 했는데,
거기에는 눈에 잘 띄지 않는 결함이 있었습니다.

위의 예행 검사 `git merge-tree`가 계산하는 것은 **합쳤을 때의 최종 상태**입니다. 그런데
실제로 돌리던 것은 재배치라서, 커밋을 하나씩 다시 쌓는 동안 **최종 상태는 부딪히지 않는데
중간 커밋 하나가 부딪히는** 일이 생길 수 있습니다. 이 워크플로는 매 턴 wip 커밋이 쌓여서
브랜치 하나에 커밋이 십수 개인 것이 보통이라, 그런 일이 날 확률이 꽤 있었습니다. 그러면
예행 검사는 "충돌 없음"이라고 통과시켰는데 재배치가 도중에 멈춰서 저장소가 "재배치
진행 중"이라는 어중간한 상태로 남아 버립니다. `done-task`는 사용자에게 중간에 물어볼 수
없는 구조라, **검사가 막으려던 바로 그 사고가 검사를 통과하고도 나는 셈**이었습니다.
검사하는 것과 실제로 하는 것이 서로 다른 동작이었던 것이 원인입니다.

합치기로 바꾸면 **검사한 그대로를 실행하므로** 이 어긋남이 사라집니다. "충돌 없음"이
나왔으면 진짜로 충돌 없이 끝납니다.

거기에 두 가지 이점이 더 붙습니다.

**충돌을 한 번만 풀면 됩니다.** 재배치는 커밋을 하나씩 다시 쌓기 때문에, 충돌 난 파일을
건드린 커밋마다 멈춰서 **같은 충돌을 여러 번 풀어야 합니다.** 반면
`git merge origin/main`은 두 갈래를 한 번에 붙여서 **충돌을 딱 한 번만 풀면 됩니다.**

**강제 push가 필요 없습니다.** 재배치는 커밋을 전부 새로 써서 커밋 해시(sha)가 싹 다
바뀝니다. 이미 push한 브랜치에 이것을 하면 원격과 내용이 어긋나서 강제 push가
필요해지는데, 이 워크플로는 강제 push를 금지합니다(§3). 그래서 예전에는 "push 전이면
재배치, push 후면 생략" 하는 식으로 갈래를 나눠야 했습니다. 합치기는 기존 커밋을 그대로
두고 병합 커밋 하나만 얹으니 sha가 바뀌지 않고, **push 전이든 후든 똑같은 방법이
통합니다.** 판정이 그만큼 단순해진 것입니다.

**그럼 재배치의 장점이던 깔끔한 기록은 어떻게 되나요?** 이 워크플로에서는 애초에 의미가 없습니다.
어차피 마지막에 뭉쳐서 합치기(squash)로 전부 하나로 뭉치기 때문에, main에 남는
결과물은 재배치했을 때와 완전히 같습니다. 차이는 PR 페이지 커밋 목록에 병합 커밋이 한 줄
끼는 것뿐인데, 거기는 애초에 wip 기록을 보관하는 자리라 문제 될 것이 없습니다.

**충돌이 나서 멈췄을 때는 어떻게 풀까요?** 가장 권하는 방법은 로컬에서
`git merge origin/main`을 직접 돌려서 충돌을 풀고 커밋한 다음 `done-task`를 다시
부르는 것입니다. 한 번 합치고 나면 내 브랜치가 origin/main을 전부 품게 되므로, 다시
부를 때 "origin/main이 앞서 있나?" 검사가 0으로 나와서 이 단계는 자연히 건너뛰어집니다.

그냥 PR만 올려 두고 GitHub 웹 화면에서 충돌을 푸는 것도 괜찮습니다 — 머지 시점에 GitHub이
충돌을 알려 주기 때문입니다.

굳이 한 줄로 깔끔한 기록(선형 기록)을 원한다면 `git rebase origin/main`으로 직접
풀 수도 있는데, 이것은 최후 수단으로 생각하세요. 커밋이 많으면 같은 충돌을 여러 번 반복해서
풀어야 하고, 이미 push한 브랜치면 강제 push가 필요해져서 §3 규칙을 어기게 됩니다.
squash로 어차피 뭉쳐지니 선형 기록을 위해 이것을 감수할 이유는 거의 없습니다.

### 8.4 브랜치 이름이 겹칠 때

팀원 A가 `feature-x`라는 브랜치를 이미 원격에 올려 놓았는데, 팀원 B가 그 사실을 모른
채 `new-task`로 똑같이 `feature-x`를 만들면 어떻게 될까요. 로컬에는 그 이름이 없으니
브랜치 생성 자체는 성공해 버립니다. 문제는 `done-task`가 push하려는 순간 원격이 이미 그
이름을 쓰고 있어서 거부당하는 것입니다 — 작업을 다 끝낸 뒤에야 실패를 알게 되는 셈입니다.

그래서 `new-task`는 브랜치를 만들기 전에 로컬뿐 아니라 원격까지 확인합니다.

```bash
git ls-remote --heads origin <이름>
```

겹치는 것이 있으면 이름 뒤에 숫자를 붙여서 만듭니다. push 단계에서 뒤늦게 막히는 대신
시작할 때 바로 다른 이름으로 비켜가는 것입니다.

### 8.5 팀원 입장의 한 사이클

팀원이 겪는 흐름을 이어서 보면 이렇습니다.

```
new-task           → main 최신 반영, 브랜치 생성 (이름 겹치면 자동으로 비켜감)
작업                → wip 커밋 쌓임
done-task           → push + PR 생성까지 (머지는 안 함)
                      → 미머지 PR은 정상 상태, 리뷰 기다리는 동안 그냥 다음 작업으로
new-task (다음 작업)  → 또 최신 main 반영, 새 브랜치 생성
...
(팀장이 PR 머지)
new-task (그다음)    → 머지된 옛 브랜치를 로컬에서 정리
```

머지가 늦게 되면 그 브랜치는 `new-task`를 부른 시점에 아직 머지 전이라 지워지지 않고
로컬에 남아 있습니다. 그래도 문제는 없습니다 — 머지가 된 다음 `new-task`를 부를 때 알아서
정리됩니다. 지워지지 않은 브랜치가 하나 더 있을 뿐입니다.

팀장은 물어보고 승인하는 사람이라 지금처럼 매번 확인하지만, 팀원은 PR을 올려 두고
바로 다음 작업으로 넘어가는 것이 기본 흐름입니다. 그래서 `new-task`를 부를 때 "아직
머지 안 된 PR이 있다"는 팀원 입장에서는 매번 물어볼 이상 상황이 아니라 자연스러운
평소 상태로 취급합니다.
