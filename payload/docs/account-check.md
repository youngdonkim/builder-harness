# 계정 검문 — 절차와 서비스별 함정

**언제 읽나**: 첫 push(원격 저장소 생성)·첫 배포(호스팅 프로젝트 생성)·6-0(DB·인증·OAuth 앱) 직전. 메인이 읽고, 그 작업에 닿는 제약만 지시서에 몇 줄로 넘긴다 (`CLAUDE.md` 위임 원칙과 같은 방식 — 에이전트에게 이 문서를 통째로 읽히지 않는다). 계정 값의 정본은 프로젝트 `AGENTS.md` 「소유와 계정」 표다 — 이 문서는 절차와 함정만 담는다.

## 원칙 다섯

**① 검문은 외부 리소스가 처음 생기는 순간마다 한다** — 첫 push(원격 저장소)·첫 배포(호스팅 프로젝트)·6-0(DB·인증·OAuth 앱) 직전에 인증된 계정을 표와 대조하고, **다르면 만들지 않고 멈춰 보고한다.** 한 번 맞춘 계정을 여러 걸음 뒤에 믿지 않는다 — 계정에 묶이는 쓰기(리소스 생성·환경변수 설정·PR 생성·머지·브라우저 콘솔 작업) 직전에, 같은 걸음에서 다시 확인한다. 리소스가 엉뚱한 계정에 이미 생겼으면 다시 만들지 말고 「이전(Transfer)」부터 찾는다 — 주소·키가 그대로면 코드·배포를 안 건드린다. 끝나면 옛 계정 토큰이 있던 자리를 전부 교체한다.

**② CLI 인증은 두 종류다 — 로그인 세션과 발급 토큰.** 로그인 세션은 `login` 류 명령이 만드는 것으로 컴퓨터당 하나만 남고 영구가 아니다(기간 만료·장기 미사용 회수). 발급 토큰은 계정 화면에서 손으로 만드는 접근 토큰으로 여러 개가 공존한다 — 무기한이어도 장기간 안 쓰면 회수하는 서비스가 있으니, 안 되면 재발급이 정답이다. 발급 토큰의 "무기한"은 서비스마다 다르다 — 만료가 있으면 계정 표에 재발급 기한과 토큰이 들어간 자리(CLI 파일·CI 시크릿)를 같이 적는다. **소유가 다른 프로젝트가 한 컴퓨터에 있으면 로그인으로 갈아타지 않는다** — 계정마다 발급 토큰을 만들어 프로젝트에 두고 CLI가 그걸 읽게 한다. 로그인 전환은 전역이라 다른 프로젝트를 조용히 망가뜨린다. **발급 토큰은 소유 계정당 하나가 기본이고, 그 소유의 프로젝트들이 사본을 나눠 갖는다** — 프로젝트 폴더에는 그 프로젝트 소유 계정의 토큰만 두고, 더 좁혀야 하면 서비스가 지원하는 프로젝트 스코프 토큰을 따로 만든다. **손으로 넣은 로컬 값은 도구가 덮어쓰거나 앱이 읽는 파일에 두지 않는다** — 배포 CLI의 환경변수 내려받기는 기본 대상 파일을 통째로 다시 쓴다(실측). CLI 토큰은 프레임워크가 실행 시 읽지 않고 내려받기가 건드리지 않는 깃 미추적 **CLI 전용 파일**(예: `.env.cli`)에 두어 명령을 부를 때만 읽어 넘기고, 그 밖에 손으로 넣은 값(DB 비밀번호 등)도 내려받기 전에 따로 보관돼 있는지 확인한다. 예외는 여러 계정을 등록해 두고 전환하는 CLI(Git 호스팅 CLI 등) — 프로젝트에 들어갈 때 활성 계정을 표와 맞춘 뒤 진행한다(로컬 전환이라 되돌리기 쉽다). 인공지능 제공사 키는 로그인이 아니라 API 키라 여기 해당 없다.

**③ 배포 플랫폼은 커밋 작성자의 Git 계정 연결로 사람을 판정한다** — 커밋 작성자의 Git 계정이 소유자의 배포 플랫폼 계정에 연결돼 있어야 배포가 된다. 연결이 없으면 유료 팀은 승인 대기, 그 외는 배포 실패다(프리뷰·실서비스 모두). Git 계정 하나는 배포 플랫폼 계정 하나에만 붙고, 판정은 커밋 이메일이 아니라 Git 계정 자체라 커밋 작성자 설정을 바꿔도 소용없다 — 한쪽에서 끊었으면 소유자 계정에 다시 붙인다.

**④ 브라우저 작업(브라우저 에이전트 포함)은 프로필이 아니라 표의 계정을 지정한다** — 여러 계정을 지원하는 서비스(구글·GitHub)는 계정을 지정해 열고, 한 번에 하나만 되는 서비스(Vercel·Supabase 등)는 로그인된 계정을 표와 대조해 다르면 전환한 뒤 진행한다. 전환할 때는 로그아웃이 실제로 됐는지(로그인 폼이 뜨는지) 확인한 뒤 로그인한다 — 세션이 살아 있으면 로그인이 "현재 계정에 연결"로 처리돼 계정이 섞인다. **서비스 간 연결(연동 로그인·앱 설치·저장소 연결)은 양쪽을 대조한다** — 연결에 붙는 건 상대 서비스(로그인·권한을 빌려주는 쪽)의 지금 세션이라, 내가 서 있는 서비스만 보면 상대 쪽의 다른 계정이 조용히 붙는다. 시작 전에 상대 서비스의 로그인 계정도 표와 대조해 다르면 거기서 먼저 전환하고(계정 선택창이 뜨면 표의 계정을 고른다), 끝나면 화면에 표시된 연결 계정을 표와 다시 대조한다. **브라우저 세션은 영구가 아니고, 2FA(2단계 인증)가 켜진 계정은 에이전트가 혼자 전환하지 못한다** — 로그인 화면에서 멈춰 사람에게 코드·패스키를 부탁한다. 복구 코드는 쓸 때마다 사라지는 소모품이라 상시 수단이 아니다. 프로필을 소유별로 나눠도 오래 안 쓴 프로필은 재로그인이 필요할 수 있다 — 프로필 분리는 재로그인 확률을 낮추는 수단이지 보장이 아니다. 손 갈 일을 줄이는 순서: CLI는 발급 토큰으로 로그인 자체를 없애고, 남는 브라우저 작업은 에이전트가 쓰는 컴퓨터에 패스키를 등록해 한 번의 승인으로 줄인다.

**⑤ 한 번만 보여주는 값은 보이는 그 순간 확보하고, 못 했으면 그 자리에서 폐기한다** — 에이전트가 토큰·키를 만들 땐 값을 그 자리에서 확보하고, 값 모르는 살아 있는 토큰을 남기지 않는다. 다단계 선택(스코프 → 프로젝트 등)은 마지막 단계 값이 화면에 표시된 것을 확인한 뒤에 만든다. 사용자가 넣은 값과 브라우저 에이전트의 "했다"는 쓰기 전에 실제 호출로 확인한다 — 값이 맞는지는 그 자격 증명으로 제공사 API를 한 번 호출하면 즉석에서 확인된다.

## 서비스별 확인·전환·함정

- **gh** — 전환형이다. 계정을 여러 개 등록해 두고 전환한다(방법은 CLI 도움말). 프로젝트를 옮겨 다닐 때마다 활성 계정을 표와 맞춘다 — 전환은 전역이라 다른 소유의 프로젝트를 오간 뒤 특히.
- **GitHub SSH 키** — 키 하나는 한 계정에만 등록된다. 소유가 다른 저장소가 한 컴퓨터에 있으면 계정별 키를 따로 두고, ssh 설정의 호스트 별칭으로 저장소 원격 주소에 어느 키를 쓸지 박아 둔다 — 별칭 규약: `github.com-<소유자 태그>`. 설정 방법은 그때 공식 문서로. (실사고: 개인 키로 회사 저장소 push 거부 — 키를 옮기면 반대쪽이 막힌다.)
- **Vercel** — CLI 인증은 발급 토큰으로 한다(로그인 갈아타기 금지 — 원칙 ②). 토큰은 CLI 전용 파일에 둔다. 프로젝트 폴더의 `.vercel/project.json`이 어느 팀(orgId)에 묶였는지가 정본이다. 대시보드에서 계정을 바꿀 땐: **다른 계정 세션이 살아 있는 채로 GitHub/Google 로그인을 누르면 "로그인"이 아니라 "현재 계정에 그 로그인 수단 연결"이 된다** — 로그아웃이 실제로 됐는지(로그인 폼이 뜨는지) 확인한 뒤 로그인한다. (실사고: 회사 Vercel 계정에 개인 GitHub이 연결돼 끊어야 했다.) 대시보드 실측 함정 다섯(쓴 시점 기준):
  - 계정 설정은 대시보드 **왼쪽 아래 사용자 메뉴**(이름·이메일 옆 톱니)에 있다. 공식 문서의 "오른쪽 위 프로필 사진"은 낡았다. 바로 가려면 `vercel.com/account/authentication`.
  - GitHub 신분 연결은 계정 설정 → Authentication → **Sign-in Methods**의 GitHub 줄이다. 팀 설정 → Git(「Origin」 연결)이 아니다. 저장소 가져오기용 깃헙 앱 설치는 프로젝트 만들 때 따로 나온다.
  - gmail 주소로 로그인돼 있어도 구글 로그인이 아닐 수 있다 — Sign-in Methods에서 Email·Google·GitHub 중 뭐가 연결됐는지 본다. (실측: 이메일 로그인 + 패스키였고 Google은 미연결.)
  - **패스키는 브라우저별이다.** 다른 브라우저에서 만든 패스키는 에이전트 브라우저에서 못 쓴다. 에이전트가 쓰는 프로필에서 Passkeys → Add로 하나 더 만든다. 기존 패스키는 지우지 않는다(지워도 얻는 게 없다).
  - 이 계정 2FA가 켜져 있으면 이메일·구글로 들어가도 두 번째 확인을 요구한다. 두 번째 수단이 다른 브라우저의 패스키뿐이면 에이전트 브라우저에서 로그인이 막히니, 에이전트 프로필에도 패스키를 두거나 인증 앱을 등록한다.
- **Supabase** — CLI 인증은 발급 토큰으로 한다. 지금 어느 계정인지는 CLI 자체의 계정·조직 조회 명령으로 확인한다. 프로젝트 `supabase/.temp/project-ref`가 어느 조직 것인지가 정본.
- **맥 키체인** — 키체인에서 CLI 토큰을 꺼내는 조회 명령은 허용 창이 떠서 무한 대기한다(실측 여러 번). 계정 확인은 그 CLI 자체의 계정·조직 조회 명령으로 하고, 무한 대기 가능성이 있는 명령은 시간 상한을 걸어 부른다.
- **브라우저 콘솔(Google·카카오·Supabase 대시보드)** — 아이디가 아니라 **오른쪽 위 프로필의 이메일**로 판단한다. 여러 계정이 동시에 로그인돼 있으면 마지막에 쓴 계정이 기본으로 열린다 — 콘솔 주소의 `authuser=` 값이나 프로필 전환으로 바꾼다.
- **Aside(브라우저 에이전트)** — 프로필을 소유자별로 가를 수도 있고, 한 프로필에 여러 소유자 계정을 같이 둘 수도 있다. 어느 쪽이든 브라우저 작업은 프로필이 아니라 **표의 계정을 지정·대조한다**(원칙 ④). 비밀번호는 Aside의 암호화 금고가 저장·자동 채움하니 표에는 계정 ID·이메일만 둔다. 실측한 함정:
  - `aside account list`의 프로필(u0·u1…)은 **Aside에 로그인한 구글 계정 단위**다. 서비스(Vercel 등) 로그인은 프로필과 별개라, 프로필이 개인 구글이어도 그 안의 Vercel은 회사 계정일 수 있다 — 판정은 늘 서비스 화면의 계정 표시로 한다.
  - u번호(u0·u1)와 UI 프로필 이름의 대응은 CLI로 안 나온다 — 프로젝트 표에 "u1 「이름」"처럼 둘 다 적는다. u0에 로그인된 구글 계정이 그 프로필의 소유를 뜻하지 않는다(실측: 직장 프로필 u0에 개인 gmail이 로그인돼 있었다).
  - **비밀번호 금고는 프로필이 아니라 Aside 계정(구글 로그인) 단위다.** 프로필마다 Aside 로그인을 따로 할 수 있고, 저장한 사이트 비번은 그 프로필에 로그인된 Aside 계정의 클라우드 금고로 올라간다.
  - Aside에 로그인하지 않은 프로필("Local Account, signed out")의 금고는 이 기기에만 남는다. 사이트 로그인·비번 저장은 그래도 정상 동작한다 — 브라우저 자체 로그인과 사이트 로그인은 별개다.
  - **이미 비번이 든 프로필의 Aside 계정을 바꾸지 않는다** — "This device holds another account's vault … items saved only on this device will be permanently deleted" 경고가 뜨면 중단한다. 기기 전용 항목이 삭제된다.
  - `aside repl`에는 파일 쓰기(`fs`)와 `getByPlaceholder` 같은 이름 로케이터가 없다 — CSS 로케이터(`page.locator('input[placeholder="…"]')`)와 `console.log` 출력만 쓴다. `openTab`으로 연 탭은 호출이 끝나면 닫혀서 다음 호출에서 다시 못 읽는다.
  - 한 번만 보여주는 값(발급 토큰 등)은 접근성 트리 스냅샷에 안 잡힌다 — 생성 직후 `page.evaluate(() => document.body.innerText)`에서 정규식으로 읽어 같은 호출 안에서 출력한다. 스코프처럼 다단계로 고르는 선택 UI는 마지막 단계까지 고른 값이 입력칸에 표시된 것을 스냅샷으로 확인한 뒤 만든다.
  - 로그아웃 확인은 로그인 폼이 스냅샷에 보이는 것으로 한다. 구글 로그인을 누르면 프로필에 든 구글 계정 전부가 선택 화면에 나오므로 이메일로 고른다.
  - 2FA 화면이 뜨면 거기서 멈춘다. 패스키 버튼은 사람이 컴퓨터 앞에 없거나 이 브라우저에 패스키가 없으면 아무 반응이 없다. 로그인 폼에 뜨는 Aside의 「Save credential」 창은 금고 저장 제안이라 무시해도 된다.
  - Aside는 사용자가 실제로 쓰는 브라우저다. 열려 있는 다른 탭을 닫거나 건드리지 않는다.
