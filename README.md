# builder-harness

혼자 AI로 며칠~몇 주 만에 작동하는 서비스를 만들어 시장 반응으로 검증하는 사람(이 문서에서는 **AI 빌더**라고 부른다)을 위한 **Claude Code 하네스**다. 아이디어를 떠올린 순간부터 MVP(Minimum Viable Product — 가설을 검증할 수 있는 최소한의 작동하는 제품)를 실제 사용자에게 내놓기까지를 **7단계 한 흐름**으로 안내한다.

용어가 낯설면 먼저 [§3 이게 무엇인가](#3-이게-무엇인가)를 읽으면 된다.

**설계 원칙**: 빌드는 AI가 거의 공짜로 해주니 — 팀·투자자에게 보여주기 위한 무거운 문서는 버리고, 빌더 자신이 뭘 만들고 뭘 안 만들지 정하는 최소 전략 + AI가 정확히 빌드하게 만드는 구체 명세만 남긴다.

## 1. 두 가지 사용 환경

Claude Code는 두 가지 방식으로 쓴다 — **데스크톱 앱**(대화 화면이 있는 프로그램)과 **인터랙티브 터미널**(터미널에서 `claude`를 실행해 대화하는 방식). 이 문서의 안내는 양쪽 모두에 해당하고, 하네스도 양쪽에서 똑같이 작동한다. 갈리는 건 **대화를 여는 방법**과 **터미널 명령을 실행하는 방법** 둘뿐이다.

| | 데스크톱 앱 | 인터랙티브 터미널 |
|---|---|---|
| 대화 한 판을 부르는 말 | 대화 | 세션 |
| 새로 열기 | 앱에서 새 대화를 만들고 작업할 프로젝트 폴더를 고른다 | 터미널에서 프로젝트 폴더로 옮겨 간 뒤 `claude` 실행 |
| 대화 비우기 | `/clear`, 또는 새 대화 열기 | `/clear`, 또는 `claude` 다시 실행 |
| 터미널 명령(git 등) | 직접 칠 일이 거의 없다 — 채팅창에 "~해줘"라고 시키면 Claude가 대신 실행한다 | 직접 쳐도 되고, 채팅창에 시켜도 된다 |

`/idea-to-mvp` 같은 **스킬 호출과 `/clear` 같은 명령은 두 환경에서 똑같이 동작한다.** 채팅 입력창에 `/`를 치면 뜨는 자동완성 목록에서 고르면 된다.

이 문서는 둘을 아울러 **세션**이라고 쓰고, 실제 행동이 갈리는 곳에서만 "터미널이면 A / 데스크톱 앱이면 B"로 나눠 적는다.

## 2. 빠른 시작 — 이 3개만 순서대로

아래 3단계는 **하네스를 프로젝트에 적용하는 사람**이 하는 일이다. 하네스가 이미 들어 있는 프로젝트를 받아서 쓰기만 하는 팀원은 아무것도 안 해도 된다 — 이 저장소에 접근할 필요조차 없다([§5.4](#54-팀원은-무엇을-하나)).

**1. 하네스 저장소 내려받기** — 컴퓨터에 **딱 한 번만**

```
git clone git@github.com:youngdonkim/builder-harness.git ~/dev/builder-harness
```

터미널이면 이 명령을 직접 치고, 데스크톱 앱이면 채팅창에 "이 주소를 `~/dev/builder-harness`에 clone해줘"라고 시키면 된다.

이 저장소는 비공개(private)다 — 소유자이거나 초대(콜라보레이터로 등록)받은 사람만 내려받아진다.

→ 자세히: [§5.1](#51-하네스-저장소-내려받기)

**2. 프로젝트에서 세션 열기** — 하네스를 쓰려는 프로젝트 폴더에서

- **터미널이면** 그 폴더로 옮겨 가 `claude`를 실행한다.

  ```
  cd <프로젝트 경로>
  claude
  ```

- **데스크톱 앱이면** 새 대화를 열고 그 프로젝트 폴더를 고른다.

**3. 하네스 적용** — 방금 열린 Claude Code 채팅창에서, 말로

```
하네스 적용해줘
```

→ 자세히: [§5.2](#52-프로젝트에-적용하기). 이 말이 안 먹으면 [§5.5](#55-자주-막히는-두-가지)에 해결법이 있다.

적용이 끝나면 채팅창에서 이 명령들을 쓴다 — 역할은 [§4 들어 있는 것](#4-들어-있는-것) 표에.

| 언제 | 명령 |
|---|---|
| 아이디어를 MVP까지 끌고 갈 때 | `/idea-to-mvp` |
| 새 작업을 시작할 때 | `/new-task` |
| 작업을 끝내고 반영할 때 | `/done-task` |
| 잘못된 작업을 되돌릴 때 | `/rewind-task` |
| 화면·색·간격 같은 디자인을 다룰 때 | `/design-system` |

## 3. 이게 무엇인가

### 3.1 하네스란

**Claude Code**는 대화하며 코딩을 맡기는 도구다. 데스크톱 앱으로도 쓰고, 터미널(컴퓨터에 명령어를 직접 쳐 넣는 검은 창)에서 `claude`를 실행해서도 쓴다([두 가지 사용 환경](#1-두-가지-사용-환경)).

**하네스(harness)**는 원래 말이나 사람에게 씌우는 마구·안전벨트를 뜻한다. 여기서는 **AI가 정해진 절차와 안전 규칙 안에서 일하도록 잡아주는 틀**이라는 의미로 쓴다. AI에게 매번 "이렇게 해줘"라고 설명하는 대신, 그 절차를 미리 문서와 규칙으로 만들어 두고 AI가 항상 그대로 따르게 하는 것이다.

이 하네스가 잡아주는 것은 두 가지다.

- **진행 절차** — 아이디어 검증부터 MVP 런치까지 7단계를 순서대로, 각 단계의 통과 기준과 함께 진행한다.
- **안전 규칙** — 코드를 잘못 날리거나 검토 없이 반영하는 일이 생기지 않게 git 작업을 막고 자동 저장한다.

### 3.2 스킬·서브에이전트·훅

이 하네스가 담고 있는 세 종류의 부품이다.

- **스킬(skill)** — Claude가 특정 작업을 할 때 읽는 **작업 설명서**다. 채팅창에서 `/이름` 형태로 직접 불러 쓴다. 예: `/idea-to-mvp`.
- **서브에이전트(subagent)** — 특정 일만 전담하는 **보조 AI**다. 본 대화와 따로 떨어져 일하기 때문에, 긴 작업을 맡겨도 본 대화가 지저분해지지 않는다. 대개 스킬이 알아서 호출하므로 사용자가 직접 부를 일은 적다.
- **훅(hook)** — 정해진 순간마다 **자동으로 실행되는 규칙**이다. 사용자가 부르지 않아도 걸린다. 예: main 브랜치에 코드를 바로 올리려 하면 막고, 답변이 끝날 때마다 작업 내용을 자동 저장한다.

이 세 부품 말고 **규칙·설정 파일**도 하네스에 들어 있다 — Claude가 항상 지킬 규칙(`CLAUDE.md`·`AGENTS.md`), 특정 파일을 다룰 때만 적용되는 세부 규칙(`.claude/rules/`), 훅을 작동시키는 등록 설정(`.claude/settings.json`에 합쳐진다) 같은 것들이다. 전체 목록은 [§5.3](#53-프로젝트에-무엇이-생기나)에 있다.

### 3.3 어떻게 전해지나 — 파일 복사

이 저장소가 하네스의 **원본(SoT, Source of Truth — 정답이 되는 하나뿐인 출처)**이다. 하네스 본체는 전부 이 저장소의 `payload/` 아래에 있고, 그 안의 구조가 곧 **프로젝트 루트에 그대로 복사될 모양**이다 — 이런 걸 미러(mirror, 거울처럼 같은 모양)라고 한다.

적용은 복사다. `/project-init` 스킬이 `payload/`를 프로젝트 루트에 같은 경로로 복사하고, 훅 등록 설정을 프로젝트 설정 파일에 합쳐 넣는다. 그래서 하네스가 한 번 적용된 프로젝트는 **그 저장소 안에 하네스를 통째로 갖고 있다.**

이 방식의 좋은 점은 세 가지다.

- 프로젝트를 열면 `.claude/` 안의 파일이 세션 시작 때 그대로 읽힌다 — 따로 켜고 끄는 설정이 없다.
- 하네스 파일도 프로젝트 저장소에 커밋되니, 팀원은 프로젝트만 내려받으면 하네스까지 같이 받는다([§5.4](#54-팀원은-무엇을-하나)).
- 어느 버전이 적용됐는지가 파일로 남아, 다음에 동기화할 때 무엇이 바뀌었는지 정확히 가려낸다([§6.4](#64-적용한-버전이-파일로-남는다)).

## 4. 들어 있는 것

부품의 종류는 [§3.2](#32-스킬서브에이전트훅)에서 설명한 스킬·서브에이전트·훅 세 가지인데, 스킬은 쓰이는 시점에 따라 다시 둘로 나뉜다.

- **단계 스킬** — 아이디어에서 MVP까지 가는 **7단계 본줄기를 진행하는 스킬**이다. 프로젝트를 앞으로 밀고 나가는 역할이라 지금은 `idea-to-mvp` 하나뿐이고, 이 하나를 여러 번 불러 단계를 하나씩 밟아간다.
- **횡단 스킬** — 몇 단계에 있든 **필요할 때마다 꺼내 쓰는 스킬**이다. 7단계 전체를 가로질러(횡단) 쓰이기 때문에 이렇게 부른다. 작업을 시작하고 마무리하고 되돌리는 일, 디자인을 다루는 일처럼 단계와 상관없이 계속 반복되는 작업들이다.

| 종류 | 이름 | 역할 |
|---|---|---|
| 단계 스킬 | `idea-to-mvp` | 7단계: UserStory · InformationArchitecture · Prototype · DemoValidation · MarketResearch · MvpBuild · MvpLaunch (통과 기준 2개) |
| 횡단 스킬 | `project-init` | 프로젝트에 하네스 적용 — `payload/`를 프로젝트 루트에 복사 + 훅 등록 설정 병합 + CLAUDE.md 뼈대 생성. 이미 적용된 프로젝트에서 재실행하면 최신 원본과 비교해 동기화 |
| 횡단 스킬 | `new-task` | main 최신화 + 머지가 끝난 옛 작업 브랜치 정리 + 새 작업 브랜치 생성 |
| 횡단 스킬 | `done-task` | 자동 저장 커밋 → 원격 올리기(push) → PR 생성 → (오너면) CI 통과 대기 → 합치기(merge) → 원격·로컬 브랜치 정리(로컬은 main으로 이동) 한 흐름. 팀원은 PR까지, 오너는 로컬 정리까지 |
| 횡단 스킬 | `rewind-task` | 자동 저장 시점으로 되돌리기 — 후보 표를 보여준 뒤 파일·브랜치·되감기 중 선택 |
| 횡단 스킬 | `design-system` | 3단 토큰 계층(foundation→semantic→component) + 조립 계층(frame·pattern) 디자인 시스템 방법론 — 화면·컴포넌트·토큰을 만들거나 수정할 때 참조 |
| 횡단 스킬 | `grok-delegation` | 그록(Grok) CLI에 작업을 위임하는 방법 — 부르는 법·읽기/쓰기 모드 고르기·결과 검증 |
| 횡단 스킬 | `harness-diet` | 지시 문서(CLAUDE.md·AGENTS.md·스킬·에이전트·rules)의 군살·중복·모순 검토 → 보고서 + 사람 결정 목록 (수정은 결정 후 별도) |
| 서브에이전트 | `git-flow` | `new-task`·`done-task`·`rewind-task`의 실제 실행자 |
| 서브에이전트 | `harness-auditor` | `harness-diet`의 회차별 감사관 — 지시 문서를 읽기 전용으로 정독해 판정만 반환 |
| 서브에이전트 | `user-scenario-writer` | 영화 시나리오형 유저 스토리 작성 |
| 서브에이전트 | `ux-writing-reviewer` | UI 문구를 UX writing 원칙과 대조해 직접 교정 |
| 서브에이전트 | `delegation-integrator` | 타 코딩 에이전트 연동 조사·설치·테스트·위임 스킬 생성/갱신 |
| 훅 | `no-main-push` | main 브랜치에 바로 올리는 것을 차단 (PR 검토 흐름 강제) |
| 훅 | `auto-wip-commit` | 응답이 끝날 때마다 작업 브랜치에 진행 중 커밋(wip)을 자동 생성 |

위 표는 부품(스킬·서브에이전트·훅)만 담았고, 함께 복사되는 규칙·설정 파일은 [§5.3](#53-프로젝트에-무엇이-생기나)에 정리돼 있다.

용어 참고 — **PR(Pull Request)**은 "내가 고친 걸 본체에 반영해 달라"고 올리는 제안이다. **CI(Continuous Integration)**는 그 제안이 반영되기 전에 코드가 깨지지 않았는지 자동으로 검사하는 절차다. **wip(work in progress)**는 아직 끝나지 않은 진행 중 상태를 뜻한다.

## 5. 적용 자세히

빠른 시작에 나온 3단계를 하나씩 풀어 설명한다.

### 5.1 하네스 저장소 내려받기

원본을 자기 컴퓨터에 통째로 내려받는다(clone — 저장소를 그대로 복제해 오는 git 명령). 컴퓨터에 **한 번만** 하면 된다.

```
git clone git@github.com:youngdonkim/builder-harness.git ~/dev/builder-harness
```

터미널이면 이 명령을 직접 치면 된다. 데스크톱 앱이면 아무 대화나 열어 "이 주소를 `~/dev/builder-harness`에 clone해줘"라고 시키면 Claude가 대신 실행한다.

`~/dev/builder-harness`가 기본 위치다. 다른 곳에 두고 싶으면 경로만 바꾸면 되는데, 그러면 [§5.5](#55-자주-막히는-두-가지)에서 경로를 알려줄 때 그 경로를 쓴다.

**이 저장소는 비공개(private)다.** 주소를 안다고 받아지지 않고, 소유자이거나 저장소에 초대(콜라보레이터로 등록)받은 사람만 내려받을 수 있다. 위 주소는 SSH 방식이라 GitHub 계정에 SSH 키가 등록돼 있어야 한다.

**내려받아야 하는 사람은 하나뿐이다** — 하네스 자체를 프로젝트에 적용·동기화하거나 하네스를 고치는 사람. 이 사람만 초대가 필요하다. 하네스가 이미 적용된 프로젝트를 받아서 쓰기만 하는 팀원은 이 저장소가 아예 필요 없다([§5.4](#54-팀원은-무엇을-하나)).

### 5.2 프로젝트에 적용하기

하네스를 쓰려는 프로젝트 폴더에서 세션을 연다([§1](#1-두-가지-사용-환경)). 그리고 채팅창에 말로 시킨다.

```
하네스 적용해줘
```

그러면 `/project-init` 스킬이 돌면서 [§5.3](#53-프로젝트에-무엇이-생기나)의 파일들을 만든다. 도중에 서비스 이름·한 줄 정의·타겟 같은 것을 몇 가지 물어보는데, 답한 내용이 그 프로젝트의 `CLAUDE.md`에 들어간다.

**첫 적용 때는 이 말이 안 먹을 수 있다.** 아직 그 프로젝트에 스킬 파일이 없어서 Claude가 무슨 말인지 모르기 때문이다. 그럴 땐 원본 경로를 직접 알려주면 된다.

```
~/dev/builder-harness의 payload/.claude/skills/project-init/SKILL.md를 읽고 그대로 실행해줘
```

한 번 적용되고 나면 그다음부터는 "하네스 동기화해줘" 같은 말만으로 스킬이 잡힌다.

**이 첫 적용만은 main에서 바로 한다.** 아직 그 프로젝트에 `/new-task` 스킬 자체가 없어서 작업 브랜치를 미리 만들 방법이 없기 때문이다. 적용이 끝난 뒤에 작업 브랜치를 만들어 커밋하면 된다. 두 번째 동기화부터는 [§6.2](#62-프로젝트에-동기화하기)처럼 작업 브랜치부터 만들고 시작한다.

### 5.3 프로젝트에 무엇이 생기나

`/project-init`이 프로젝트에 만드는 것들이다. 앞의 다섯은 원본 `payload/`에서 같은 경로로 복사돼 오는 것이고, 뒤의 다섯은 스킬이 따로 만든다.

- **`.claude/skills/`·`.claude/agents/`·`.claude/hooks/`** — 세션을 열 때 읽혀서 스킬·서브에이전트·훅이 작동한다.
- **`.claude/rules/`** — 특정 종류의 파일을 다룰 때만 적용되는 세부 규칙 모음.
- **`.claude/templates/`** — `delegation-integrator` 에이전트가 다른 AI 도구 연동을 세팅할 때 쓰는 문서 틀(sources·status).
- **`docs/git-workflow.md`** — 훅과 작업 스킬들이 따르는 git 작업 흐름을 사람이 읽으라고 정리해둔 문서.
- **`.github/workflows/ci.yml`** — `done-task`가 머지 전에 통과를 기다리는 lint + build 검사.
- **`CLAUDE.md`** — 그 프로젝트에서 Claude가 항상 지켜야 할 규칙을 적어두는 파일. 세션을 열 때마다 자동으로 읽힌다. 이것만은 그대로 복사되지 않고, 원본의 `CLAUDE.md.template`에 인터뷰 답을 채워 만든다.
- **`AGENTS.md`** — Claude뿐 아니라 Grok·Codex 같은 다른 AI 도구도 읽는 규칙 파일. 이것도 그대로 복사되지 않고, 원본의 `AGENTS.md.template`에 인터뷰 답을 채워 만든다. 내용은 `<!-- BEGIN:project-rules -->` 마커 구역 안에 들어가고, 빈 자리는 프로젝트가 채워 나간다. 이미 있으면 덮어쓰지 않고 우리 구역만 덧붙인다.
- **`.claude/settings.json`** — 원본의 `settings-hooks.json`에 적힌 훅 등록 내용이 이 파일에 합쳐진다. 이미 있던 다른 설정은 그대로 둔다.
- **`.claude/harness-version`** — 지금 적용한 하네스가 어느 버전인지 적어두는 표시 파일이다([§6.4](#64-적용한-버전이-파일로-남는다)).
- **`mvp/`·`docs/` 폴더** — 단계 산출물과 사람이 읽는 문서가 쌓이는 자리.

이 파일들은 전부 그 프로젝트 저장소의 일부다. 프로젝트의 git 흐름(작업 브랜치 → PR)으로 커밋하면 된다.

### 5.4 팀원은 무엇을 하나

**아무것도 안 해도 된다.** 하네스 저장소는 내려받을 필요도, 접근 권한을 받을 필요도 없다 — 비공개 저장소에 초대받지 않은 상태 그대로 하네스를 다 쓴다.

프로젝트 저장소를 내려받거나(clone) 당겨오면(pull) `.claude/` 안에 스킬·서브에이전트·훅·설정이 이미 커밋돼 있어서, 세션을 여는 순간 그대로 작동한다. 하네스가 개선돼서 프로젝트에 반영되는 일은 [§6](#6-업데이트--새-버전-받기)대로 한 사람이 해두면 되고, 나머지 팀원은 프로젝트를 당겨오기만 하면 된다.

### 5.5 자주 막히는 두 가지

- **첫 적용 때 "하네스 적용해줘"가 안 먹는다.** 아직 그 프로젝트에 스킬 파일이 없어서다. [§5.2](#52-프로젝트에-적용하기)처럼 원본의 `SKILL.md` 경로를 알려주면 된다.
- **스킬 이름은 짧은 형태로 친다.** 입력창 자동완성에 뜨는 이름 그대로 — `/project-init`·`/idea-to-mvp`처럼 쓴다. 데스크톱 앱이든 터미널이든 같다.

## 6. 업데이트 — 새 버전 받기

하네스가 개선됐을 때 그걸 프로젝트에 반영하는 방법이다. 길은 이 하나뿐이고, 세 걸음이다.

1. 하네스를 맡은 사람이 자기 컴퓨터의 원본이 깨끗한 main 상태인지 확인해 둔다([§6.1](#61-원본-저장소가-깨끗한-main인지-확인하기)).
2. 프로젝트마다 작업 브랜치부터 만들고 "하네스 동기화해줘"로 옮긴 뒤, `/done-task`로 그 프로젝트의 PR을 만들어 main에 합친다([§6.2](#62-프로젝트에-동기화하기)).
3. 나머지 팀원은 프로젝트를 당겨오기만(git pull) 하면 끝이다.

### 6.1 원본 저장소가 깨끗한 main인지 확인하기

내려받아 둔 하네스 저장소 폴더를 미리 최신으로 당겨올 필요는 없어졌다. `/project-init`이 동기화를 시작할 때 원본을 스스로 최신으로 당겨오기 때문이다. (미리 `git pull`을 쳐둬도 상관은 없다 — 그냥 안 해도 된다는 뜻이다.)

대신 새로 생긴 조건이 있다. 다음 셋 중 하나라도 안 맞으면 `/project-init`이 **동기화를 시작하지 않고 그 자리에서 멈춘다**.

- 원본 저장소가 **`main` 브랜치**에 있어야 한다.
- **커밋 안 된 변경이 없어야** 한다.
- 원본을 최신으로 당겨오는(pull) 데 **성공해야** 한다.

멈추는 이유는 **잘못된 원본이 프로젝트로 새어 나가는 걸 막기 위해서**다. 원본이 작업 중인 브랜치에 있으면 아직 확정되지 않은 내용이 프로젝트에 그대로 복사될 수 있다. 게다가 그 상태로 복사하면 프로젝트에 남는 버전 표시(`.claude/harness-version`, [§6.4](#64-적용한-버전이-파일로-남는다))가 실제로 적용한 내용과 다른 값을 갖게 돼서, 다음 동기화 때 판단이 틀어진다.

⚠️ **하네스를 직접 고치는 사람은 특히 여기서 자주 걸린다.** 하네스 저장소를 고치는 중이면 원본 폴더가 작업 브랜치에 가 있는 경우가 많은데, 그 상태로 다른 프로젝트에서 "하네스 동기화해줘"를 돌리면 멈춘다. 하네스 쪽 작업을 PR로 올려 main에 합치거나([§7.1](#71-새-버전이-만들어지는-흐름)), 원본 폴더에서 `git switch main`으로 돌아간 뒤 다시 동기화하면 된다.

막히면 `/project-init`이 무엇이 문제인지 그대로 짚어준다. 안내대로 원본을 정리한 뒤 "하네스 동기화해줘"를 다시 시키면 된다.

### 6.2 프로젝트에 동기화하기

새 버전을 쓸 프로젝트에서, 이 순서로 진행한다.

```
/clear  →  /new-task 하네스 동기화  →  "하네스 동기화해줘"  →  /clear  →  /done-task
```

1. **`/clear`** — 지금 연 세션이 옛 스킬을 들고 있을 수 있다. 그대로 다음 단계로 가면 옛 버전이 돈다.
2. **`/new-task 하네스 동기화`** — 작업 브랜치부터 만든다(그 프로젝트 폴더에서 세션을 연다 — [§1](#1-두-가지-사용-환경)). 왜 브랜치를 먼저 만드는지는 바로 아래에 있다.
3. **"하네스 동기화해줘"** — `/project-init`이 동기화 모드로 돌면서 프로젝트에 있는 하네스 파일을 최신 원본과 하나씩 비교해 갱신한다.
4. **`/clear`** — 방금 동기화로 스킬 파일 자체도 바뀌었는데, 지금 세션은 아직 옛 버전을 쓰고 있다. 새로 열어야 방금 받은 `/done-task`가 최신으로 잡힌다([§6.3](#63-언제부터-적용되나)).
5. **`/done-task`** — 갱신된 파일을 커밋하고 PR을 만들어 main에 합친다.

**왜 작업 브랜치를 맨 먼저 만드나:**

1. **`auto-wip-commit` 훅은 작업 브랜치에서만 돈다.** 이 훅은 턴이 끝날 때마다 바뀐 파일을 알아서 커밋해두는 자동 저장 장치인데, main 브랜치에서는 작동하지 않는다. main에 있는 채로 동기화하면 바뀐 파일 20개 안팎이 커밋 안 된 채 그냥 쌓인다 — 자동 저장이 안 걸리는 것이다. 작업 브랜치에서 하면 이 문제가 아예 없고, 매 턴 자동 저장되니 바로 아래 나오는 미커밋 검사에도 걸리지 않는다.
2. **main에서 먼저 동기화하면 그다음이 꼬인다.** 그 상태로 `/new-task`를 부르면 "커밋 안 된 변경이 있다"며 멈추고 세 갈래를 물어보는데, 커밋을 고르면 **main에 바로 커밋**돼서 PR 흐름을 건너뛰게 되고, 임시 보관(stash — 변경 내용을 잠깐 치워뒀다가 나중에 다시 꺼내 쓰는 git 기능)을 고르면 나중에 직접 꺼내야 해서 잊어버리기 쉽다. 브랜치를 먼저 만들면 이 갈림길 자체가 안 생긴다.

**시작하기 전에 프로젝트 쪽에도 확인하는 조건이 하나 있다.** 동기화는 프로젝트에 있는 하네스 파일(`.claude/`·`docs/git-workflow.md`·`.github/workflows/ci.yml`)을 최신 원본 내용으로 덮어쓴다. 그래서 `/project-init`은 시작하기 전에 이 자리에 커밋 안 된 변경이 있는지 먼저 보고, 있으면 멈춘 뒤 커밋하거나 되돌려 달라고 물어본다 — 그대로 진행하면 그 변경이 되돌릴 수 없이 사라지기 때문이다. **이 검사는 저 세 자리에만 해당한다.** 프로젝트의 다른 파일에 커밋 안 된 작업이 남아 있는 건 상관없다 — 동기화가 안 건드리는 파일이라 그대로 둬도 된다.

파일별 비교 결과는 이렇게 처리된다.

- 같으면 그냥 넘어간다.
- 새로 생긴 파일은 복사한다.
- 달라진 파일은 **최신 원본으로 바꾸는 게 기본이다.** 다만 프로젝트가 그 파일을 손댄 흔적이 있으면 그냥 덮지 않고, 어디가 다른지 짚어준 뒤 원본으로 교체할지 손본 걸 유지할지 물어본다.

`CLAUDE.md`와 `AGENTS.md` 둘만 예외다. 프로젝트마다 고유한 내용(서비스 정의·타겟, 직접 덧붙인 규칙)이 담긴 파일이라 덮어쓰지 않고 **합친다** — 원본에서 온 공용 문구와 구조만 비교해 최신으로 맞춘 안을 보여준 뒤, 확인을 받고 반영한다. 그래야 프로젝트 내용은 지키면서 하네스가 바뀔 때 낡아버린 안내 문구를 잡아낼 수 있다. `AGENTS.md`는 다른 도구(예: `next dev`)가 자기 구역을 만들어 두는 파일이기도 해서, 하네스는 `<!-- BEGIN:project-rules -->` 구역만 관리하고 나머지는 건드리지 않는다.

갱신된 파일은 위에서 미리 만들어둔 작업 브랜치에 `auto-wip-commit` 훅이 턴마다 알아서 쌓아준다. 다 됐으면 위 절차의 4·5단계로 마무리한다.

### 6.3 언제부터 적용되나

하네스 파일이 프로젝트 폴더 안에 있어서, 세션이 시작될 때 그 자리에서 읽힌다.

다만 **지금 열려 있는 세션에는 안 들어온다.** 세션은 열릴 때 읽어둔 내용을 계속 쓰기 때문이다. 대화를 새로 시작하면 최신 파일이 잡힌다 — 방법은 [§1](#1-두-가지-사용-환경) 표의 '대화 비우기' 행.

### 6.4 적용한 버전이 파일로 남는다

`/project-init`은 하네스를 적용·동기화할 때마다 프로젝트에 `.claude/harness-version`이라는 표시 파일을 남긴다. 어느 시점의 하네스를 적용했는지 적어두는 파일이다.

```
repo=youngdonkim/builder-harness
commit=<적용한 하네스 커밋 sha 12자리 이상>
date=<YYYY-MM-DD>
```

이 파일이 쓰이는 곳은 다음 동기화 한 군데뿐이다([§6.2](#62-프로젝트에-동기화하기)). 프로젝트의 하네스 파일이 원본과 다를 때, 여기 적힌 커밋 시점의 원본과 대조해서 **그냥 낡은 것인지 프로젝트가 일부러 손본 것인지**를 가른다. 낡은 것이면 조용히 최신으로 바꾸고, 손본 흔적이면 어떻게 할지 물어본다.

## 7. 하네스를 직접 고치는 사람에게

이 저장소 자체를 만들고 고치는 사람을 위한 내용이다.

### 7.1 새 버전이 만들어지는 흐름

어느 프로젝트에서든 하네스의 개선점 발견 → 이 저장소에서 수정 → PR → 관리자가 main에 합침(merge). merge된 순간부터 [§6](#6-업데이트--새-버전-받기)의 절차로 각 프로젝트에 옮길 수 있다.

**서브 에이전트도 프로젝트 규칙을 자동으로 받는다.** 일반형이든 `.claude/agents/`의 커스텀이든, 서브 에이전트는 프로젝트 `CLAUDE.md`와 그 안에서 펼쳐지는 `@AGENTS.md`를 그대로 받는다(2026-08-19 실측 확인). 그래서 에이전트 파일에 공통 규칙을 다시 적지 않는다 — 적는 건 공통 규칙을 덮어쓰는 선언뿐이다. 예를 들어 `git-flow` 에이전트에는 "위임 원칙은 메인 세션용이고 너는 그 위임을 받은 실행자다"라고만 적혀 있다.

**이 저장소 자체도 하네스 사용자다.** 루트의 `.claude/`에 `payload/`와 같은 스킬·서브에이전트·훅이 적용돼 있어서, 하네스를 고치는 작업도 `/new-task`·`/done-task`로 한다. main에 바로 올리는 것도 `no-main-push` 훅에 막혀 관리자든 기여자든 반드시 PR을 거친다. 만드는 제품이 없는 저장소라서 규칙도 범용 작업 원칙뿐이고, 프로젝트에 권하는 것과 같은 방식으로 루트 `AGENTS.md`(모든 AI 도구용)와 `CLAUDE.md`(클로드 전용) 둘로 나눠 두었다.

### 7.2 버전 번호 정책

버전 번호를 따로 매기지 않는다. 커밋할 때마다 자동으로 생기는 고유 값(커밋 해시)이 버전 역할을 해서, 커밋 하나하나가 전부 새 버전으로 인식된다. 프로젝트에 적용된 버전을 기록하는 `.claude/harness-version`에도 이 커밋 값이 그대로 들어간다([§6.4](#64-적용한-버전이-파일로-남는다)). 만든 사람이 직접 매일 써보면서 바로바로 고치는 중이라 이렇게 해뒀다(이런 방식을 "도그푸딩"이라고 부른다). 나중에 다른 사람들에게 정식으로 배포할 때는 버전 번호를 정해 관리하는 방식으로 바꿀 것이다.

### 7.3 저장소 구조

```
README.md
AGENTS.md                             # 어느 AI 도구가 읽어도 지켜야 하는 규칙 (저장소 규칙·글쓰기 원칙)
CLAUDE.md                             # 클로드만 알면 되는 규칙 (위임 원칙) — 끝의 @AGENTS.md로 위 파일도 함께 읽는다
.claude/                              # 이 저장소에 적용된 하네스 — payload/.claude/와 같은 내용
payload/                              # 프로젝트 루트의 미러 — 이 구조 그대로 프로젝트에 복사된다
payload/.claude/skills/               # 단계 스킬·횡단 스킬
payload/.claude/agents/               # 서브에이전트
payload/.claude/hooks/                # 훅 스크립트
payload/.claude/rules/                # 특정 파일을 다룰 때만 적용되는 세부 규칙
payload/.claude/templates/            # delegation-integrator가 쓰는 sources·status 문서 틀
payload/docs/git-workflow.md          # 훅·done-task가 참조하는 작업 흐름 문서
payload/.github/workflows/ci.yml      # done-task가 머지 전 통과를 기다리는 lint + build 검사
payload/.claude/settings-hooks.json   # (예외) 복사 아님 — 훅 등록 원본, 프로젝트 설정 파일에 합쳐 넣는 내용
payload/CLAUDE.md.template            # (예외) 복사 아님 — 인터뷰 답을 채워 프로젝트 CLAUDE.md를 만드는 틀
payload/AGENTS.md.template            # (예외) 복사 아님 — 인터뷰 답을 채워 프로젝트 AGENTS.md를 만드는 틀
```

`payload/` 아래 구조가 곧 프로젝트 루트에 놓일 모양이다. 여기에 파일을 더하면 그게 그대로 프로젝트로 간다. **예외는 끝의 세 파일뿐**이다 — 그대로 놓이는 파일이 아니라서 복사에서 빠지고, 하나는 병합 원본으로 나머지 둘은 가공할 틀로 쓰인다. 그래서 이 셋만 `payload/` 안에서 자리가 특별하다(템플릿 둘은 payload 루트에).

`ci.yml`은 앱 코드(`package-lock.json`)가 아직 없는 프로젝트에서는 자동으로 통과 처리되고, 앱 코드가 생기는 순간부터 실제 lint + build 검사가 돌기 시작한다.
