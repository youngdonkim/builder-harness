# builder-harness

혼자 AI로 며칠~몇 주 만에 작동하는 서비스를 만들어 시장 반응으로 검증하는 사람(이 문서에서는 **AI 빌더**라고 부른다)을 위한 **Claude Code 플러그인**이다. 아이디어를 떠올린 순간부터 MVP(Minimum Viable Product — 가설을 검증할 수 있는 최소한의 작동하는 제품)를 실제 사용자에게 내놓기까지를 **7단계 한 흐름**으로 안내한다.

용어가 낯설면 먼저 [§1 이게 무엇인가](#1-이게-무엇인가)를 읽으면 된다.

**설계 원칙**: 빌드는 AI가 거의 공짜로 해주니 — 팀·투자자에게 보여주기 위한 무거운 문서는 버리고, 빌더 자신이 뭘 만들고 뭘 안 만들지 정하는 최소 전략 + AI가 정확히 빌드하게 만드는 구체 명세만 남긴다.

## 빠른 시작 — 이 4개만 순서대로

이 빌더 하네스를 빠르게 사용하시려면 아래 4단계를 실행하시면 됩니다.

**1. 마켓플레이스 등록** — 터미널에서, 컴퓨터에 **딱 한 번만**

```
claude plugin marketplace add youngdonkim/builder-harness
```

→ 자세히: [§1.2](#12-마켓플레이스란), [§3.2](#32-마켓플레이스-등록--역할에-따라-하나만-고른다)

**2. 플러그인 설치** — 터미널에서, **쓰려는 프로젝트마다 한 번**

```
cd <프로젝트 경로>
claude plugin install builder-harness@builder-harness --scope project
```

→ 자세히: [§1.5](#15-스코프--왜-프로젝트-하나에만-설치하나), [§3.3](#33-플러그인-설치)

**3. 세션 열기** — 그 프로젝트 폴더에서

```
claude
```

**4. 첫 세팅** — 방금 열린 Claude Code 채팅창에서

```
/project-init
```

→ 자세히: [§3.4](#34-첫-세팅--project-init)

설치가 끝나면 채팅창에서 이 명령들을 쓴다 — 역할은 [§2 들어 있는 것](#2-들어-있는-것) 표에.

| 언제 | 명령 |
|---|---|
| 아이디어를 MVP까지 끌고 갈 때 | `/idea-to-mvp` |
| 새 작업을 시작할 때 | `/new-task` |
| 작업을 끝내고 반영할 때 | `/done-task` |
| 잘못된 작업을 되돌릴 때 | `/rewind-task` |
| 화면·색·간격 같은 디자인을 다룰 때 | `/design-system` |

## 1. 이게 무엇인가

### 1.1 플러그인이란

**Claude Code**는 터미널(컴퓨터에 명령어를 직접 쳐 넣는 검은 창)에서 대화하며 코딩을 맡기는 도구다. **플러그인(plugin)**은 그 Claude Code에 기능을 끼워 넣는 확장 꾸러미다 — 스마트폰에 앱을 깔아 기능을 늘리는 것과 같은 개념이다.

builder-harness는 그런 플러그인 하나다. 설치하면 Claude Code가 원래는 모르던 "아이디어를 MVP까지 끌고 가는 방법"과 "git 작업을 안전하게 처리하는 절차"를 알게 된다.

### 1.2 마켓플레이스란

**마켓플레이스(marketplace)**는 플러그인이 모여 있는 **목록**이다. 앱스토어에 해당한다. Claude Code는 아무 플러그인이나 그냥 설치하지 못하고, "이 플러그인은 어디에 있다"는 정보를 먼저 알아야 한다. 그 정보를 알려주는 작업이 **마켓플레이스 등록**이다.

한 번 등록해두면 그 정보가 컴퓨터의 `~/.claude` 폴더에 저장되어, 이후에는 어떤 프로젝트에서든 이 플러그인을 설치할 수 있다. 그래서 등록은 **컴퓨터에 한 번**, 설치는 **프로젝트마다**다.

이 저장소는 조금 특이하게 **플러그인 본체와 마켓플레이스 목록이 같은 곳에 있다** — 즉 builder-harness 저장소 하나가 "가게"와 "상품" 역할을 겸한다. 그래서 설치 명령에 이름이 두 번 나온다: `builder-harness@builder-harness`는 "builder-harness라는 마켓플레이스에 있는 builder-harness라는 플러그인"이라는 뜻이다.

**마켓플레이스 하나에는 플러그인을 여러 개 담을 수 있다.** 지금 이 마켓플레이스에 들어 있는 것은 builder-harness 하나뿐이지만, 목록 파일(`.claude-plugin/marketplace.json`)의 `plugins` 칸이 여러 개를 나열할 수 있는 형태라서 늘릴 수 있다. 플러그인이 늘어나도 **마켓플레이스 등록은 여전히 한 번**이고, 사용자는 그 목록에서 **원하는 것만 골라 설치**한다.

```
claude plugin install builder-harness@builder-harness --scope project
claude plugin install another-plugin@builder-harness --scope project
```

`@` 뒤는 항상 마켓플레이스 이름이고, 앞이 플러그인 이름이다. 지금 이 둘이 똑같아 보이는 것은 우연이고, 플러그인이 늘면 앞부분만 달라진다.

### 1.3 하네스란

**하네스(harness)**는 원래 말이나 사람에게 씌우는 마구·안전벨트를 뜻한다. 여기서는 **AI가 정해진 절차와 안전 규칙 안에서 일하도록 잡아주는 틀**이라는 의미로 쓴다. AI에게 매번 "이렇게 해줘"라고 설명하는 대신, 그 절차를 미리 문서와 규칙으로 만들어 두고 AI가 항상 그대로 따르게 하는 것이다.

이 하네스가 잡아주는 것은 두 가지다.

- **진행 절차** — 아이디어 검증부터 MVP 런치까지 7단계를 순서대로, 각 단계의 통과 기준과 함께 진행한다.
- **안전 규칙** — 코드를 잘못 날리거나 검토 없이 반영하는 일이 생기지 않게 git 작업을 막고 자동 저장한다.

### 1.4 스킬·서브에이전트·훅

이 플러그인이 담고 있는 세 종류의 부품이다.

- **스킬(skill)** — Claude가 특정 작업을 할 때 읽는 **작업 설명서**다. 채팅창에서 `/이름` 형태로 직접 불러 쓴다. 예: `/idea-to-mvp`.
- **서브에이전트(subagent)** — 특정 일만 전담하는 **보조 AI**다. 본 대화와 따로 떨어져 일하기 때문에, 긴 작업을 맡겨도 본 대화가 지저분해지지 않는다. 대개 스킬이 알아서 호출하므로 사용자가 직접 부를 일은 적다.
- **훅(hook)** — 정해진 순간마다 **자동으로 실행되는 규칙**이다. 사용자가 부르지 않아도 걸린다. 예: main 브랜치에 코드를 바로 올리려 하면 막고, 답변이 끝날 때마다 작업 내용을 자동 저장한다.

### 1.5 스코프 — 왜 프로젝트 하나에만 설치하나

**스코프(scope)**란 이 플러그인을 **어디까지 적용할지** 정하는 설정이다. 두 가지가 있다.

- **project 스코프** — 지정한 프로젝트 폴더 하나에만 적용된다.
- **user 스코프** — 이 컴퓨터의 모든 프로젝트에 적용된다.

이 하네스는 **항상 project 스코프로만** 설치한다(`--scope project`). 이유는 [§1.4](#14-스킬서브에이전트훅)의 훅 때문이다 — 훅은 사용자가 부르지 않아도 자동으로 걸리는 규칙이라, user 스코프로 설치하면 이 하네스와 아무 상관 없는 다른 프로젝트에서까지 "main에 올리기 금지"와 "자동 커밋"이 걸려 곤란해진다.

## 2. 들어 있는 것

부품의 종류는 [§1.4](#14-스킬서브에이전트훅)에서 설명한 스킬·서브에이전트·훅 세 가지인데, 스킬은 쓰이는 시점에 따라 다시 둘로 나뉜다.

- **단계 스킬** — 아이디어에서 MVP까지 가는 **7단계 본줄기를 진행하는 스킬**이다. 프로젝트를 앞으로 밀고 나가는 역할이라 지금은 `idea-to-mvp` 하나뿐이고, 이 하나를 여러 번 불러 단계를 하나씩 밟아간다.
- **횡단 스킬** — 몇 단계에 있든 **필요할 때마다 꺼내 쓰는 스킬**이다. 7단계 전체를 가로질러(횡단) 쓰이기 때문에 이렇게 부른다. 작업을 시작하고 마무리하고 되돌리는 일, 디자인을 다루는 일처럼 단계와 상관없이 계속 반복되는 작업들이다.

| 종류 | 이름 | 역할 |
|---|---|---|
| 단계 스킬 | `idea-to-mvp` | 7단계: UserStory · InformationArchitecture · Mockup · DemoValidation · MarketResearch · MvpBuild · MvpLaunch (통과 기준 2개) |
| 횡단 스킬 | `project-init` | 새 프로젝트에 하네스 적용 — CLAUDE.md 뼈대 + rules 템플릿 복사. 이미 적용된 프로젝트에서 재실행하면 복사본을 최신 템플릿과 비교해 동기화 |
| 횡단 스킬 | `new-task` | main 최신화 + 방금 끝낸 이 작업 폴더·브랜치만 정리(다른 창의 작업 폴더는 안 건드림) + 새 작업 폴더·브랜치 생성 |
| 횡단 스킬 | `done-task` | 자동 저장 커밋 → 원격 올리기(push) → PR 생성 → (오너면) CI 통과 대기 → 합치기(merge) → 원격 브랜치 삭제 한 흐름. 팀원은 PR까지, 오너는 머지까지 |
| 횡단 스킬 | `rewind-task` | 자동 저장 시점으로 되돌리기 — 후보 표를 보여준 뒤 파일·브랜치·되감기 중 선택 |
| 횡단 스킬 | `design-system` | 3단 토큰 계층(foundation→semantic→component) + 조립 계층(frame·pattern) 디자인 시스템 방법론 — 화면·컴포넌트·토큰을 만들거나 수정할 때 참조 |
| 서브에이전트 | `git-flow` | `new-task`·`done-task`·`rewind-task`의 실제 실행자 |
| 서브에이전트 | `user-scenario-writer` | 영화 시나리오형 유저 스토리 작성 |
| 서브에이전트 | `ux-writing-reviewer` | UI 문구를 UX writing 원칙과 대조해 직접 교정 |
| 훅 | `no-main-push` | main 브랜치에 바로 올리는 것을 차단 (PR 검토 흐름 강제) |
| 훅 | `auto-wip-commit` | 응답이 끝날 때마다 작업 브랜치에 진행 중 커밋(wip)을 자동 생성 |
| 훅 | `stale-plugin-notice` | 설치된 플러그인이 최신보다 뒤처지면 세션이 열릴 때마다 알림 — 같은 버전 조합은 6시간에 한 번만 |
| 훅 | `pending-worktree-guard` | `new-task`가 만든 새 작업 폴더로 세션이 실제로 옮겨 갔는지 확인 — 안 옮겼으면 한 번 막고 알림 |

용어 참고 — **PR(Pull Request)**은 "내가 고친 걸 본체에 반영해 달라"고 올리는 제안이다. **CI(Continuous Integration)**는 그 제안이 반영되기 전에 코드가 깨지지 않았는지 자동으로 검사하는 절차다. **wip(work in progress)**는 아직 끝나지 않은 진행 중 상태를 뜻한다.

## 3. 설치 자세히

빠른 시작에 나온 명령들을 하나씩 풀어 설명한다.

### 3.1 명령을 어디에 치나 — 터미널과 세션

이 문서의 명령은 두 곳 중 하나에 입력한다. 헷갈리면 **명령의 첫 글자**를 보면 된다.

| 입력하는 곳 | 무엇인가 | 명령 모양 |
|---|---|---|
| **터미널** | Claude Code를 켜기 전, 컴퓨터의 명령어 창(터미널 앱) | `claude plugin ...` |
| **Claude Code 세션** | 터미널에서 `claude`를 실행해 채팅 화면이 뜬 상태. 그 채팅창 안 | `/plugin ...`, `/project-init` |

플러그인 관련 명령은 둘 다에서 된다. 터미널 명령 앞의 `claude `를 빼고 `/`를 붙이면 세션용 명령이 된다 — 동작은 같다.

```
claude plugin marketplace add youngdonkim/builder-harness   ← 터미널
/plugin marketplace add youngdonkim/builder-harness         ← 세션
```

### 3.2 마켓플레이스 등록 — 역할에 따라 하나만 고른다

플러그인이 어디 있는지 알려주는 방법이 두 가지 있다. **둘을 다 하는 게 아니라, 자기 역할에 맞는 하나만 고른다.**

**역할 A. 플러그인 사용자** — 이 하네스를 가져다 쓰기만 하는 사람. 하네스 코드를 고칠 일이 없다. **대부분이 여기에 해당한다.**

**GitHub 주소**로 등록한다. GitHub는 이 플러그인의 원본 코드가 올라가 있는 인터넷 사이트다. 이 방법을 쓰면 미리 내려받아 둘 파일이 하나도 없다 — Claude Code가 인터넷에서 알아서 가져온다.

```
claude plugin marketplace add youngdonkim/builder-harness
```

**역할 B. 하네스 개발자** — builder-harness 저장소 자체를 만들고 고치는 사람. 이 저장소의 관리자이거나, 저장소를 자기 컴퓨터에 내려받아(clone) 수정한 뒤 PR로 올리는 기여자다.

**저장소를 내려받아 둔 폴더 경로**로 등록한다. 이렇게 하면 파일을 고칠 때마다 그 수정이 **자기 컴퓨터의 Claude Code에서만** 곧바로 반영된다 — GitHub에 올리기 전에 자기 환경에서 먼저 시험해보기 위한 방식이고, 다른 사용자에게는 아무 영향이 없다. 다른 사용자에게 반영되는 정식 경로는 [§5.1](#51-새-버전이-만들어지는-흐름)에 있다.

```
claude plugin marketplace add ~/dev/builder-harness
```

(`~/dev/builder-harness`는 예시다. 각자 저장소를 내려받은 실제 폴더 경로로 바꾼다.)

### 3.3 플러그인 설치

쓰려는 프로젝트 폴더로 이동한 뒤 설치한다.

```
cd <프로젝트 경로>
claude plugin install builder-harness@builder-harness --scope project
```

`builder-harness@builder-harness`의 의미는 [§1.2](#12-마켓플레이스란), `--scope project`의 의미는 [§1.5](#15-스코프--왜-프로젝트-하나에만-설치하나)에 있다.

세션에서 하려면 그 프로젝트 폴더에서 `claude`로 세션을 열고 `/plugin install builder-harness@builder-harness`를 입력한 뒤, 스코프 선택지에서 `project`를 고른다.

### 3.4 첫 세팅 — `/project-init`

프로젝트의 Claude Code 세션 채팅창에서 실행한다.

```
/project-init
```

CLAUDE.md 뼈대와 `.claude/rules/` 템플릿이 그 프로젝트로 **복사**된다. 플러그인이 CLAUDE.md와 rules를 직접 싣지 못하기 때문에 복사가 필요하다.

- **CLAUDE.md** — 그 프로젝트에서 Claude가 항상 지켜야 할 규칙을 적어두는 파일. 세션을 열 때마다 자동으로 읽힌다.
- **`.claude/rules/`** — 특정 종류의 파일을 다룰 때만 적용되는 세부 규칙 모음.

### 3.5 자주 막히는 두 가지

- **설치 직후 같은 세션에서는 스킬이 아직 안 잡힌다.** `/reload-plugins`를 먼저 치거나, 세션을 새로 연다.
- **스킬 이름은 짧은 형태로 친다.** 입력창 자동완성에는 `/project-init`·`/idea-to-mvp`처럼 짧은 이름만 뜬다. 긴 정식 이름(`/builder-harness:project-init`)을 치면 오히려 추천 목록에 나타나지 않는다. 긴 이름은 같은 이름의 스킬이 여러 플러그인에 있을 때 구분하는 용도일 뿐이다.

## 4. 업데이트 — 새 버전 받기

설치를 마친 사람이 새 버전을 받는 방법이다. 역할 A·B 누구든 똑같이 한다. 명령은 전부 **터미널**에서.

**Claude 데스크톱 앱**(터미널 대신 창을 띄워 쓰는 Claude 앱)으로 Claude Code를 쓴다면 자동 갱신이 **안 돌 수도 있다**. 그럴 땐 아래 [§4.1](#41-컴퓨터에-새-버전-받아두기)~[§4.2](#42-프로젝트에-적용하기)의 수동 갱신을 직접 해주면 된다 — 자세한 사정은 [§4.5](#45-자동-갱신-켜기)에 있다.

### 4.1 컴퓨터에 새 버전 받아두기

아무 폴더에서나, 컴퓨터에 한 번 실행한다.

```
claude plugin marketplace update builder-harness
```

이 단계는 새 버전을 컴퓨터에 **받아만 두는 것**이다 — 아직 어떤 프로젝트에도 반영되지 않는다.

### 4.2 프로젝트에 적용하기

새 버전을 쓸 프로젝트 폴더마다 각각 실행한다.

```
cd <프로젝트 경로>
claude plugin update builder-harness@builder-harness --scope project
```

이 명령을 실행한 프로젝트만 새 버전이 되고, 실행하지 않은 프로젝트는 기존 버전에 머문다. 스코프가 헷갈리면 그 프로젝트에서 `claude plugin list`로 `Scope:` 값을 확인해 그대로 넣는다 — 안 맞으면 "not found"나 "not installed" 에러가 난다.

### 4.3 언제부터 적용되나

이미 열려 있는 Claude Code 세션에는 곧바로 반영되지 않는다("Restart to apply changes"라는 안내가 뜬다). 여기서부터는 Claude Code를 **어디서 쓰느냐**에 따라 갈린다.

- **터미널에서 `claude`로 쓰는 경우** — 그 세션 안에서 `/reload-plugins`를 치면 바로 반영된다. 안 쳐도 **다음에 새로 여는 세션부터** 적용된다.
- **Claude 데스크톱 앱으로 쓰는 경우** — `/reload-plugins`가 듣지 않고, **새 대화를 열어도 안 된다**(둘 다 직접 확인한 결과다). 앱에서 "새 대화"는 창만 새로 여는 것이라 Claude Code 프로그램 자체는 계속 떠 있고, 플러그인은 그 프로그램이 **처음 뜰 때 한 번 읽고 고정**되기 때문이다. **앱을 완전히 종료했다가 다시 켜야** 새 버전이 적용된다 — 창을 닫는 게 아니라 `Cmd+Q`로 앱 자체를 끝내거나 독 아이콘을 우클릭해 종료를 고른다.

### 4.4 템플릿 사본 동기화 — 따로 챙겨야 하는 것

[§4.1](#41-컴퓨터에-새-버전-받아두기)~[§4.2](#42-프로젝트에-적용하기)로 새로 받는 것은 **스킬·서브에이전트·훅뿐이다.** `/project-init`이 예전에 각 프로젝트로 **복사해준 파일들** — `CLAUDE.md`, `.claude/rules/*`, `docs/git-workflow.md`, `.github/workflows/ci.yml` — 은 이미 그 프로젝트 저장소의 일부라서, 플러그인을 업데이트해도 저절로 바뀌지 않는다.

템플릿이 개선된 새 버전을 받았다면, 그 파일을 쓰고 있는 프로젝트의 세션에서 `/project-init`을 **다시** 실행한다. 이미 적용된 프로젝트에서는 자동으로 동기화 모드로 동작해, 이 스킬이 만들거나 갱신하는 파일을 하나도 빼놓지 않고 최신 템플릿과 비교한다.

- 복사본과 최신 템플릿이 같으면 그냥 넘어간다.
- 새로 생긴 파일은 복사한다.
- 달라진 파일은 **병합이 기본이다** — 프로젝트가 일부러 손봐둔 내용은 그대로 두고 템플릿에서 새로 생기거나 바뀐 대목만 합친 안을 보여준 뒤, 확인을 받고 반영한다. 커스텀을 버리고 템플릿으로 교체하거나 반대로 템플릿 변경을 무시하는 것도 그 자리에서 고를 수 있다.

`CLAUDE.md`는 프로젝트마다 고유한 내용(서비스 정의·타겟, 직접 덧붙인 규칙)이 담긴 파일이라, 템플릿에서 온 공용 문구와 구조만 비교하고 나머지는 건드리지 않는다. 그래야 하네스가 바뀔 때 낡아버린 안내 문구를 잡아낼 수 있다.

**정리하면 하네스가 바뀌었을 때 할 일은 두 가지다.** ① [§4.1](#41-컴퓨터에-새-버전-받아두기)~[§4.2](#42-프로젝트에-적용하기)로 플러그인 업데이트 (데스크톱 앱이면 완전 종료 후 재시작 — [§4.3](#43-언제부터-적용되나)) → ② 각 프로젝트에서 `/project-init` 동기화. ①만 하면 스킬은 최신인데 복사본은 옛날 그대로다.

갱신된 파일은 그 프로젝트의 git 흐름(작업 브랜치 → PR)으로 커밋한다.

팀 프로젝트라면 이렇게 갱신해서 main에 합쳐두는 것만으로 충분하다 — 그 저장소를 새로 내려받거나(clone) 당겨오는(pull) 팀원은 고쳐진 사본을 자동으로 받는다. 팀원이 따로 할 일은 자기 컴퓨터에서 플러그인을 설치·업데이트해두는 것뿐이다.

### 4.5 자동 갱신 켜기

프로젝트의 `.claude/settings.json` 파일에서 `extraKnownMarketplaces.builder-harness` 항목에 `"autoUpdate": true`를 추가하면, Claude Code가 최신본이 나왔는지 알아서 확인하도록 맡길 수 있다.

```json
{
  "extraKnownMarketplaces": {
    "builder-harness": {
      "source": { "source": "github", "repo": "youngdonkim/builder-harness" },
      "autoUpdate": true
    }
  }
}
```

이 저장소처럼 Anthropic이 아니라 개인·커뮤니티가 만든 마켓플레이스는 이 자동 확인이 기본적으로 꺼져 있어서, 켜고 싶으면 직접 설정해야 한다.

**다만 이 설정이 실제로 도는지는 Claude Code를 어디서 쓰느냐에 따라 갈린다.**

- **터미널에서 `claude`로 쓰는 경우 — 작동한다.** 공식 문서에 따르면 세션이 시작되고 나서 **최대 10분 뒤**에 배경에서 검사와 갱신이 돌아간다. 그래서 "세션만 열면 곧바로 최신"은 아니다 — 지금 세션은 열 때 읽어둔 옛 버전을 계속 쓴다. 갱신되면 `/reload-plugins`를 치라는 알림이 뜨는데, 그때 치거나 그냥 두고 **다음 세션부터** 새 버전을 쓰면 된다.
- **Claude 데스크톱 앱으로 쓰는 경우 — 안 돌 수도 있다.** 확인해 보니 앱이 자기가 띄우는 Claude Code에 `DISABLE_AUTOUPDATER=1`이라는 **환경변수(environment variable — 프로그램을 띄울 때 같이 넘겨주는 설정값)**를 넣어두고 있었다. 공식 문서에 따르면 이 값은 Claude Code와 **모든 플러그인**의 자동 갱신을 함께 끈다. 앱이 자기 버전을 스스로 관리하느라 내장 Claude Code의 자동 갱신을 끄는데, 그 여파로 플러그인 쪽까지 같이 꺼지는 것으로 보인다.

  **다만 늘 그런 건 아니다.** 같은 컴퓨터에서 며칠 전에는 자동 갱신이 정상으로 돌았던 기록이 남아 있었다 — 공식 플러그인 버전이 실제로 올라갔고 이 마켓플레이스도 같은 순간에 최신을 받아왔다. 앱 버전이나 실행 방식에 따라 달라질 수 있으니 **된다·안 된다를 미리 단정하지 말고, 아래 방법으로 확인하는 게 확실하다.**

  ```
  claude plugin list
  ```

  `Version:` 값이 최신 커밋과 다르면 자동 갱신이 안 돈 것이다. 그때 [§4.1](#41-컴퓨터에-새-버전-받아두기)~[§4.2](#42-프로젝트에-적용하기)를 직접 실행하면 된다.

  이 값이 실제로 켜져 있다면 **직접 되돌리기는 쉽지 않다.** 셸 설정 파일(`.zshrc` 같은, 터미널을 켤 때 자동으로 읽히는 파일)에 값을 적어도 소용없다 — 앱은 터미널을 거치지 않고 Claude Code를 바로 띄우기 때문이다(직접 확인한 결과다). `settings.json`의 `env` 칸도 안 된다 — 공식 문서에 따르면 `env`는 Claude Code가 **띄우는 자식 프로그램**에 넘어가는 값이지 Claude Code 자신에게 적용되는 값이 아닌데, 자동 갱신은 Claude Code 자신이 하는 일이다.

  **그래서 데스크톱 앱을 쓴다면 [§4.1](#41-컴퓨터에-새-버전-받아두기)~[§4.2](#42-프로젝트에-적용하기)의 수동 갱신이 유일한 방법이다.**

그래도 이 설정은 켜둘 만하다. 같은 저장소를 쓰는 팀원 중 터미널로 작업하는 사람에게는 그대로 유효하고, 앱 쪽 동작은 나중에 바뀔 수도 있다.

직접 손으로 쓸 필요는 없다 — `/project-init`이 새 프로젝트를 세팅할 때(또는 이미 적용된 프로젝트에서 템플릿 동기화를 다시 실행할 때)마다 자동 갱신을 켤지 물어보고, 켜기로 하면 기존 설정(특히 `enabledPlugins`)을 보존한 채 위 항목을 대신 넣어준다.

`.claude/settings.json`은 저장소에 커밋되는 파일이라, 팀원 한 명이 이 설정을 켜서 main에 합쳐두면 그 저장소를 내려받거나 당겨오는 팀원 전원에게 똑같이 적용된다. 다만 각자 컴퓨터에서 처음 한 번은 Claude Code의 마켓플레이스 신뢰 확인을 직접 통과해야 한다. 이 경우에도 새로 받아온 것이 지금 열린 세션에 저절로 들어오지는 않는다 — [§4.3](#43-언제부터-적용되나)대로 터미널이면 `/reload-plugins`를 치고, 데스크톱 앱이면 새 대화 세션을 연다.

## 5. 하네스를 직접 고치는 사람에게

[§3.2](#32-마켓플레이스-등록--역할에-따라-하나만-고른다)의 **역할 B**에 해당하는 사람을 위한 내용이다.

### 5.1 새 버전이 만들어지는 흐름

어느 프로젝트에서든 하네스의 개선점 발견 → 이 저장소에서 수정 → PR → 관리자가 main에 합침(merge). merge된 순간부터 [§4](#4-업데이트--새-버전-받기)의 절차로 누구나 새 버전을 받을 수 있다.

이 저장소는 main에 바로 올리는 것이 훅으로 막혀 있어, 관리자든 기여자든 반드시 PR을 거친다.

### 5.2 버전 번호 정책

버전 번호를 `plugin.json`에 따로 적지 않는다. 커밋할 때마다 자동으로 생기는 고유 값(커밋 해시)이 버전 역할을 해서, 커밋 하나하나가 전부 새 버전으로 인식된다. 만든 사람이 직접 매일 써보면서 바로바로 고치는 중이라 이렇게 해뒀다(이런 방식을 "도그푸딩"이라고 부른다). 나중에 다른 사람들에게 정식으로 배포할 때는 버전 번호를 정해 관리하는 방식으로 바꿀 것이다.

### 5.3 저장소 구조

```
.claude-plugin/
  plugin.json        # 플러그인 선언
  marketplace.json   # 이 저장소 자체가 마켓플레이스 (source: "./")
skills/              # 단계 스킬·횡단 스킬
agents/              # 서브에이전트
hooks/               # hooks.json + 스크립트
skills/project-init/templates/                   # 새 프로젝트로 복사되는 CLAUDE.md·rules·docs·CI 템플릿
skills/project-init/templates/docs/              # git-workflow.md — 훅·done-task가 참조하는 작업 흐름 문서
skills/project-init/templates/.github/workflows/ # ci.yml — done-task가 머지 전 통과를 기다리는 lint+build 검사
```

`ci.yml`은 앱 코드(`package-lock.json`)가 아직 없는 프로젝트에서는 자동으로 통과 처리되고, 앱 코드가 생기는 순간부터 실제 lint+build 검사가 돌기 시작한다.

### 5.4 플러그인을 하나 더 추가하려면

[§1.2](#12-마켓플레이스란)에서 말한 대로 이 마켓플레이스에 플러그인을 더 담을 수 있는데, **지금 구조에는 걸림돌이 하나 있다.** `marketplace.json`의 `source`가 `"./"`, 즉 **저장소 루트 전체가 곧 플러그인 본체**다(`skills/`·`agents/`·`hooks/`가 루트에 그대로 있다). 이 상태로는 두 번째 플러그인이 들어갈 자리가 없다.

플러그인을 늘리려면 이렇게 바꾼다.

- 플러그인마다 **자기 폴더**를 주고, 그 안에 각각 `.claude-plugin/plugin.json`과 `skills/`·`agents/`·`hooks/`를 둔다.
- `marketplace.json`의 `plugins` 목록에 항목을 추가하고, 각 `source`가 그 폴더를 가리키게 한다.
- 플러그인 본체가 이 저장소 밖에 있어도 된다 — `source`에 다른 GitHub 저장소(`{"source": "github", "repo": "user/repo"}`)를 넣을 수 있다. 마켓플레이스는 **위치를 적어둔 목록**일 뿐이기 때문이다.

파일 위치를 옮기면 이미 설치해 쓰던 사람들의 설치 경로가 달라지므로, 두 번째 플러그인을 실제로 만드는 시점에 한 번에 정리하는 편이 낫다.
