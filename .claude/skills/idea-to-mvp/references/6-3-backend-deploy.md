DB와 로그인까지 붙었으면 앱은 아직 반쪽이다 — 데이터가 갈 곳은 생겼는데 화면은 여전히 로컬스토리지를 보고 있다. 이 문서는 그 마지막 구간이다. **읽기·쓰기 경로를 Supabase로 갈아끼우고 로컬스토리지를 걷어낸 뒤**, 검색 노출을 켜고, 밖에서 보이는 계약을 스모크 테스트로 굳히고, (사람이 있으면) 베타로 공유해 치명 결함을 확인하고, 퍼널 계측을 심어 최종 배포까지 간다.

6단계 전체의 **완료 체크리스트**(§3)와 산출물 `backend-build.md` 스펙(§4)도 여기 있다. 6단계 도중에 다시 들어왔다면 §3 체크리스트를 코드와 대조해 어디까지 됐는지부터 확인한다.

> ⚠ **여기 적힌 외부 도구(Vercel·Supabase·Next.js 등)의 설정 이름·기본값·대시보드 위치는 이 글을 쓴 시점 기준이다.** 그대로 따라 하기 전에 공식 문서로 지금도 맞는지 확인하고, 달라졌으면 공식 문서를 따르고 이 문서를 고쳐야 한다고 사용자에게 보고한다. 반대로 **[실측]이 붙은 숫자는 우리가 직접 잰 기록**이라 공식 문서에 없다 — 값이 그대로인지는 다시 재서 확인하되, "왜 재봐야 하는가"라는 교훈 자체는 그대로 지킨다.

## 1. 이 하위 단계가 하는 일

앞선 하위 단계에서 만든 것 — 마이그레이션으로 올린 스키마, 붙여 놓은 로그인·동의 — 을 **앱 코드에 실제로 물려 배포까지 끝낸다.** 여기까지 오면 6단계가 끝나고 7단계(MvpLaunch)로 넘어간다.

이 구간의 작업도 SKILL.md §1.5 **초안 모드**다 — AI가 끝까지 완주한 뒤 완성본으로 리뷰받는다. 다만 **클릭 검증과 통과 판정은 사람 몫**이라 §2.4·§2.6에서 멈춰 사용자를 기다린다.

**범위는 앞에서 정한 그대로다** — 5단계 앱 코드에 없는 화면·기능은 여기서도 추가하지 않는다. "이것도 있으면 좋겠는데" 신호는 `추후 결정:`으로 `backend-build.md`에 마킹만 한다.

## 2. 진행 절차

### 2.1 읽기·쓰기 경로 교체와 로컬스토리지 제거

1. **읽기·쓰기 경로 교체** — 로컬스토리지 호출을 Supabase 클라이언트 호출로 바꾼다.
2. **로컬스토리지 코드 제거** — 남겨두고 폴백으로 쓰지 않는다. 두 갈래로 남으면 어느 쪽이 진짜 데이터인지 알 수 없어져, 베타 공유·계측 숫자가 전부 오염된다. (기기 간 이어쓰기용 마이그레이션도 하지 않는다 — 5단계에서 브라우저에 쌓인 데이터는 버리는 데이터다.)

**보안 baseline**: auth·API·업로드·`supabase/` 코드를 만지면 `.claude/rules/security-baseline.md`가 자동 로드된다 — 1부 외부 도달 baseline(http-only cookie·민감정보·업로드 검증·rate limit·에러에 stack 미노출)과 2부 Supabase 권한 baseline 준수. 광고로 모르는 사람들이 실제로 들어오는 코드다.

**에스컬레이션**: 명세와 모순 발견·구조가 크게 갈리는 선택·외부 서비스 추가 필요 시 멈추고 배치 질문. 그 외 애매함은 합리적 가정 + `추후 결정:` 마킹 후 계속.

### 2.2 검색 노출(SEO) — 이 시점에 같이 한다

로컬스토리지 시절엔 데이터를 서버가 모르니 검색엔진에 보여줄 HTML을 애초에 만들 수가 없었다. 그래서 검색 노출은 위에서 읽기·쓰기 경로를 Supabase로 갈아끼우는 **바로 그때 같이** 한다. 따로 떼어두면 잊히고, 나중에 하려면 서버가 데이터를 채워 보내는 구조부터 다시 뜯게 된다.

1. **기본 세트 적용** — 페이지별 제목·설명, 공유 미리보기(OG — 링크를 카톡·슬랙에 붙였을 때 뜨는 제목·설명·이미지), sitemap·robots, 없는 콘텐츠에 404 상태코드. 구체적인 방법은 여기 적지 않는다 — 널리 알려진 일반 지식이라 그때그때 최신 방식으로 하면 된다.
2. **5단계에서 걸어둔 색인 제외를 여기서 푼다** — `5-frontend-build.md` §2.6에서 프로토타입 전체를 검색에 안 잡히게 막아뒀다. 검색 노출을 켠다는 건 그걸 푸는 일이다. 단 **전부 푸는 게 아니다** — `.claude/rules/security-baseline.md` 1부가 말하는 대로 검색엔진은 외부 도달 경로라, 공개할 페이지만 열고 운영 콘솔·개인 전용 화면은 계속 막아둔다. 어느 화면이 공개인지는 4단계 인벤토리의 역할 열을 **출발점으로 참고**하되, 판정은 **현재 코드에 실제 있는 화면 기준**으로 한다 — 인벤토리는 1세대 기록이라 5단계 이후 코드에서 바뀐 화면이 반영돼 있지 않다.
3. **함정: 빈 상태가 200으로 나간다** — 4단계 상태 매트릭스대로 화면마다 빈 상태를 만들어 뒀기 때문에, 없는 콘텐츠 주소로 들어와도 "아직 없어요" 화면이 정상(200) 응답으로 나가기 쉽다. 검색엔진은 그걸 내용 없는 페이지로 색인한다. **데이터가 0개인 것(빈 상태, 200)과 그 주소가 아예 없는 것(404)을 갈라서** 처리한다.
4. **함정: `loading.tsx`가 404를 200으로 바꿔 놓는다 (Next.js)** — 라우트에 `loading.tsx`를 두면 그 라우트는 **스트리밍**(화면 뼈대를 먼저 보내고 내용은 준비되는 대로 이어 보내는 방식)으로 바뀐다. 뼈대를 먼저 보내는 순간 **응답 상태코드가 200으로 확정**되고, 그 뒤에 `notFound()`를 불러도 상태 줄은 이미 나간 뒤다. 결과는 없는 주소가 **200 + "불러오는 중"**으로 응답하는 것 — 검색엔진이 없는 페이지를 빈 내용으로 색인한다. 라우터가 아예 모르는 주소는 그대로 404가 나오니 **눈치채기 어렵다.**
   - **해법**: 있는지 없는지만 확인하는 **가벼운 조회 하나를 먼저 `await`** 한다 — 아직 아무것도 안 보낸 시점이라 여기서 부르는 `notFound()`는 진짜 404를 낸다. 무거운 나머지 조회는 `<Suspense>`로 감싸 흘려보낸다. `loading.tsx`는 **존재 확인이 필요 없는 화면**(목록·홈)에만 둔다.
   - **메타데이터도 같이 가른다** — `generateMetadata`는 가벼운 조회만 쓰게 한다. 제목·설명·OG는 한 줄이면 되는데 무거운 조회를 기다리면 첫 응답이 그만큼 늦어진다.
   - **이 함정은 실제로 겪은 기록이다** (§2.3 ①). 다만 파일 이름·동작은 Next.js 버전을 타니, **고치기 전에 없는 주소의 상태 코드를 직접 재서 지금도 같은지 확인하고** 해법은 그 버전 공식 문서에 맞춘다. 확인은 §2.3 스모크 테스트가 어차피 계속 해준다.
5. **판정** — `curl <배포 URL> | grep <화면에 보이는 콘텐츠 문구>`가 잡혀야 통과. 안 잡히면 서버가 데이터를 안 채워 보낸 것이라 나머지가 전부 무의미하다. **브라우저를 안 여는 검사라 AI가 직접 끝까지 확인한다** (SKILL.md §1.5 "사람 몫"은 화면을 눈으로 보는 검증 얘기고, 이건 응답 본문을 확인하는 일이라 해당 없다).

**연동이 끝나면 배포해 링크를 갱신한다** — §2.4 베타 공유에 쓸 링크가 실데이터로 돌아야 한다. 5단계 배포 링크는 그대로 두고 재배포하면 된다.

### 2.3 스모크 테스트 — 밖에서 보이는 계약만

여기서 **스모크 테스트(smoke test — 크게 깨진 데가 없는지 빠르게 훑는 최소 검사)**를 처음 도입한다.

**5단계에는 테스트를 쓰지 않는다** — 화면을 만들고 고치는 동안 구조가 매일 뒤집히는데 테스트를 쓰면 매번 다시 쓰게 되고, 싸야 할 검증 루프가 비싸진다. 그 구간이 싼 건 의도된 설계다. 거기선 깨지면 화면에 바로 보이니 사람 눈이 제일 싸고 빠르다.

**6단계에서 시작한다** — 백엔드와 검색 노출이 붙는 순간 **깨져도 눈에 안 보이는 것**이 생기기 때문이다. 실제로 있었던 일 셋: ① `loading.tsx`를 붙였더니 없는 주소가 404 대신 200으로 나갔는데 화면은 멀쩡해서 사람이 상태 코드를 손으로 재고서야 발견 ② 로그인 토큰이 만료되자 로그인과 상관없는 공개 화면이 통째로 죽었는데 사용자 신고로 발견 ③ 서버 렌더로 옮기며 조회 경로가 두 벌로 갈라진 것은 따로 검토를 돌려서야 발견. 상태 코드·크롤러가 받는 HTML·색인 제외·권한은 브라우저로 눌러봐선 안 보인다.

거창한 테스트 피라미드를 세우자는 게 아니다. **밖에서 보이는 계약만** 확인한다.

**기본 세트** — 도는 서버에 실제 요청을 넣어 확인한다:

| 확인 | 왜 |
|---|---|
| 공개 화면이 200 + **내용이 HTML에 실려 있음** | 검색 노출의 전제 (§2.2 5번 `curl` 판정을 테스트로 굳힌 것) |
| 목록→상세가 **진짜 `<a href>`** | 크롤러가 따라갈 길 |
| 낱개 제목·공유 미리보기(OG) 태그 | 링크를 붙였을 때 페이지마다 다 같아 보이면 안 됨 |
| **없는 주소는 404, 빈 상태는 200** | §2.2 3·4번이 못 박은 것 — 브라우저로는 절대 안 보임 |
| `robots.txt`·사이트맵이 열리고, 막을 것을 막음 | |
| **색인 제외 상태** — 아직 공개 전인 5단계 상태면 켜져 있어야 | 공개하는 날 이 테스트를 뒤집는다. 코드와 짝이라 한쪽만 고치면 걸린다 |
| **로그인 토큰이 만료돼도 공개 화면이 열림** | 공개 데이터는 로그인 상태와 무관해야 함 |

**만드는 법 — 도구를 늘리지 않는다**:

- **Node 내장 테스트 러너(`node:test`)면 충분하다** — 새로 깔 게 0개. vitest·jest는 컴포넌트를 하나하나 테스트할 필요가 생겼을 때 판단할 일이지, 이 목적으로 새로 깔지 않는다.
- **대상 주소는 사이트맵에서 뽑는다** — DB에 붙지 않아도 되고, 주소만 바꾸면 로컬이든 배포본이든 같은 테스트가 그대로 돈다.
- `package.json`에 실행 항목 하나 (예: `"smoke": "node --test ..."`).

**⚠ CI에서 도는 것과 안 도는 것을 갈라 쓴다**:

- **스모크 테스트는 깃허브 CI에서 못 돌 수 있다** — CI에는 로컬 DB가 없다. `done-task` 전에 **로컬에서 돌리는 검사**로 두거나, 배포된 미리보기 주소를 향해 쏜다. **CI에 넣었다고 착각하게 쓰지 마라 — 안 도는 검사는 없는 검사보다 나쁘다** (있다고 믿게 되니까).
- **반면 라우트 정적 검사는 CI에서 돈다** — `notFound()`를 부르는 `page.tsx`가 있는 라우트 갈래에 `loading.tsx`가 있으면 실패시키는 검사다. 파일만 읽으면 되니 서버도 DB도 필요 없다. §2.2 4번 함정을 빌드 전에 기계로 막는 자리다.

**새 검사를 언제 늘리나** — 사람 손으로 한 번 확인한 것이 **두 번째로 필요해지면** 그때 테스트로 옮긴다. 위 기본 세트도 손으로 열 번 넘게 반복한 `curl` 묶음이 그대로 굳은 것이다.

### 2.4 베타 공유

**이 절은 건너뛸 수 있다.** 5단계에서 프로토타입을 같이 본 지인·팀 동료가 있으면, 배포된 링크를 그 사람들에게 보내 **실제 사용 반응**을 확인한다. **마땅한 사람이 없으면 이 절을 통째로 건너뛰고 §2.5(퍼널 계측)로 간다** — 이걸 하려고 사람을 새로 구하러 다니지 않는다.

**왜 백엔드 연동 뒤인가**: 5단계에서 이미 화면은 보여줬으니 화면 반응은 새로 볼 게 없다. 이 시점 공유가 볼 값어치가 있는 건 **실데이터가 흐를 때의 행동**이다 — 진짜로 계정을 만드는지, 자기 데이터가 남는 걸 확인하고 다시 들어오는지, 핵심 플로우에서 어디서 이탈하는지.

**판정 아님**: 계속/중단을 가르는 관문이 아니라 치명 결함(가입 실패·데이터 유실·핵심 플로우 이탈·심각한 오해) 확인용이다. 발견되면 수정 후 재공유, 없으면 §2.5(퍼널 계측)로 진행. 관찰 내용은 `backend-build.md`에 짧게 기록한다.

**사용자가 직접 클릭하며 검증한다** — AI가 Playwright 같은 도구로 자동 사인오프하지 않는다 (SKILL.md §1.5 "사람 몫 불변"). AI는 배포까지 준비하고, 실제로 눌러보고 확인하는 건 사람 몫.

### 2.5 퍼널 계측

7단계(MvpLaunch) 판정은 **여기서 심은 이벤트가 전부다** — 계측이 빠지면 광고비를 쓰고도 판정 불능. 5종 기본 이벤트:

| # | 이벤트 | 정의 (예시 — 서비스에 맞게 구체화) | 퍼널 위치 |
|---|---|---|---|
| 1 | 유입 | 랜딩 도착 (유입 채널 구분 파라미터 포함 — 발품 vs 광고 vs 기타) | 최상단 |
| 2 | 가입 | 계정 생성 완료 | 전환 1 |
| 3 | 핵심행동 | *이 서비스의 aha 순간* 1회 완료 (예: 매물 진단 1회) — 무엇으로 할지 사용자와 결정 | 활성화 |
| 4 | 재방문 | 가입 후 7일 내 재방문 | retention |
| 5 | 결제 | (지불 가설 있으면) 결제 완료 / (없으면) 가격 페이지 도달 등 지불 의사 프록시 | 수익 |

- **채널 구분이 필수** — 발품 유입과 광고 유입을 구분 못 하면 7단계(MvpLaunch) 이중 채널 판정이 무너진다. UTM 파라미터 등으로 구분.
- **기본 5종 말고 이 서비스에만 필요한 이벤트가 있으면 AI가 먼저 제안한다** — 예: 중고 거래의 '채팅 시작', 강의 마켓의 '미리보기 재생'처럼 그 서비스의 성패를 가르는 행동. 5단계 화면을 읽어 후보를 1~2개 뽑아 사용자에게 보여주고, **승인받은 것만** 심는다. 승인 없이 늘리지 않는다 — 이벤트가 늘수록 7단계 판정이 흐려진다.
- 계측 도구는 **Supabase 자체 이벤트 테이블 기본** (고정 스택에 이미 있음 — 별도 analytics SaaS 없이 테이블에 적재, 퍼널 쿼리를 SQL로). 무거운 SaaS는 지양. **이벤트 테이블에도 다른 표와 똑같이 RLS를 건다 — 예외 없다.**
- **이벤트 정의는 코드에만 둔다** — 이벤트 테이블 스키마와 추적 코드가 정의의 SoT다. `backend-build.md`에 표로 옮겨 적지 않는다. 7단계 launch-plan은 **코드에서 직접 읽어** 퍼널을 짠다 (문서와 코드가 어긋나 이름이 달라지는 사고를 원천에서 막는다).

#### 2.5.1 에러 관측

퍼널 계측과 별개로 에러를 감지할 수단도 확보한다 — 최소 배포 후 Vercel 대시보드의 런타임 로그(Runtime Logs, 서버 실행 중 발생한 에러·로그를 모아 보여주는 화면)를 확인하는 방법을 알아둔다. 원하면 Sentry류 경량 에러 추적 도구를 붙여도 되지만 필수는 아니다. 7단계 측정 기간에 가입 실패·결제 에러 같은 버그가 조용히 나면 퍼널 숫자가 나쁜 게 제품 탓인지 버그 탓인지 구분을 못 해 판정이 오염된다 — "버그는 즉시 고친다"는 룰(7단계)이 있어도 버그가 났다는 걸 아는 수단이 없으면 소용없다.

### 2.6 배포·완료

**Vercel 함수 리전은 DB 리전에 맞춘다** — 기본값에 맡기지 말고 배포 설정에 직접 명시한다. 서버 함수가 DB에서 멀면 질의마다 대륙 왕복이 곱해진다. [실측 1건: 상세 페이지 첫 응답 566→188ms] 프로젝트별 구체 리전 값은 각 프로젝트 AGENTS.md에 적는다. **설정 키 이름과 기본 리전은 Vercel이 바꿀 수 있으니** 적기 전에 공식 문서로 지금 이름과 기본값을 확인한다 (작성 시점엔 `vercel.json`의 `regions`, 기본값은 미국 동부 `iad1`이었다).

성능 참고 하나 더 — **스켈레톤(skeleton — 본문이 오기 전 잠깐 보여주는 뼈대 화면)은 공짜가 아니다.** 페이지 안 `<Suspense fallback>`이든 라우트 `loading.tsx`든, 스켈레톤이 화면에 한번 그려지면 React가 깜빡임 방지용 공개 지연을 걸어서 **본문이 준비돼도 그 시간을 채울 때까지 안 보여준다.** (작성 시점 React 내부값은 300ms였다 — **공개된 설정이 아니라 라이브러리 내부 상수라 버전에 따라 바뀐다.** 숫자를 믿지 말고 아래처럼 실측한다.) 조회가 그보다 빠르면 스켈레톤 없이 다 기다렸다 한 번에 보내는 쪽이 오히려 빠르다. 어느 쪽이 이득인지는 실측으로 정한다. [실측 2건: 페이지 안 Suspense 제거로 클릭→본문 380ms→60ms / 라우트 `loading.tsx`가 남은 화면은 스켈레톤→본문 간격이 정확히 ~300ms] 단 `useSearchParams()`처럼 프레임워크가 Suspense를 강제하는 자리는 예외다. (강제 규칙이 아니라 참고 지식이다 — §2.2의 `loading.tsx` 404 함정과는 별개 축이니 거기 해법과 함께 판단한다.)

1. 최종 배포 (5단계에서 붙여둔 Vercel 그대로). main 직접 push 금지 — PR 워크플로 (repo 훅이 막음).
2. **사용자가 배포 URL을 브라우저로 직접 클릭** — 핵심 시나리오 끝까지 통과 + 가입·핵심행동 이벤트가 실제로 찍히는지 확인 (AI가 자동 도구로 검증·사인오프하지 않음 — SKILL.md §1.5 사람 몫).
3. 실결제 연동했으면 **실결제 테스트 1건** (결제 → 환불) — 사용자가 직접.
4. 발견된 문제는 초안 모드로 수정 → 재배포 → 재확인 (자율 재작업 상한 2회 — SKILL.md §1.5).

백엔드 연동·베타 공유·계측·배포가 모두 끝나면 7단계(MvpLaunch)로 넘어간다.

### 2.7 옛 단계 내용 가져오기 — SKILL.md §2.2 검토 절차 적용

이 단계 산출물에 옛 문서 내용을 근거로 가져올 땐 SKILL.md §2.2의 **확인 질문 4개**를 순서대로 거친다. 통과한 내용엔 표시 3종(**✅ 이번 단계에서 직접** / **🔵 옛 단계에서 가져옴** / **🟡 애매함**)을 붙이고, 4번(넓혀 말한 경우)으로 통과한 건 넓혀 말한 근거 한 줄 + 근거 위치를 함께 적는다. 2·3번에 걸린 내용은 가져오지 않고 문서 끝 `# 🟥 버린 내용 목록`에 한 줄씩 남긴다 (§4.1).

**단계 항목 × 옛 단계 표준 섹션 종류 매핑** — 옛 단계의 *섹션 종류(역할)* 기준이다:

| 이 단계 항목 | 가져오는 옛 단계 섹션 종류 | 비고 |
| --- | --- | --- |
| 화면 카피 조정 | `user-story.md`의 *입력 (확정)* — 서비스 한 줄 정의·로그라인 | 톤이 맞는지만 본다 |
| 빌드 스코프 판단 | `market-research.md`의 *조사 요약* | 참고 맥락 — 게이트 아님 |

**표시 판정 적용 예시**:

- **(가) `market-research.md` 조사 요약의 빈틈 정보를 빌드 스코프 근거로 가져올 때** — **5단계 앱 코드에 그 화면·기능이 실제로 있는지**부터 본다. 코드에 없으면 이 단계에서 만들지 않는다 — **🟥**로 버린 내용 목록에 남기고, 필요하면 `추후 결정:`으로 마킹한다. 코드에 있으면 **🔵**로 쓰고 근거 위치를 병기한다.
- **(나) `user-story.md`의 표현을 랜딩 화면 카피 근거로 넓혀 쓸 때** — 지금 앱 코드의 어느 화면이 그 내용을 품는지 짚을 수 있어야(확인 질문 4번) **🔵**로 쓰고, 못 짚으면 **🟡**로 두고 사용자에게 확인받는다.

## 3. 완료 체크리스트

다음이 모두 충족되어야 다음 단계(MvpLaunch)로 진입. **6단계 전체를 덮는 목록이라 앞선 하위 단계에서 한 일도 여기 다 들어 있다** — 재진입했으면 이 목록을 코드와 대조해 부족한 것부터 채운다.

- [ ] **백엔드·DB·auth 연동 완료** — 테이블·auth 생성, Supabase RLS 활성화·정책 확인 포함.
- [ ] **스키마가 마이그레이션 파일로 남아 있음** — 대시보드로 직접 만든 것도, 따로 만든 DB 설계 문서도 없음. 로컬 리셋(래퍼가 있으면 래퍼로) 통과 + **함수·트리거를 실제로 불러 확인**한 뒤 `db push`로 클라우드에 반영. 새로 만든 함수마다 실행 권한도 회수됨. **올린 뒤 클라우드에서 권한·storage·auth 관련이 실제로 걸렸는지 확인** — 함수 실행 권한이 진짜 걸렸는지, `storage.objects`에 정책이 만들어지는지, `auth.users`에 트리거가 걸리는지는 로컬로 확인이 안 되는 것들이다.
- [ ] **마이그레이션을 클라우드에 실제로 밀었음** — 마이그레이션이 든 PR을 머지했다고 자동으로 올라가지 않는다. `npx supabase db push --linked`를 따로 돌렸고, `npx supabase migration list --linked`에 안 올라간 게 없음. CI가 이걸 잡아주도록 깃허브 Secret 셋(`SUPABASE_ACCESS_TOKEN`·`SUPABASE_PROJECT_REF`·`SUPABASE_DB_PASSWORD`)도 넣어뒀음.
- [ ] **백업 상태 확인** — `npx supabase backups list --linked`로 확인. 자동 백업·시점 복구(PITR)가 꺼져 있으면 켜거나, `db dump`로 파일 백업을 정기적으로 남기는 방법을 정해뒀음.
- [ ] **로그인·동의 처리 완료** — 받는 정보를 필수/선택으로 갈랐음. 선택 정보를 받으면 인증 뒤 신규 가입자만 온보딩으로 보내 동의를 받고(필수·선택 체크박스 분리, 거부해도 가입 가능, 선택 칸 nullable), 필수만 받으면 고지문 한 줄. 약관·개인정보처리방침 페이지가 실제로 있고 로그인 화면 밖에서도 접근됨.
- [ ] **로컬스토리지 저장 경로 제거 확인** (§2.1) — 폴백으로도 남아 있지 않음.
- [ ] **5단계 앱 코드의 핵심 플로우(랜딩 → 가입 → 핵심행동)가 실제로 동작** (§2.1) — 로컬스토리지가 아니라 실 DB로 데이터가 흐름.
- [ ] **(추가 스택 있으면) ADR 기록** — 결제 PG 등 이 단계에서 새로 붙인 것만. 고정 스택 조합·버전은 5단계 기록 참조.
- [ ] **검색 노출 기본 세트 + curl 판정 통과** (§2.2) — 제목·설명·OG·sitemap/robots·404 상태코드. 5단계 색인 제외를 공개 페이지만 풀었고 비공개 화면은 계속 막힘. `curl`로 콘텐츠 문구가 잡힘.
- [ ] **스모크 테스트 기본 세트 통과** (§2.3) — 상태 코드·HTML 내용·링크·OG·robots/사이트맵·색인 제외·토큰 만료 시 공개 화면. 베타 공유(§2.4) 전에 갖춰 둔다.
- [ ] (해당 시) **베타 공유·치명 결함 확인** (§2.4) — 5단계에서 프로토타입을 같이 본 사람에게 실데이터 붙은 링크 공유, 가입 실패·데이터 유실·핵심 플로우 이탈·심각한 오해 없음(또는 발견분 수정·재공유 완료). **마땅한 사람이 없어 건너뛰었으면 그렇게 기록.**
- [ ] **퍼널 이벤트가 실제로 찍힘** (§2.5) — 기본 5종 + (승인받았으면) 서비스 전용 이벤트. 사용자가 직접 클릭해 발화 확인. 채널 구분 동작.
- [ ] **에러 로그 확인 수단 확보** (§2.5.1) — 최소 Vercel 런타임 로그 확인 방법 숙지.
- [ ] **(화면에 결제 흐름이 있으면) 실결제 1건 테스트 완료** (§2.6, 결제 → 환불).
- [ ] **공개 URL 접속 가능** (§2.6) — 배포 완료, 핵심 시나리오가 실데이터로 끝까지 돈다.
- [ ] **`backend-build.md` 작성됨** (§4) — 스택 추가분·베타 공유 관찰(해당 시)·배포 정보·추후 결정·빌드 중 발견. **스키마 표·이벤트 정의·화면 구현 현황 같은 코드 서술은 안 적혀 있음.**
- [ ] **옛 단계에서 가져온 내용에 표시가 붙음** (§2.7) — 확인 질문 4개를 거쳐 🔵(또는 ✅·🟡)를 달았고, 걸러진 내용은 문서 끝 🟥 버린 내용 목록에 기록됨.
- [ ] (사용자 검증) **사람이 브라우저로 배포물 클릭 검토 완료** (§2.6) — 광고 유입 랜딩 경로(랜딩→가입→핵심행동)는 모바일 화면에서도 확인.

### 3.1 다음 단계 핸드오프

## 4. 산출물 스펙

위치: **앱 코드**(프로젝트 루트, 5단계에서 이어짐) + 프로젝트 루트의 `mvp/backend-build.md`

### 4.1 `backend-build.md` 템플릿

```markdown
---
name: backend-build
created_at: YYYY-MM-DD
updated_at: YYYY-MM-DD
status: draft | confirmed
---

# 스택
- 기본 조합·핀한 버전은 5단계에서 확정 — 여기 다시 적지 않는다 (5단계 ADR 링크만).
- 이번 단계에서 추가한 것만: {예: 결제 PG(토스페이먼츠) — 사유 한 줄 + ADR 번호 링크}
- (추가 없으면) 5단계 조합 그대로.

# 베타 공유 관찰

_해당 시에만. 5단계에서 프로토타입을 같이 본 사람이 없어 건너뛰었으면 "건너뜀 — 대상 없음" 한 줄._

- 공유 대상: {누구에게 — 인원·경로}
- 관찰: {실제 가입 여부·핵심 플로우 이탈 지점·오해 포인트 등 — 없으면 "치명 결함 없음"}
- 조치: {발견분 수정·재공유 이력, 없으면 "조치 없음"}

# 배포 정보
- URL: ...
- 배포 방식: (예: main merge → 자동 deploy)

# 추후 결정
- [빌드 중 마킹한 항목들]

# 빌드 중 발견 (7단계 MvpLaunch·production 입력)
- [명세 모순·개선 아이디어 — 화면을 역방향으로 갈아엎지 않고 여기 기록]

# 🟥 버린 내용 목록

_확인 질문 2·3번에 걸려 가져오지 않은 옛 내용 (§2.7). 없으면 "없음" 한 줄._

- {옛 내용 한 줄} — 출처: {옛 문서 §섹션} / 사유: {확인 질문 2 또는 3}
```

### 4.2 frontmatter 규칙

- `name`: `backend-build`
- `created_at` / `updated_at`: ISO 날짜
- `status`: `draft` (연동 중) → `confirmed` (백엔드 연동·계측·배포 완료)
- 스택 필드는 두지 않는다 — 스택은 5단계에서 확정되므로 여기 frontmatter의 몫이 아니다. 이 단계에서 추가한 것만 본문 `# 스택`에 적는다.

## 5. 사용자 응대 톤 + 코칭

- **톤**: SKILL.md §1.3대로 반말·친근·짧게.
- **진입 안내**: "지금 앱은 데이터가 네 브라우저 안에만 쌓여서 다른 기기로 열면 텅 비어 있어. 이제 진짜 DB랑 로그인 붙여서 실서비스로 만들 차례야 — 백엔드 붙이고, 퍼널 계측 심어서 배포 완주할게. 만드는 기준은 지금 화면 그대로야 — 화면에 있는 걸 진짜로 돌게 만들고, 화면에 없는 건 안 만들어. 스택도 5단계에서 이미 정해놔서 새로 고를 건 없어."
- **빌드 중**: 잘게 확인 요청 금지 (초안 모드). 에스컬레이션 기준 해당 시에만 멈추고 배치로 질문.
- **베타 공유 안내**: "이번엔 진짜 데이터가 도는 링크야 — 프로토타입 같이 봐준 사람들한테 보내서 실제로 가입하고 쓰는지 보자. 판정이 아니라 치명적인 거 있는지 확인이야. 보낼 사람 없으면 건너뛰어도 돼."
- **화면 구조를 다시 뒤집자는 요청**: 코드를 고치는 건 이 단계에서도 정상이다 — 백엔드 붙이며 화면이 조금씩 바뀌는 건 당연. 다만 **화면이 늘거나 빠지는 구조 변경**이면 5단계로 돌아가 프로토타입을 고친 뒤 다시 오는 게 순서라고 짚는다. 화면 절반을 새로 짜는 수준이면 그건 피봇이라 4단계 재실행으로 다루고(SKILL.md §2.2 — 인벤토리는 1세대 기록이라 갱신하지 않는다), 급하지 않으면 7단계(MvpLaunch) 이후 production으로 넘기자고 안내한다.
- **범위 압박 대응**: 사용자가 "이 기능도 넣자" 하면 — **5단계 앱 코드에 그 화면이 있는지**부터 짚고, 없으면 핵심 플로우(랜딩→가입→핵심행동)에 꼭 필요한지 확인. 필요 없으면 "런치 검증(7단계) 끝나고 production에서" 권유 (강제는 아님 — 사용자가 원하면 명세 먼저 갱신 후 빌드).
- **완료 시**: 배포 URL + "핵심 시나리오대로 클릭해봐 + 이벤트 찍히는 것도 같이 확인하자" + 체크리스트 현황.
- **배포·클릭 검증 안내**: "배포까진 내가 하는데, 실제로 눌러보고 확인하는 건 네 몫이야 — 자동 검증 도구로 대신 사인오프 안 해" (SKILL.md §1.5 사람 몫).
