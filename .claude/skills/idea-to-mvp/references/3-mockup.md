## 1. 단계 목표

이 단계의 목표는 **2단계에서 만든 `information-architecture.md`와 `user-story.md`를 함께 외부 Claude Design에 입력해 전체 화면 플로우의 standalone HTML(외부 파일 참조 없이 폰트·이미지·컴포넌트 소스까지 전부 내장된 자급자족 단일 파일) 목업을 만드는 것**이다. 산출물은 **프로젝트 루트**의 `[projectName]-proto.html` 하나(projectName = 프로젝트 폴더명, 항상 최신본 하나) — 이 목업이 4단계(DemoValidation) 데모 인터뷰의 도구이자 화면 영역의 SoT(Source of Truth — 진실의 원천) 시작점이다. 개발에 넘길 문서 꾸러미(`mvp/handoff/`)는 **첫 요청부터 목업과 함께** 같은 대화에서 받는다 — 목업을 재생성할 땐 꾸러미도 같이 갱신해서 둘이 항상 같은 세대이게 한다. 동결 시점의 최종 꾸러미가 6단계(MvpBuild)가 참고로 읽는 보조 입력이 된다 (§2.5).

입력이 두 개인 이유는 **맡은 역할이 다르기 때문**이다:

- **`information-architecture.md` — 완전성 담당.** 어떤 화면을 몇 개 만들지, 빈 상태·오류 같은 상태 변형까지 무엇을 빠뜨리지 않을지가 여기서 나온다. 화면 인벤토리 표가 만들 것의 전체 목록이다.
- **`user-story.md` — 정서·톤·마이크로카피 담당.** 화면에 들어갈 말투, 버튼 문구, 어느 장면에 힘을 줄지가 여기서 나온다.

둘 중 하나만 넣으면 안 된다. 인벤토리만 넣으면 빠진 화면은 없는데 말투가 밋밋해지고, 유저 스토리만 넣으면 감은 좋은데 화면이 통째로 빠진다.

**AI는 안내·프롬프트 준비까지만 한다** — Claude Design 실행과 결과물 저장은 사용자 몫이다. Claude Design은 이 스킬 바깥의 외부 도구라 AI가 대신 호출·실행할 수 없다. 목표를 이뤘는지는 §3 완료 체크리스트로 판정한다.

## 2. 진행 절차

### 2.1 단계 시작 — 이전 정리 내용을 보여주고, 이번 단계가 할 일을 안내한다

이전 단계(InformationArchitecture)가 남긴 산출물이 있다. `mvp/information-architecture.md`를 읽고 이걸 짧게 요약해 보여주는 것으로 시작한다:

- **만들 화면 개수** — 인벤토리 표에서 `MVP 포함 = O`인 화면이 몇 개인지 (전체 몇 개 중 몇 개인지 같이).
- **커버리지 자가 점검 결과** — 고아 화면(진입 경로 0개)·막다른 골목(이탈 경로 0개)이 0건인지, 일곱 갈래 점검에서 X가 남아 있는지.

여기서 X나 0건이 아닌 항목이 보이면 목업부터 만들지 말고 **2단계로 잠깐 돌아가 인벤토리를 먼저 채우자고** 안내한다. 인벤토리가 곧 만들 화면 목록이라, 표에 없는 화면은 목업에도 안 생긴다.

이어서 `mvp/user-story.md`의 **로그라인**(logline — 서비스의 정서를 담은 한 줄 요약)도 한 줄 보여준다 — 이번 목업의 말투 기준이다.

그다음 **화면 인벤토리를 그대로 화면으로 옮기는 단계**라는 걸 설명한다.

설명 골자 — 그대로 또는 풀어서 전달:

> 2단계에서 만든 화면 인벤토리가 이번에 만들 화면의 전체 목록이야. 유저 스토리만 보고 바로 목업을 만들면 시나리오 주인공이 겪는 성공 경로만 그려져서, 빈 상태·오류 화면·반대편 역할 화면이 통째로 빠져. 그래서 2단계에서 표로 한번 훑고 온 거고, 이번 단계는 그 표를 화면으로 옮기는 자리야. 인벤토리는 "무엇을 빠짐없이", 유저 스토리는 "어떤 말투로"를 맡는다고 보면 돼. 화면 명세를 문서로 두껍게 쓰는 게 아니라 표 하나로 끝내는 이유는, AI 빌더 시대엔 목업 만드는 게 몇 분짜리 작업이라 두꺼운 설계서를 따로 유지하는 게 이중 비용이기 때문이야.

이미 프로젝트 루트에 `[projectName]-proto.html`이 있으면(스킬 중간 재실행 등) §3 체크리스트로 검증해 부족한 부분만 보완하도록 안내한다 — 처음부터 다시 만들지 않는다.

### 2.2 Claude Design 안내

목업 제작은 사용자가 외부 [Claude Design](https://support.claude.com/en/articles/14604416-get-started-with-claude-design)에서 직접 진행한다. AI(여기)는 그 호출에 들고 갈 것을 준비해 안내하는 것까지만 한다.

**① 모드 선택**

유저 스토리의 플랫폼 맥락과 인벤토리의 네비게이션 구조(탭·스택·모달)를 보고 고른다:
- 모바일 앱이 중심이면 → **Mobile app design**
- 웹이 중심이면 → **UI mockups**
- 애매하면 사용자에게 확인.

(참고: 4단계 데모 검증 단계에선 링크 하나로 공유되는 웹 쪽이 공유 마찰이 적다.)

**② 입력 — 파일 두 개를 첨부**

`mvp/information-architecture.md`와 `mvp/user-story.md` **파일 두 개를 Claude Design 대화창에 그대로 끌어다 놓는다**(첨부). 본문을 복사해 붙여넣는 방식은 쓰지 않는다 — 인벤토리 표가 길어서 붙여넣다 잘리기 쉽고, 잘린 만큼 화면이 빠진다. 요약해서 넣는 건 더 안 된다.

첨부가 안 되는 상황이면 그때만 두 문서 **전문**을 통째로 붙여넣되, 인벤토리 표와 상태 매트릭스가 끝까지 다 들어갔는지 확인한다.

**③ 권장 프롬프트**

두 파일을 첨부한 뒤 아래를 그대로 붙여넣는다. 목업과 개발 인계 꾸러미(프롬프트에선 "핸드오프 패키지"라고 부른다)를 **한 번에** 요청하는 프롬프트다 — 왜 같이 받는지는 §2.5.

```
첨부한 파일 두 개가 입력이야 — information-architecture.md(만들 화면 목록)와 user-story.md(문구·말투의 원천).

인벤토리에서 MVP 포함 = O인 화면만 ID 순서대로 하나도 빠짐없이 만들어줘.
상태 매트릭스에 표시된 상태 변형(빈 상태·오류 등)도 함께 만들어줘.
화면 속 모든 문구(버튼 이름·안내문·빈 화면 문구)는 네가 짓지 말고 user-story.md에 있는 표현을 그대로 써줘.
인벤토리에 없는 화면은 만들지 말고, MVP 포함 = X인 화면으로 이동하는 버튼도 그리지 마 — 눌러도 갈 곳이 없는 죽은 버튼이 된다. 어느 버튼인지는 인벤토리의 "미룬 화면을 가리키는 버튼" 표에 있어.
반응형 웹으로 — 데스크톱 폭 기본, 모바일 폭으로 줄여도 배치가 깨지지 않게.

목업 자체는 백엔드 없이 동작하는 프로토타입이면 돼 (가짜 데이터로 화면 전환·인터랙션이 돌아가는 수준).

완성되면 개발 인계용 핸드오프 패키지로 내보내줘:
1. README — 제품 정의, 핵심 규칙, 우선순위(P0 흐름)
2. data-model — 엔티티/필드/상태 전이. 나중에 Supabase(Postgres)에 옮길 것을 감안한 구조로
3. rules — 핵심 규칙·산정식을 의사코드로
4. screens — 화면별 상태, 빈 상태, 에러 문구(마이크로카피 그대로)
5. design-tokens — 색·타이포·간격·라운드를 CSS 변수로 추출
6. 목업 파일 자체 — standalone.html(외부 참조 없이 전부 내장된 단일 파일)

없는 규칙을 지어내지 말고, 목업에 실제로 들어간 것만 정리해줘. 백엔드 연동은 나중에 Claude Code가 이 패키지를 받아 Next.js·Supabase로 구현할 거야.
```

- **반응형 줄은 웹 모드에서만** — "반응형 웹으로 — ..." 줄은 ①에서 웹(UI mockups)을 고른 경우에만 넣는다. 모바일 앱(Mobile app design)은 폭이 하나로 고정이라 해당 없으니 그 줄은 빼고 붙여넣는다. 반대로 웹인데 이 줄을 빼면 데스크톱 폭에만 맞는 화면이 나오기 쉽고, 4단계 데모를 폰으로 보여주거나 6단계에서 광고 유입(대부분 모바일)을 받을 때 그대로 깨진다.
- **프로젝트 얘기를 프롬프트에 덧붙이지 않는다** — 무엇을 만들지는 첨부한 두 파일이 다 말해 준다. 여기에 화면 설명을 덧대면 파일과 어긋난 지시가 섞인다.

**④ 결과물 받기 — 목업 + 문서 다섯 개**

Claude Design이 완성하면 목업 파일과 문서 1~5번을 **같이** 받는다:

- 목업은 **standalone.html** 하나로 다운로드한다 — 여러 파일로 쪼개진 산출물(컴포넌트 폴더 등)은 받지 않는다.
- 문서는 README·data-model·rules·screens·design-tokens 다섯 개. 목업만 챙기고 문서를 건너뛰지 않는다 — 이 둘은 항상 같은 세대로 붙어 다닌다 (§2.5).

**역할 분담** — Claude Design이 만들어 주는 건 프런트엔드와 가짜 데이터로 도는 프로토타입까지다. 진짜 백엔드(DB·로그인·서버)는 못 만든다. 프롬프트에 Supabase·Next.js 같은 스택 이름이 나오는 건 **문서(data-model 등)를 나중 구현에 맞는 모양으로 정리시키려는 것**이지, 목업을 Next.js 앱으로 만들라는 뜻이 아니다. 실제 구현은 6단계에서 Claude Code가 이 꾸러미를 받아서 한다.

### 2.3 저장 규칙

받은 결과물은 두 군데로 나눠 저장한다.

- **목업(standalone.html)** → **프로젝트 루트**에 `[projectName]-proto.html`로 저장 (`projectName`은 이 저장소 최상위 폴더 이름 그대로).
- **문서 1~5번** → **`mvp/handoff/` 폴더**에 받은 이름 그대로 저장 (`README.md`·`data-model.md`·`rules.md`·`screens.md`·`design-tokens.css` 등).
- **6번(목업 파일 자체)은 `mvp/handoff/`에 또 넣지 않는다** — 루트의 `[projectName]-proto.html`이 이미 그 역할이다. 같은 파일을 두 군데 두면 어느 쪽이 최신인지 따지는 비용만 생긴다.

둘 다 **버전 폴더 없이 같은 이름으로 덮어쓴다** — zip 압축 해제·별도 README를 만들지 않고 항상 최신 하나만 존재한다.

### 2.4 순환 갱신 (4단계에서 복귀 시)

4단계(DemoValidation)의 데모 인터뷰에서 **구조적 수정사항**(플로우·화면 구성·핵심 기능이 바뀌어야 하는 피드백)이 나오면 이 단계로 되돌아온다. 절차:

1. **`mvp/information-architecture.md`를 먼저 고친다.** 화면이 늘거나 줄거나 순서가 바뀌면 인벤토리 표(ID·진입 경로·이탈 경로)와 상태 매트릭스·네비게이션 구조를 그에 맞게 갱신한다. **문서가 먼저, 목업이 나중이다** — 목업만 고치면 인벤토리와 어긋나서 다음 라운드에 또 화면이 빠진다.
2. AI가 갱신된 인벤토리를 기준으로 **Claude Design용 반영 프롬프트**를 정리한다 — 무엇을 어떻게 바꿔야 하는지 **화면 ID로** 구체적으로 (예: "S-04(카드 정보 입력)를 온보딩에서 빼고 S-03 다음에 바로 S-05로 넘어가게 해줘 — 이유: 인터뷰이 다수가 그 화면에서 이탈"). **꾸러미도 같이 갱신해 달라는 요청을 같은 프롬프트에 넣는다** (예: "바뀐 내용에 맞춰 핸드오프 패키지도 같이 업데이트해줘").
3. 사용자가 그 프롬프트로 Claude Design을 재호출해 목업과 꾸러미를 함께 재생성한다.
4. 받은 standalone.html을 같은 파일명(`[projectName]-proto.html`)으로 교체하고, 갱신된 문서 1~5번도 `mvp/handoff/`에 같은 이름으로 덮어쓴다.
5. 갱신된 인벤토리와 새 목업을 다시 ID로 대조한다(§3 체크리스트).
6. 4단계로 복귀해 다음 라운드 데모를 진행한다.

**목업만 새로 받고 꾸러미를 두면 안 된다** — 옛 규칙 문서가 새 화면과 어긋난 채 남는다. 목업과 꾸러미는 항상 같은 세대여야 한다.

4단계가 **수렴**(구조적 수정 0건 — 4-demo-validation.md §2.8) 판정을 내리면 이 파일을 **동결**한다 — 이후 더 이상 재생성하지 않는다. 동결된 이 파일이 6단계(MvpBuild)의 정답지가 되고, 그 시점에 손에 있는 꾸러미가 그대로 최종 꾸러미가 된다 (매 순환마다 같이 갱신해 왔으니 따로 다시 받을 게 없다).

### 2.5 개발 인계 꾸러미 — 왜 목업과 같이 받나

목업은 그림이라 **왜 그렇게 생겼는지**는 못 담는다. 어떤 조건에서 다음 화면으로 넘어가는지, 타이머가 몇 초인지, 점수를 어떤 식으로 계산하는지 같은 규칙은 화면을 아무리 들여다봐도 안 읽힌다. 그래서 목업을 만든 **같은 Claude Design 대화에서** 개발에 넘길 문서 꾸러미(§2.2③ 프롬프트의 "핸드오프 패키지")를 함께 받는다.

같은 대화인 게 핵심이다 — 그 대화엔 인벤토리·유저 스토리·방금 만든 화면의 맥락이 이미 다 있다. 대화를 새로 열고 다시 설명하면 목업과 어긋난 문서가 나온다.

**언제 — 첫 요청부터 목업과 함께.** §2.2③ 프롬프트가 목업과 꾸러미를 한 번에 요청하게 돼 있어서 나중에 따로 이어 물을 게 없다. 3↔4 순환에서 목업을 재생성할 때도 **같은 대화에서 꾸러미를 같이 갱신한다**(§2.4). 미루지 않는 이유는 두 가지다: (1) 목업만 바뀌고 문서는 옛 세대로 남기 쉽고, (2) 라운드를 여러 번 돈 뒤에 몰아 받으면 무엇이 왜 그렇게 정해졌는지가 그 대화 안에서도 이미 흐려진 뒤다. 매번 같이 갱신하면 동결 시점에 손에 있는 꾸러미가 곧 6단계로 넘길 최종본이다.

Claude Design이 "개발 스택 정해진 게 있나요?"라고 되물으면 다섯 가지(Next.js·React·TypeScript·Supabase·Vercel)를 그대로 알려준다 — 하네스 고정 스택이라 여기서 다시 고를 게 없다 (6-mvp-build.md §2.2.1).

**용도와 경계 (중요)**

- **용도**: 6단계(MvpBuild)의 입력 — 동결된 목업(정답지)과 **함께** 참조한다. 목업이 못 담는 규칙·수치·상태 전이가 여기 적혀 있어서 구현할 때 추측할 일이 줄어든다.
- **경계**: 화면 영역의 SoT는 **여전히 목업 → 코드 승격 체계 그대로**다 (SKILL.md §2.2). 꾸러미는 참고 자료(보조 입력)지 SoT가 아니다. **꾸러미와 동결된 목업이 어긋나면 목업이 기준**이고, 꾸러미 쪽을 고치거나 무시한다 — 반대로 하면 검증받은 화면이 아니라 문서가 진실 행세를 하게 된다.

## 4. 산출물 스펙

위치: **프로젝트 루트**의 `[projectName]-proto.html` 파일 하나 + `mvp/handoff/` 폴더.

**① 목업 (본 산출물)**

- **파일명**: `[projectName]-proto.html` (`projectName` = 프로젝트 폴더명)
- **형태**: standalone.html — 폰트·이미지·컴포넌트 소스까지 전부 내장된 자급자족 단일 파일
- **버전 없음, 항상 최신 하나** — 버전 폴더·zip 압축 해제·README 없음
- **동결 시점**: 4단계가 수렴 판정을 내릴 때까지는 반복 갱신(같은 이름 덮어쓰기) 대상. 수렴 후엔 동결 — 6단계(MvpBuild)의 정답지로 넘어간다.

**② 개발 인계 꾸러미 (§2.5, 목업과 항상 같은 세대)**

- **위치**: `mvp/handoff/` — 받은 파일 이름 그대로 (`README.md`·`data-model.md`·`rules.md`·`screens.md`·`design-tokens.css` 등)
- **받는 시점**: 첫 목업부터 같은 대화에서 함께. 목업을 재생성할 때마다 같이 갱신하고, 동결 시점의 꾸러미가 6단계로 넘어간다.
- **버전 폴더 없음, 같은 이름으로 덮어쓰기** — 항상 최신 하나
- **목업 파일은 여기 중복 저장하지 않는다** — 루트의 `[projectName]-proto.html`이 그 역할
- **성격**: 6단계(MvpBuild)의 **참고 입력**. 화면 SoT는 목업(→코드)이고 꾸러미는 보조 — 어긋나면 목업이 기준.

## 5. 사용자 응대 톤

- **톤**: SKILL.md §1.3 따름 — 반말·친근·짧게.
- **AI는 Claude Design을 대신 실행하지 않는다** — 프롬프트 준비·결과 저장 안내까지만. 사용자가 "네가 대신 만들어줘" 하면 외부 도구라 AI가 못 들어간다는 걸 짚어준다.
- **목업 품질 불만**: "화면이 별로다", "이상하게 나왔다" 하면 다시 만들어달라고만 던지지 말고, §2.2③ 프롬프트를 더 구체화(빠진 화면 ID·상태 변형 짚기)해서 재생성하자고 안내한다.
- **모드 선택 애매**: 억지로 정하지 말고 사용자에게 확인.
- **화면이 너무 많다고 할 때**: 인벤토리에서 임의로 화면을 빼지 말고, 2단계로 돌아가 `MVP 포함` 칸을 다시 정하자고 안내한다 — 목록에서 지우는 게 아니라 이번엔 안 만든다고 표시하는 거다.
- **꾸러미는 나중에 몰아 받자고 할 때**: 목업만 먼저 받고 문서는 마지막에 받자고 하면, 그 대화 맥락이 살아 있을 때 같이 받는 게 싸고 정확하다고 짚어준다 (§2.5). 그래도 미루겠다면 말리진 말되, 목업을 재생성할 때마다 꾸러미도 같은 세대로 맞춰야 한다는 것만 알린다.
- **백엔드까지 만들어 달라고 할 때**: Claude Design은 가짜 데이터로 도는 프런트엔드까지가 한계라고 짚고, 진짜 DB·로그인은 6단계에서 이 꾸러미를 받아 붙인다고 안내한다 (§2.2④).
- **순환 중 재요청**: 4단계에서 돌아온 경우 §2.4 절차대로 인벤토리 갱신부터 하고 반영 프롬프트를 정리해 주고, 사용자가 그 프롬프트로 재호출하도록 안내한다 — AI가 임의로 목업 내용을 지어내지 않는다.
