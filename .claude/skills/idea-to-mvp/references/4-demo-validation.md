## 1. 단계 목표

이 단계의 목표는 **프로토타입(3단계 산출물)을 들고 하는 데모 인터뷰로 painkiller 신호와 Pull 신호(데모를 본 사람이 자발적으로 "써보고 싶다"고 끌려오는 반응)를 검증하고, 피드백이 구조적이면 3단계 코드에 반영하는 순환을 수렴까지 돌린 뒤, 빌드 단계(6단계 MvpBuild)에 들어갈 자격을 판정하는 것**이다 — 통과 기준①. 산출물은 `demo-validation.md` 한 파일: 인터뷰 질문지·라운드별 데모 노트, 진입 평가(3항목), go 판정 시 `# 최종 확정 아이디어`(+비목표·검증 가설·북극성)까지 담는다 (형식은 §4.1). 목표를 이뤘는지는 §3 완료 체크리스트로 판정한다.

## 2. 진행 절차

### 2.1 단계 시작 — 이전 정리 내용을 보여주고, 이번 단계가 할 일을 안내한다

이 단계부터는 이전 단계(Prototype)가 남긴 산출물이 있다. `mvp/user-story.md`의 **로그라인**(logline — 서비스의 정서를 담은 한 줄 요약)과 **확정 입력 4개**(§2.2에서 도출에 쓸 것)를 짧게 요약해 보여주고, 3단계가 Vercel에 배포한 **리액트 프로토타입 링크**가 준비돼 있음을 확인하는 것으로 시작한다. 이 프로토타입은 로컬스토리지(브라우저에 데이터를 저장하는 방식)로 실제 데이터가 저장·조회되는 워킹 앱이다 — standalone.html 목업 파일은 `mvp/handoff/` 안에만 있고 인터뷰이에게 직접 보여주는 대상이 아니다.

이미 `demo-validation.md`가 있으면(스킬 중간 재실행 등) 읽고 §3 체크리스트로 검증해 부족한 부분만 보완한다.

**마이그레이션 — 옛 `idea-validation.md`가 있는 프로젝트라면**: 그 파일의 질문지·정찰 결과·운영자 모드·인터뷰 노트를 이 단계의 출발점으로 그대로 흡수한다(처음부터 다시 만들지 않는다). 흡수한 뒤 옛 파일 끝에 포인터 한 줄을 남긴다: `→ YYYY-MM-DD 이후 데모 검증 내용은 demo-validation.md 참조`.

**폴백 — `user-story.md`가 없으면**: 강행 진입(SKILL.md §4)으로 1단계를 건너뛴 경우다. "이전 정리 보여주기"는 생략하고, §2.2는 자유 형식 직접 입력(폴백 절차)으로 진행한다.

> **진통제(painkiller) 신호** = 머리 아플 때 약국으로 뛰어가는 그 약처럼, _사람들이 지금 당장_ 풀고 싶어하는 문제라는 증거. 반대말은 비타민(있으면 좋고 없어도 사는 것). _이 단계 전체의 핵심 검증 대상 중 하나._

설명 골자 — 아이디어 도출(§2.2) 전에 사용자에게 그대로 또는 풀어서 전달:

> 아이디어를 본격 만들기 시작하면 경쟁자 조사·실개발 같은 *비싼 작업*이 줄줄이 따라온다. 그 작업 다 끝낸 뒤에야 "사람들이 이 문제 별로 안 아파해요"라는 걸 알게 되면 그 비용 전부 매몰비용 — 회수 못 함.
>
> 다행히 리액트 프로토타입은 이미 만들어놨고, AI 빌더 시대엔 이 정도 워킹 프로토타입 만드는 비용도 예전보다 훨씬 낮아졌어. 그러니 이 단계는 *빈손 인터뷰*로 거르는 대신, **프로토타입을 들고 보여주고 반응으로 거른다.** YC 파트너들이 입에 달고 사는 한마디는 여전히 유효해:
>
> > _"Talk to N users first. If they're not already hacking around the problem, **don't even bother building**."_
> >
> > (먼저 사용자 몇 명과 직접 이야기해봐. 사람들이 이미 _임시방편으로 해결하고 있지 않다면_ **만들 생각도 하지 마**.)
>
> 이미 사람들이 _지금 임시방편을 만들어 쓰고 있는지_(1부 맘 테스트)와, 프로토타입을 보여줬을 때 _자발적으로 끌리는지_(2부 데모)를 함께 본다. 둘 다 확인돼야 빌드(6단계 MvpBuild) 진입 자격.
>
> 인터뷰 수는 아이디어 출처에 따라 다르게 권장 — 자세한 표는 §2.5.

### 2.2 아이디어 도출 — user-story.md에서

**먼저 사용자에게 자유 형식으로 묻지 않는다.** `user-story.md`가 있으면 AI가 그 문서의 `# 입력 (확정)` 섹션(①서비스 이름과 한 줄 정의 ②타겟 ③현재의 대안과 불편함(문제) ④해결책의 핵심 아이디어)에서 아래 형식의 아이디어 한두 문장을 **도출**한다:

```
예시 형식 (참고용, 강제 X):
- "[누구]가 [상황]에서 [문제] 겪는 걸 [어떻게] 풀어준다"
- 예: "팀 회의를 자주 하는 직장인은 회의에서 정한 걸 나중에 정리하기 어려워서 결정사항·할 일을 놓치는 경우가 있다. 회의 녹음을 넣으면 결정사항·할 일을 자동 정리해주는 기능으로 빠뜨림 없이 정리하도록 도와준다"
```

도출한 한두 문장을 사용자에게 보여주고 **확인·수정**을 받는다 (본질 보존 — SKILL.md §1.4). 사용자가 손볼 부분이 있으면 반영해 재확인. 확정본을 산출물 `# 아이디어`로 보존 — 이후 AI가 인터뷰 질문지 만들 때 이 문구를 토대로 도메인·페르소나·문제 영역을 끌어낸다.

**솔루션 부분이 자세해도 OK** — 어차피 1부 인터뷰에선 솔루션·프로토타입 _언급 안 함_ (맘 테스트 원칙). 다만 *어떤 문제를 푸는지*가 모호하면 AI가 좋은 질문을 못 만든다 — 모호하면 AI가 한 번 더 되묻는다.

**폴백 — `user-story.md`가 없으면**(강행 진입 — SKILL.md §4): 도출할 원천이 없으니 기존처럼 자유 형식으로 직접 받는다.

```
이 아이디어 한두 문장으로 뭐야? — 누구의 어떤 문제를 어떻게 푸는 거?

예시 형식 (참고용, 강제 X):
- "[누구]가 [상황]에서 [문제] 겪는 걸 [어떻게] 풀어준다"
- 예: "팀 회의를 자주 하는 직장인은 회의에서 정한 걸 나중에 정리하기 어려워서 결정사항·할 일을 놓치는 경우가 있다. 회의 녹음을 넣으면 결정사항·할 일을 자동 정리해주는 기능으로 빠뜨림 없이 정리하도록 도와준다"
```

### 2.3 조사 결과는 아직 없다 — 정찰은 5단계(MarketResearch)

구현사례 정찰(경쟁자·빈틈 조사, prior-art recon)은 **5단계(MarketResearch)에서 한다** — 이 단계 시점엔 조사 결과가 **아직 없는 게 정상**이다. 순서를 이렇게 둔 이유는 단순하다: 인터뷰·데모로 아이디어 방향이 뒤집히는 일이 흔한데, 뒤집히기 전에 해둔 조사는 통째로 버려진다. 그래서 방향이 굳은 뒤(이 단계 go 판정) 확정된 아이디어를 들고 조사한다.

그러니 이 단계 질문지(§2.6)는 **경쟁자 정보 없이** 만든다 — 재료는 아이디어 한두 문장(§2.2)·타겟·출처(§2.5)다. 경쟁자 목록이 없다고 질문이 무뎌지지 않는다: 1부 맘 테스트는 원래 *그 사람이 지금 어떻게 때우고 있는지*를 캐는 자리라, 캐는 대상이 남의 서비스가 아니라 눈앞의 사람이다.

- **`mvp/market-research.md`가 없는 게 기본**이다 — 없다고 이 단계를 미루거나 조사부터 하러 가지 않는다.
- **예외적으로 파일이 있으면**(옛 순서로 진행하던 프로젝트, 사용자가 미리 조사해둔 경우) 읽고 경쟁자의 공개 불만·빈틈을 질문지에 반영해도 좋다 — 있으면 보너스, 없으면 그만.
- **사용자가 "경쟁자부터 조사하자"고 하면**: 지금은 인터뷰가 먼저고 조사는 5단계라고 짚어준다. 그래도 미리 보고 싶어하면 말리지 않되, 그것 때문에 이 단계 인터뷰를 미루지는 말자고 안내한다.

> **인터뷰로만 잡히는 신호**: 나중에 5단계 정찰이 보는 건 §2.7.2 강도표 기준 **★★(기존 열등 대체재 반복 사용 — 제품·리뷰·불만글)**까지다. **★★★(자기가 만든 사적 임시방편 — 엑셀·반복 문의)**는 검색에 안 잡혀 *이 단계 인터뷰에서만* 발굴된다. 조사를 뒤로 미뤄도 잃는 게 없는 건 이 때문이다 — 제일 중요한 신호는 애초에 검색으로 안 나온다.

### 2.4 운영자 맥락 받기 — 모드·동기

아이디어 받고 출처 분류(§2.5) 전에 **운영자 위치·동기**를 한 줄로 받는다. 이 정보는 _단계의 목표·기조_(진통제 검증·인터뷰·평가)는 그대로 두고, *AI가 사용자에게 답하는 방식*만 사용자 상황(시간 여유·매출 압박·동기)에 맞춰 조정하는 데 쓴다. 구체적으로 네 가지:

- **응답 톤** — 압박 강도·진지함의 수준 (풀타임 창업이면 매출 압박을 강하게, 사이드·취미면 가볍게)
- **인터뷰 대상수 권장값** — 몇 명 만나라는 기준 (풀타임이면 권장값 그대로, 사이드면 권장값/2까지 OK)
- **만들 범위 추천** — 작은 기능 조각 vs 통합 솔루션 (사이드라면 1년 운영 가능한 작은 조각으로 좁힘)
- **다음 갈래(go / 인터뷰 더 / 아이템 폐기) 추천 기준** — 어느 결과에서 폐기를 권장할지의 frame

받을 두 가지:

- **모드** (위치): 풀타임 창업자 / 직장 다니며 사이드(장인) / 학생 / 부업·취미 / 기타
- **동기** (목적): 매출 / 즐거움·학습 / 포트폴리오 / 자기 dogfooding / 미정

받은 답은 산출물 frontmatter `operator_mode` / `operator_motivation` 필드에 보존 (§4.2). 이 단계 이후 모든 응답은 이 값을 frame으로 참조한다.

frame 조정 방향(시간 압박·대상수 권장·스코프 등)은 §6.1 모드·동기별 frame 표 참조. 응답 시 모드를 frame으로 명시한다 — 예: "장인 모드라 빌더 통째론 3년+ 걸리니 기능 단위로 좁히자".

### 2.5 아이디어 출처 분류 + 인터뷰 대상수 권장

아이디어 출처를 분류한다 — 위험 정도에 따라 인터뷰 강도가 달라진다. 출처는 1단계 입력 4개에 없으므로, 실제로 쓰이는 이 자리에서 사용자에게 직접 묻는다:

```
이 아이디어 어디서 나왔어?
- 자기 경험 — 본인이 그 문제를 겪고 있음 / 겪었음
- 지인 관찰 — 가까운 사람한테서 직접 들음 / 봄
- 사회적 발견 — 언론·책·통계·데이터에서 봄 (당사자 직접 만난 적 X)
- 순수 추정 — 머릿속 상상, 당사자도 안 만났고 데이터도 거의 없음
```

복합 출처 가능 (예: "지인 1명 + 통계") — 가장 약한 출처 기준으로 진행.

| 출처            | 위험 | 권장 인터뷰 대상수           | 위험 사유                                           |
| --------------- | ---- | ----------------------- | --------------------------------------------------- |
| **자기 경험**   | 중   | 본인 외 대상수 3~5명 같은 집단 | 본인 경험을 일반화하는 함정 — 본인이 유별날 수 있음 |
| **지인 관찰**   | 중   | 지인 비슷한 사람 대상수 3~5명  | 표본이 1명이라 지인이 예외 사례일 수 있음           |
| **사회적 발견** | 높음 | 실제 당사자 대상수 5~10명      | 기사·통계는 보도이지 경험이 아님                    |
| **순수 추정**   | 최고 | 대상수 10명 이상 필수              | 당사자랑 만난 적 없으면 진통제 여부 알 길 없음      |

대상수는 **권장** — 강제 X. 미달이면 이후 진통제 신호 부족할 위험이 늘어남, 미달 사유는 산출물에 기록. 이 대상수는 **§2.8 순환의 모든 라운드를 합친 누적치**다.

### 2.6 AI가 맞춤 인터뷰 질문지 생성 (1부 맘 테스트용)

이 질문지는 §2.7의 **1부(맘 테스트)** 전용이다 — 2부(프로토타입 데모)는 질문지가 아니라 관찰 중심이라 별도 절차(§2.7.3)로 다룬다.

이 단계는 **질문지 생성 전 설명(§2.6.1~2) → 질문지 생성(§2.6.3) → 질문 수정 검토(§2.6.4)** 순으로 진행한다 — §2.7(인터뷰 진행)와 같은 구조(설명 먼저 → 행동).

#### 2.6.1 질문지 생성 전 — 사용자에게 AI 시대에 인터뷰가 더 중요해진 이유 설명

질문지 생성(§2.6.3) 전에 사용자에게 **왜 이 인터뷰가 단순 통과 판정이 아니라 *다음에 AI에게 넘길 맥락의 해상도*를 만드는 작업인지** 짚어준다.

설명 골자 (사용자에게 그대로 또는 풀어서 전달):

> 만들기 비용이 거의 0에 가까워졌지만, *제대로 만들 의도를 빚는 일*은 그대로 무겁다 — 오히려 더 무거워졌다.
>
> > **AI는 그럴듯한 쓰레기와 훌륭한 서비스를 똑같이 잘 만들어 준다.** 둘을 가르는 건 코드 솜씨가 아니라, *무엇을 만들지 깊이 안 사람*의 의도다.
>
> 그래서 이 7단계 전체에서 **기획(의도)이 절반 이상**을 차지해야 한다. 사용자가 어떤 자리에서, 어떤 마음으로, 어떻게 임시방편을 만들고 있는지를 _손에 잡힐 만큼_ 알지 못한 채 AI에게 던지면, AI는 빛의 속도로 *그럴듯한 쓰레기*를 만들어 준다.
>
> 이 생각을 떠받치는 권위 두 사람:
>
> > **Paul Graham (Y Combinator 공동 창업자)**
> > "What you need to succeed in a startup is not expertise in startups. What you need is **expertise in your own users**."
> > _(스타트업을 잘하려면, 스타트업을 잘 아는 게 필요한 게 아니다. 필요한 건 **네가 만날 사람들을 깊이 아는 것**이다.)_
>
> > **YC 2025~2026년 흐름 (Garry Tan 외)**
> > "Bottleneck is human intent, not code production. Winners are orchestrators who know what to build and how to direct AI."
> > *(막힘은 사람의 의도에 있지, 코드를 짜는 데 있지 않다. 이기는 사람은 *무엇을 만들지*와 *AI를 어떻게 부릴지*를 아는 지휘자다.)*
>
> 이 인터뷰는 그래서 두 가지를 한꺼번에 한다:
>
> 1. **걸러내기** — 진통제 신호·Pull 신호가 정말 있는지 확인해 거르기
> 2. **의도 빚기** — 다음에 AI에게 넘길 *맥락의 해상도*를 높이기
>
> 둘째가 더 크다.

#### 2.6.2 질문지 생성 전 — 사용자에게 맘 테스트가 뭔지 설명

질문지 생성(§2.6.3) 전에 사용자에게 **맘 테스트가 뭔지** 짚어준다. 인터뷰 질문지가 왜 *현재·과거 행동*만 묻고 _솔루션·프로토타입 언급 X_ 원칙으로 만들어지는지 사용자가 알아야 함. 인터뷰 중 즉석에서 질문 만들 때도 같은 원칙.

설명 골자 (사용자에게 그대로 또는 풀어서 전달):

> **맘 테스트(Mom Test)** = Rob Fitzpatrick의 책 *The Mom Test*에서 온 인터뷰 원칙. 사용자한테 "이거 어때?"라고 물으면 (엄마처럼) 사회적으로 좋아 보이는 답만 돌아옴. *과거 행동·현재 임시방편*만 물어야 거짓말을 거른다.
>
> **핵심**: 사용자 얘기를 듣는다. 우리 아이디어를 팔지 않는다. 우리 솔루션·프로토타입 언급 X — **1부에서는 특히**. 프로토타입을 먼저 보여주고 물으면 답이 프로토타입에 끌려가(닻 내림(anchoring) — 처음 본 정보에 판단이 묶이는 심리 현상) 신호가 오염된다. 그래서 1부(맘 테스트)를 다 마친 뒤에만 2부(프로토타입 데모)로 넘어간다.
>
> - ✅ 좋은 질문: "마지막에 언제 X 했어? 그때 어떻게 했어?" (과거·구체)
> - ❌ 나쁜 질문: "X 있으면 쓸 거 같아?" (미래 의향 — 거짓말 유도)
>
> AI가 만들어준 질문도 위 원칙을 따르고, 인터뷰 중 즉석에서 추가 질문 만들 때도 마찬가지.

전체 좋은/나쁜 질문 패턴은 §2.6.3 (AI 작업 가이드)에 정리.

#### 2.6.3 질문지 생성 절차 + 맘 테스트 원칙

아이디어 + 출처 받으면 **AI가 맘 테스트 원칙(이 절 후반)에 따라 그 아이디어 맞춤 1부(맘 테스트) 인터뷰 질문지 5~10개를 직접 생성**해 사용자에게 보여준다. 사용자가 처음부터 질문 만들 필요 X — 검토·수정하는 형태로 부담 ↓.

_갈래 (c) "강도 측정" 질문은 §2.7.2 강도표의 ★★★/★★/★ 신호를 끌어낼 목적으로 작성._

##### 생성 절차

1. AI가 §2.2 아이디어 한두 문장에서 **도메인·페르소나·문제 영역**을 끌어낸다.
2. 맘 테스트 원칙 5가지 갈래에 맞춰 도메인 맞춤 질문 작성:
   - (a) 과거 사건 끌어내기
   - (b) 현재 임시방편 탐지
   - (c) 임시방편 강도·시간 비용 측정
   - (d) 반대 신호 검증 (신호가 _없는지_ 확인)
   - (e) 인근 관계자·영향 (선택)
3. 사용자에게 보여주고 "이 질문지 어때? 빼거나 수정할 거 있어?" 확인.
4. 사용자 수정 반영해 최종 확정 → `demo-validation.md` `# 인터뷰 질문지 (1부)`로 보존.

##### 예시 — "회의 결정사항 정리 도구" 아이디어 + 자기 경험 출처

> **1부 인터뷰 질문지 (5~7개, 15~20분 권장, 프로토타입 보여주기 전)**
>
> _원칙: 솔루션·프로토타입 언급 X, 인터뷰이의 현재·과거 행동만._
>
> 1. **과거 사건**: "최근에 한 팀 회의 언제였어? 그때 정한 걸 어떻게 정리했어?"
> 2. **임시방편 탐지**: "결정사항·할 일 _빠뜨리지 않으려고_ 뭘 했어? 녹음·메모·따로 카톡 정리 같은 거 한 적 있어?"
> 3. **강도 측정**: "정리에 시간 얼마나 썼어? 그게 짜증났어, 별일 아니었어?"
> 4. **임시방편 한계**: "[임시방편 언급되면 더 자세히] 녹음 다시 들으며 정리한 거 시간 얼마나 걸렸어? 그러고도 빠뜨린 적 있어?"
> 5. **반대 신호**: "회의 내용 중 _굳이 정리 안 하는_ 것도 있어? 왜?"
> 6. (선택) **인근 영향**: "그 정리를 같이 보는 사람 있어? (팀원·상사·클라이언트)"

이 질문지를 사용자가 검토 → 수정 → §2.7 인터뷰(1부→2부) 진행.

##### 맘 테스트 인터뷰 원칙 (AI가 질문 만들 때 따르는 가이드)

_맘 테스트 정의는 §2.6.2 (사용자 설명용). 여기는 AI 질문 생성·검열용 좋은/나쁜 패턴 전체._

**핵심**: _사용자 얘기를 듣는다. 우리 아이디어를 팔지 않는다._ 우리 솔루션·프로토타입 언급 X.

**좋은 질문 패턴 (✅)**

- 과거 사건: "마지막에 언제 X 했어? 그때 어떻게 했어?" — 구체적이고 사실 확인 가능
- 임시방편 탐지: "지금 X 할 때 어떻게 해?"
- 강도 측정: "그게 왜 불편해? 얼마나 자주 그래?"
- 반대 신호 검증: "왜 그게 큰 문제 아니라고 생각해?"
- 감정 + 최근성: "X 때문에 짜증났던 게 마지막에 언제야?"

**나쁜 질문 패턴 (❌, AI 절대 생성 금지)**

- 미래 의향: "X 있으면 쓸 거 같아?" (사회적 거짓말 유도)
- 추상: "이거 어떻게 생각해?" (의미 없는 칭찬 유도)
- 솔루션·프로토타입 쪽: "X 만들려는데 어때?" / "이 화면 어때?" (맘 테스트 위반 — 특히 1부에서 프로토타입을 미리 노출하는 실수 주의)
- 유도 질문: "이 기능 필요하다고 생각해?"
- 가정형: "X 하면 더 편할 것 같지 않아?"

AI가 질문 생성할 때 위 ❌ 패턴이 하나라도 들어가면 자기 검열 후 다시 작성.

**응답 형태 룰 — 본 게임은 open, 메타·강도만 선다**

인터뷰 본 게임 질문(임시방편·과거 행동)은 거의 항상 *open*이어야 함. 선다형은 *우리가 미리 짠 답*만 받으니, 진짜 painkiller가 우리 옵션 밖에 있으면 **false negative**(좋은 아이디어가 옵션에 안 매칭돼 묻힘) 함정 — §2.7.2의 가장 무서운 함정.

| 자리                                            | open vs 선다       | 이유                                  |
| ----------------------------------------------- | ------------------ | ------------------------------------- |
| **인터뷰 본 게임 질문** (임시방편·과거 행동)    | open 강제          | 우리가 모르는 임시방편 발굴           |
| **운영자 모드·동기** (§2.4)                   | 선다 OK            | 우리가 옵션 완전히 파악한 메타 영역   |
| **인터뷰 후 분류** (§2.7.2 강도표 ★★★/★★/★)      | 선다 OK (AI 사후)  | 사용자 답변에 영향 X                  |
| **본질문 다음 follow-up 강도·빈도**             | 선다 OK + "기타" 필수 | 행동(open) 받은 *후* 강도만 좁히기 |

- ❌ 본 게임 위반 예: "회의 정리 어떻게 했어? ①녹음 ②메모앱 ③안 함" — 진짜 답("팀 막내가 늘 정리해서 공유해준다") 묻힘
- ✅ open + follow-up: "대출 가능한지 *어떻게* 알아냈어?" (open) → 답 받고 "그 답 *얼마나 믿었어*? ①거의 안 믿음 ②반반 ③거의 다 믿음" (선다 follow-up OK)

사용자가 본 게임 질문을 선다형으로 박자고 제안하면 §2.6.4 절차 따라 거른다.

#### 2.6.4 사용자가 새 질문 제시·기존 질문 수정 요청 시 — 맘 테스트 검토 절차

사용자가 인터뷰 질문지에 **새 질문을 추가**하거나 **기존 질문을 수정**해달라고 요청하면, AI는 *즉시 적용하지 말고* 다음 절차로 진행:

1. **맘 테스트 검토** — §2.6.3 ❌ 나쁜 질문 패턴(미래 의향·추상·솔루션 유도·유도 질문·가정형)에 해당하는지 짚는다.
2. **위반 시 피드백** — 어느 패턴 위반인지 + 왜 위험한지 짧게 설명 (예: "추상 질문이라 사회적 답변 유도", "미래 의향이라 거짓말 함정").
3. **같은 의도 + 통과 변형 제시** — 사용자가 그 질문으로 *끌어내려는 신호*를 유지하면서 ✅ 좋은 패턴(과거·구체·임시방편·강도·반대신호·감정+최근성)으로 재작성한 변형 옵션 2~3개 제시. 추천 + 이유 명시.
4. **사용자 확인 후 적용** — 사용자 선택 받아 산출물 질문지에 반영. 위반 없으면 그대로 적용.

인터뷰 *중* 즉석에서 던지는 질문 검열은 §6 응대 톤의 "사용자 즉석 질문 검열" 줄 참조 — 같은 원칙, 시점만 다름.

### 2.7 인터뷰 진행 — 1부 맘 테스트 → 2부 프로토타입 데모

인터뷰 1회는 **2부 구성**이다: **1부(맘 테스트) → 2부(프로토타입 데모)**. **이 순서를 반드시 지킨다** — 프로토타입을 먼저 보여주면 이후 답이 프로토타입에 끌려가(닻 내림(anchoring) — 처음 본 정보에 판단이 묶이는 심리 현상) 신호가 오염된다. 1부 질문(§2.6에서 만든 질문지)을 다 마친 뒤에만 프로토타입 링크를 꺼낸다.

#### 2.7.1 인터뷰 진행 전 — 사용자에게 사람 구하기 부담 줄이는 5가지 길 설명

질문지 확정 후 사용자가 "인터뷰할 사람 못 구하겠다"고 막힐 가능성이 크다. 인터뷰 진행 직전에 **사람 모집 부담 줄이는 길**을 짚어준다.

설명 골자 (사용자에게 그대로 또는 풀어서 전달):

> "인터뷰할 사람 구하기 어렵다"는 보통 *완벽한 타겟*을 찾으려 해서. §2.9 평가 2항목의 "10명 명단"도 *완벽한 타겟*이 아니라 *연락 가능한 후보*다. 현실적 5가지:
>
> 1. **친구·지인부터** — 그 도메인 경험자 1명만 잡으면 소개로 1~2명 더 이어짐. 시작점 3~4명이면 5명 채워짐.
> 2. **시간 짧게 제안** — "15~20분", "카톡으로도 OK"라 하면 부담 확 줄어듦.
> 3. **답례** — 커피 쿠폰 5천원 (5명 = 2.5만원, 광고비보다 쌈).
> 4. **커뮤니티 글** — 당근·블라인드·오픈채팅에 짧은 모집 글. 광고비 0.
> 5. **본인 SNS 1회성** — "X 경험 있는 분 짧게 얘기해주실 분?" — 의외로 답 옴.
>
> 광고는 _익명 응답_ 모으는 데 적합하지 *인터뷰 모집*엔 비효율. 같은 비용이면 커피 쿠폰 + 친구 소개가 더 빠름.

#### 2.7.2 1부: 맘 테스트 (프로토타입 보여주기 전)

> **임시방편(hack/workaround)** = 사용자가 그 문제를 풀려고 _직접 시간·노력을 들여_ 만들어 쓰는 _일회용_ 해결책. 시중에 우리가 만들려는 솔루션이 없어서 *직접 감당*하고 있다는 뜻. 진통제 검증의 가장 강력한 근거.

§2.9 평가 1항목이 _임시방편 보유_ 여부를 묻는다. 그런데 "결과물을 만들었나"만 보면 너무 좁다 — 결과물 _없어도_ 반복적·의도적 노력 패턴이 있으면 진통제 신호. 그래서 강도를 3단계로 나눠 본다.

| 강도        | 패턴                             | 예시                                                                                                                             |
| ----------- | --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **★★★ (강함)** | 직접 결과물 만듦                 | 엑셀·구글시트 비교표, 노션 템플릿 매번 복사 사용, 수기 노트·Apple Notes 정리, 갤러리·폴더 임의 분류, 화면 캡처 공유 후 의견 모음 |
| **★★ (중간)** | 반복적 substitution·시간·돈 투자 | 5개 사이트·5개 후기 돌면서 수동 비교, 친구·SNS 여러 명한테 반복해서 물어봄, 매번 30분+ 검색, 반품·교환 경험으로 시간·돈 손해     |
| **★ (약함)** | 1회성·수동적 행동                | 구글 한 번 검색, 유튜브 한 편 시청, 친구한테 한 번 물어봄                                                                        |
| **· (없음)** | 행동 안 함                       | "그냥 안 했어", "별로 관심 없어", "어떻게 풀었는지 기억 안 남"                                                                   |

**핵심 판별 기준**: 사용자가 그 문제 앞에서 _반복적·의도적으로 노력을 들이는가_. 강도는 가중치 — 평가(§2.9)에서 ★★★·★★ 합쳐 카운트.

**왜 결과물만 보면 안 되나** — "딱 맞는 상품 찾기" 같은 도메인은 대부분 사용자가 _결과물은 안 만들지만_ 5개 사이트 돌고·친구한테 물어보고·반품 경험까지 한다. 이건 진통제 맞는데 결과물 기준만 보면 잘못 폐기됨(**거짓 부정(false negative)** — 진짜 painkiller인데 평가가 "아니다"로 잘못 판정하는 실수. 좋은 아이디어가 조용히 사라져 더 무서운 함정). 위 강도표는 이 false negative를 ★★(반복 노력)까지 끌어올려 막는다.

**·없음인데 폐기가 틀릴 수 있는 단 하나의 예외 — *수요 창출형*, 그러나 이 하네스 범위 밖** — 임시방편이 ·(없음)이어도 폐기가 틀린 경우가 하나 있다: 사람들이 그 문제를 _문제로 인식조차 못 해서_ 행동이 안 보이는 **수요 창출형**(잠재 욕구) 아이디어. TikTok·트위터·스냅챗처럼 _보여주기 전엔 욕구 자체가 없던_ 제품이 여기 산다 — 진통제(목마른 사람한테 물 팔기)가 아니라 *없던 욕구를 만드는 일*(물을 처음 마시게 만들기). 그런데 **이 하네스는 이 부류를 의도적으로 안 다룬다**: 수요 창출형은 기능이 본체가 아니라 막대한 **배포력·자본·운(luck)**이 본체이고("build and wait" — 만들어 놓고 시장을 교육하며 기다림), _혼자 AI로 며칠~몇 주에 시장 반응으로 검증하는 빌더_가 노릴 판이 아니다. 출입국 심사가 "여권 없으면 못 지나감"이라고 해서 밀입국 루트가 없다는 뜻이 아니듯, ·없음을 폐기로 보는 건 _그런 아이디어가 나쁘다_가 아니라 _이 하네스 범위 밖_이라는 뜻. 그래서 ·없음은 이 하네스 안에서는 폐기로 판정한다. (사용자가 ·없음 아이디어를 수요 창출형이라 주장하면 AI는 이 한계 — 배포력·자본·운 필요 + build and wait 위험 — 을 짚고, 이 하네스로는 검증 못 하는 영역임을 안내한다.)

_AI 노트 정리 시 위 강도표로 각 응답을 ★★★/★★/★/· 분류. §4.1 표의 "1부 신호 강도" 칸이 이 자리._

1부는 §2.6 확정 질문지를 그대로 진행 — **프로토타입은 아직 꺼내지 않는다.** 질문지 확정 후 **사용자가 직접 인터뷰 진행** — AI는 안 함. AI 역할:

- 인터뷰 진행 중 추가 질문 후보 제안 (사용자 요청 시)
- 1부 끝나면 사용자가 들려준 응답을 §4.1 노트 형식으로 정리

사용자가 인터뷰 노트를 AI한테 줄 때 형식:

- 거친 메모도 OK ("익명1, 주 3회 회의, '회의 끝나고 녹음 다시 들으며 30분 수기 정리, 그래도 할 일 하나 빠뜨림'")
- AI가 임시방편 종류·강도·핵심 인용으로 분해해서 §4.1 표 형식으로 정리.

#### 2.7.3 2부: 프로토타입 데모 (반드시 1부 다음)

1부가 끝난 그 사람에게, 이어서 3단계가 Vercel에 배포한 **리액트 프로토타입 링크**를 보여준다 — 링크를 보내거나 그 자리에서 열어서 직접 써보게 한다. **설명 없이** 자유롭게 써보게 한다 — 안내 문구·기능 설명을 미리 늘어놓지 않는다(실제 첫 사용자가 마주할 상황과 같게 만들기 위해서). 이 프로토타입은 로컬스토리지로 실제 동작하는 워킹 앱이라 인터뷰이가 직접 입력한 내용이 그대로 남고 다시 열어도 보인다 — 정적 화면만 보여주던 옛 목업보다 관찰할 수 있는 반응의 폭이 넓다. 측정하는 3가지:

1. **반응·이해도** — 설명 없이도 뭘 하는 앱인지 스스로 알아보는가. 헤매면 어디서 헤매는지 관찰·기록.
2. **Pull 신호** — 사용자가 **자발적으로** "나오면 써보고 싶다" / "나오면 알려줘" 같은 반응을 보이는가. **유도 금지** — "이거 나오면 쓸 거 같아?"처럼 묻지 않는다(맘 테스트 위반, 미래 의향 유도 — §2.6.3). 묻지 않았는데 스스로 나온 반응만 Pull로 카운트한다.
3. **UI·플로우 피드백** — 화면 순서·구성·문구·버튼 등에 대한 반응. §2.8에서 구조적/미세로 분류할 원재료.

관찰·발화는 그대로 노트에 남긴다 — AI가 요약·해석해도 원문 인용은 보존한다. 이 인터뷰이의 1부+2부 결과가 §4.1 "라운드별 데모 노트" 표의 한 행이 된다.

### 2.8 순환 규칙 — 구조적/미세 피드백, 3단계 복귀, 수렴

**라운드** = 1부+2부를 마친 인터뷰 묶음 하나(또는 그 회차에 진행한 여러 인터뷰이 묶음). 라운드마다 나온 UI·플로우 피드백(§2.7.3③)을 두 종류로 분류한다:

- **구조적** — 플로우 순서·화면 구성·핵심 기능이 바뀌어야 하는 피드백 (예: "이 화면이 왜 이렇게 빨리 나와? 순서가 이상해", "이 기능이 없으면 못 씀").
- **미세** — 카피·색·간격 등 표면적인 피드백 (예: "버튼 글씨가 작다", "이 색은 좀...").

**한 라운드에서 구조적 피드백이 1건이라도 나오면** → 3단계(Prototype)로 돌아가 **코드를 직접 고친다** — Claude Design 목업 재생성은 없다(목업은 첫 요청 1회만 부른다). 화면이 늘거나 빠지는 구조 변경이어도 2단계 인벤토리는 갱신하지 않는다 — 마이그레이션 시점에 이미 1세대 기록으로 넘어갔다(`3-prototype.md` §2.7 순환 갱신 절차 참조). 코드를 고친 뒤 Vercel에 재배포하고, 갱신된 링크로 다음 라운드 인터뷰로 이어간다.

**수렴 조건** — 다음 두 개를 동시에 만족하면 순환을 멈추고 §2.9 평가로 넘어간다:

1. 그 라운드에서 구조적 수정 0건 (미세 피드백만 남음, 또는 아예 없음)
2. §2.5 표의 권장 인터뷰 대상수(누적)를 충족

**로그** — 라운드마다 누구에게 보여줬고, 무슨 피드백이 나왔고, 무엇을 반영했는지 산출물 §4.1 "라운드별 데모 노트" 표에 기록한다. 이 로그가 "순환이 실제로 돌았다"는 증거다.

### 2.9 다음 단계 진입 평가

인터뷰(모든 라운드 누적)가 §2.8 수렴 조건을 만족하면 다음 3항목으로 평가한다.

_1항목 카운트 기준은 §2.7.2 강도표 — (★★★+★★) 합산이 등급 결정. 3항목은 §2.7.3에서 관찰한 자발적 Pull 발화 기준._

| 항목                   | 평가 방법                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 1. **임시방편 보유** | "지금 어떻게 해?" 답을 §2.7.2 강도 3단계(★★★/★★/★/·)로 분류해 카운트. 종류·구체성·강도 기록. 아래 등급표로 ✅/⚠️/❌ 판정 |
| 2. **타겟 구체성**   | 다음 단계에서 만날 사람을 실명·연락처·소속까지 적을 수 있는지. 이름만 X — 연락 가능한 수준 10명+ 명단                     |
| 3. **Pull 신호**     | 프로토타입 데모(2부)를 본 사람 중 **자발적으로** "써보고 싶다/알려달라"고 발화한 비율                                            |

**1항목 통과 등급** (강도 가중치)

| 등급         | 기준                                                 |
| ------------ | ---------------------------------------------------- |
| ✅ 통과      | 인터뷰 대상의 **절반 이상**이 ★★★(강함) 또는 ★★(중간), 그중 **★★★이 최소 1명**                       |
| ⚠️ 통과 직전 | ★★★+★★ 합이 절반 이상인데 ★★★ 0명 / 또는 ★★★+★★ 합이 **30~50%**                       |
| ❌ 미달      | ★★★+★★ 합이 **30% 미만** — 대부분 ★(약함) 또는 ·(없음)                                |

**2항목 통과 등급**

| 등급         | 기준                                  |
| ------------ | ------------------------------------- |
| ✅ 통과      | 10명+ 실명·연락 가능한 수준 명단 가능 |
| ⚠️ 통과 직전 | 5~9명 명단 가능                       |
| ❌ 미달      | 5명 미만 또는 이름만 가능             |

**3항목 통과 등급** (Pull 신호)

| 등급         | 기준                                            |
| ------------ | ------------------------------------------------ |
| ✅ 통과      | 데모(2부)를 본 사람 **절반 이상**이 자발적 Pull 발화 |
| ⚠️ 통과 직전 | **1명 이상**이지만 절반 미만                       |
| ❌ 미달      | **0명** — 아무도 자발적으로 끌리지 않음             |

세 항목 모두 binary가 아닌 ✅/⚠️/❌로 판정한다 — 작은 표본은 흔들리니 "통과 직전"을 분리해 둔다.

### 2.10 go/no-go 판정 + 다음 처리

평가 후 사용자에게 갈래 안내:

```
데모 검증 평가 결과: 1항목 [✅/⚠️/❌], 2항목 [✅/⚠️/❌], 3항목(Pull) [✅/⚠️/❌]

다음 갈래:
- go (MvpBuild 진입): 1·2항목 ✅ (3항목은 ✅/⚠️ 둘 다 go) → MvpBuild 단계로.
- no-go (인터뷰 더 또는 프로토타입 방향 수정): 1·2항목 ✅인데 3항목 ❌ → painkiller는 있는데 이 프로토타입엔 안 끌림. 인터뷰를 더 하거나, 3단계로 돌아가 코드를 고쳐 방향을 다시 본다.
- no-go (인터뷰 더): 표본 부족 / 1항목 ⚠️ / 2항목 ❌ → 인터뷰 더 하고 재평가.
- no-go (아이템 폐기): 1항목 ❌ → 진통제 신호 없음. 다른 아이디어로.

어느 쪽?
```

**판정 가이드**

- 1·2항목 ✅, 3항목 ✅ 또는 ⚠️ → **go (MvpBuild)**
- 1·2항목 ✅, 3항목 ❌ → **no-go (인터뷰 더 또는 프로토타입 방향 수정)** — 문제는 확인됐지만 이 해결책 형태가 아직 안 맞을 수 있다. 먼저 인터뷰를 늘려 재확인하고, 그래도 0명이면 3단계로 돌아가 코드를 고쳐 방향을 다시 짚는다.
- 1항목 ✅, 2항목 ❌ → **no-go (인터뷰 더)** — 집단 좁히거나 명단 추가
- 1항목 ⚠️, 2항목 ✅ → **no-go (인터뷰 더)** — 표본 늘리거나 다른 집단 시도
- 1항목 ❌ → **no-go (아이템 폐기)** — 진통제 신호 부재, 다른 아이디어
- 둘 다 ❌ → **no-go (아이템 폐기)**

**갈래별 처리**

| 갈래                    | 다음 액션                                                                                                                                                                                            |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **go (MvpBuild 진입 자격 확보)**    | `demo-validation.md` 머리말 `status: confirmed`. §2.10.1로 *최종 확정 아이디어 + 비목표·검증 가설·북극성*을 산출물에 박은 시점이 인계 완료. 바로 다음 5단계(MarketResearch)가 이 확정 아이디어로 경쟁 지형을 조사하고(`5-market-research.md`), 6단계(MvpBuild)가 이 내용과 인터뷰 노트를 자기 기준으로 읽음 (`6-mvp-build.md` §2 참조).                                                   |
| **no-go (인터뷰 더 또는 프로토타입 방향 수정)** | `status: in-progress` 유지. 먼저 인터뷰 추가로 표본 늘리기, 그래도 Pull 0명이면 3단계 복귀해 코드를 고쳐(`3-prototype.md` §2.7 순환 갱신 절차) 방향 재검토.                                                       |
| **no-go (인터뷰 더)**   | `status: in-progress` 유지. 인터뷰 추가 진행, 재평가. 이 단계는 안 끝남.                                                                                                                       |
| **no-go (아이템 폐기)** | `demo-validation.md`는 **보존** (학습 자료). 같은 폴더에서 새 아이디어 시작하면 `demo-validation-v2.md`로 누적. 새 레포로 갈 필요 X. |

#### 2.10.1 go 분기 — 최종 확정 아이디어 + 비목표·검증 가설·북극성 확정 (다음 단계 인계 직전)

go 판정이 나오면 *다음 단계로 넘어가기 전*에 한 단계 더 — **최종 확정 아이디어**뿐 아니라 **비목표(안 만들 것)·검증 가설·북극성**까지 함께 확정한다. 이 4개(구 MarketResearch "최종 서비스 기획 요약" 역할을 이 단계가 흡수)가 이후 아이디어·가설의 SoT(Source of Truth)가 되고, `이전 결론 → 이번 결론` 체인(SKILL.md §2.2)이 여기서 시작된다. 이게 다음 단계로 넘기는 인계 지점이다 — 5단계 조사도, 6단계 빌드도 여기서 박은 문장을 base로 출발한다.

**왜 여기서 4개를 한꺼번에 박나** — 인터뷰가 painkiller 신호를 확인하면서 *솔루션 방향이 미세하게 바뀌는* 경우가 흔하다. 예: "회의록 정리 도구"로 시작했는데 인터뷰로 *결정사항·담당자 추적 부담*이 진짜 painkiller임을 발견 → 솔루션이 "할 일·담당자 추적 도구"로 이동. 이 *바뀐 결과*를 명시적으로 못 박지 않으면 MvpBuild 단계가 *초기 아이디어*를 base로 잘못 출발한다. 안 만들 것(비목표)·검증할 가설·장기 방향(북극성)도 마찬가지 — 실제 반응을 본 지금(4단계) 정하는 게, 아직 아무 반응도 못 본 앞 단계에서 정하는 것보다 근거가 튼튼하다. 그래서 이 4개의 확정 자리를 이 단계로 모았다.

절차:

1. AI는 인터뷰 결과(라운드별 데모 노트·평가)를 검토하고, 초기 아이디어 대비 *변경된 부분*을 파악한다 (솔루션 방향·타겟 집단·문제 정의 중 어디가 이동했는지). 경쟁 지형·차별화 힌트는 아직 손에 없다 — 그건 여기서 확정한 아이디어를 들고 5단계(MarketResearch)에서 조사한다.
2. 사용자에게 다음 4개를 순서대로 제안하고 확인받는다:

   **(1) 최종 확정 아이디어** (한 문단):
   > "**[누구]가 [상황]에서 [문제] 겪는 걸 [어떻게] 풀어준다**"
   변경이 *없으면* "초기와 동일" 명시 (intent가 *그대로*를 명시적으로 받도록).

   **(2) 비목표 (안 만들 것)** — 형식 `[X] 안 함 — [이유]`. 최소 1개, 그중 **1+개는 MvpBuild 스코프**("이번 빌드에선 X 안 함 — 이유"). *왜*: 프로토타입(3단계)은 이미 화면과 로컬스토리지 동작까지 다 구현해놨지만, 실제 백엔드 연동(6단계 MvpBuild)까지 다 확장하면 무한 증식한다. 비목표가 그 브레이크.

   **(3) 검증 가설** — 형식 `[조건]하면 [예측]할 것이다`. 1~2개, 그중 **1+개는 MvpBuild 베타 공유로 확인 가능한 형태**. 6단계 베타 공유 관찰과 7단계 런치 기준(launch-plan) 설계의 직접 입력.

   **(4) 북극성 (1줄, 선택)** — 2~3년 horizon 방향 한 줄(행동·규모·포지셔닝 중 1개). 이번 검증에 묶인 수치 금지(그건 7단계 launch-plan·retro). 가벼운 방향타로 충분 — 생략 가능.

   **코칭**: (2)(3)(4)는 founder 의지라 추정 금지 — AI가 후보 2~3개 제시 → 사용자가 골라 다듬는다(SKILL.md §1.4). 빈칸 압박 대신 후보로.
3. 사용자 확인·수정 받기.
4. 산출물 `# 최종 확정 아이디어 (MvpBuild 진입 입력)` 섹션에 4개를 함께 박음 (§4.1 형식).
5. **CLAUDE.md 프로젝트 정의 갱신** — 프로젝트 CLAUDE.md 상단의 프로젝트 정의 줄(한 줄 정의·타겟, project-init이 채운 것)을 최종 확정 아이디어와 일치하게 덮어쓴다. CLAUDE.md는 매 세션 자동 로드되는 유일한 파일이라, 여기를 안 고치면 다음 단계부터 모든 세션이 검증 전 낡은 정의를 계속 읽는다.
6. MvpBuild 단계는 이 4개를 base로 시작.

go 분기가 아닌 갈래(인터뷰 더·아이템 폐기)에선 이 절차 X.

**4단계(DemoValidation) 산출물 경계** — 4단계 산출물은 `demo-validation.md` *한 파일만*(순환 중 갱신되는 프로토타입 코드는 3단계 산출물). `market-research.md`·`mvp-build.md` 등 다음 단계 산출물을 미리 만들거나 placeholder로 채우지 않는다 (절차 5의 CLAUDE.md 프로젝트 정의 갱신은 산출물 생성이 아니라 프로젝트 설정 갱신이라 무방). 이 4개를 4단계 산출물 안에 박은 시점이 인계 완료. 다음 단계 진입은 사용자가 `/clear` 후 `/idea-to-mvp` 재호출 (SKILL.md §3.2) → 5단계(MarketResearch)가 `demo-validation.md`의 최종 확정 아이디어를 input으로 받아 경쟁 지형을 조사하고, 이어 6단계(MvpBuild)가 같은 문서를 빌드 스펙으로 받는다.

### 5.1 인터뷰 질문 (1부)

> "회의 정리 도구 있으면 쓸 거 같아?" (미래 의향)
> "회의 정리가 어려운 이유가 뭐라고 생각해?" (추상)
> "이 화면 어때? (프로토타입 먼저 보여줌)" (1부·2부 순서 위반 — 닻 내림)

### 5.2 인터뷰 노트 기록

**좋은 예** (구체·임시방편·인용)

> 익명3, 주 3회 회의 28세. "회의 끝나면 녹음을 다시 들으면서 노션에 손으로 정리해요. 30분쯤 걸리는데, 지난주엔 할 일 하나를 빠뜨려서 일정이 밀렸어요."
> → 임시방편: 녹음 재청취 + 수기 정리 / 강도: ★★ / 시간 비용: 회의당 30분

**나쁜 예** (추상·일반·평가)

> 다들 회의 정리가 귀찮다고 함. 도구 있으면 좋겠다고 함.

### 5.3 Pull 신호

**좋은 예** (자발적 발화만 카운트)

> 프로토타입의 "회의 끝 자동 요약" 화면을 보여주자 인터뷰이가 먼저 "어 이거 진짜 나오면 저 좀 알려주세요, 저 맨날 이거 때문에 시간 날려요"라고 말함 → **Pull ✅** 카운트. 묻지 않았는데 스스로 나온 반응.

**나쁜 예** (유도된 답 — 카운트 불가)

> 인터뷰어가 "이거 나오면 쓸 거 같아요?"라고 물어 "네, 아마요"라는 답을 받음 → 미래 의향 유도 질문이라 맘 테스트 위반, **Pull로 카운트 불가**.

### 5.4 평가점수표

**좋은 예** (강도 분류 + 구체 근거)

> 1항목 ✅ — 대상수 5명 중 ★★★ 1명(엑셀 비교표 직접 작성), ★★ 3명(5개 사이트 돌면서 후기 비교·친구 여러 명 반복 문의·반품 경험), ★ 1명(구글 한 번 검색). (★★★+★★)=4/5=80%, ★★★ 1명+ 조건 충족. 인용: "..."
> 3항목 ✅ — 데모 본 5명 중 3명이 자발적 Pull 발화("나오면 알려주세요" 류). 3/5=60%.

**나쁜 예** (추측·일반화·강도 분류 없음)

> 1항목 ✅ — 다들 어려워하니까 통과로 보임.
> 3항목 ✅ — 다들 좋아하는 것 같았음.

### 5.5 출처별 시나리오

**자기 경험 + go**

> 본인이 매주 회의 정리에 시달리던 founder. 같은 처지(주 3회+ 회의) 3명 인터뷰 → 1부에서 모두 녹음 재청취·수기 메모로 임시방편 시도, 2부 프로토타입 데모에서 3명 중 2명이 자발적 Pull 발화. 1·2·3항목 ✅ → MvpBuild 진입.

**순수 추정 + no-go (폐기)**

> 기사로 "직장인 회의 시간 낭비 심각" 본 founder. 당사자 만난 적 X. 대상수 10명 인터뷰 → 1부에서 다들 회의 정리는 "끝나고 대충 메모하고 넘김"이라 임시방편이라 할 게 부재. 1항목 ❌ → 아이템 폐기(2부 데모까지 갈 필요도 없음). 학습: 회의가 길다는 불만은 있지만 _정리_ 단계엔 진통제 없음.

**1·2항목 ✅, 3항목 ❌ + 순환 사례**

> 대상수 6명 인터뷰 — 1부 임시방편 신호 강함(★★★+★★ 5/6=83%), 타겟 명단 10명+ 확보. 그런데 2부 프로토타입 데모에서 6명 중 0명이 자발적 Pull 발화 — 다들 "화면은 이해되는데 딱히 쓸 이유는..." 반응. 3항목 ❌ → no-go(인터뷰 더 또는 프로토타입 방향 수정). 재검토 결과 프로토타입이 "정리"에만 집중돼 있었고 인터뷰이들이 진짜 아파하는 건 "담당자 추적"이었음을 발견 → 3단계 복귀해 코드에 담당자 추적 화면 추가(구조적 반영) → 다음 라운드에서 Pull ✅.

### 5.6 모드·동기별 대상수·평가 적용 차이

**나쁜 예 (모드 미적용)**

> 직장 사이드 / 즐거움·학습 동기인데 풀타임 창업과 같은 기준으로 평가 → 대상수 2명면 "표본 부족, 인터뷰 더" 자동 권장 → 매주 10시간 페이스에 인터뷰 5명+은 _과한 의례_ → 사용자 페이스 안 맞아 진행 자체가 흐지부지.

**좋은 예 (모드 적용)**

> 직장 사이드 / 학습 동기 → 대상수 2명 충분, 1항목 ⚠️도 통과로 보고 진행. 사유 기록: "장인 모드, 매출 압박 없음 — 시간 보호용 인터뷰 대상수 2명로 OK".

> 풀타임 창업 / 매출 동기 → 대상수 5명 풍부, 1항목 ⚠️면 진짜 인터뷰 더 필요. 매몰 위험 명시.

> 부업·취미 / dogfooding 동기 → 인터뷰 대상수 1명 (자기 자신만 충실히) 또는 친구 1명 가벼운 확인. 평가는 _자기 사용 빈도 가설_ 중심.

## 6. 사용자 응대 톤 + 인터뷰 코칭

- **톤**: SKILL.md §1.3 따름 — 반말·친근·짧게.
- **코칭**: generic 발췌 코칭(잘 모르겠어→후보 제시·본질 보존 등)은 SKILL.md §1.4 따름. 아래 항목들은 이 단계 *고객 인터뷰*(맘 테스트 + 프로토타입 데모) 특화 코칭 — SoT는 §2.6.3·§2.7.3.
- **흐름**: 아이디어 도출·확인(§2.2) → 조사 시점 안내(§2.3) → 운영자 맥락 받기(§2.4) → 출처 도출·확인(§2.5) → **AI 맞춤 1부 질문지 생성**(§2.6) → 사용자 인터뷰 진행(1부→2부, §2.7) → AI 노트 정리 → 순환 판단(§2.8) → 진입 평가(§2.9) → go/no-go(§2.10). 단계 건너뛰지 말 것 — 특히 §2.2 아이디어 도출 전에 §2.5 출처부터 묻는 점프 금지, §2.7에서 2부(프로토타입)를 1부보다 먼저 보여주는 순서 위반 금지.
- **1부→2부 순서 강제**: 사용자가 "그냥 프로토타입부터 보여주고 싶다"고 하면, 순서를 지켜야 신호가 안 오염된다(닻 내림)고 짚고 1부 질문지부터 진행하도록 안내한다.
- **조사 시점 안내** (§2.3): 사용자가 "경쟁자부터 조사하자" 하면, 조사는 5단계고 지금은 인터뷰가 먼저라고 짚는다 — 데모로 방향이 뒤집히면 미리 한 조사는 버려진다. 경쟁자를 몰라 불안해하면 *★★★ 사적 임시방편은 검색이 아니라 인터뷰에서만 잡힌다*는 점을 알려준다. (예외적으로 `market-research.md`가 이미 있으면 그 빈틈을 질문지에 반영해도 좋다 — 경쟁자가 있다는 건 좌절 신호가 아니라 수요 신호다.)
- **AI는 인터뷰 _직접_ 안 함** — 사용자가 1부·2부 모두 진행. AI는 질문지·코드 반영 프롬프트·노트·평가만.
- **인터뷰 대체 시도 차단**: 사용자가 *실제 인터뷰* 대신 AI 가상 인터뷰·광고+설문으로 때우려 하면 막는다 — 그건 *보조*(질문지 리허설·모집 깔때기·정량 분포)지 *대체*가 아냐. 진통제·Pull 신호는 실제 행동·구체 인용·실제 프로토타입 반응에서만 나옴.
- **솔루션 함정**: 사용자가 솔루션 아이디어부터 길게 말하려는 경향. AI는 §2.2에서 솔루션 부분도 받되 (어차피 1부에서 언급 안 함), 세부 기능·화면은 프로토타입(3단계)에 이미 있으니 *그걸로 2부에서 검증하자*고 안내.
- **사용자 즉석 질문 검열**: 사용자가 인터뷰 중 즉석에서 질문 만들 때 ❌ 패턴(미래 의향·추상·유도) 발견되면 AI가 짚고 좋은 형식으로 다시 쓰자고 권유.
- **Pull 신호 유도 차단**: 사용자가 2부 진행 중 "이거 나오면 쓸 거예요?" 같은 질문을 던지려 하면 막는다 — 그건 유도된 답이라 카운트 불가(§5.3). 관찰하고 기다리라고 안내.
- **구조적 피드백 나오면 즉시 순환 안내**: 2부에서 구조적 피드백이 나오면 그 자리에서 "이건 구조적 피드백이라 3단계로 돌아가 코드를 고쳐야 해"라고 짚어준다 — 미세 피드백과 헷갈려 넘어가지 않도록.
- **대상수 미달**: "권장 대상수에 미달인데 강행할래? 미달 사유 기록할게." 결정은 사용자. _모드·동기 frame_(§6.1) 적용 — 직장 사이드·취미 모드면 대상수 미달이어도 페널티 약하게.
- **인터뷰 결과 모호**: "이 임시방편이 진짜 진통제인지 헷갈리면 그 인터뷰이한테 '왜 이걸로 안 풀려?'를 한 번 더 물어보자."

### 6.1 모드·동기별 frame 조정

§2.4에서 받은 운영자 모드·동기에 따라 응답 frame을 조정. **단계 목표·기조**(진통제·Pull 검증·인터뷰·평가)는 그대로, *압박 강도·대상수 권장값·스코프·갈래 추천*만 조정.

| 모드                     | 시간 압박                    | "현재 매출 필요" 압박                      | 인터뷰 대상수 조정 (§2.5 권장 대비)                    | 스코프 권장                           | 주의                                             |
| ------------------------ | ---------------------------- | ------------------------------------------ | ------------------------------------------------- | ------------------------------------- | ------------------------------------------------ |
| **풀타임 창업**          | 강 (6~18개월 매출 압박 명시) | 강 (현재 통증 + 미래 비전 하이브리드 강조) | 권장값 그대로                                     | 빌더·통합 솔루션도 가능 (자금 있으면) | "build and wait" 위험 명시                       |
| **직장 사이드 프로젝트** | 약 (long-term OK)            | 약 (매출 N/A)                              | 권장값/2 까지 OK (예: 사회적 발견 대상수 5~10명 → 대상수 2~5명) | 기능 단위, 1년 운영 가능한 작은 조각  | dogfooding 가치 ↑. *시기상조 가설*도 페널티 약함 |
| **학생**                 | 약                           | X                                          | 대상수 2~3명 약하게                                      | 완성도·데모 가능한 형태               | 학습·포트폴리오 가치 인정                        |
| **부업·취미**            | X                            | X                                          | 대상수 1~2명 (너 시간 보호용)                            | 본인이 매주 쓸 작은 도구              | "재밌으면 됨" 인정                               |

**동기별 추가 조정**:

- **dogfooding 동기**: 자기 자신이 대상수 1명 충실 표본. 인터뷰는 보조. 본인이 매주 _진짜로_ 쓰는지가 핵심 검증.
- **포트폴리오 동기**: 완성도·시각적 데모 가능성 강조. 시장 진입·매출 frame 거의 X.
- **즐거움·학습 동기**: 인터뷰는 *너 시간 보호*용 (대상수 1~2명). 진통제 평가 ⚠️도 통과로 보고 진행 OK.
- **매출 동기**: §2.5 권장 대상수 그대로. 1항목 ❌면 진짜 아이템 폐기 권장.
- **미정 동기**: 만들면서 정해도 OK. 가장 작은 조각부터 시작 권장.

**응답 시 모드를 frame으로 명시** — 예시:

- "장인 모드라 빌더 통째론 3년+ 걸리니 기능 단위로 좁히자"
- "직장 사이드 + 학습 동기니까 대상수 2명도 충분, 다음 단계 가자"
- "풀타임 창업 + 매출 동기라 진짜 진통제 신호 없으면 위험 — 가설 다시 보자"

**모드 전환 처리**: 직장 → 풀타임 창업, 학생 → 직장 등 모드 변경 시 frontmatter 갱신. 진행 중 전환되면 그 시점부터 새 frame 적용.
