## 1. 먼저 경고 두 개

사람 몫을 시작하기 **전에** 둘 다 말한다.

> 토큰 값은 이 대화창에 붙여 넣지 마세요. 대화 기록에 남습니다. 토큰은 화면에 한 번만 보이니, 복사해서 바로 Vercel 칸과 비밀 보관처에 넣으시면 됩니다.

> 진행 중에 설정 화면 캡처를 보여 달라고 할 수 있습니다. 그때 키·토큰·시크릿이 보이면 가리고 올려 주세요.

## 2. 계정 대조

- 프로젝트 `AGENTS.md` 「소유와 계정」 표의 GitHub 계정과, 사용자가 브라우저에서 로그인한 GitHub 계정(화면 오른쪽 위)이 같은지 먼저 확인받는다. 토큰은 그 계정으로 만들고, 캡처 저장소는 코드 저장소와 같은 주인(조직 또는 개인) 아래에 만든다.
- [AI] 단계 1에서 이미 읽어 둔 값으로 갈래를 정한다 — 코드 저장소 주인이 **조직**이고 작업 계정이 조직 **member**면 5.2(승인 요청)가 필요하다. `admin`(소유자)이거나 **개인** 저장소면 5.2를 건너뛴다(개인 저장소 갈래는 실측 없음 — 화면이 다르면 그대로 따른다).

## 3. 캡처 저장소 만들기

캡처 그림만 쌓는 **별도 비공개 저장소**다. 코드 저장소에 쌓지 않는 이유: 코드 저장소에 Contents 쓰기 토큰을 두면, main 보호 규칙이 없는 저장소(무료 조직의 비공개 저장소는 못 켬)에선 토큰이 샐 때 main에 바로 밀려 실서비스까지 배포될 수 있다. 커밋마다 미리보기 빌드가 도는 것도 막는다.

[AI] 먼저 있는지 본다: `env GH_TOKEN="$(sed -n 's/^GH_TOKEN=//p' .env.cli 2>/dev/null)" gh repo view <주인>/<이름> --json visibility,defaultBranchRef`. 있고 비공개·기본 브랜치가 있으면 건너뛴다.

없으면 묻는다 — "캡처 저장소 `<주인>/<프로젝트>-qa-shots`(비공개)를 제가 만들까요, 직접 만드시겠습니까?"

- **AI가 만들 때** (허락받은 뒤): `env GH_TOKEN="$(sed -n 's/^GH_TOKEN=//p' .env.cli 2>/dev/null)" gh repo create <주인>/<이름> --private --add-readme --description "QA 피드백 화면 캡처 (비공개)"`. 조직 설정상 멤버가 저장소를 못 만들면 실패한다 — 재시도하지 않고 사람 몫으로 넘긴다.
- **사람이 만들 때**: GitHub → (조직이면 조직 화면) → **New repository** → 이름 → **Private** → **Add a README file** 체크 → **Create repository**.

> README를 꼭 넣어 주세요. 기본 브랜치가 있어야 캡처를 커밋할 수 있습니다.

끝나면 확인할 것 하나 — **이슈를 볼 사람이 이 캡처 저장소에도 읽기 권한이 있어야 이슈에서 그림이 보인다.** 조직 기본 권한이 「없음」이면 팀이나 사람을 이 저장소에 따로 넣어 달라고 안내한다.

## 4. 라벨 만들기

[AI] 있는지 본다: `env GH_TOKEN="…" gh label list --repo <코드 저장소> --search qa`. 있으면 건너뛴다.

없으면 묻는다 — "코드 저장소에 `qa` 라벨을 제가 만들까요?"

- **AI가 만들 때**: `env GH_TOKEN="$(sed -n 's/^GH_TOKEN=//p' .env.cli 2>/dev/null)" gh label create qa --repo <코드 저장소> --description "QA 피드백 (화면 3번 터치)" --color FBCA04`
- **사람이 만들 때**: 코드 저장소 → **Issues** → **Labels** → **New label** → 이름 `qa` → **Create label**.

라벨 이름을 `qa`가 아닌 것으로 정했으면 그 이름으로 만들고, 환경변수 `GITHUB_QA_LABEL`에 같은 이름을 넣는다.

## 5. 토큰 두 개 발급

토큰은 **저장소 하나·권한 하나**짜리 세분화 토큰(fine-grained personal access token — 고른 저장소에 고른 권한만 주는 열쇠) 두 개다. 하나로 두 저장소를 고르면 두 저장소 모두에 같은 권한이 붙어 코드 저장소에 Contents 쓰기가 생긴다 — 그래서 둘로 나눈다.

**승인 대기를 코드 작업과 겹치게** — 조직 승인은 몇 시간~며칠 걸릴 수 있다. 이 단계는 코드 깔기(단계 3) 전에 먼저 시작한다.

길: GitHub 오른쪽 위 프로필 사진 → **Settings** → 왼쪽 맨 아래 **Developer settings** → **Personal access tokens** → **Fine-grained tokens** → **Generate new token**.

### 5.1 칸별로 넣을 값

| 칸 | 이슈용 토큰 | 캡처용 토큰 |
|---|---|---|
| Token name | `<프로젝트>-qa-issue` | `<프로젝트>-qa-shots` |
| Description | `QA 피드백 — <코드 저장소>에 qa 이슈를 만듦 (Issues 쓰기만)` | `QA 피드백 — <캡처 저장소>에 화면 캡처를 커밋 (Contents 쓰기만)` |
| Resource owner | 저장소 주인 — 조직이면 **그 조직**, 개인이면 본인 | 같음 |
| Expiration | 조직이 허용하는 최대(예: 366일). 개인이면 정식 공개 예정일 조금 뒤로 Custom. **만료일은 장부에 적는다** | 같음 |
| Repository access | **Only select repositories** → 코드 저장소 **하나만** | **Only select repositories** → 캡처 저장소 **하나만** |
| Repository permissions | **Issues → Read and write** 하나만 (Metadata: Read-only는 저절로 붙음) | **Contents → Read and write** 하나만 (Metadata는 저절로) |
| Account permissions (조직이면 Organization permissions도) | 아무것도 주지 않음 | 아무것도 주지 않음 |
| Request message (조직 승인이 필요할 때만 보임) | 5.2 견본 | 5.2 견본 |

→ **Generate token** → 화면에 **한 번만** 보이는 값을 복사해 바로 6.2(Vercel)와 비밀 보관처(7)에 넣는다. 대화창에는 붙여 넣지 않는다.

[AI] 다 됐다고 하면 받아 둘 것 — 토큰 **이름**과 **만료일**(장부용). 값은 받지 않는다.

### 5.2 조직 소유자 승인 요청

조직이 승인을 요구하면 토큰이 **Pending(승인 대기)**으로 남는다. 그동안 GitHub는 그 토큰의 호출을 **404**로 거절한다 — 비공개 저장소는 권한이 없으면 존재 자체를 숨기기 때문이다. 승인은 조직 소유자가 조직 **Settings** → **Personal access tokens** → **Pending requests**에서 한다.

소유자가 처음 보는 요청이라도 바로 이해하게, 아래 다섯 가지를 담아 보낸다(Request message 칸과, 따로 메신저로 보낼 때 같은 글). 사용자에게 견본을 주고 고쳐 쓰게 한다.

> 안녕하세요. `<코드 저장소>`에 넣는 QA 피드백 기능용 GitHub 토큰 두 개의 승인을 부탁드립니다.
> 1. **무슨 토큰인지** — 테스터가 앱 화면에서 남긴 한 줄 피드백을 GitHub 이슈로 자동 등록하는 데 씁니다. 이슈용 `<토큰 이름>`, 화면 캡처 저장용 `<토큰 이름>` 두 개입니다.
> 2. **권한이 얼마나 좁은지** — 이슈용은 `<코드 저장소>` 하나에 Issues 쓰기만, 캡처용은 `<캡처 저장소>` 하나에 Contents 쓰기만 있습니다. 코드 저장소의 코드는 쓸 수 없습니다.
> 3. **왜 막혀 있는지** — 조직 정책상 소유자 승인 전까지 토큰이 승인 대기라 기능이 동작하지 않습니다(GitHub가 404로 거절합니다).
> 4. **어디서 승인하는지** — 조직 Settings → Personal access tokens → Pending requests입니다.
> 5. **언제든 끊을 수 있음** — 같은 화면에서 언제든 승인을 취소할 수 있고, 만료일은 `<날짜>`입니다.

## 6. Vercel에 넣기

### 6.1 배포 보호 확인

테스터가 **어느 주소로 들어오는지**를 먼저 정한다. Vercel 프로젝트 → **Settings** → **Deployment Protection**에서 지금 값을 사용자에게 확인받는다(단정하지 않는다 — 계정 종류·설정마다 다르다).

- 미리보기 주소에 Vercel 로그인이 걸려 있으면, 테스터는 미리보기 주소를 못 연다 → 테스터는 **실서비스 주소**로 받는다(idea-to-mvp 5단계 지인 공유와 같음). 이때 로그인 없는 방식은 **Production에도 켜야** 테스터가 쓸 수 있다.
- 실서비스 기본 주소(`<프로젝트>.vercel.app`)에도 보호가 걸려 있는지, 보호를 켠 채 테스터용 공유 링크로 열었을 때 `/api/qa-feedback` 보내기가 통과하는지는 **실측 필요** — 단계 5에서 테스터 주소로 한 번 보내 확인한다.
- 만드는 사람 자신의 1차 실측(단계 4)은 로그인된 브라우저로 미리보기 주소를 직접 연다.

### 6.2 환경변수 넣기

길(2026-10 화면): Vercel → 팀 → 프로젝트 → **Settings** → **Environments** → **Preview**(또는 **Production**) 줄을 눌러 들어감 → **Add** → Key·Value → **Type**에서 **Secret / Config** 중 고름 → **Environments** 드롭다운에서 **Production·Preview**를 같이 체크할 수 있음 → 저장. (예전 안내 「Settings → Environment Variables」는 낡은 길이다.)

| 이름 | 값 | Type | 언제 넣나 |
|---|---|---|---|
| `QA_FEEDBACK` | `on` | Config 권장(값을 다시 볼 수 있게) | 단계 2 — Preview. Production은 단계 5에서 정한 뒤 |
| `GITHUB_QA_REPO` | 코드 저장소 `owner/repo` | Config 권장 | 단계 2 |
| `GITHUB_QA_SHOTS_REPO` | 캡처 저장소 `owner/repo` | Config 권장 | 단계 2 |
| `GITHUB_QA_LABEL` | (`qa`가 아닐 때만) 라벨 이름 | Config | 단계 2 |
| `GITHUB_QA_ISSUE_TOKEN` | 이슈용 토큰 | **Secret** | 단계 5 직전(1차 실측 뒤) |
| `GITHUB_QA_SHOTS_TOKEN` | 캡처용 토큰 | **Secret** | 단계 5 직전 |

- 비밀 아닌 설정값 넷은 AI가 `vercel env add`로 넣을 수 있다(SKILL.md 단계 3 — 묻고 나서, 실패 2회면 사람 몫).
- **Config 타입의 뜻(다시 볼 수 있는지, 빌드 때 읽히는지)은 실측 필요** — `QA_FEEDBACK`을 Config로 넣었는데 단계 4에서 3번 터치로 창이 안 뜨면, 넣은 값이 빌드에 안 들어간 것이다. Secret으로 다시 넣어 본다.
- 터미널이 편하면 **사용자 자신의 터미널에서** `npx vercel env add GITHUB_QA_ISSUE_TOKEN production`처럼 치면 값을 묻는 칸이 나온다 — 대화창이 아니라 그 칸에 붙여 넣는다.
- **넣은 뒤 다시 배포해야 적용된다** — 브랜치에 푸시하면 미리보기가 새로 만들어진다. `QA_FEEDBACK`은 빌드 때 화면 코드에 박히는 값이라 특히 그렇다.

[AI] 확인: `vercel env ls`로 **이름만** 본다(값은 출력하지 않는다).

## 7. 로컬과 비밀 보관처

- **로컬(`.env.local`)엔 기본적으로 넣지 않는다.** 토큰이 없으면 서버가 이슈를 만들지 않고 「이렇게 만들 뻔했어요」 로그만 남긴다 — 개발하다 시험 삼아 누른 게 진짜 이슈로 쌓이지 않게. GitHub 연결을 로컬에서 꼭 봐야 할 때만 사용자가 직접 넣고, 끝나면 토큰 줄을 지운다.
- 토큰 두 개의 사본과 만료일은 사용자의 비밀 보관처(비밀번호 관리자 등 — 프로젝트 장부의 「저장된 곳」)에 둔다. Vercel의 Secret은 나중에 다시 못 보기 때문이다.

## 8. 테스터 안내 — 로그인 없는 방식

로그인 없는 방식은 **주소를 아는 누구나** 보낼 수 있다 — 주소가 곧 공개 범위다. 테스터에게 링크를 보내기 전에 아래 뜻을 함께 보내라고 사용자에게 견본을 준다(말투는 사용자가 고친다).

> 테스트 주소: `<주소>`
> - 이 주소는 테스트용입니다. 다른 곳(단톡방·SNS 등)에 올리지 말아 주세요.
> - 쓰다가 이상한 점이 있으면, 화면의 **빈 곳**(글자·버튼·그림이 없는 곳)을 빠르게 세 번 눌러 주세요. 한 줄 창이 뜹니다.
> - **글 앞에 이름을 써 주세요.** (예: `민수: 버튼을 눌러도 안 넘어가요`) 로그인이 없어서 누가 보냈는지 알 수 없습니다.
> - 보내면 그 순간의 **화면 사진과 기기 정보**가 함께 갑니다. 남에게 보이면 안 되는 것이 화면에 있을 땐 보내지 말아 주세요.
> - 연달아 보내면 「조금 뒤에 다시」가 뜰 수 있습니다(30초에 한 번).

같은 와이파이에서 여럿이 테스트하면 30초 1번·하루 20번을 함께 쓴다 — 자주 막히면 사용자에게 알리고 `rate-limit` 어댑터 값을 늘릴지 묻는다.

## 9. 실패할 때 — 404면 먼저 승인 대기

보냈는데 이슈가 안 생기면 **화면 문구보다 서버 로그를 먼저 본다.** 실패한 제출도 「30초에 1번」에 세서, 실패 직후 다시 누르면 「조금 뒤에 다시」만 떠 진짜 원인이 가려진다.

[AI] Vercel 함수 로그에서 `[qa-feedback]` 줄을 찾는다(`vercel logs <배포 주소>` 또는 대시보드 → 프로젝트 → **Logs**). 줄에는 상태 코드와 캡처 바이트만 있다.

| 로그 | 뜻 | 할 일 |
|---|---|---|
| `이슈를 만들 뻔했어요 (GitHub 설정 없음)` + `missing` | 환경변수가 빠졌거나 넣은 뒤 다시 배포 안 함 | 6.2의 이름 확인 → 다시 배포 |
| `GitHub 설정이 잘못됐어요` | 저장소 이름이 `owner/repo` 모양이 아님 | 값 확인 |
| `이슈를 만들지 못했어요` + `issue: 404` (또는 캡처 `status: 404`) | **먼저 토큰이 Pending(승인 대기)인지** — 그다음 Repository access에 그 저장소가 골라졌는지, Resource owner가 맞는지 | 5.2 승인 확인. 401·403·404는 재시도하지 않고 원인을 바꾼다 |
| `issue: 401` | 토큰 값이 틀렸거나 만료·폐기 | 재발급 → 6.2 |
| `issue: 403` 또는 `429` | 권한 부족 또는 GitHub 한도 | 권한 칸 확인. 한도면 기다린다(재시도 금지) |
| `이슈를 만들었어요` + `label: "included"` 또는 `label: 200` | 성공 — 200은 GitHub가 라벨을 조용히 버려서 「라벨 붙이기」를 한 번 더 불러 붙인 것 | 없음 |
| `이슈를 만들었어요` + `label`이 그 밖의 숫자 | 이슈는 생겼고 라벨 붙이기만 실패 | 라벨 이름·존재 확인(4) |
| `shot: { state: "upload-failed", status: … }` | 캡처 커밋만 실패 — 이슈엔 「캡처 실패」 | 캡처용 토큰·캡처 저장소(README로 기본 브랜치가 있나) 확인 |
| 로그가 아예 없음, 화면은 403 | 같은 출처 검사 — 다른 주소에서 보냈거나(로그인 없는 방식) Origin 머리글이 없는 환경 | 어느 브라우저·주소였는지 사용자에게 묻는다(실측 필요 항목) |
