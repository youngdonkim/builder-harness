# project-init — 프로젝트에 하네스 적용·동기화

하네스는 **파일 복사로 배포**한다. builder-harness 저장소가 원본(SoT, Source of Truth — 정답이 되는 하나뿐인 출처)이고, 이 스킬이 그 원본의 파일들을 프로젝트로 복사해 하네스 적용을 완성한다. 복사된 파일은 프로젝트 저장소에 커밋되므로, 팀원은 프로젝트를 clone(내려받기)만 하면 하네스가 이미 들어 있다 — 하네스 저장소를 따로 받을 필요가 없다.

이미 하네스가 적용된 프로젝트에서 재실행하면, 신규 복사 대신 원본과 비교해 갱신하는 동기화 모드로 동작한다.

## 전제 확인

1. **현재 폴더가 프로젝트 루트인가** — 프로젝트의 최상위 폴더에서 실행해야 한다.
2. **git repo인가** — 아니면 `git init -b main` 제안 (done-task·new-task·훅 모두 git 전제).
3. **하네스 원본 저장소가 어디 있나** — 아래 [하네스 원본 찾기](#하네스-원본-찾기).

## 하네스 원본 찾기

복사해 올 원본은 **로컬에 clone된 builder-harness 저장소**다. 순서대로 찾는다.

1. **기본 위치 `~/dev/builder-harness`** 를 먼저 본다. `payload/.claude/`가 있으면 그게 원본이다.
2. 없으면 사용자에게 경로를 묻는다 — "하네스 저장소를 어디에 받아뒀어?"
3. 아직 안 받았다면 clone을 제안한다:

   ```bash
   git clone https://github.com/youngdonkim/builder-harness.git ~/dev/builder-harness
   ```

원본을 찾았으면 **최신인지 확인**한다. `git -C <원본경로> pull --ff-only`를 제안한다 — 옛 원본을 복사하면 적용하자마자 뒤처진 상태가 된다.

그 다음 **적용할 커밋을 기록해둔다**. 스탬프 파일에 쓸 값이다:

```bash
git -C <원본경로> rev-parse --short=12 HEAD
```

## 모드 판별

프로젝트 루트에 `CLAUDE.md`가 이미 있거나 `.claude/harness-version`이 있으면 이미 하네스가 적용된 프로젝트다 → **동기화 모드**(아래 [동기화 모드 절차](#동기화-모드-절차))로 진행한다. 없으면 **신규 적용 모드**(아래 [진행 순서](#진행-순서-신규-적용-모드))로 진행한다.

## 진행 순서 (신규 적용 모드)

### 1. 아이디어 인터뷰 (3질문)

사용자에게 묻는다 — 이미 대화에서 나왔으면 생략. 답을 쉽게 꺼내게, 앞 두 질문은 아래 예시를 붙여 안내한다:

- **서비스 이름과 한 줄 정의** (이름은 repo명과 같아도 됨) — 예시: "밥심 — 혼자 사는 직장인을 위한 저녁 메뉴 추천 앱"
- **타겟 — 누가, 어떤 상황에서** — 예시: "야근 잦은 자취 직장인이 퇴근길에 '오늘 뭐 먹지' 고민할 때"
- **현재 상태** — 완전 새 아이디어인지, 이미 검증 일부 진행했는지

앞 두 답은 idea-to-mvp 1단계(UserStory)의 필수 입력 1·2와 같은 항목이다 — CLAUDE.md에 박혀 1단계가 다시 묻지 않는다.

### 2. 하네스 본체 복사 — 스킬·에이전트·훅

원본의 `payload/.claude/` 아래 세 폴더를 프로젝트 `.claude/`로 **통째로 복사**한다 (폴더 없으면 생성). 원본의 폴더 구조가 곧 프로젝트에 놓일 모양이다.

```
<원본>/payload/.claude/skills/  →  <프로젝트>/.claude/skills/
<원본>/payload/.claude/agents/  →  <프로젝트>/.claude/agents/
<원본>/payload/.claude/hooks/   →  <프로젝트>/.claude/hooks/
```

훅 스크립트에 실행 권한을 준다: `chmod +x <프로젝트>/.claude/hooks/*.sh`

`payload/.claude/settings-hooks.json` 자체는 복사하지 않는다 — 다음 단계에서 내용만 병합한다.

### 3. 훅 등록 — settings.json 병합

원본의 `payload/.claude/settings-hooks.json`은 **훅 등록 원본**이다. 이 파일의 `hooks` 블록을 프로젝트의 `.claude/settings.json`에 병합한다.

- 프로젝트에 `settings.json`이 없으면 그 내용 그대로 새로 만든다.
- 있으면 **기존 키를 전부 보존한 채** `hooks` 블록만 넣는다. 프로젝트가 이미 자기 훅을 등록해뒀다면 지우지 말고, 같은 이벤트 안에 하네스 훅을 덧붙인다 — 겹치는 하네스 훅(같은 스크립트 경로)은 하나만 남긴다.

경로는 `"$CLAUDE_PROJECT_DIR"/.claude/hooks/<이름>.sh` 형태라 프로젝트를 어디에 두든 그대로 작동한다.

`.claude/settings.json`은 저장소에 커밋되는 파일이라, 이 상태로 main에 합쳐두면 팀원 전원에게 똑같이 적용된다.

### 4. CLAUDE.md 생성

원본의 `payload/.claude/skills/project-init/templates/CLAUDE.md.template`을 프로젝트 루트에 `CLAUDE.md`로 복사하고 `{{...}}` placeholder를 1번 답으로 채운다. 템플릿 구조(작업 원칙 + 디자인 시스템 adapter 자리 + 앱 개발 컨벤션 자리)는 **수정하지 않고 그대로** — 하네스 표준이다. **idea-to-mvp 방법론 설명은 CLAUDE.md에 넣지 않는다** — 방법론은 스킬 발동 중에만 필요하고 스킬이 전부 관리한다. CLAUDE.md는 만드는 제품(앱)과 사용자 취향의 자리다.

### 5. rules 복사

템플릿의 `rules/` 아래 모든 파일을 프로젝트의 `.claude/rules/`로 복사한다 (폴더 없으면 생성). 현재 포함: `threat-model.md` (외부 도달 위협 모델 — 6단계 MvpBuild부터 실질 작동), `markdown-style.md` (마크다운 목차는 중첩 리스트로 — `**/*.md` 편집 시 트리거).

### 6. mvp 구조 생성

```
mvp/                   # 단계 산출물 (market-research.md 등이 단계 진행하며 생김)
docs/                  # 사람이 읽는 문서 (Claude 자동 로드 X)
```

**`.gitignore`에 `.claude/worktrees/` 추가** — 하네스는 작업을 워크트리(worktree, 같은 저장소를 작업 폴더 여러 개로 펼치는 git 기능) 단위로 하고, 워크트리 폴더가 저장소 안 `.claude/worktrees/`에 생긴다. 이걸 무시 목록에 넣지 않으면 `auto-wip-commit` 훅이 워크트리 폴더를 통째로 커밋해버린다. `.claude/`의 나머지(스킬·에이전트·훅·settings.json)는 계속 추적해야 하므로 `.claude/` 전체가 아니라 반드시 `worktrees/`까지 포함한 경로로 적는다.

### 7. 문서·CI 템플릿 복사

- 템플릿의 `docs/git-workflow.md`를 프로젝트의 `docs/git-workflow.md`로 복사한다 — `no-main-push`·`auto-wip-commit` 훅과 `new-task`·`done-task`·`rewind-task` 스킬이 따르는 워크플로를 사람이 읽게 정리해둔 문서다.
- 템플릿의 `.github/workflows/ci.yml`을 프로젝트의 `.github/workflows/ci.yml`로 복사한다 — lint + build를 도는 CI로, `done-task`가 머지 전에 이 통과를 기다린다.

### 8. 버전 스탬프 기록

프로젝트에 `.claude/harness-version` 파일을 만든다. `stale-harness-notice` 훅이 이 값을 원본 저장소의 최신 커밋과 대조해 뒤처짐을 알린다.

```
repo=youngdonkim/builder-harness
commit=<하네스 원본 찾기에서 구한 12자리 이상 커밋 sha>
date=<오늘 날짜 YYYY-MM-DD>
```

`repo=`는 원본 저장소 주소다. 포크해서 쓴다면 그 주소로 적는다 — 훅이 이 값으로 원격을 조회한다.

### 9. 마무리 안내

사용자에게 알린다:

- 방금 프로젝트에 들어온 것: `.claude/skills/`·`.claude/agents/`·`.claude/hooks/`·`.claude/settings.json`(훅 등록)·`.claude/harness-version`, 그리고 `CLAUDE.md`·`.claude/rules/`·`docs/git-workflow.md`·`.github/workflows/ci.yml`. **전부 이 프로젝트 저장소에 커밋할 파일**이다 — 커밋해서 main에 합치면 팀원은 프로젝트를 clone하는 것만으로 하네스를 그대로 받는다. 팀원이 하네스 저장소를 따로 받을 필요는 없다.
- 훅 2개가 자동 작동: `no-main-push`(main 직접 push 차단), `auto-wip-commit`(응답 끝날 때마다 feature 브랜치에 wip 커밋 — 메인 폴더는 main이라 자동으로 건너뛰고, 워크트리에서만 돈다). 뭔가 잘못돼서 되돌리고 싶으면 `/rewind-task` 스킬을 쓴다.
- **지금 열린 세션에는 새 스킬·훅이 아직 안 잡힌다** — 새 세션을 열거나 `/clear`를 하면 잡힌다.
- 하네스를 나중에 최신으로 올리려면: 하네스 원본 저장소에서 `git pull` → 이 프로젝트 세션에서 "하네스 동기화해줘". **앱 재시작은 필요 없다.**
- 다음 단계: `/idea-to-mvp`로 1단계 UserStory 시작. (이미 검증 일부 진행한 프로젝트면 해당 단계부터.)

## 동기화 모드 절차

이미 하네스가 적용된 프로젝트에서는 신규 복사 대신, 프로젝트에 있는 파일을 원본과 비교해 갱신한다. 먼저 [하네스 원본 찾기](#하네스-원본-찾기)로 원본 위치를 확인하고 최신인지 확인한다.

비교 대상 파일은 **소유가 누구냐에 따라 두 부류**로 갈리고, 부류마다 기본 처리가 다르다.

### 1. 하네스 소유물 — 교체가 기본

프로젝트에서 고치지 않는 전제의 파일들이다. 하네스가 관리하니 **원본 내용으로 교체**하는 게 기본이다.

- `payload/.claude/skills/*` ↔ `.claude/skills/*`
- `payload/.claude/agents/*` ↔ `.claude/agents/*`
- `payload/.claude/hooks/*` ↔ `.claude/hooks/*`
- `payload/.claude/settings-hooks.json`의 hooks 블록 ↔ `.claude/settings.json`의 hooks 블록

처리 갈래:

- **동일** → 넘어간다.
- **프로젝트에 없음** (원본에 새로 생긴 파일) → 복사한다.
- **원본에서 사라짐** (이름이 바뀌었거나 폐기된 파일) → 프로젝트에서도 지운다. 지우기 전에 목록으로 보여주고 확인받는다.
- **다름** → 아래 [로컬 수정 흔적 판별](#2-로컬-수정-흔적-판별)로 갈라진다.

`settings.json`은 파일 전체가 아니라 **hooks 블록만** 하네스 소유물이다. 나머지 키(`permissions`·`env` 등 프로젝트가 넣은 것)는 손대지 않는다.

교체한 훅 스크립트에는 실행 권한을 다시 준다: `chmod +x .claude/hooks/*.sh`

### 2. 로컬 수정 흔적 판별

하네스 소유물인데 프로젝트 쪽이 원본과 다를 때, 그냥 뒤처진 것인지 프로젝트가 손댄 것인지 가른다.

- **원본의 옛 버전과 같다** → 그냥 뒤처진 것이다. 조용히 교체한다.
  - 옛 버전은 스탬프의 `commit=` 값으로 꺼낸다: `git -C <원본경로> show <스탬프커밋>:payload/.claude/<경로>`
- **원본의 옛 버전과도 다르다** → 프로젝트가 로컬에서 고친 흔적이다. **충돌로 보고 사용자에게 묻는다** — 어디가 어떻게 다른지 짚어주고 (a) 원본으로 교체 (b) 로컬 수정 유지 중 고르게 한다. 임의로 정하지 않는다.
- 스탬프가 없거나 그 커밋을 원본에서 못 찾으면(옛 원본이거나 커밋이 사라졌으면) 판별할 수 없다 → 안전하게 **충돌로 보고 물어본다**.

### 3. 프로젝트 소유물 — 병합이 기본

프로젝트가 자기 사정에 맞게 고칠 수 있는 파일들이다. 덮어쓰지 않고 **병합**한다.

- `templates/CLAUDE.md.template` ↔ `CLAUDE.md` (전체가 아니라 공용 문구만 — 비교 범위는 아래 [4. CLAUDE.md 비교 범위](#4-claudemd-비교-범위--공용-문구만))
- `templates/rules/*` ↔ `.claude/rules/*`
- `templates/docs/git-workflow.md` ↔ `docs/git-workflow.md`
- `templates/.github/workflows/ci.yml` ↔ `.github/workflows/ci.yml`

(템플릿 경로는 원본의 `payload/.claude/skills/project-init/templates/` 아래다.)

파일마다 세 갈래로 처리한다:

- **동일** → 넘어간다.
- **프로젝트에 없음** (템플릿에 새로 추가된 파일) → 그대로 복사한다.
- **다름** → **병합이 기본 동작이다.** 프로젝트가 의도적으로 커스텀했을 수 있으니 덮어쓰지 말고, AI가 곧장 병합안을 만든다 — 기존 내용은 그대로 두고 템플릿에서 새로 생기거나 바뀐 대목만 합친다. 어떤 파일의 무엇이 어떻게 합쳐지는지 요지를 한 줄씩 모아 보여주고, 사용자가 확인하면 반영한다.

병합에는 안전 규칙 둘이 있다:

- **진짜 충돌은 AI가 임의로 정하지 않는다** — 같은 대목을 템플릿과 프로젝트가 서로 다르게 고쳤으면, 그 대목만 양쪽 내용을 나란히 짚어 어느 쪽으로 갈지 사용자에게 물어본다. 안 겹치는 나머지는 그대로 합친다.
- **확인 없이 파일에 쓰지 않는다** — 병합도 예외가 아니다. 병합안을 보여주고 사용자 확인을 받은 뒤에만 파일을 고친다.

병합안을 본 사용자가 다른 걸 원하면 아래 두 갈래로 빠질 수 있다 (기본이 아닌 예외 경로다):

- **(a) 템플릿으로 교체** — 커스텀을 버리고 최신 템플릿 내용으로 덮어쓴다.
- **(b) 커스텀 유지** — 템플릿 변경을 무시하고 그대로 두고, 마무리 보고에 남긴다.

### 4. CLAUDE.md 비교 범위 — 공용 문구만

`CLAUDE.md`도 비교 대상이다. 다만 다른 파일과 성격이 달라서, 파일 전체가 아니라 **템플릿에서 온 부분만** 대조한다.

- **보존 대상 (대조 안 함)** — placeholder가 채워진 프로젝트 고유 내용(서비스 이름·한 줄 정의·타겟 등)과 프로젝트가 스스로 추가한 문장·섹션(디자인 시스템 adapter에 채워진 경로, 앱 개발 컨벤션에 쌓인 규칙 등). 템플릿과 다른 게 정상이고, 병합해도 그대로 남는다.
- **대조 대상** — 템플릿에서 그대로 오는 공용 문구와 구조. 작업 원칙 섹션, 진행 방식·기획 문서 위치 안내문, 섹션 골격과 제목, 그 안에 박힌 단계 번호 같은 것. 신규 적용 모드에서 "수정하지 않고 그대로" 복사하는 부분([4. CLAUDE.md 생성](#4-claudemd-생성))이 곧 이 범위다.

*왜 대조하나*: 공용 문구는 하네스가 바뀌면 같이 낡는다. 예를 들어 `/idea-to-mvp`가 7단계로 개편되면 프로젝트 CLAUDE.md에 남은 "6단계로 검증·개발한다"가 틀린 안내가 되는데, 파일 전체를 비교에서 빼두면 아무도 못 잡는다.

다르면 §3과 똑같이 병합이 기본이다 — 프로젝트 고유 내용은 손대지 않고 공용 문구만 최신으로 맞춘 병합안을 보여주고, 확인받아 반영한다.

### 5. 폴더·설정 보정

`mvp/`·`docs/` 폴더는 신규 모드와 동일하게, 없으면 채운다. `.gitignore`에 `.claude/worktrees/` 항목이 없으면 채운다.

### 6. 스탬프 갱신

반영이 끝나면 `.claude/harness-version`의 `commit=`을 이번에 적용한 원본 커밋으로, `date=`를 오늘 날짜로 갱신한다. 파일이 없으면 [8. 버전 스탬프 기록](#8-버전-스탬프-기록) 형식으로 새로 만든다.

**사용자가 로컬 수정을 유지하기로 골라서 원본과 다른 파일이 남았어도 스탬프는 갱신한다** — 스탬프는 "언제 기준 원본과 맞춰봤나"를 가리키는 값이지 "모든 파일이 원본과 똑같다"는 보증이 아니다. 다만 남은 차이는 마무리 보고에 반드시 적는다.

### 7. 마무리 보고

**두 부류가 드러나게** 나눠 보고한다.

- **하네스 소유물** (스킬·에이전트·훅·훅 등록) — 교체됨 / 새로 복사됨 / 삭제됨 / 로컬 수정 유지됨(사용자가 고름) / 전부 최신
- **프로젝트 소유물** (CLAUDE.md 공용 문구·rules·git-workflow.md·ci.yml) — 병합됨 / 새로 복사됨 / 템플릿으로 교체됨(사용자가 고름) / 커스텀 유지됨(사용자가 고름) / 전부 최신

끝에 스탬프를 어느 커밋으로 갱신했는지 적고, 갱신·복사·병합한 파일의 커밋은 그 프로젝트의 git 워크플로(feature 브랜치 → PR)를 따르도록 안내한다. **지금 열린 세션에는 바뀐 스킬·훅이 아직 안 잡히니 새 세션이나 `/clear` 뒤부터 적용된다**는 것도 함께 알린다.

## 안 하는 것 (의도적)

- ❌ 앱 스캐폴딩(`package.json`·`src/`) 생성 — 그건 6단계 MvpBuild 영역
- ❌ GitHub repo 생성·push — 사용자가 원할 때 별도로
- ❌ 기존 CLAUDE.md 무단 덮어쓰기 — 동기화 모드에서도 프로젝트 고유 내용은 병합으로 보존하고, 반영은 사용자 확인 뒤에만
- ❌ 하네스 원본 저장소를 프로젝트에서 고치기 — 하네스 개선은 builder-harness 저장소에서 PR로. 프로젝트 `.claude/` 안의 복사본을 고쳐봐야 다음 동기화에서 충돌로 잡힌다
- ❌ 프로젝트 `.claude/settings.json`의 hooks 이외 키 건드리기
