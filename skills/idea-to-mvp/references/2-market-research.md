## 1. 단계 목표

- **경쟁 지형 파악** — 비슷한 서비스가 이미 있는지, 있으면 얼마나 자리잡았는지 찾아본다.
- **시장 크기 감 잡기** — 정확한 시장 규모 추정이 아니라, "이 정도면 관심 있을 사람이 있겠다/없겠다"를 가늠할 참고 수치(트래픽·다운로드·언론 노출 등) 정리.
- **판정 없음** — 경쟁 강도(없음/약함/강함/매우 강함) 판정과 차별화 축 분석은 여기서도 정리하지만, *참고 정리*지 게이트가 아니다. "매우 강함이니 접어라" 같은 권고 문구는 쓰지 않는다. **경쟁이 너무 치열하거나 시장이 없다고 유저가 판단하면 여기서 접는 것도 존중한다** — 이 스킬은 정보만 제공하지, 계속할지 포기할지를 대신 정하지 않는다. 반대로 강함·매우 강함이어도 유저가 계속하고 싶으면 그대로 진행해도 된다.
- **구현사례 정찰 겸함** — 이후 4단계(DemoValidation) 인터뷰 질문지를 날카롭게 만들 때 쓸 경쟁자·빈틈 정보도 이 단계에서 함께 정리한다(정찰은 이 단계 하나로 일원화 — 4단계엔 이 결과를 참조하는 짧은 포인터만 남는다).

**왜 그래도 이 조사를 하나** — 게이트가 아니라고 조사 자체가 무의미한 건 아니다. 경쟁자·시장 감을 미리 봐두면 3단계(Mockup) 목업 방향을 잡을 때(어떤 화면·기능에 힘을 줄지), 4단계(DemoValidation) 인터뷰 질문을 만들 때(어떤 불만·빈틈을 찌를지) 훨씬 날카로워진다. 게이트가 아니라 **다음 단계를 더 잘하기 위한 사전 조사**로 이 단계를 본다.

## 2. 진행 절차

### 2.1 단계 시작 — 이전 정리 내용을 보여주고, 이번 단계가 할 일을 안내한다

1. **이전 단계까지 정리된 내용을 먼저 보여준다.** `mvp/user-story.md`의 로그라인과 `# 입력 (확정)` 5개(①서비스 이름과 한 줄 정의 ②타겟 ③현재의 대안과 불편함 ④해결책의 핵심 아이디어 ⑤아이디어를 떠올린 경로)를 짧게 요약해 보여준다.
2. **그 내용을 기반으로 이번 단계가 무엇을 하는지 설명한다.** 비슷한 서비스가 있는지 찾아보고, 있으면 어느 정도로 자리잡았는지 보고, 다음 단계(목업 제작) 방향을 잡는 데 참고할 힌트를 정리하는 자리라고 안내한다. **판정은 하지 않는다는 것도 짚는다** — "여기서 뭐가 나오든 계속할지는 네가 정하는 거야, 나는 정보만 정리해줄게".
3. **진입 조건**: `user-story.md`가 있으면 그걸 입력으로 진행. 없으면(강행 진입 — SKILL.md §4) 아이디어·타겟을 자유 형식으로 직접 받아 진행한다.
4. **이미 `market-research.md`가 있으면**(스킬 중간 재실행 등) 읽고 §3 체크리스트로 검증해 부족한 부분만 보완한다.

### 2.2 Step 1. 경쟁자 발견 — 사용자 + Agent deep research

**소스 둘**:

1. **user-story.md에서 언급된 대안·임시방편** — 입력 ③(현재의 대안과 불편함)에 이미 있는 단서.
2. **AI가 Agent tool로 deep research 위임** — 사용자가 모르는 경쟁자 발견 (아래 "실행 전 확인" 통과 시).

**0번 경쟁자 = 사용자의 현재 해결책 (필수 포함)** — 경쟁자는 같은 업종 서비스만이 아니다. 사용자가 지금 문제를 때우는 방법(엑셀·카톡 메모·네이버 카페 검색·"그냥 참기")이 실전에서 가장 센 경쟁자인 경우가 많다. `user-story.md`의 대안·불편함 단서를 **경쟁자 표의 0번 줄**에 넣는다.

#### 실행 전 — 요금제·한도 확인 (필수)

deep-research는 무거운 워크플로다 — 검색·검증 에이전트가 수십 개 돌고 토큰이 수백만 단위로 나갈 수 있다. AI는 사용자의 요금제·남은 한도를 볼 수 없으므로, 실행 전에 반드시 사용자에게 확인받는다:

1. **고지·질문**: "이 조사는 토큰을 많이 쓰는 작업이라 먼저 확인하자 — ① 고한도 요금제(예: Claude Max 20x, 월 $200대)야? ② 남은 사용량 여유 있어? (터미널 `/usage`, 웹·앱은 claude.ai 설정 > 사용량)" — 한도 종류는 요금제마다 달라 나열하지 않고 "남은 사용량"으로 뭉뚱그려 묻는다.
2. **분기**:
   - 고한도 요금제 + 여유 → deep-research 실행
   - 고한도 요금제 + 애매·부족 → (a) 한도 리셋 후 실행 (b) 아래 라이트 정찰 먼저, 본 정찰은 회복 후
   - **그 외 요금제 → 라이트 정찰이 기본** — deep-research를 권하지 않는다
3. **실행 중 한도 초과로 일부 실패하면**: 검증 통과분만으로 종합하되 검증 못 끝낸 주장은 **미검증**으로 구분 표기하고, 리셋 후 이어서 재실행 가능함을 알린다.

#### 라이트 정찰 — deep-research 대체 경로 (기본값)

대부분의 요금제에서는 이 경로가 기본이다:

- AI가 워크플로 없이 웹 검색 몇 건으로 **유사 서비스를 최대한 발굴**한다 (이름·한 줄 설명·수익화 방식 수준).
- 리뷰·평판 수집은 **사용자 몫으로 안내**한다 — 발굴된 각 서비스에 대해 **어디를 보면 좋은지** 짚어준다: 앱스토어·플레이스토어 리뷰(별점 낮은 순 정렬), 네이버 카페·블로그 참가 후기, 커뮤니티(블라인드·디시 등) 검색어까지.
- 사용자가 모아 온 리뷰·후기를 AI가 아래 형식(빈틈·불만)으로 정리한다.

라이트 정찰이든 deep-research든, 캐는 것은 같다:

| 캐는 것 | 예 |
|---|---|
| 존재·구현·수익화 방식 | 같은 문제 푸는 서비스 각자 *어떻게* |
| 채택·트랙션 | 다운로드·투자·*서비스 종료* 여부 |
| **공개 불만 (★1~2 리뷰·카페)** | *뭐가 불편한지 글로 박힌 것* |
| **빈틈** | 다들 *얕게*만 하거나 안 건드리는 부분 |
| tarpit | 많이 시도→다 실패·다 얕음 = 구조적 이유 의심 |

> **정찰의 한계 — 인터뷰로 넘길 것**: 이 정찰이 보는 건 (4단계 §2.7.2 강도표 기준) **★★(기존 열등 대체재 반복 사용 — 제품·리뷰·불만글)**까지다. **★★★(자기가 만든 사적 임시방편 — 엑셀·반복 문의)**는 검색에 안 잡혀 4단계(DemoValidation) 인터뷰에서만 발굴된다. 정찰 = *빈틈 가설 생성기*일 뿐, **정찰로 인터뷰를 대체하지 말 것.**

##### 표본 정직성 룰 — 리뷰·평판을 부풀리지 않는다

정찰이 수집한 앱스토어·플레이스토어 리뷰, 카페·커뮤니티 글은 **검색에 걸린 극히 일부 표본**이다. 보고할 때:

- **건수·날짜를 그대로 밝힌다** — "2021년 리뷰 1건"처럼. 3건 미만이면 "사용자들이 불만"류 복수·일반화 표현 금지, "개별 사례"로 표기한다.
- **실제 사용자 글과 AI의 구조 관찰을 구분한다** — "리뷰에 불만이 있다"와 "페이지를 보니 그 기능이 없더라"는 다른 종류의 근거다.
- **한계를 말한 뒤, 사용자가 직접 볼 곳을 권한다**: 앱스토어·플레이스토어 리뷰 전체(별점 낮은 순), 네이버 카페·블로그 참가 후기, 커뮤니티 검색. 직접 10분 훑는 표본이 AI 검색 표본보다 크다.

#### Agent 호출 명세 (선택 — 고한도 요금제 + 더 깊이 보고 싶을 때)

- **agent type**: `general-purpose`
- **호출 시점**: 위 "실행 전 확인"에서 deep-research 분기가 났을 때
- **prompt 형식**:

```
다음 아이디어의 경쟁자를 한국·전세계 시장에서 N=3~7개 찾아 분석해줘.

각 경쟁자별 다음 항목:
- 한 줄 요약 (서비스 정의)
- 코어 기능 리스트
- 입력 방식·결과 형태
- 가격 모델 (무료·프리미엄·B2B)
- 타겟 사용자
- UX 인상 (직관·복잡)
- **약점·빈틈** (서비스가 못 해주는 것 — 가장 중요)

아이디어: [`user-story.md` § 입력 확정 ①②④에서 도출한 한 줄]
도메인 키워드: [도메인 키워드 3~5개 — 예: "일정 관리", "팀 협업", "노트 앱"]

WebSearch·WebFetch 활용. 결과는 markdown 표로 정리해 반환.
직접 도구가 없으면 *블로그·법무사 글·언론 콘텐츠* 수준이라고 명시.
```

#### 호출 결과 처리

- Agent 결과를 사용자에게 보여주고 _false positive(경쟁자 아닌데 잘못 잡힌 것) 제거·추가 경쟁자 보강_ 받음
- 사용자가 *경쟁자 없다*고 우길 때: AI가 한 번 더 _검증 권장_ (자기 검열) — 진짜 없을 수도 있고 못 찾은 것일 수도

### 2.3 Step 2. 경쟁자 깊이 분석 — 각 경쟁자 WebFetch 보강

Step 1 결과 + 사용자 추가 경쟁자에 대해:

- 각 경쟁자별 WebFetch로 상세 페이지 확인 (가격·기능·UX)
- *직접 접속 가능*한 경쟁자만 (앱·인증 필요 서비스는 사용자가 알려준 내용 기반)
- §4.1 산출물 스펙 표 형식으로 정리

### 2.4 Step 3. 경쟁 강도 참고 정리 (등급 4개 — 텍스트 표기, 판정 아님)

| 등급          | 설명                                           | 참고 포인트                               |
| ------------- | ---------------------------------------------- | --------------------------------------- |
| **없음**      | 직접 경쟁 서비스가 없다 (블로그 글·법무사 글·뉴스 수준만) | §2.4.1 의심 절차로 왜 없는지 한 번 점검해두면 좋음 |
| **약함**      | 경쟁 서비스가 있지만 일부 기능만 하거나, UX가 약하거나, 사용자가 적다 | 차별화 힌트 1~2개 정도만 정리해도 충분 |
| **강함**      | 제대로 된 서비스 + 시장 점유 + 충성 사용자가 있다 | §2.5 차별화 축을 좀 더 살펴보면 도움 됨                       |
| **매우 강함** | 기존 강자(incumbent)가 자본·브랜드·네트워크 등 해자로 시장을 쥐고 있다 | 해자가 세다는 뜻 — §2.5를 꼼꼼히 보고, 이 조건에서 계속할지는 유저가 판단 |

**정리에 포함하면 좋은 것**:

- 시장 점유 수치 (트래픽·다운로드·언론 노출 등 추정 가능 데이터)
- 충성 고객 신호 (커뮤니티 후기·재사용·추천(referral))
- **해자 체크리스트 5개** — "강함"과 "매우 강함"을 가를 때 아래 5개를 훑고 결과를 기록해두면 참고가 된다. 해자는 성 둘레에 파 놓은 물길이다 — 후발주자가 쉽게 못 건너는 장벽. ("몇 개 이상이면 매우 강함" 같은 기계적 기준은 두지 않는다 — 근거 없는 숫자는 가짜 정밀함이다.)

| 해자 | 확인 질문 |
|---|---|
| 네트워크 효과 | 사용자가 늘수록 그 서비스가 더 좋아지는 구조인가? (양면 시장·커뮤니티) |
| 전환 비용 | 사용자가 갈아타려면 무엇을 잃는가? (쌓아둔 데이터·익힌 습관·연동) |
| 데이터 축적 | 경쟁자가 시간을 들여 쌓은 데이터를 후발주자가 따라잡을 수 있는가? (schlep — 하기 싫지만 쌓이면 해자가 되는 고된 노동) |
| 브랜드·신뢰 | 이 분야에서는 신뢰가 구매를 결정하는가? |
| 규제·독점 계약 | 면허·라이선스·독점 공급 계약이 진입을 막는가? |

#### 2.4.1 등급 "없음"일 때 — 기뻐하지 말고 의심하라 (참고 절차)

경쟁자가 하나도 없다는 것은 좋은 신호가 아닐 때가 훨씬 많다. **경쟁자가 없다는 건, 그 시장에 돈 낼 사람이 없다는 뜻일 가능성부터 의심해볼 만하다.** 목 좋은 길목인데 가게가 하나도 없다면, "내가 처음 발견했다!"보다 "여기 장사가 안 되는 이유가 있나?"를 먼저 묻는 것과 같다.

아무도 안 만든 이유는 보통 셋 중 하나다:

1. **사람들이 그 문제 해결을 안 원한다** (시장 없음 — 제일 흔함)
2. **만들어도 돈이 안 된다** (돈 낼 사람이 없다)
3. **정말로 새 기회다** (제일 드묾 — 이 경우엔 "왜 하필 지금 가능해졌나(why now — 기술·규제·행동 변화)"에 답할 수 있어야 한다)

**절차**: AI가 사용자에게 "왜 아무도 안 만들었을까?"를 묻고, 셋 중 어디에 해당하는지 함께 판단해 산출물에 기록한다. 이 판단은 참고용이지 폐기를 강제하지 않는다 — 1·2번에 해당한다고 느껴도 유저가 진행하고 싶으면 그대로 4단계(DemoValidation) 인터뷰에서 진통제 신호로 다시 확인하면 된다 (그 단계가 진짜 게이트다).

**반대 방향도 기억하라**: 경쟁자가 있다는 건 그 문제에 돈과 시간을 쓰는 사람들이 실제로 있다는 증거다. 그래서 "약함·강함 + 명확한 차별화"가 "없음"보다 오히려 좋은 패일 수 있다.

### 2.5 Step 4. 카테고리 재정의·차별화 축 검토 (참고 — 강함·매우 강함일 때 특히 유용)

**9개 차별화 축(axis) 후보**:

| 축(axis)                  | 설명                                                       |
| ------------------------- | ------------------------------------------------------------ |
| **A. 좁은 타겟**          | 고객 세그먼트 1개에 집중 (예: 특정 직군·상황 하나)         |
| **B. 통합 쐐기(wedge)**   | 여러 진통제를 한 흐름에 묶음 (예: 검색 + 비교 + 결제)      |
| **C. 사용 시점 이동**     | 경쟁자가 안 가는 시점으로 (작업 전·후 등)                  |
| **D. 유통 쐐기(distribution wedge)** | 콘텐츠·커뮤니티·검색으로 진입 (SEO·블로그·유튜브) |
| **E. 가이드 톤**          | 친구·멘토 톤 (점수 X → 다음 액션 안내)                     |
| **F. B2B 변환**           | 개인 대상 → 기업 대상(B2B)                                 |
| **G. 데이터 확장**        | 새 데이터 소스 추가 (공공·후기·암묵지)                     |
| **H. 가격 모델**          | 무료·프리미엄·구독(subscription) 등으로 차별               |
| **I. 카테고리 재정의**    | _흐름 역행·정의 자체 변경_ (예: 호텔 예약 → 남의 집 묵기 = Airbnb) |

각 axis × **사이드 모드 적합도** + **YC 평가** 두 점수를 매겨 참고 표로 정리한다. 추천 조합(예: A+B+D+E+I) + 사유도 기록해두면 3단계(Mockup) 방향 잡을 때 참고가 된다.

### 2.6 Step 5. YC 파트너 4명 시뮬 (선택)

큰 차별화나 카테고리 재정의를 고민 중이면 참고로 YC 4인 시뮬을 해볼 수 있다:

| 파트너                 | 시뮬 시각                                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **Paul Graham**        | 10x on one axis / Live in future / Schlep blindness — _한 축에서 10배 더 나은가, 미래 흐름에 부합하나, schlep을 피하지 않나_ |
| **Garry Tan**          | Why now·you / Schlep moat / Distribution — _지금 왜 이게 가능한가, 너가 왜 만드는가, 해자 있는가_                              |
| **Michael Seibel**     | Founder market fit / Make 10 users love it — _너가 이 사용자를 깊이 아는가, 10명이 사랑할 형태인가_                            |
| **Jessica Livingston** | Distribution path / Retention vs Referral — _사용자가 어떻게 발견하나, 돌아오나·소문 내나_                                     |

각자 _이 차별화로 들어가면_ 평가 1줄. 참고 신호일 뿐 통과·탈락 기준은 아니다.

### 2.7 Step 6. 조사 요약 정리

조사 결과를 한눈에 볼 수 있게 정리한다:

1. **경쟁 지형 한눈 요약** — 발견한 경쟁자·강도 등급·해자 체크 결과.
2. **차별화 힌트** — §2.5·§2.6에서 나온 축 추천(있으면).
3. **참고 수치** — 시장 크기 감을 잡을 수 있는 데이터(트래픽·다운로드·검색량 등, 있는 만큼).

**여기서 하지 않는 것 — 최종 아이디어·비목표·검증 가설·북극성 확정**: 이 4개(구 "빌더 가드레일")를 못 박는 절차는 이 문서가 아니라 **4단계(DemoValidation)의 go 분기**로 옮겼다 — 실제 인터뷰·데모 반응으로 검증된 시점에 확정하는 게 더 맞기 때문이다. 절차는 `4-demo-validation.md` §2.10.1 참조.

## 3. 완료 체크리스트

이 체크리스트는 **게이트가 아니라 품질 확인용**이다 — 미충족이어도 다음 단계 진행을 막지 않는다. 다만 부실하면 3단계(Mockup) 방향이 감으로 흐를 수 있다는 점을 유저에게 안내한다.

- [ ] **경쟁자 N=3+ 발견** (§2.2) — Agent 또는 라이트 정찰 + 사용자가 아는 경쟁자 통합 + **0번 줄(사용자의 현재 해결책)** 포함. §4.1 표 작성
- [ ] **각 경쟁자 깊이 분석** (§2.3) — 코어 기능·입력·가격·약점 채움
- [ ] **경쟁 강도 참고 정리** (§2.4) — 없음/약함/강함/매우 강함 + 근거 (시장 점유·충성 신호 + **해자 체크 5개 기록**)
- [ ] **등급 "없음"이면 의심 절차 기록** (§2.4.1) — "왜 아무도 안 만들었나" 판단 기록
- [ ] **(강함·매우 강함 시, 참고) 차별화 축 검토** (§2.5) — axis 후보 + 사이드 모드 + YC 점수 표
- [ ] **(선택) YC 4인 시뮬** (§2.6)
- [ ] **조사 요약 정리** (§2.7) — 경쟁 지형·차별화 힌트·참고 수치

## 5. 좋은 예 vs 나쁜 예

예시는 도메인 무관 — *유명 서비스*로 패턴만 본다. 핵심은 **구체·검증 가능·간결**(좋은) vs **추상·일반론**(나쁜).

### 5.1 경쟁자 발견

**좋은 예** (0번 경쟁자 + 발견 + 약점 구체):

> 할 일 앱 — 0번: "메모 앱 + 머릿속" (user-story.md 입력 ③). 경쟁자 N=5: Todoist · TickTick · Things · Notion · Apple 미리알림. 약점: "Notion = 무겁고 느림 / Apple 미리알림 = 협업 X".

**나쁜 예** ← 사용자 1명이 말한 것만:

> 경쟁자: Notion.

### 5.2 강도 참고 정리

**좋은 예** (점유·해자 근거):

> 매우 강함. 범용 검색엔진 진입 — Google 점유 90%+. 해자 체크: 네트워크 효과 O(검색량→품질 개선 고리) · 전환 비용 X · 데이터 축적 O(수십 년) · 브랜드 O · 규제 X. "그래도 좁은 틈새로 가볼래" — 유저 판단으로 진행.

**나쁜 예** ← 추측:

> 없음. 별로 없어 보임.

### 5.3 차별화 축(axis)

**좋은 예** (포화 시장 + 단일 축 10배):

> Superhuman: 이메일(포화 시장)에 A(좁은 타겟: 파워유저) + E(속도 단일 축 10배). "Gmail보다 빠른 이메일" 한 줄로 선다.

**나쁜 예** ← 막연:

> UX를 더 좋게 만들어 이긴다.

### 5.4 카테고리 재정의

**좋은 예** (흐름 자체를 바꿔 직접 경쟁 회피 — YC 단골 사례):

> Airbnb. 기존 카테고리 "호텔을 예약한다" → 재정의 "남의 집 빈방에 묵는다". 호텔 체인과 같은 링에서 안 싸운다.

**나쁜 예** ← 같은 카테고리 안 표면 차별:

> 더 싸고 예쁜 호텔 예약 앱.

### 5.5 모드·동기별 적용 차이

**나쁜 예** (모드 무시, 강행 권고):

> 사이드 + 매출인데 "매우 강함"이라고 무조건 "접어" → 유저 판단을 뭉갬.

**좋은 예** (참고만 주고 판단은 맡김):

> 사이드 + 매출 & 강함 → "이 정도면 축 1~2개로 좁힌 작은 쐐기(wedge)로 가는 게 유리해 보여. 계속할지는 네가 정해." / 풀타임 + 매출 & 강함 → "축 3+ 묶어서 정면 도전도 가능할 정도야. 자원 상황에 맞게 판단해."

## 6. 사용자 응대 톤 + 인터뷰 코칭

톤·코칭은 SKILL.md §1.3·§1.4 따름. 핵심 동작:

- §2 순서 따름: 발견 → 분석 → 강도 참고 정리 → 축 → 시뮬(선택) → 조사 요약.
- **게이트 아님을 반복 확인** — 판정 결과를 보여줄 때마다 "이건 참고 정보야, 계속할지는 네가 정해"를 붙인다.
- **사용자가 *경쟁자 없다*고 우길 때** — 한 번 더 검증 권장 (자기 검열). 진짜 없을 수도 있지만 못 찾은 것일 가능성 명시. 그래도 없으면 §2.4.1 의심 절차.
- **사용자가 모든 axis 욕심**낼 때 — 1~2개로 좁히기 권장 (참고일 뿐이라도 시간 보호 차원에서).
- **경쟁이 세다고 유저가 접겠다 하면** — 말리지 않는다. "그래, 그게 여기서 접는 거면 그것도 맞는 판단이야" — 존중하고 새 아이디어 시작 절차(SKILL.md §3) 안내.
- **정리한 산출물 보여주고 확인** — "이거 맞아? 고칠 데 있어?"
- 모르는 부분은 `추후 결정: ...`으로 명시.
