## 1. 단계 목표

- **배포된 실서비스** — 동결된 목업(`[projectName]-proto.html`)을 화면 정답지 삼아 실제 개발환경에서 구현하고, 백엔드·DB·auth·계측을 붙여 공개 URL로 접속 가능하게 배포.
- **베타 공유로 치명 결함 거르기** — 배포 링크를 4단계(DemoValidation) 인터뷰이에게 보내 실사용 반응 확인 (판정 아닌 확인).
- **퍼널 계측 심기** — 유입·가입·핵심행동·재방문·결제 5종 이벤트가 실제로 찍힘. 7단계(MvpLaunch) 판정의 데이터 원천.
- **(지불 가설 있으면) 실결제** — `demo-validation.md` 검증 가설에 지불 검증이 포함되면 실결제 연동 (fake door 아님).
- **`mvp-build.md`** — 스택 선택(ADR 링크)·계측 이벤트 정의·배포 정보·베타 공유 관찰 기록.

**SoT 책임** (SKILL.md §2.1): 스택 선택·버전 조합·퍼널 계측 이벤트 정의·배포 정보 = `mvp-build.md`. 화면·플로우 명세는 동결된 `[projectName]-proto.html`(정답지) 참조만 — 여기 중복 금지.

**여기서 안 하는 것 (의도적)**:

- ❌ PRD·Architecture·Design 문서 작성 — 동결된 proto.html이 스펙. 문서 ceremony 금지.
- ❌ 명세 밖 기능·화면 추가 — `추후 결정:` 마킹만.
- ❌ 다크모드·다국어·반응형 정교화·성능 튜닝·부하 대비 — production 영역. (단, 광고 유입 랜딩 경로(랜딩→가입→핵심행동)는 모바일 화면 확인이 필수 — 7단계 소액 광고 유입은 대부분 모바일이라, 이 경로가 모바일에서 깨져 있으면 퍼널 실측이 제품 반응이 아니라 깨진 화면을 재는 꼴이 돼 통과 기준②가 오염된다.)
- ❌ CI·테스트 스위트 정교화 — 검증 가설과 무관한 인프라 투자는 production에서.
- ❌ 광고·채널 준비 — 7단계(MvpLaunch) 영역 (단 결제 PG 심사처럼 리드타임 긴 것만 병렬 시작 OK).

## 2. 진행 절차

### 2.1 단계 시작 — 이전 정리 내용을 보여주고, 이번 단계가 할 일을 안내한다

이 단계에 들어오면 가장 먼저 사용자와 "지금까지 어디까지 왔고, 이제 무엇을 할지"를 맞춘다:

1. **이전 단계까지 정리된 내용을 먼저 보여준다.** 입력이 셋이다 — 동결된 프로젝트 루트의 `[projectName]-proto.html`(화면 정답지), `demo-validation.md` § 최종 확정 아이디어(+비목표·검증 가설·북극성 — 4단계 go 분기에서 확정된 4개), 그리고 직전 5단계 `market-research.md`의 조사 요약(경쟁 지형·차별화 힌트). 셋 다 짧게 요약해 보여준다. 앞의 둘이 **무엇을 만들지**를 정하는 스펙이고, 조사 요약은 **무엇부터 만들지·무엇을 미룰지**를 판단할 때 쓰는 참고 맥락이다 (없으면 없는 대로 진행). 여기에 `mvp/handoff/`(3단계 동결 시점에 받은 개발 인계 꾸러미 — 데이터 모델·규칙 의사코드·화면별 상태와 문구·디자인 토큰)가 있으면 **참고 입력으로 함께 읽는다**: 목업이 못 담는 규칙·수치가 적혀 있어 구현할 때 추측이 줄어든다. 단 화면 SoT는 여전히 동결된 목업이라 **둘이 어긋나면 목업이 기준**이다 (`3-mockup.md` §2.5).
2. **그 내용을 기반으로 이번 단계가 무엇을 하는지 설명한다.** 목업은 화면만 있는 정지된 그림이라, 이제 스택을 정하고 실제 개발환경에서 데이터가 흐르는 서비스로 구현 → 베타 공유로 치명 결함 확인 → 백엔드·계측을 붙여서 배포까지 한 번에 완주하는 단계라고 안내한다.
3. **`mvp-build.md` 머리에 `# 이전 결론 → 이번 결론` 섹션을 적는다** (SKILL.md §2.2). 체인의 직전 결론은 4단계(DemoValidation)의 '이번 결론'(최종 확정 아이디어·비목표·검증 가설·북극성)이다 — 5단계 MarketResearch는 참고 자료라 이 체인에 들어가지 않는다. 그 결론과 대조해 변경 여부를 확인한다 — 목업 순환(3↔4단계) 중이나 5단계 조사 중에 방향이 바뀌었다면 그 델타를 여기서 기술한다. 변경 없으면 `변경 없음 — demo-validation.md §최종 확정 아이디어 그대로` 한 줄로 충분.
4. **이미 `mvp-build.md`·앱 코드가 있으면**(스킬 중간 재실행 등) 읽고 §3 체크리스트로 검증해 부족한 부분만 보완한다.

**진입 조건**: 프로젝트 루트에 `[projectName]-proto.html`이 존재하고, 4단계(DemoValidation) go 판정(구조적 수정 0건 수렴)을 통과한 상태여야 한다. 아직 순환 중이면 강행하지 말고 4단계로 돌아가 마무리를 안내한다. 5단계 `market-research.md`는 있으면 참고하고 없으면 없는 대로 간다 — 그 단계는 게이트가 아니다.

### 2.2 스택 선택

이 절차는 SKILL.md §1.5 **인터뷰 모드** — 에스컬레이션 기준 (c) "결과를 되돌리기 비싼 갈림길"에 해당하는 결정이라, AI가 임의로 정하지 않고 사용자에게 확인받는다.

**기본: React 웹.** idea-to-mvp의 고정 스택(Next.js · React · TypeScript · Supabase · Vercel)과 그대로 정합되고, 배포하면 링크 하나로 공유돼 베타 공유(§2.4)의 마찰이 가장 적다. 별다른 이유가 없으면 이걸로 간다.

**Expo/React Native로 갈아타는 경우** — 다음처럼 **네이티브 기능이 검증 가설 자체의 핵심**일 때만:

- 푸시 알림
- 위치(GPS)
- 카메라(QR 스캔 등)
- 오프라인 동작

이 경우 다음을 사용자에게 명시적으로 짚는다:

- **앱스토어 심사 마찰** — 심사 기간·정책 리스크가 있어 배포가 웹보다 느리다.
- **공유 비용** — 베타 공유(§2.4) 대상자가 Expo Go 앱을 설치해야 접근 가능하다(링크 하나로 끝나는 웹보다 마찰이 크다).
- **고정 core와의 괴리** — Supabase·Vercel 등 아래 §2.2.1 고정 core는 웹 기준으로 짜여 있어, Expo를 택하면 그 조사·적용 절차 상당 부분을 스스로 다시 판단해야 한다.

**선택 결과는 ADR로 기록한다** (`mvp/adr.md` — SKILL.md §3.1 "스택 주요 컴포넌트 추가·제거" 트리거). **스택 자체는 이후 에스컬레이션·재논의 대상이 아니다** — 한 번 정하면 이 단계 끝까지 고정.

#### 2.2.1 고정 core — 최신 호환 버전 조합만 조사·적용 (React 웹 선택 시, 초안 모드)

**React 웹을 택했으면 스택 자체는 고정이다 — 후보 제시·사용자 선택 없음.** idea-to-mvp 웹앱은 무조건 이 조합으로 빌드한다:

| 영역 | 고정 (mandated core) |
|---|---|
| 프레임워크 | Next.js (App Router) |
| 언어 | TypeScript |
| UI | React |
| DB·Auth | Supabase (`@supabase/ssr` + `@supabase/supabase-js`) |
| 호스팅 | Vercel |
| lint | eslint-config-next |
| 패키지 매니저 | npm |

**왜 고정** (매 프로젝트 재결정 안 함): 목업이 React 기반(Claude Design 산출물)이라 Next 이식이 자연스럽고, Supabase는 DB+Auth+소셜 로그인이 붙으면 바로 되는 최단 경로, Vercel은 main 머지→자동 배포+프리뷰. 빌드가 싼 시대엔 *뭘 쓸지*를 매번 고르는 ceremony를 없애고 *뭘 만들지*에 집중한다.

**mandated core 밖**은 프로젝트별 추가 (지도=leaflet, 아이콘=lucide, 결제 PG 등) — 검증 가설에 필요할 때만. core에서 빼거나 다른 것으로 갈아타는 건 이 단계에서 하지 않는다. (결제: 지불 가설 있으면 실결제 PG(토스페이먼츠·Stripe 등) 추가 — 심사 리드타임 있어 빌드와 병렬 시작.)

**이 단계에서 실제로 하는 일 = 고정 스택의 최신 호환 버전 조합을 상호 의존성 고려해 조사·적용** (초안 모드 — AI가 조사·적용·보고, 사용자 선택 없음). **버전 숫자는 휘발성이라 이 references에 박지 않는다.** 조합은 빌드 시점에 조사해 `mvp-build.md`·ADR에 기록한다:

1. Next.js 최신 stable 확인 → 그것이 요구하는 React·Node 버전(peer deps) 파악.
2. TypeScript·eslint-config-next를 그 Next와 호환되는 최신으로.
3. Supabase(`@supabase/ssr`·`@supabase/supabase-js`) 최신.
4. **조합 설치 검증** — `npm install`이 peer-dep 충돌(`ERESOLVE`) 없이 통과하는지. 충돌 시 마지막 호환 조합으로 한 칸 물러선다 (`--force`·`--legacy-peer-deps`로 덮지 말 것).
5. 해소된 정확한 버전을 `package.json`에 핀 + `mvp-build.md` 스택 표 + ADR에 조합 기록.

- **조사 소스**: 공식 docs·npm registry·context7 (최신 버전·peer 요구). LLM 학습 시점 이후 버전은 반드시 조사로 확인 — 기억으로 박지 말 것.
- **graceful degradation**: 조사가 불확실하면 마지막 known-good 조합으로 진행하고 `추후 결정: [무엇을 재확인]` 마킹.
- **에스컬레이션**: 고정 스택 자체를 못 쓰는 근본 비호환(예: 목업이 React 아님)일 때만 멈추고 사용자에게. 그 외엔 조사·적용 완주.

### 2.3 프런트 구현

이 절차는 SKILL.md §1.5 **초안 모드** — AI가 `[projectName]-proto.html`을 스펙 삼아 구현을 끝까지 완주한 뒤 완성본으로 리뷰받는다. 중간에 화면 하나하나 승인받지 않는다.

**`[projectName]-proto.html`은 이 시점부터 동결·정답지 전용이다** — 4단계 수렴 판정과 함께 이미 동결됐고, 이 단계에서 재생성하지 않는다. 화면 영역의 SoT(Source of Truth — 진실의 원천)는 이제 이 실제 코드로 승격된다.

#### ⚠️ standalone HTML에서 소스·카피 읽는 법 (grep이 안 먹힌다 — 반드시 이 절차로)

`[projectName]-proto.html`은 자급자족 단일 파일이라 **앱 소스(JSX/JS)·카피가 대개 압축·인코딩되어 들어있다.** 화면에 뻔히 렌더되는 문구를 `grep`/평문 검색하면 **0건이 나온다** — 없는 게 아니라 인코딩돼 있는 것이다. "파일에 없네" 하고 부차 파일로 폴백하면 안 된다 (SoT 아님). 화면이 렌더된다 = 카피는 이 HTML 안에 반드시 있다. 다음 순서로 뚫는다:

1. **가장 흔한 형: gzip → base64 리소스 맵** (Claude Design standalone 기본). 파일 안에 `{"<uuid>":{"mime":"application/javascript","data":"H4sI…"}}` 형태의 리소스 맵이 있고, `data`가 **`H4sI…`로 시작하면 gzip 시그니처**다. 추출: 그 JSON을 파싱 → 각 JS 리소스의 `data`를 **base64 디코드 → gunzip → utf-8 디코드** 하면 읽을 수 있는 원본 소스(카피 포함)가 나온다. (파이썬: `gzip.decompress(base64.b64decode(data)).decode("utf-8")`.)
2. **1번이 안 맞으면 파일 구조부터 파악** — 형식은 도구/버전마다 다르다. `grep 0건`을 "없음"으로 단정하지 말고 다른 인코딩 가능성을 훑는다: 인라인 `type="text/babel"` 스크립트(평문 JSX), JSON 이스케이프된 HTML 셸 문자열, 유니코드 이스케이프(`\uXXXX`), HTML 엔티티, 별도 base64 data URI 등. 가장 긴 줄들을 뜯어보면 어디에 뭉쳐 있는지 보인다.
3. **그래도 안 뚫리면** 브라우저 렌더 결과(사용자 스크린샷·DOM)를 근거로 삼되, **읽어낸 카피의 출처는 항상 이 HTML**로 고정한다.

**데이터**: 실 DB(Supabase) 연결과 로컬 상태(mock) 중, 이번 검증에 필요한 최소로 고른다. 검증 가설(`demo-validation.md` §최종 확정 아이디어 아래 검증 가설)을 확인하는 데 실제 저장·조회가 필요하면 실 DB로, 화면만 오가면 되는 부분은 로컬 상태로 충분하다 — 전부 실 DB로 미리 짓지 않는다.

**스코프**: `demo-validation.md`에서 확인된 핵심 플로우(Pull 신호가 나온 화면·기능)를 우선 구현한다. `demo-validation.md` §비목표에 명시된 것은 만들지 않는다.

**디자인 시스템 baseline**: 목업의 토큰·컴포넌트·화면을 실코드로 옮기는 작업은 같은 플러그인의 `design-system` 스킬을 호출해 그 방법론대로 한다. 빌드 시작 시 토큰 3층(foundation→semantic→component) 구축 + 컴포넌트 인벤토리 생성 + CLAUDE.md 연결 정보(adapter) 기록은 스킬의 bootstrap-project.md 절차대로 — 목업 HTML에 내장된 토큰·CSS가 이때 foundation·semantic을 채우는 원료다. 이후 모든 화면·컴포넌트 코드는 semantic 토큰만 참조한다 (hex·px 하드코딩 금지 — 스킬 철칙). 목업 화면이 스킬의 안티패턴에 걸리면(예: 목록 항목마다 카드 감싸기·상태색 장식 사용) 그대로 베끼지 않고 **스킬 쪽으로 고쳐서 이식한다** — 목업이 검증한 것은 플로우·구성·첫인상이지 최종 시각이 아니다. 무엇을 왜 고쳤는지는 `mvp-build.md` `# 빌드 중 발견`에 한 줄씩 기록.

**보안 baseline**: auth·API·업로드 코드를 만지면 `.claude/rules/threat-model.md`가 자동 로드된다 — 그 baseline(http-only cookie·권한 검사·IDOR 회피·rate limit·에러에 stack 미노출 등) 준수. 광고로 모르는 사람들이 실제로 들어오는 코드다.

**에스컬레이션**: 명세와 모순 발견·스키마가 크게 갈리는 선택·외부 서비스 추가 필요 시 멈추고 배치 질문. 그 외 애매함은 합리적 가정 + `추후 결정:` 마킹 후 계속.

**구현이 끝나면 임시 배포한다** — §2.4 베타 공유에 쓸 링크가 필요하다. 이 시점 배포는 백엔드가 아직 최소 상태(로컬 상태 위주면 그대로, 실 DB 연결이 필요한 부분만 최소 동작)여도 된다. 본격적인 백엔드·계측·최종 배포는 §2.5~2.6에서 마저 한다.

### 2.4 베타 공유

배포된 링크를 **4단계(DemoValidation) 인터뷰이(와 타겟 명단)**에게 보내 **실제 사용 반응**을 확인한다. 목업 데모가 못 보는 단 하나 — *동작할 때의 행동*(진짜 가입하나, 핵심 플로우에서 이탈하나) — 을 여기서 본다.

**판정 아님**: go/no-go 게이트가 아니라 치명 결함(가입 실패·핵심 플로우 이탈·심각한 오해) 확인용. 발견되면 수정 후 재공유, 없으면 §2.5(백엔드·계측)로 진행. 관찰 내용은 `mvp-build.md`에 짧게 기록한다.

**사용자가 직접 클릭하며 검증한다** — AI가 Playwright 같은 도구로 자동 사인오프하지 않는다 (SKILL.md §1.5 "사람 몫 불변"). AI는 배포까지 준비하고, 실제로 눌러보고 확인하는 건 사람 몫.

### 2.5 백엔드·계측

베타 공유에서 치명 결함이 없으면(또는 발견분을 수정·재공유했으면), 실서비스로 완성하는 작업을 마저 한다: 백엔드·DB·auth 연동 + 퍼널 계측 심기 + (지불 가설 있으면) 실결제 연동.

**범위 가드 (강제)**:

- 동결된 `[projectName]-proto.html` 명세에 없는 화면·기능 추가 금지. "이것도 있으면 좋겠는데" 신호는 `추후 결정:`으로 `mvp-build.md`에 마킹만.
- `demo-validation.md` §비목표 화면·기능은 빌드에도 없음.
- §2.3에서 MVP 마스크 처리했던 영역이 있다면 — 이번에 *실제로 작동*시켜야 하는지 `demo-validation.md`(핵심 플로우·검증 가설) 기준으로 판단. 가설 검증에 불필요하면 마스크 유지.
- 다크모드·다국어·반응형 정교화·성능 튜닝·CI 정교화는 범위 밖 (§1 "여기서 안 하는 것").

#### 백엔드·DB·auth 연동

**Supabase 연동 시 RLS(행 단위 보안 규칙, Row Level Security — 테이블마다 "누가 어느 행을 읽고 쓸 수 있나"를 DB가 직접 강제하는 규칙) 활성화 + 정책 작성은 필수다.** Supabase의 공개 키(anon key)는 브라우저에 그대로 노출되는 구조라, RLS를 안 걸면 그 키만으로 아무나 모든 테이블을 읽고 쓸 수 있다 — Supabase 프로젝트에서 가장 흔하고 치명적인 사고 지점이다. §2.3 보안 baseline(threat-model.md)과 함께 배포 전 반드시 확인한다.

#### 퍼널 계측 심기 (이 단계의 핵심)

7단계(MvpLaunch) 판정은 **여기서 심은 이벤트가 전부다** — 계측이 빠지면 광고비를 쓰고도 판정 불능. 5종 기본 이벤트:

| # | 이벤트 | 정의 (예시 — 서비스에 맞게 구체화) | 퍼널 위치 |
|---|---|---|---|
| 1 | 유입 | 랜딩 도착 (유입 채널 구분 파라미터 포함 — 발품 vs 광고 vs 기타) | 최상단 |
| 2 | 가입 | 계정 생성 완료 | 전환 1 |
| 3 | 핵심행동 | *이 서비스의 aha 순간* 1회 완료 (예: 매물 진단 1회) — 무엇으로 할지 사용자와 결정 | 활성화 |
| 4 | 재방문 | 가입 후 7일 내 재방문 | retention |
| 5 | 결제 | (지불 가설 있으면) 결제 완료 / (없으면) 가격 페이지 도달 등 지불 의사 프록시 | 수익 |

- **채널 구분이 필수** — 발품 유입과 광고 유입을 구분 못 하면 7단계(MvpLaunch) 이중 채널 판정이 무너진다. UTM 파라미터 등으로 구분.
- 계측 도구는 **Supabase 자체 이벤트 테이블 기본** (고정 스택에 이미 있음 — 별도 analytics SaaS 없이 5종을 테이블에 적재, 퍼널 쿼리를 SQL로). 무거운 SaaS는 지양.
- **이벤트 정의를 `mvp-build.md`에 표로 기록** — 7단계(MvpLaunch) launch-plan이 이 정의를 그대로 참조한다 (이름·정의 drift 방지).

#### 에러 관측

퍼널 계측과 별개로 에러를 감지할 수단도 확보한다 — 최소 배포 후 Vercel 대시보드의 런타임 로그(Runtime Logs, 서버 실행 중 발생한 에러·로그를 모아 보여주는 화면)를 확인하는 방법을 알아둔다. 원하면 Sentry류 경량 에러 추적 도구를 붙여도 되지만 필수는 아니다. 7단계 측정 기간에 가입 실패·결제 에러 같은 버그가 조용히 나면 퍼널 숫자가 나쁜 게 제품 탓인지 버그 탓인지 구분을 못 해 판정이 오염된다 — "버그는 즉시 고친다"는 룰(7단계)이 있어도 버그가 났다는 걸 아는 수단이 없으면 소용없다.

### 2.6 배포·완료

1. 최종 배포 (관리형 호스팅 기본). main 직접 push 금지 — PR 워크플로 (repo 훅이 막음).
2. **사용자가 배포 URL을 브라우저로 직접 클릭** — 핵심 시나리오 끝까지 통과 + 가입·핵심행동 이벤트가 실제로 찍히는지 확인 (AI가 자동 도구로 검증·사인오프하지 않음 — SKILL.md §1.5 사람 몫).
3. 실결제 연동했으면 **실결제 테스트 1건** (결제 → 환불) — 사용자가 직접.
4. 발견된 문제는 초안 모드로 수정 → 재배포 → 재확인 (자율 재작업 상한 2회 — SKILL.md §1.5).

베타 공유·백엔드·계측·배포가 모두 끝나면 7단계(MvpLaunch)로 넘어간다.
