# new-task

사용자 대신 **작업 폴더 단위**로 작업 전환을 안전하게 자동화하는 스킬.

작업 폴더는 워크트리(worktree)로 만든다 — 같은 저장소를 작업 폴더 여러 개로 펼치는 git 기능이다. 작업 하나에 폴더 하나, 브랜치 하나가 1:1로 붙는다.

폴더까지 나누는 이유가 있다. 세션 2개를 같은 폴더에서 돌리면 `auto-wip-commit` 훅이 `git add -A`로 폴더 전체를 커밋하기 때문에, 한 세션이 다른 세션이 편집 중이던 파일까지 쓸어담는다 (실제로 문서 개편 283줄이 무관한 PR에 섞여 머지된 사고가 있었다). 폴더가 나뉘면 훅이 애초에 남의 파일을 볼 수 없어 이 문제가 구조적으로 사라진다.

그래서 저장소 루트(= 메인 폴더)는 **항상 main을 지킨다.** 작업은 전부 `.claude/worktrees/<type>/<topic>` 폴더에서 한다.

**세션 이동은 2단이다.** fork로 도는 이 스킬은 워크트리를 만들고 경로를 보고할 뿐이고, 세션을 그 폴더로 옮기는 `EnterWorktree` 호출은 **메인 세션이** 한다 (서브에이전트가 호출해봐야 부모 세션은 안 따라온다).

이 2단 인계는 실제로 끊긴 적이 있다. fork 결과는 `<local-command-stdout>` 블록으로 메인 세션에 도착하는데, 하네스가 그 블록에 "명령 출력에 반응하지 말라"는 주의문을 붙인다. 그래서 보고 끝에 붙여둔 "메인 세션이 할 일"이 통째로 무시되고 세션이 메인 폴더(main)에 그대로 남았다. 그 상태로 작업하면 편집이 메인 폴더에 쌓이고, `auto-wip-commit`은 main에서 skip이라 자동 저장도 안 걸린다.

그래서 인계를 **두 겹**으로 건다:

1. **보고 맨 앞** — 완료 보고의 첫 블록이 `EnterWorktree` 호출 지시다 (§5). 맨 끝에 두면 묻힌다.
2. **인계 표식 + 훅** — 워크트리를 만들 때 `git config`에 표식을 남기고(§4-c), `pending-worktree-guard` 훅이 응답이 끝날 때마다 세션이 실제로 그 폴더에 앉았는지 확인해 안 옮겼으면 한 번 막고 알린다. 1번이 뚫려도 여기서 걸린다.

이 스킬은 `context: fork`로 git-flow 서브에이전트(sonnet)에서 격리 실행된다 — 메인 세션 토큰 절약 목적. 실행 중 사용자 질문이 불가능하므로 결정 지점은 [결정 필요] 반환 → 메인이 사용자에게 확인 → **사용자가 직접** 결정을 args에 담아 슬래시 명령으로 재호출하는 프로토콜을 쓴다. (`disable-model-invocation: true`라 AI는 이 스킬을 재호출할 수 없다 — 재호출 입력은 반드시 사용자 몫. 예외적으로 급할 땐 메인 세션이 git-flow 에이전트를 직접 호출해 SKILL.md 절차 + 결정을 프롬프트로 넘겨 실행하는 우회가 가능하다.)

## 진입 전 가정

- 프로젝트 루트 디렉토리는 git repo임
- `.gitignore`에 `.claude/worktrees/`가 들어 있음 (`project-init`이 넣어준다) — 없으면 `auto-wip-commit`이 작업 폴더를 통째로 커밋에 담는다
- 호출 위치는 메인 폴더든 옛 워크트리든 상관없음 — §1-a에서 판별해서 절차를 갈라 쓴다
- 사용 시나리오 둘 다 OK:
  - **일반 사용**: 직전 작업이 PR로 정리된 상태 (`done-task` 직후 — 보통 그 옛 워크트리 안에서 호출된다)
  - **첫 사용**: 메인 폴더 main 위에서 새 프로젝트 첫 작업 시작 — 옛 워크트리·브랜치 0개도 정상 동작 (엣지 케이스 표 참조)

## 실행 흐름

### 1. 안전 검사 (실패 시 사용자 안내 후 중단)

```bash
# 1-a. 지금 어디에 있나 — 메인 폴더인가, 워크트리 안인가
git rev-parse --git-common-dir   # 메인 폴더의 .git 경로
git rev-parse --show-toplevel    # 지금 폴더
git worktree list --porcelain    # 전체 목록 (첫 줄이 메인 폴더)
```

- `--git-common-dir`이 `.git`이면 (또는 `--show-toplevel`이 목록 첫 줄의 경로와 같으면) **메인 폴더**, 아니면 **워크트리 안**이다.
- 목록 첫 줄 `worktree <경로>`에 적힌 경로가 **메인 폴더 절대 경로**다. §2·§3·§4에서 계속 쓰니 기억해둬라.
- 이건 중단 조건이 아니라 뒤 절차를 가르는 판별이다. 여기서 멈추는 경우는 없다.

```bash
# 1-b. 현재 브랜치 확인
git rev-parse --abbrev-ref HEAD
```

- **브랜치에 안 묶인 상태 (detached HEAD)** → 중단. "지금 어느 브랜치에도 위치하지 않고 과거 커밋한 파일들을 보고 있어. 이 스킬은 지금 작업을 정리하고 새 작업 폴더를 만들어서 전환하는 도구라, 어느 브랜치에서 시작할지 알려줘" 안내.

```bash
# 1-c. working tree 깨끗한가?
git status --porcelain
```

- **비어있지 않으면** args에 결정 지시(예: "변경은 커밋하고 진행")가 있으면 그대로 적용하고 계속. 없으면 **[결정 필요] 반환**:
  ```
  [결정 필요] 지금 폴더에 커밋되지 않은 변경(수정·추가·삭제된 파일)이 남아 있어.
  이 스킬은 지금 폴더를 깨끗이 정리하고 새 작업 폴더로 넘어가는 도구라, 이 변경을 먼저
  정리해야 해. 그대로 두고 떠나면 나중에 이 폴더를 지울 때 git이 거부해서 또 걸린다.

  선택지:
  (a) 지금 변경을 커밋하고 진행
  (b) 임시 보관소에 넣어두고 진행 (`git stash` — 나중에 다시 꺼낼 수 있어)
  (c) 중단 — 직접 정리할게

  재호출 예시: `/new-task <의도> — 변경은 커밋하고 진행` / `/new-task <의도> — stash하고 진행`
  ```

```bash
# 1-d. 현재 feature 브랜치라면 PR 상태 확인
gh pr status 2>/dev/null || true
```

- 현재 브랜치의 PR이 **미머지**면, 미머지 상태를 물어볼지 그냥 넘어갈지는 **내 권한**에 따라 갈린다. 팀원은 PR 올려두고 팀장 머지를 기다리며 다음 작업으로 넘어가는 게 정상 흐름이라 매번 물으면 마찰만 커서다.

  ```bash
  # 1-d-1. 내 권한 확인 (owner/repo는 gh repo view --json nameWithOwner로 구해라)
  gh api repos/{owner}/{repo} --jq '.permissions'
  ```

  - **`admin`·`maintain` 둘 다 `false` (팀원) 또는 권한 조회 자체가 실패** → 묻지 않고 그냥 진행. 이 판정은 브랜치를 지우는 게 아니라 "물어볼지 말지"만 정하는 거라, 조회가 실패해도 틀려서 잃을 게 없다. 대신 완료 보고(§5)에 다음 줄을 남겨라:
    ```
    ℹ️ PR #<N>은 아직 리뷰 대기 중이야 (<url>) — 이 작업 폴더와 브랜치는 그대로 남겨뒀어.
       나중에 머지되고 치우고 싶으면 그 경로를 담아서 `/new-task <의도> — <경로>도 정리`로 불러줘.
    ```
    브랜치는 당연히 보존한다 (§3에서 처리). 다음 `/new-task`는 **그때 앉아 있는 폴더만** 정리하니, 지금 떠나는 이 폴더는 알아서 치워지지 않는다 — 그래서 치우는 방법을 같이 알려주는 것이다.
  - **`admin`이나 `maintain` 둘 중 하나라도 `true` (팀장)** → 지금 그대로 [결정 필요]로 멈춘다. 오너가 미머지 PR을 두고 떠나는 건 여전히 이례적이라 "머지 깜빡했나?" 신호로 쓸모 있어서다. args에 "그래도 진행" 류 지시가 있으면 통과. 없으면 **[결정 필요] 반환**:
    ```
    [결정 필요] 지금 브랜치의 PR(코드 합치기 요청)이 아직 머지되지 않았어 (#번호·URL).
    이 브랜치를 떠나면 작업이 main에 들어가지 않은 채로 남아.

    선택지:
    - 그래도 떠나서 새 작업 시작
    - 중단하고 먼저 PR 머지

    재호출 예시: `/new-task <의도> — 그래도 진행`
    ```
- 메인 폴더의 main이면 skip.

### 2. main 싱크 — 기준점은 `origin/main`

새 작업 폴더는 `origin/main`을 기점으로 만든다. 그래서 **반드시 필요한 건 원격 추적 참조(origin/main) 갱신 하나**뿐이다. 이건 메인 폴더든 워크트리든 어디서 실행해도 된다.

```bash
git fetch origin main          # origin/main을 최신으로
```

- 이게 실패하면 (네트워크 등) 중단하고 안내: "GitHub에서 최신 main을 못 받아왔어. 새 작업 폴더는 원격 main 최신 위에서 시작해야 해서 여기서 멈췄어. 연결 확인하고 다시 호출해줘."

로컬 `main` 브랜치까지 최신으로 맞추는 건 **선택**이다. 지금 위치에 따라 갈린다:

| 지금 위치                        | 하는 일                                                              |
| -------------------------------- | -------------------------------------------------------------------- |
| 메인 폴더 + 브랜치가 `main`      | `git pull origin main`                                               |
| 메인 폴더 + feature 브랜치       | `git switch main` 후 `git pull origin main` (메인 폴더에선 전환 가능) |
| 워크트리 안                      | `git -C <메인폴더> pull origin main` 시도. 실패해도 그냥 진행         |

- **워크트리 안에서 `git switch main`을 시도하지 마라** — 반드시 실패한다: `fatal: 'main' is already used by worktree at <메인 폴더>`. 한 브랜치는 폴더 하나에만 올릴 수 있어서다.
- 같은 이유로 워크트리 안에서 `git fetch origin main:main` (로컬 main을 직접 갱신하는 형태)도 막힌다: `refusing to fetch into branch 'refs/heads/main' checked out at ...`. 로컬 main은 위 표의 `-C` 방식으로만 건드려라.
- pull 충돌 발생 시 (드물지만 다른 컴퓨터에서 push했을 가능성):
  - **메인 폴더에서 났으면** → 중단 후 안내: "메인 폴더의 main 최신 가져오기(pull)에 충돌이 났어. 메인 폴더가 합치는 중간 상태로 남아 있어서 먼저 풀어야 해. 해결하고 다시 호출해줘."
  - **`-C`로 메인 폴더를 건드리다 났으면** → 그냥 진행한다 (새 작업은 `origin/main` 기준이라 영향 없음). 대신 §5 보고에 남겨라: `ℹ️ 메인 폴더의 로컬 main 갱신은 충돌로 건너뛰었어 — 새 작업엔 영향 없지만 메인 폴더는 한 번 정리해줘.`

### 3. 방금 끝낸 이 작업 폴더·브랜치 정리

**정리 대상은 지금 세션이 앉아 있는 작업 폴더와 그 브랜치, 딱 하나다.** 다른 작업 폴더·브랜치는 **PR이 머지됐든 아니든 손대지 않는다.**

예전엔 로컬 feature 브랜치를 전부 훑어서 머지된 건 다 지웠는데, 그러면 **다른 창에서 열려 있는 세션의 폴더까지 지운다.** 폴더가 발밑에서 사라진 세션은 대화는 살아 있는데 파일 작업이 전부 먹통이 되고, `pwd`는 사라진 옛 경로를 그대로 답해서 원인을 찾기도 어렵다. 정리해서 얻는 건 디스크 몇 MB인데 잃는 건 남의 세션이라, 안 건드리는 쪽이 남는 장사다.

먼저 **이미 사라진 것들의 기록만** 정리한다 — 살아있는 폴더는 하나도 안 건드리는 안전한 작업이다:

```bash
git remote prune origin         # 원격에서 이미 지워진 브랜치의 추적 참조 정리
git worktree prune              # 폴더가 이미 사라진 워크트리 기록 정리
```

이제 정리 대상 하나를 판정한다. 지금 폴더와 지금 브랜치는 §1-a·§1-b에서 이미 구해뒀다.

- **메인 폴더 + 브랜치가 `main`** → 정리할 게 없다. §3 전체 skip.
- **워크트리 안** 또는 **메인 폴더 + feature 브랜치** → 그 브랜치 하나만 아래로 판정.

```bash
gh pr list --head <현재 브랜치> --state merged --json number,state,url --limit 1
```

| 조회 결과      | 처리                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------ |
| 머지된 PR 있음 | 정리 대상 — 아래 절차로. 내용이 GitHub에 보존돼 되돌릴 수 있어서 args 지시 없이 바로 진행한다 |
| PR 있는데 미머지 | 보존. §1-d에서 이미 다뤘으니 여기선 §5 보고에만 남긴다                                     |
| PR 없음        | 보존. 아직 ship 안 한 작업이라 지우면 되살릴 사본이 GitHub에 없다. §5 보고에 남긴다          |

**머지된 경우** — 지금 그 폴더에 앉아 있느냐로 갈린다:

- **워크트리 안에서 호출됐으면 — 여기서 지우지 마라.** 자기가 앉은 워크트리는 `git worktree remove`가 종료코드 0으로 **성공해버려서** 세션 폴더가 통째로 증발한다. 브랜치도 그 폴더가 쓰고 있어 못 지운다. **"정리 대기"**로 §5 보고에 올려라 — 메인 세션이 새 폴더로 옮기면 점유가 풀리니, 그때 §5 인계 블록 2번이 지운다.
- **메인 폴더에서 feature 브랜치인 채로 호출됐으면** 딸린 워크트리가 없다 (§2에서 이미 `main`으로 옮겨왔다). 바로 지운다:
  ```bash
  git branch -D <branch>               # squash merge라 force delete 필수
  git push origin --delete <branch>    # 원격에도 남아 있을 때만
  ```

결과는 완료 보고(§5)에 폴더 경로 + branch명 + PR 번호·URL로 명시한다.

**손대지 않은 폴더도 보고에 적어라.** §1-a의 `git worktree list --porcelain` 결과에서 메인 폴더와 지금 폴더를 뺀 나머지가 그 목록이다. 각각의 PR 상태까지 조회할 필요는 없다 — 안 건드릴 거라 알 필요가 없고, 폴더마다 `gh` 호출이 붙으면 느려지기만 한다. 경로만 세어서 알린다.

#### 3-a. 다른 작업 폴더도 치우기 (args에 경로가 명시됐을 때만)

머지 끝난 작업 폴더를 방치하면 계속 쌓이니, 치우는 길은 열어둔다. 단 **사용자가 경로를 직접 지목했을 때만** 손댄다:

```
/new-task <의도> — .claude/worktrees/feat/hero-redesign 도 정리
```

지목된 경로에 대해서만:

1. 그 폴더의 브랜치가 **머지됐는지 확인한다** (위와 같은 `gh pr list`). 머지 안 됐으면 **지우지 말고 [결정 필요]로 되돌려라** — GitHub에 사본이 없어 되살릴 방법이 없다.
2. **폴더 먼저, 브랜치 나중.** 반대로 하면 실패한다 (`error: cannot delete branch 'X' used by worktree at ...`).
   ```bash
   git worktree remove <경로>
   git branch -D <branch>
   git push origin --delete <branch>    # 원격에도 남아 있을 때만
   ```
3. `git worktree remove`가 거부되면 (`fatal: '<경로>' contains modified or untracked files, use --force`) → **`--force`를 자동으로 쓰지 마라.** 커밋 안 된 변경이 그대로 날아간다. args에 그 폴더 처리 지시가 없으면 **[결정 필요] 반환**:
   ```
   [결정 필요] 정리해달라고 한 작업 폴더 <경로>에 커밋되지 않은 변경(수정·추가된 파일)이 남아 있어서
   폴더를 지우지 못했어. 지우면 그 변경은 되살릴 방법이 사실상 없어서 밀어붙이지 않았어.

   선택지:
   - 남은 변경 버리고 폴더 정리 (`git worktree remove --force`)
   - 그대로 두기 — 직접 열어보고 판단할게 (딸린 브랜치도 같이 남아)

   재호출 예시: `/new-task <의도> — <경로> 변경 버리고 정리` / `/new-task <의도> — <경로> 그대로 둬`
   ```
4. ⚠️ **그 폴더에 다른 창의 세션이 앉아 있으면 그 세션은 깨진다.** 지웠으면 §5 보고에 이 사실을 한 줄 남겨서, 사용자가 해당 창을 닫도록 알려라.

### 4. 새 작업 폴더·브랜치 자동 생성

#### 4-a. 사용자 의도 수집

- **args에 있으면** 사용:
  - `/new-task hero 영역 다시 디자인` → "hero 영역 다시 디자인"
  - `/new-task feat hero-redesign` → 명시적 type·topic 패턴이면 그대로 사용 (skip 4-b)
- **args 없으면** **[결정 필요] 반환** (fork는 질문 불가):
  ```
  [결정 필요] 다음 작업이 뭔지 알아야 작업 폴더를 만들 수 있어.

  재호출 예시: `/new-task hero 영역 다시 디자인` / `/new-task feat hero-redesign`
  ```

#### 4-b. type·topic 추론 (Claude)

**type 추론 키워드**:

| 의도 키워드                                                                       | type       |
| --------------------------------------------------------------------------------- | ---------- |
| 새 기능·추가·신규·페이지·컴포넌트                                                 | `feat`     |
| 버그·에러·깨짐·안 됨·고치기                                                       | `fix`      |
| CI·deps·설정·환경·정리                                                            | `chore`    |
| `CLAUDE.md` · `.claude/**` (rules·skills·agents·hooks) 하네스 파일 변경·생성·갱신 | `harness`  |
| 리팩터·구조 개선·이름 변경·정합                                                   | `refactor` |
| `src/content/**` 카피·글·콘텐츠 변경                                              | `content`  |
| `docs/` 사람 읽는 문서 추가·수정                                                  | `docs`     |

애매하면 가장 가까운 것 선택, 사용자가 다르면 수정 요청 가능.

**topic 생성 규칙**:

- kebab-case 명사구
- 30자 이하 (긴 의도는 핵심 키워드만 압축)
- 한글 의도 → 영문 키워드로 번역 (`헤더 색깔 변경` → `header-color-change`)
- 모호한 표현 제거 (`다시`, `좀`, `더` 등)
- 브랜치명이 곧 폴더명이라 글자 제한이 있다 — `/`로 나뉜 각 구간은 영문자·숫자·점·밑줄·붙임표만, `<type>/<topic>` 전체 64자 이하 (메인 세션이 쓸 `EnterWorktree` 도구의 제약이다)

#### 4-c. 생성·보고

생성 전에 이름 충돌부터 확인한다 — **로컬 브랜치·원격 브랜치·작업 폴더 세 군데**를 다 봐야 한다. 로컬에 없어도 팀원이 이미 같은 이름을 GitHub에 올려놨을 수 있고, 이 경우 지금은 생성이 성공해도 나중에 `done-task`에서 push할 때 거부된다 (원격에 이미 다른 내용이 있어서). 작업 다 끝낸 뒤 터지면 특히 아프니 미리 걸러라.

```bash
git branch --list "${type}/${topic}"
git ls-remote --heads origin "${type}/${topic}"
git worktree list --porcelain          # 같은 경로가 이미 등록돼 있나
```

앞 두 명령은 **결과가 있으면 존재, 출력이 비어 있으면 없음**으로 판정한다 (둘 다 이름이 없어도 exit code는 0이라, exit code가 아니라 출력 유무로 봐야 함). 워크트리 목록에 `.claude/worktrees/${type}/${topic}` 경로가 이미 보여도 충돌이다.

- 셋 다 비어있으면 그대로 생성:
  ```bash
  git worktree add "<메인폴더>/.claude/worktrees/${type}/${topic}" -b "${type}/${topic}" origin/main
  ```
  - 이 한 줄이 폴더 만들기 + 브랜치 만들기 + 그 폴더에 브랜치 올리기를 한꺼번에 한다. 기점이 `origin/main`이라 로컬 `main`이 낡아 있어도 새 작업은 최신에서 시작한다.
  - **경로는 반드시 메인 폴더 기준 절대 경로로 써라** (§1-a에서 구해둔 그 경로). 워크트리 안에서 상대 경로로 실행하면 새 폴더가 지금 앉아 있는 옛 폴더 밑에 파묻힌다. `git -C <메인폴더> worktree add ".claude/worktrees/..."` 형태도 같은 효과다.
- 하나라도 결과가 있으면 → §엣지 — 이름 충돌 참고.
- `git worktree add`가 `fatal: '<경로>' already exists`로 실패하면, git에 등록은 안 됐지만 폴더만 남아 있는 경우다. 이것도 이름 충돌과 똑같이 suffix를 올려 재시도한다.

생성이 끝나면 **인계 표식을 반드시 남겨라.** 메인 세션이 `EnterWorktree`를 건너뛰었을 때 `pending-worktree-guard` 훅이 잡아주는 근거가 이 표식 하나다.

```bash
git config --local builderharness.pendingworktree \
  "${CLAUDE_CODE_SESSION_ID}:<메인폴더 절대경로>/.claude/worktrees/${type}/${topic}"
```

- 경로는 `git worktree add`에 쓴 **절대 경로 그대로**여야 한다 — 훅이 세션의 현재 폴더와 문자열이 아닌 실제 경로로 비교하지만, 상대 경로를 넣으면 어느 폴더 기준인지 알 수 없어 비교가 어긋난다.
- 앞의 `${CLAUDE_CODE_SESSION_ID}`는 지금 세션을 가리키는 값이다. 이게 있어야 훅이 **다른 세션의 표식을 자기 것으로 착각하지 않는다** — 착각하면 세션 둘이 한 폴더에 앉는, 이 하네스가 폴더를 나눠 막으려는 바로 그 사고가 난다. 값이 비어 있으면 훅은 막지 않고 표식만 지우니, 굳이 우회해서 채우려 하지 말고 그대로 둬라.
- `--local`은 저장소 공용 설정이라 어느 작업 폴더에서 실행해도 같은 곳에 쓰인다. 표식은 훅이 인계를 확인한 뒤 알아서 지운다.

그다음 시작 지점을 확인해 §5 보고에 담아라:

```bash
git rev-parse --short origin/main
```

완료 보고(§5)에는 **새 폴더 경로와 브랜치명을 둘 다** 넣는다. 이름을 바꾸고 싶으면 `git branch -m <새이름>`은 브랜치 이름만 바꾸고 폴더 이름은 그대로 남으니, 둘을 맞추려면 원하는 이름을 담아 재호출하는 쪽이 낫다고 안내한다.

#### 엣지 — 이름 충돌

로컬·원격·폴더 셋 중 어디서든 같은 이름이 걸리면 suffix 숫자를 붙여 재시도한다 (`feat/hero-redesign-2`). 그 이름도 겹치면 `-3`, `-4`... 로 숫자를 올려가며 **세 군데 다 비어있는 이름이 나올 때까지** 반복한다 — 한 번만 시도하고 끝내면, 팀 작업 특성상 `-2`까지 이미 누가 쓰고 있는 경우(예: 다른 팀원이 같은 기능을 먼저 손댔거나, 재시도가 여러 번 있었던 경우) 충돌이 그대로 재발한다.

```bash
# n=2부터 시작해서 셋 다 비어있는 번호를 찾을 때까지 올린다
git branch --list "${type}/${topic}-${n}"
git ls-remote --heads origin "${type}/${topic}-${n}"
git worktree list --porcelain          # .claude/worktrees/${type}/${topic}-${n} 이 있나
```

- **10회 시도**(`-2`부터 `-11`까지)**해도 전부 겹치면** → 자동 재시도를 멈추고 **[결정 필요] 반환**. 그 지경이면 이름 자체가 너무 흔한 것이라 숫자를 더 올려도 의미가 없다:
  ```
  [결정 필요] "${type}/${topic}"부터 "${type}/${topic}-11"까지 로컬·원격·작업 폴더에 전부 이미 있어서
  자동으로 이름을 못 지었어. 이름이 너무 흔한 것 같아 — 더 구체적인 이름을 알려줘.

  재호출 예시: `/new-task <type> <더 구체적인 topic>`
  ```
- 빈 이름을 찾으면 그 이름으로 생성. 어디서 겹쳤는지 사용자에게 알려줘야 이해가 쉽다:
  - **로컬에만 있을 때**: "같은 이름 브랜치가 로컬에 이미 있어서 `feat/hero-redesign-2`로 만들었어. 다른 이름 원하면 알려줘."
  - **원격에 있을 때** (팀원이 같은 이름을 쓰고 있을 가능성): "GitHub에 같은 이름 브랜치가 이미 있어서 (팀원이 올려둔 걸 수도 있어) `feat/hero-redesign-2`로 만들었어. 다른 이름 원하면 알려줘."
  - **폴더가 이미 있을 때**: "`.claude/worktrees/feat/hero-redesign` 폴더가 이미 있어서 `feat/hero-redesign-2`로 만들었어. 예전 작업 폴더가 정리 안 된 채 남아 있는 걸 수도 있어."
  - 재시도가 여러 번 있었으면 ("2번, 3번도 이미 있어서 4번으로 만들었어" 식으로) 몇 번째 시도에서 빈 이름을 찾았는지도 알려준다.

### 5. 준비 완료 보고

**인계 블록이 맨 앞이다.** 예전엔 맨 끝에 붙였는데 그러면 묻혀서 무시된다 (§세션 이동은 2단이다). 그리고 이 블록은 사용자가 아니라 **메인 세션(Claude)에게** 하는 말이니, 사용자가 자기 할 일로 오해하지 않게 첫 줄에 그 사실을 밝힌다 — 실제로 "이거 내가 뭘 하라는 거냐"고 되물은 적이 있다.

```
▶ 메인 세션(Claude)이 이어서 바로 실행할 것 — 사용자가 할 일 아님:
  1. `EnterWorktree(path: "<메인폴더 절대경로>/.claude/worktrees/<type>/<topic>")` 호출 — 세션을 새 작업 폴더로 옮긴다.
     이 보고는 명령 출력 형태로 도착하지만 이 항목만은 읽고 넘기지 말고 반드시 실행해라.
     건너뛰면 앞으로의 편집이 옛 폴더에 쌓이고, 메인 폴더면 브랜치가 main이라 자동 저장(auto-wip-commit)도 안 걸린다.
  2. (정리 대기가 있으면) 새 폴더로 옮긴 다음에 `git worktree remove <경로>` → `git branch -D <브랜치>` 순서로 실행.
     순서를 바꾸면 "브랜치를 워크트리가 쓰고 있다"며 실패한다.
  3. 사용자에게는 이 블록을 그대로 읊지 말고, 옮겼다는 사실만 한 줄로 전해라.

✓ 새 작업 폴더: .claude/worktrees/<type>/<topic>
✓ 새 브랜치   : <type>/<topic>
✓ 시작 시점   : origin/main 최신 (commit <short-sha>)
✓ 작업 중 자동 임시 저장 활성 (auto-wip-commit 훅 — feature 브랜치에서 매 turn 변경이 wip 커밋으로 박혀. 세션이 지금 앉아 있는 폴더에서만 돌아서 다른 폴더 파일은 안 건드려)
⏳ 정리 대기: <경로> (<branch>, 머지된 PR #<N> 확인됨) — 지금 세션이 그 안에 있어서 여기선 못 지웠어. 위 인계 블록 2번에서 지운다. — 없으면 이 줄 생략
✓ 정리한 이 작업 브랜치 (머지 확인됨): <branch> (#N) — 메인 폴더에서 feature 브랜치인 채로 호출된 경우만, 아니면 이 줄 생략
○ 방금 떠난 작업 폴더·브랜치는 그대로 남겨뒀어: <경로> (<branch>) — <PR #N 리뷰 대기 중 / PR 없음>.
  치우려면 `/new-task <의도> — <경로>도 정리`로 불러줘. — 미머지·PR 없음일 때만, 아니면 이 줄 생략
○ 다른 작업 폴더 <N>개는 손대지 않았어 (머지 여부와 상관없이 안 건드려 — 다른 창에서 쓰고 있을 수 있어서):
  <경로 목록> — 살아있는 다른 워크트리가 있을 때만, 없으면 이 줄 생략
✓ 지목해서 정리한 작업 폴더·브랜치: <경로 (branch, #N)> — §3-a로 정리했을 때만, 아니면 이 줄 생략
  ⚠️ 그 폴더를 열어둔 창이 있으면 지금 먹통이야 — 그 창은 닫아줘. — 바로 위 줄이 있을 때만

이름 바꾸려면 원하는 이름을 담아 재호출해줘 (`git branch -m`은 브랜치 이름만 바뀌고 폴더 이름은 그대로 남아).
다음 작업 알려줘.
```

## 사용자 응대 톤

톤은 `CLAUDE.md 대화 스타일`을 따름. 이 스킬 고유: 결정이 필요하면 진행을 멈추고 [결정 필요] 보고로 반환한다 (fork 실행이라 실행 중 질문 불가). 안전 검사 결과는 반환 보고에 모아서.

## 엣지 케이스

| 상황                                                      | 처리                                              |
| --------------------------------------------------------- | ------------------------------------------------- |
| 메인 폴더에서 main인 채로 호출 (첫 사용의 기본 모습)      | §1-d(PR 확인) skip. §2는 fetch + pull, §3은 정리 대상이 없어 prune 두 줄만, §4는 그대로 |
| 메인 폴더가 feature 브랜치에 있음                         | 메인 폴더에서는 `git switch main`이 되니 main으로 되돌리고 pull 후 진행 |
| working tree 변경이 새 작업과 무관 (예: 환경 설정 잔여물) | stash 옵션 권장                                   |
| 지금 워크트리에 앉아 있는데 그게 머지 끝난 워크트리        | 제거하지 않고 "정리 대기"로 보고 — 메인 세션이 새 폴더로 옮긴 뒤 정리 |
| 다른 창에서 작업 중인 워크트리가 있음                     | 머지됐든 아니든 **손대지 않음.** §5 보고에 "손대지 않았어"로 목록만 알림 |
| 다른 작업 폴더를 치워달라고 args에 경로가 명시됨          | §3-a — 그 경로만 머지 확인 후 폴더 먼저·브랜치 나중으로 정리        |
| args로 지목된 폴더의 브랜치가 미머지                      | 지우지 않고 [결정 필요]로 반환 — GitHub에 사본이 없어 되살릴 수 없음 |
| args로 지목된 폴더에 커밋 안 된 변경이 있어 remove가 거부됨 | `--force` 자동 실행 금지. [결정 필요]로 반환해 사용자에게 물음 |
| `.claude/worktrees/<type>/<topic>` 폴더가 이미 있음       | 브랜치 이름 충돌과 같은 규칙으로 suffix 재시도            |
| PR이 머지 안 됐는데 새 작업 가야 함 — 나는 팀원(push만)   | 묻지 않고 진행. 완료 보고(§5)에 PR 대기 알림, 브랜치 보존         |
| PR이 머지 안 됐는데 새 작업 가야 함 — 나는 팀장(admin·maintain) | args에 명시 지시 없으면 [결정 필요] 반환. 이 브랜치 삭제 X (보존) |
| 권한 조회(`gh api .../permissions`) 실패                  | 팀원 취급 (묻지 않고 진행 + 보고에 남김)          |
| 지금 브랜치에 PR이 아예 없음 (ship 안 하고 떠남)           | 폴더·브랜치 모두 보존. §5 보고에 "그대로 남겨뒀어"로 알림 |
| 새 브랜치 이름이 로컬에 이미 있음                         | suffix 숫자를 올려가며 로컬·원격·폴더 셋 다 비는 이름 나올 때까지 재시도 후 생성, 완료 보고에 "로컬에서 겹침" 알림 |
| 새 브랜치 이름이 원격(GitHub)에 이미 있음                 | 위와 동일하게 재시도 후 생성, 완료 보고에 "팀원이 같은 이름을 쓰고 있을 수도" 알림 |
| suffix 10회(`-2`~`-11`)까지 전부 겹침                     | 자동 재시도 중단, [결정 필요]로 더 구체적인 이름 요청           |
| 메인 세션이 `EnterWorktree`를 건너뜀                      | `pending-worktree-guard` 훅이 응답 끝에 한 번 막고 호출을 지시. 그래도 안 옮기면 표식 지우고 통과 |
| 다른 세션이 남긴 인계 표식이 보임                         | 손대지 않고 통과 — 표식의 session_id가 자기 것일 때만 반응한다  |

## 호출 패턴

- `/new-task` — args 없음. §4-a에서 [결정 필요] 반환 ("다음 작업 의도를 담아 재호출해줘")
- `/new-task <자연어 의도>` — 의도 텍스트에서 type·topic 추론
  - 예: `/new-task hero 영역 sticky note 색깔 바꾸기` → `content/hero-sticky-note-color`
- `/new-task <type> <topic>` — 명시적 패턴이면 그대로 사용 (의도 파싱 skip)
  - 예: `/new-task feat hero-redesign` → `feat/hero-redesign` 그대로
- `/new-task <의도> — 변경은 커밋하고 진행` — §1-c [결정 필요]에 대한 결정을 담아 재호출
  - 예: `/new-task feat hero-redesign — stash하고 진행`
- `/new-task <의도> — <경로>도 정리` — §3-a. 지목한 다른 작업 폴더까지 함께 정리 (경로 명시가 있을 때만 손댄다)
  - 예: `/new-task feat hero-redesign — .claude/worktrees/fix/login-error 도 정리`
- `/new-task <의도> — <경로> 변경 버리고 정리` — §3-a 워크트리 제거 거부에 대한 결정을 담아 재호출

명시적 패턴 감지: `$0`이 valid type 목록 중 하나 + `$1`이 kebab-case면 명시 패턴, 아니면 전체를 자연어로 처리.

## 안 하는 것 (의도적)

- ❌ PR 자동 머지 — 사용자가 직접 또는 GitHub UI에서 결정
- ❌ commit·push — 새 작업 폴더·브랜치 만들기만, 작업 내용 commit은 별개
- ❌ 다른 base 브랜치 지원 — `origin/main` 전제. 다른 base 필요하면 별 스킬
- ❌ Claude 자동 invoke — `disable-model-invocation: true`로 차단
- ❌ 작업 폴더 생성 전 type·topic 확인 받기 — 자동 생성 후 사후 수정 받음 (마찰 최소화)
- ❌ 지금 앉아 있는 워크트리 제거 — git이 종료코드 0으로 성공시켜버려서 세션 폴더가 증발한다. "정리 대기"로 넘긴다
- ❌ 다른 작업 폴더·브랜치 자동 정리 — 머지가 끝났어도 손대지 않는다. 다른 창의 세션이 그 안에 앉아 있으면 발밑이 사라진다. args에 경로가 명시될 때만 (§3-a)
- ❌ PR 없는 로컬 브랜치 정리 — GitHub에 사본이 없어 지우면 되살릴 방법이 사실상 없다. 그대로 둔다
- ❌ 워크트리 안에서 `git switch main` — git이 막는다 (한 브랜치는 폴더 하나에만)
- ❌ `git worktree remove --force` 자동 실행 — 커밋 안 된 변경이 날아간다. 거부되면 [결정 필요]로 반환
- ❌ `EnterWorktree` 직접 호출 — fork가 호출해도 메인 세션은 안 따라온다. 경로만 보고하고 호출은 메인 세션 몫 (§5). 대신 인계 표식을 남겨 `pending-worktree-guard` 훅이 확인하게 한다 (§4-c)
- ❌ `cd`로 세션 옮기기 — 하네스가 Bash 호출이 끝날 때마다 셸 폴더를 세션 폴더로 되돌린다 (`Shell cwd was reset to ...`). 세션의 작업 폴더를 바꾸는 수단은 `EnterWorktree`뿐이라 이 인계 2단은 없앨 수 없다. 참고로 워크트리 **생성**은 이 스킬이 순수 `git worktree add`로 하고, `EnterWorktree`는 `path:` 모드(이미 있는 폴더로 이동)로만 쓴다 — 이 모드는 폴더·브랜치를 만들지 않는다
- ❌ 인계 표식 직접 지우기 — 훅이 인계 확인 후 알아서 지운다. 스킬이 미리 지우면 안전망이 사라진다
